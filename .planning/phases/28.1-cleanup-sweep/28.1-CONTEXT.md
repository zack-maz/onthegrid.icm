## Phase Boundary

Phase 28.1 is the **cleanup** child of the v1.4-closeout umbrella. It runs **first** in the 28.x sequence (D-02) because cleanup is the most regression-prone surgical work, and the dev/prod sync (28.2) and load test (28.3) need a clean codebase to land against.

Scope is exactly four bands of work, executed across **7 waves API-first serial** per D-28:

1. **API reliability (W1+W2)** — one-shot audit + fix-up of every `/api/*` endpoint and upstream adapter (W1), then build a `/api/health` aggregate endpoint + DevApiStatus consumer with severity-tiered reaction policy (W2). Replaces the umbrella's "UI bugs + debugging items" band per D-22; user's stated #1 priority for 28.1 is "making sure all APIs are working all the time." Pure visual UI bugs not surfaced as API-broken symptoms drop out of 28.1 scope.
2. **Ghost code + duplicate code sweep (W3+W4)** — mechanical via `npx knip` + `npx ts-prune` followed by a manual codebase walk (W3 triage doc, read-only); atomic per-module deletion commits (W4) with conservative-bias triage per D-29.
3. **Hardcode generalization (W5+W6)** — operator-tunable env vars (D-12, W5), centralized domain constants (D-11 `src/lib/domain.ts`, W5), CSS @theme color migration (D-13, W6).
4. **Normalization (W7)** — 7 sub-categories per D-27, each its own atomic commit: TS strict → lint → Zustand selectors → Redis keys → vitest → imports → logging audit.

**Out of scope for 28.1:**

- Dev/prod feature promotion (D-05/D-06/D-07/D-08/D-09) → that's 28.2.
- Domain rename (D-03) → that's 28.2.
- Rate-limiter Bearer-bypass (D-04) → that's 28.2.
- Edge cache + Redis architecture (D-19) → that's 28.3.
- k6 sweep, PASS/FAIL bar, polling parity (D-15/D-16/D-17/D-18/D-20/D-21) → that's 28.3.

## Implementation Decisions (filtered from umbrella for 28.1 scope)

### Phase Shape & Sequencing

- **D-01:** Phase 28 split into three child phases (28.1 → 28.2 → 28.3). Each merges to `main` before next starts. **For 28.1:** must close cleanly before 28.2 begins.
- **D-02:** Sequence is **cleanup → sync → load**. **For 28.1:** the value of cleanup running first is "kill the most regression risk early" — accept the trade-off that cleanup may uncover deep bugs and slow the umbrella critical path.

### Hardcode Tolerance & Generalization (the four-band cleanup scope)

- **D-10:** **Aggressive operator-tunable rule for operational levers** — anything an operator might want to nudge during incident response or tuning iteration becomes an env-var override. Pattern matches Phase 27.4.x precedent (`LLM_BATCH_TIMEOUT_MS`, `LLM_V3_CONCURRENCY`, `V3_WATCHDOG_ROLLBACK_THRESHOLD`).
- **D-11:** **Domain-definitional constants stay hardcoded, centralized in `src/lib/domain.ts`** (mirror at `server/lib/domain.ts` if needed) — IRAN_BBOX, IRAN_CENTER, WAR_START, ADS-B 500NM radius. NOT env-tunable. Single source of truth, no derivation. These define what "this dashboard monitors."
- **D-12:** **Polling intervals + thresholds are env-tunable.** Each gets a documented env var with current value as default:
  - `POLL_FLIGHTS_MS` (5s), `POLL_SHIPS_MS` (30s), `POLL_EVENTS_MS` (15min), `POLL_NEWS_MS` (15min), `POLL_MARKETS_MS` (60s), `POLL_WATER_PRECIP_MS` (6h), `POLL_LLM_STATUS_MS` (TBD).
  - `STALE_FLIGHT_MS` (60s — flight stale threshold).
  - `ATTACK_RADIUS_KM` (5km — site/event cross-reference).
  - `PROXIMITY_ALERT_KM` (50km — flight/ship proximity-to-site alert).
  - `SEVERITY_HALF_LIFE_HOURS` (6h — recency decay in `src/lib/severity.ts`).
  - Naming convention: `SCREAMING_SNAKE_CASE`, follows existing `LLM_*` / `NIM_*` precedent.
- **D-13:** **Visual constants migrate to CSS custom properties + Tailwind v4 `@theme` block** in `src/app.css`. Entity colors become CSS vars:
  - `--color-flight` (#eab308), `--color-flight-unidentified` (#ef4444), `--color-ship` (#a78bfa).
  - `--color-event-airstrike` (#ff3b30), `--color-event-on-ground` (#c0392b), `--color-event-explosion` (#e74c3c), `--color-event-targeted` (#dc143c), `--color-event-other` (#800000).
  - `--color-site-healthy` (#22c55e), `--color-site-attacked` (#f97316).
  - Faction palette (`src/lib/factions.ts`): `--color-faction-us-aligned` (#3b82f6), `--color-faction-iran-aligned` (#dc2626), `--color-faction-neutral` (#64748b), `--color-faction-disputed` (#f59e0b).
  - Existing `@theme` z-index scale is the precedent pattern.
  - **Stays as TS constants:** icon sizes (4000m flights, 3000m events, 2000m sites) — these are deck.gl props, not styling. Tailwind v4 conventions apply for var naming.
- **D-14:** **Ghost code detection methodology** — both passes required, in this order:
  1. **Mechanical:** `npx knip` + `npx ts-prune` for dead-export enumeration.
  2. **Manual:** codebase walk for logically-dead-but-type-reachable code (Zustand selectors-of-removed-fields, dead union variants, orphaned hooks called from removed callers).
  3. **Triage doc** committed before any deletions — categorized list with confidence levels.
  4. **Atomic per-module deletion commits** — never bundle.

### API Reliability (replaces "UI bugs" band — discussed 2026-04-30)

The user's stated #1 priority for 28.1 is "making sure all APIs are working all the time." Per discussion 2026-04-30, the "UI bugs + remaining debugging items" band from the umbrella is reframed as **API reliability**: a one-shot audit + observability layer. Pure visual UI bugs (e.g., misaligned tooltips) drop out of 28.1 unless surfaced during the audit as symptoms of a broken API.

- **D-22:** **API reliability is 28.1's first-priority band.** Replaces the umbrella's "UI bugs + debugging items" band. Two sub-bands: (a) one-shot audit + fix-up of every `/api/*` endpoint and upstream adapter, (b) build a `/api/health` aggregate endpoint + DevApiStatus consumer. UI bugs not surfaced as API-broken symptoms are deferred (added to umbrella `<deferred>` if surfaced during the audit).
- **D-23:** **One-shot audit, no automated regression test in CI.** Hand-curated probe of every endpoint + adapter during cleanup, fix what's broken, ship. No new vitest/script that re-runs the probe in CI on every PR. Rationale: CI flakiness risk (any upstream blip would fail CI) outweighs the catch-future-drift benefit; `/api/health` (D-24) replaces test-as-monitoring.
- **D-24:** **Both surfaces: new `/api/health` aggregate endpoint + DevApiStatus consumer.** `/api/health` returns JSON status of every endpoint + adapter — `{name, status, lastSuccessTs, lastErrorReason, freshnessMs, latencyMs}`. DevApiStatus reads from this single source of truth and renders an "All APIs" tab. Agents/operators can also probe `/api/health` directly without opening the browser. Composable, single source of truth.
- **D-25:** **Endpoint-specific freshness thresholds.** Each endpoint declares a "fresh enough" SLA. The `/api/health` endpoint computes per-endpoint status against this table:

  | Endpoint                    | Threshold | Source                                       |
  | --------------------------- | --------- | -------------------------------------------- |
  | `/api/flights`              | 2 min     | 5s poll + 60s stale clear                    |
  | `/api/ships`                | 5 min     | 30s poll, 120s stale threshold               |
  | `/api/events`               | 30 min    | 15min cache TTL; 4am UTC cron                |
  | `/api/news`                 | 30 min    | 15min poll, GDELT DOC cadence                |
  | `/api/markets`              | 5 min     | 60s poll                                     |
  | `/api/sites`                | 48 h      | 24h cache, infrastructure changes slowly     |
  | `/api/water`                | 48 h      | 24h cache, same rationale as sites           |
  | `/api/water/precip`         | 12 h      | 6h poll                                      |
  | `/api/sources`              | 10 min    | Config status, near-static                   |
  | `/api/llm-status`           | 5 min     | Live progress; >5min stall = breaker tripped |
  | `/api/dashboard/auth-check` | 200 only  | Probe endpoint, no freshness concept         |
  | `/api/geocode`              | 200 only  | Cache reader, no freshness concept           |
  | `/api/cron/health`          | 26 h      | Last-tick ts; daily 0 0 \* \* \*             |
  | `/api/cron/warm`            | 26 h      | Last-tick ts; daily 0 12 \* \* \*            |
  | `/api/cron/refresh-events`  | 26 h      | Last-tick ts; daily 0 4 \* \* \*             |

- **D-26:** **Severity-tiered reaction policy** when `/api/health` flags an endpoint as unhealthy:
  - **Critical (banner)** — `/api/flights`, `/api/events`, `/api/ships`. Render a dashboard banner/toast.
  - **Non-critical (HUD dot)** — `/api/markets`, `/api/news`, `/api/water/precip`, `/api/sources`, `/api/llm-status`. StatusPanel HUD dot turns red/amber; no banner.
  - **Static (log only)** — `/api/sites`, `/api/water`. Server log; no UI surface (these are 24h-cached infrastructure).
  - **Probe-only (200 check)** — `/api/dashboard/auth-check`, `/api/geocode`. 200 OK is the only health signal.
  - **Cron** — `/api/cron/health`, `/api/cron/warm`, `/api/cron/refresh-events`. Own category surfaced in DevApiStatus "Cron" tab; banner only if all three are stale (suggests Vercel cron service is down).

### Normalization Scope Expansion (discussed 2026-04-30)

Umbrella locked TS strict + Zustand selectors + Redis cache key naming as normalization scope. Per discussion 2026-04-30, four additional sub-categories fold in:

- **D-27:** **Normalization expands to 7 sub-categories.** Each becomes its own atomic commit per 27.4.x precedent:
  1. **TS strict-mode tightening** (umbrella) — narrow remaining `noUncheckedIndexedAccess` and `strictNullChecks` issues across `src/` and `server/`.
  2. **Zustand selector-pattern audit** (umbrella) — confirm every store consumer uses `s => s.field` selectors, not full-state subscriptions; flag re-render hot spots.
  3. **Redis cache key naming consistency** (umbrella) — audit all `cacheGet`/`cacheSet` keys for the established `<domain>:<source>:<version>` pattern (e.g., `events:llm:v3`, `sites:v3`, `water:facilities:v3`); align outliers.
  4. **Lint rule tightening** — pass through `any` usages and either narrow or `unknown`-cast (`@typescript-eslint/no-explicit-any`); resolve the 6 `react-hooks/exhaustive-deps` warnings (especially the `dismissTimers` ref in `ProximityAlertOverlay` — may indicate a real bug).
  5. **Vitest patterns + mock standardization** — audit test file naming, mock placement (`src/test/__mocks__/` vs inline), `it.todo` stub cleanup, snapshot test policy (use sparingly).
  6. **Import ordering + path-alias consistency** — standardize import order (external/internal/relative), audit `@/` vs relative usage, sort imports via lint rule.
  7. **Logging audit** — every `console.log`/`.error`/`.warn` site, distinguish dev-debug noise (delete) from operational logging (keep, possibly migrate to a tiny logger module). High yield in `server/` paths (LLM extractor, adapters); low yield in `src/`.

### Wave Structure & Sequencing (discussed 2026-04-30)

- **D-28:** **7-wave API-first serial.** Each wave gates on `vitest run` green + ESLint 0 errors + `prettier --check` clean + `tsc --noEmit` clean before downstream waves start. Slowest wall-time but cleanest bisect; honors "don't compromise current features" by surfacing API health regressions FIRST and gating every subsequent wave on green CI:
  - **W1 — API audit** (D-22a). Hand-curated probe + fix every `/api/*` endpoint and upstream adapter. Fix what's broken before any cleanup-side work touches the same code paths. Output: a triage table in the wave's PLAN summary documenting probe results + fixes.
  - **W2 — `/api/health` + DevApiStatus consumer** (D-22b/D-24/D-25/D-26). New endpoint, severity tier wiring, banner component, "All APIs" tab in DevApiStatus.
  - **W3 — knip/ts-prune triage doc** (D-14 step 1+2+3). Read-only mechanical pass + manual codebase walk; commits ONLY the triage doc, no deletions yet.
  - **W4 — knip-validated deletions** (D-14 step 4). Atomic per-module deletion commits informed by W3 triage doc + D-29 bias.
  - **W5 — Hardcode generalization** (D-11 + D-12). Move IRAN_BBOX/IRAN_CENTER/WAR_START/ADS-B-radius into `src/lib/domain.ts`; introduce env vars per the D-12 list with defaults preserved.
  - **W6 — CSS @theme migration** (D-13). Move entity/event/site/faction color palettes into Tailwind v4 `@theme` block; update consumers to use the CSS vars.
  - **W7 — Normalization** (D-27). 7 sub-category atomic commits, in this order: TS strict → lint → Zustand selectors → Redis keys → vitest → imports → logging audit.

### Knip Triage Bias (discussed 2026-04-30)

- **D-29:** **Conservative default + per-category exceptions.** When reviewing the W3 triage doc:
  - **Default bias:** keep unless proven dead. Honors umbrella user directive "don't compromise current features or functionality."
  - **Confidence tagging:** every flagged item is annotated `high-dead` (mechanically + semantically dead with no plausible runtime path) | `probable-dead` (knip flags, no obvious user) | `ambiguous` (Zustand selectors of removed fields, dynamic imports, barrel re-exports, conditional code paths).
  - **Batch approval:** `high-dead` items in well-understood-dead categories (test helpers never imported, deprecated utility modules, orphaned hooks called from removed callers) get bulk approval.
  - **Individual review:** `probable-dead` and `ambiguous` items each get a yes/no decision before W4 deletes.
  - **Atomic commit per module** (D-14) preserved regardless of triage confidence.
