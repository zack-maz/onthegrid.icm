### Pattern 1: `/api/health` Probe-Strategy Mix (W1 + W2)

**What:** Per-endpoint mix of probe strategies, declared in a table.
**When to use:** Always — different endpoints have different cost/freshness tradeoffs.

| Endpoint                    | Probe Strategy                                                                           | Why                                                                                                                                              |
| --------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `/api/flights`              | cache-state introspection (`cacheGet`)                                                   | Hot polling endpoint; client polls every 5s, so the cache is freshest source. Direct upstream call would burn API credits on every health check. |
| `/api/ships`                | cache-state introspection                                                                | Same.                                                                                                                                            |
| `/api/events`               | cache-state introspection (`events:llm:v3` → bridge to `events:llm:v2` → `events:gdelt`) | Cron-driven (4am UTC); cache is ground truth. Pitfall 1 bridge already handles graceful degradation.                                             |
| `/api/news`                 | cache-state introspection                                                                | 15-min cadence; cache is fresh source.                                                                                                           |
| `/api/markets`              | cache-state introspection                                                                | 60s cadence; cache acceptable.                                                                                                                   |
| `/api/sites`                | cache-state introspection                                                                | 24h TTL; static infrastructure.                                                                                                                  |
| `/api/water`                | cache-state introspection                                                                | Same as sites.                                                                                                                                   |
| `/api/water/precip`         | cache-state introspection                                                                | 6h cadence.                                                                                                                                      |
| `/api/sources`              | direct call (`/api/sources` is itself near-free)                                         | Returns config status synchronously.                                                                                                             |
| `/api/llm-status`           | read `server/lib/llmProgress.ts` in-memory state directly                                | Already in-process; cheapest probe.                                                                                                              |
| `/api/dashboard/auth-check` | 200-only probe                                                                           | No freshness concept.                                                                                                                            |

| `/api/cron/health`          | last-tick timestamp (Redis key written by the cron handler)                              | Cron self-reports its last successful run; `/api/health` reads that ts.                                                                          |

**Example response shape (recommend):**

```typescript
// Source: synthesized from D-24/D-25/D-26 + existing CacheResponse<T> shape

type HealthStatus = 'healthy' | 'degraded' | 'unhealthy' | 'unknown';
type HealthTier = 'critical' | 'non-critical' | 'static' | 'probe-only' | 'cron';

type EndpointHealth = {
  name: string; // e.g., "/api/flights"
  status: HealthStatus;
  tier: HealthTier;
  lastSuccessTs: number | null; // ms epoch, null if never
  lastErrorReason: string | null; // null if currently healthy
  freshnessMs: number | null; // ms since last fresh data; null for probe-only
  freshnessThresholdMs: number; // D-25 table value
  latencyMs: number | null; // ms taken to run THIS probe
};

type HealthResponse = {
  endpoints: Record<string, EndpointHealth>;
  summary: {
    critical: { healthy: number; degraded: number; unhealthy: number };
    nonCritical: { healthy: number; degraded: number; unhealthy: number };
    static: { healthy: number; degraded: number; unhealthy: number };
    cron: { healthy: number; degraded: number; unhealthy: number };
    probeOnly: { healthy: number; unhealthy: number };
  };
  generatedAt: number; // ms epoch
};
```

**Status enum semantics:**

- `healthy` — `freshnessMs <= freshnessThresholdMs` AND last probe succeeded.
- `degraded` — `freshnessMs > freshnessThresholdMs` AND `freshnessMs <= 2*freshnessThresholdMs` (stale but recent).
- `unhealthy` — `freshnessMs > 2*freshnessThresholdMs` OR last probe threw.
- `unknown` — cache empty (cold deploy) AND no error history.

### Pattern 2: Vercel Fluid Compute Considerations

**What:** Fluid Compute keeps instances warm; in-memory state can be shared across requests within an instance, but NOT across instances.

**Implications for `/api/health`:**

- Don't try to maintain in-memory `lastSuccessTs` history per endpoint — instances spin up cold, and a fresh instance answering `/api/health` would show null history. Use Redis keys for any "last success" state that must survive cold starts.
- Cold-start penalty for `/api/health` itself: each probe adds latency. Recommend running probes in parallel via `Promise.all`, with per-probe `withTimeout(probe, 2000ms)` so a single hung adapter can't drag the whole response past Vercel's request limit.
- DO NOT pre-warm probes via a 4th cron entry — Hobby cap = 3 (CLAUDE.md "Cron-Driven Pipeline Trigger"). The 60s client poll IS the warm-up.

### Anti-Patterns to Avoid

- **Adding a 4th cron entry for `/api/health` warm-up.** Hobby cap = 3 (CLAUDE.md, 28.1-CONTEXT canonical_refs). The client polling at 60s warms the function naturally.
- **Re-introducing fire-and-forget extraction in `/api/events`.** Phase 27.4.6 anti-pattern #17. The route is cache-only; cache-write happens only in cron path.
- **Modifying `events:llm:v3` cache in `/api/health`.** Read-only probe.
- **Bundling W3 deletions into a single mega-commit.** D-14 step 4 + 27.4.x atomic-per-concern canon.
- **Auto-fixing lint warnings inside `.claude/worktrees/`.** 27.4.2 worktree-isolation pattern (3 instances now established as canonical).
- **Changing existing Redis key names during W7 sub-4 (Redis keys consistency).** If a key name needs migration, that's its own atomic commit with version bump (e.g., `events:llm:v3` → `events:llm:v4`). The Pitfall 1 bridge depends on these names.
- **Replacing `console.*` with `log.*` in a single sweep commit.** W7 sub-7 should be incremental — start with the highest-yield modules (`server/lib/llmEventExtractor.v3.ts`, `server/adapters/*.ts`) and leave `src/` `console.*` for follow-up.

## Common Pitfalls

### Pitfall 1: Knip flags Zustand selectors of removed fields as dead

**What goes wrong:** Knip sees `s => s.removedField` as an unused selector; deleting it breaks the store consumer.
**Why it happens:** Selectors are typed, mechanical, and look like dead helpers from a static perspective.
**How to avoid:** D-29 `ambiguous` confidence tag — every Zustand selector flagged by knip gets individual review, never bulk-approved.
**Warning signs:** Filename pattern `src/stores/*.ts` or `src/components/**/*.tsx` with selector literal in the diff.

### Pitfall 2: Vite `import.meta.glob()` patterns invisible to knip

**What goes wrong:** Files matched by `import.meta.glob('./layers/*.tsx')` look unimported to knip; deleting them breaks runtime.
**Why it happens:** Knip can't statically resolve glob patterns.
**How to avoid:** Audit `src/` for `import.meta.glob` usage during W3; add the matched paths to knip's `ignore` list in the per-run config.
**Warning signs:** Any `*.tsx` flagged in `src/components/map/layers/*` or anywhere with a `Layer` suffix.

### Pitfall 3: deck.gl peer-dep externals look unused but are imported by the bundler

**What goes wrong:** `vite.config.ts` `vendor-deckgl` `manualChunks` includes packages whose entry isn't directly imported by source. Phase 27.4.2 Plan 04 already hit this — `@deck.gl/react` and `@deck.gl/aggregation-layers` were listed but not installed.
**Why it happens:** Bundler hints, not source imports.
**How to avoid:** Cross-reference any "unused dep" knip flags against `vite.config.ts` `manualChunks` and `package.json` peer-dep relationships before deleting.
**Warning signs:** `@deck.gl/*`, `maplibre-gl`, `@vis.gl/react-maplibre` flagged.

### Pitfall 4: ts-prune false-positives on barrel re-exports

**What goes wrong:** A file like `src/lib/index.ts` re-exporting `./domain` shows `./domain` exports as "used in module" but nothing else uses them downstream — ts-prune may still flag.
**Why it happens:** ts-prune's reachability analysis is single-hop.
**How to avoid:** Use `--ignore "(used in module)"` or manually filter; D-29 `ambiguous` tag.
**Warning signs:** Module under `src/lib/` with `index.ts` sibling.

### Pitfall 5: severity.ts has TWO conflicting half-life values (latent bug)

**What goes wrong:** `CLAUDE.md` documents `halfLife = 6h` for severity recency decay. `src/lib/severity.ts:50` actually computes `1 / (1 + ageHours / 24)` — a 24h scale, NOT 6h.
**Why it happens:** Doc drift across phase boundaries.
**How to avoid:** During W5 D-12 introduction of `SEVERITY_HALF_LIFE_HOURS`, this is a forced-clarification moment. Pick one value (recommend 24h matching the code, since changing to 6h would alter notification ranking behavior) and update CLAUDE.md to match. Flag this in the W5 PLAN explicitly so the executor doesn't silently change behavior.
**Warning signs:** Any commit touching `src/lib/severity.ts` should also touch CLAUDE.md "Notification Center (Phase 17)" section.

### Pitfall 6: The `dismissTimers` ref in ProximityAlertOverlay is NOT a real bug

**What goes wrong:** D-27 sub-category 4 + deferred-items-promotion language ("may indicate a real bug") suggests the `dismissTimers` ref is suspicious.
**Why it happens:** Refs in dep arrays are usually anti-pattern.
**Investigation finding:** Read `src/components/map/ProximityAlertOverlay.tsx:88-109`. The ref pattern is intentional and correct — `dismissTimers` is a `Map<string, Timeout>` accumulating per-site dismiss timers. The cleanup useEffect at line 105-109 reads from `dismissTimers.current.values()` on unmount. ESLint warns because `dismissTimers` itself isn't in the dep array of the cleanup effect, but that's correct — refs don't trigger effect re-runs by design. The fix is `// eslint-disable-next-line react-hooks/exhaustive-deps -- ref intentionally excluded; cleanup runs on unmount only` with the rationale comment.
**How to avoid:** Don't add `dismissTimers` to the dep array. That would cause the cleanup effect to re-bind on every dismiss, defeating the cleanup-on-unmount intent. The W7 sub-4 fix is the eslint-disable comment, not a refactor.
**Warning signs:** Any planner who reads "may indicate a real bug" and assumes the fix is a refactor — push back during plan-checker review.

### Pitfall 7: CSS @theme + deck.gl interop — single source of truth is fragile

**What goes wrong:** D-13 migrates entity colors to `--color-flight` etc. CSS vars. deck.gl needs RGBA tuples `[234, 179, 8]`, not hex strings. Two failure modes:

1. Naive: read CSS var via `getComputedStyle()` at every render — expensive, runs on every map frame.
2. Drift: keep CSS hex separate from TS RGBA arrays, they disagree silently.
   **How to avoid:** **Read once at module load**, parse to RGBA tuple, export. See "Focus Area 4" recommendation below for the precise pattern.
   **Warning signs:** Any deck.gl `getColor` callback referencing `getComputedStyle()` in its body.

### Pitfall 8: `/api/health` probe burst at startup hits rate limiter

**What goes wrong:** Hot polling endpoints (`/api/flights`) have rate limits. If `/api/health` runs probes via direct internal HTTP fetch, every health check is itself a request. At 60s client poll × N concurrent dashboards, this could spike the rate-limit counter.
**How to avoid:** Use cache-state introspection for hot endpoints (Pattern 1 above). Internal HTTP probe is reserved for `/api/sources` which is near-free.
**Warning signs:** `/api/health` route handler containing `fetch('/api/flights')` calls.

## Code Examples

### CSS @theme + deck.gl bridge (Focus Area 4)

```typescript
// Source: synthesized from existing src/components/map/layers/constants.ts pattern
// File: src/lib/colorBridge.ts (NEW in W6)

/**
 * Read a CSS custom property from :root once at module load and parse to RGBA.
 * Falls back to a TS-literal default if the CSS var is missing.
 *
 * Why: deck.gl getColor callbacks fire per frame; getComputedStyle is too expensive there.
 * Why: keeping color values in CSS @theme block is canonical (D-13); TS literals would drift.
 */
function readCssRGB(varName: string, fallback: [number, number, number]): [number, number, number] {
  if (typeof window === 'undefined') return fallback; // SSR / test
  const raw = getComputedStyle(document.documentElement).getPropertyValue(varName).trim();
  if (!raw) return fallback;
  // Parse hex (#eab308) or rgb()
  if (raw.startsWith('#')) {
    const hex = raw.slice(1);
    return [
      parseInt(hex.slice(0, 2), 16),
      parseInt(hex.slice(2, 4), 16),
      parseInt(hex.slice(4, 6), 16),
    ];
  }
  const m = raw.match(/rgb\((\d+),\s*(\d+),\s*(\d+)\)/);
  if (m) return [Number(m[1]), Number(m[2]), Number(m[3])];
  return fallback;
}

// Module-load read; deck.gl getColor closures reference these constants
export const COLOR_FLIGHT = readCssRGB('--color-flight', [234, 179, 8]);
export const COLOR_FLIGHT_UNIDENTIFIED = readCssRGB('--color-flight-unidentified', [255, 255, 100]);
// ... etc
```

**Tradeoff:** Module-load read means CSS theme switches at runtime (e.g., dark/light mode toggle) won't re-read colors. For 28.1 there's only one theme, so this is fine. If theme switching is added later, wrap reads in a `useMemo` keyed on a theme version counter.

// File: server/lib/log.ts (NEW in W7 sub-7)

type Level = 'debug' | 'info' | 'warn' | 'error';
const LEVEL_NUMERIC: Record<Level, number> = { debug: 10, info: 20, warn: 30, error: 40 };

const ENV_LEVEL = (process.env.LOG_LEVEL ?? 'info').toLowerCase() as Level;
const MIN_LEVEL = LEVEL_NUMERIC[ENV_LEVEL] ?? LEVEL_NUMERIC.info;

function emit(level: Level, msg: string, ctx?: Record<string, unknown>) {
  if (LEVEL_NUMERIC[level] < MIN_LEVEL) return;
  const line = JSON.stringify({ level, msg, ts: new Date().toISOString(), ...(ctx ?? {}) });

  else if (level === 'warn') console.warn(line);
  else console.log(line);
}

  debug: (msg: string, ctx?: Record<string, unknown>) => emit('debug', msg, ctx),
  info: (msg: string, ctx?: Record<string, unknown>) => emit('info', msg, ctx),
  warn: (msg: string, ctx?: Record<string, unknown>) => emit('warn', msg, ctx),
  error: (msg: string, ctx?: Record<string, unknown>) => emit('error', msg, ctx),
};

### Focus Area 2: `/api/health` aggregate endpoint design

**Confidence: HIGH** — pattern synthesized from existing `cacheGet` infrastructure + DevApiStatus precedent + D-25 freshness table.

See "Pattern 1" + Code Examples sections above. Key design decisions:

1. **Response shape:** `{ endpoints: Record<name, EndpointHealth>, summary: TierRollup, generatedAt: ts }`. Zod-validated.
2. **Status enum:** 4-state `healthy | degraded | unhealthy | unknown`. `degraded` = stale-but-recent (1x to 2x threshold); `unhealthy` = stale beyond 2x threshold OR last probe threw.
3. **Freshness computation:** for cache-introspection probes, read `cacheGet(key, threshold).lastFresh`; compute `Date.now() - lastFresh` for `freshnessMs`. Status comes from comparing to `freshnessThresholdMs`.
4. **Vercel Fluid Compute:** state must survive instance churn — no in-memory probe history. Use Redis if any persistent history is wanted, but for V1 just probe-on-demand and return current state.
5. **Cold-start penalty:** parallelize probes via `Promise.all(probes.map(p => withTimeout(p, 2000)))`. Per-probe timeout caps the total response time.
6. **No 4th cron entry** — Hobby cap = 3. Client poll IS the warmup.
7. **Read-only:** `/api/health` MUST NOT mutate any cache key. Phase 27.4.6 anti-pattern #17.

### Focus Area 3: W1 audit probe implementation

**Confidence: HIGH** — D-25 freshness table + existing cache pattern direct evidence.

Per-endpoint mix already specified in "Pattern 1" table above. Three probe families:

**Cache-state introspection** (preferred for hot polling + static + cron endpoints): read `cacheGet(key, threshold)` and check `.lastFresh + .stale`. Costs zero upstream calls. Already-correct API surface.

**Direct adapter call** (only for `/api/sources` which is itself near-free): call the adapter function directly. Costs one network call per probe; OK for low-frequency endpoints.

**Cron last-tick timestamp** (for `/api/cron/*`): each cron handler writes a Redis key `cron:lastTick:<name>` on success. `/api/health` reads these keys; freshness threshold = 26h (D-25). The cron handlers ALREADY write `events:llm-process-ts` (CLAUDE.md "Cron-Driven Pipeline Trigger") — extend the pattern to all 3 crons.

**DO NOT use internal HTTP fetch for hot endpoints** — Pitfall 8 (rate-limit interaction) + Pitfall on cold-start latency multiplication.

```typescript
// src/hooks/useHealthStatus.ts
import { useEffect, useState } from 'react';
import type { HealthResponse } from '@/lib/healthClient';

export function useHealthStatus(intervalMs = 60_000) {
  const [health, setHealth] = useState<HealthResponse | null>(null);
  const [error, setError] = useState<Error | null>(null);

  useEffect(() => {
    let cancelled = false;
    let timer: ReturnType<typeof setTimeout>;

    const tick = async () => {
      try {
        const res = await fetch('/api/health');
        if (!res.ok) throw new Error(`/api/health ${res.status}`);
        const json = (await res.json()) as HealthResponse;
        if (!cancelled) setHealth(json);
      } catch (err) {
        if (!cancelled) setError(err as Error);
      }
      if (!cancelled) timer = setTimeout(tick, intervalMs);
    };

    tick();
    return () => {
      cancelled = true;
      clearTimeout(timer);
    };
  }, [intervalMs]);

  return { health, error };
}
```

Pattern matches existing `useFlightPolling` recursive-setTimeout shape (CLAUDE.md "Flight Data Patterns").
