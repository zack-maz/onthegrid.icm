# Phase 28.1 W7 Sub-4 — Redis Cache Key Audit

> Audit-only. NEVER renames load-bearing Phase 27.4.x bridge keys (Pitfall 1
> fallback chain depends on them). Outliers are documented; opportunistic
> renames only happen IF they're clearly NOT in any bridge chain AND have no
> operator-known external probes.

## Convention

`<domain>:<source>:<version>` per D-27 sub-3. In practice four shapes coexist
across the codebase, and divergence is principled (not noise):

| Shape                         | Example                                                                    | When applied                                                                                |
| ----------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `<domain>:<source>:<version>` | `events:llm:v3`                                                            | Multi-version cache where bridges + cold-fallback need to coexist (LLM pipeline canonical). |
| `<domain>:<source>`           | `events:gdelt`, `news:gdelt`                                               | Single-version cache; versioning would invalidate operator history without benefit.         |
| `<domain>:<version>`          | `sites:v3`, `water:facilities:v3`                                          | Single-source domain (Overpass) where source segment is implicit.                           |
| `<domain>:<facet>`            | `events:backfill-ts`, `events:llm-process-ts`, `news:feed`, `water:precip` | Marker / control / aggregation keys; not a primary data cache.                              |

The four shapes are intentional. The audit below confirms zero NON-PRINCIPLED
outliers — i.e. no key shape that's accidental rather than tier-driven.

## Outliers (semi-conformant or clearly non-conformant)

Two cron-warm constants drifted relative to their route-side counterparts.
Both are READ-ONLY warmer paths (cron pre-fills the cache for downstream
route reads) — IF the cron-warm constants and the route-side constants
target different keys, the warm is a no-op. This is a real but low-impact
drift; opportunistic alignment is APPROPRIATE here.

| Key                                              | Reason for non-conformance                                                                                                                  | Recommended action                                                                                                    |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| server/routes/cron-warm.ts:14 `sites:v2`         | STALE — route-side `server/routes/sites.ts:56` uses `sites:v3`. Cron warm targets the wrong key; fills `sites:v2` which no reader consumes. | ALIGN to `sites:v3` — zero risk, no current consumer of `sites:v2`. See "Renames Performed" below.                    |
| server/routes/cron-warm.ts:15 `water:facilities` | STALE — route-side `server/routes/water.ts:120` uses `water:facilities:v3`. Cron warm targets the wrong key.                                | ALIGN to `water:facilities:v3` — zero risk, no current consumer of `water:facilities`. See "Renames Performed" below. |

Note both renames were CAUGHT in the W7 sub-4 audit pass and are aligned in a
SEPARATE atomic commit AFTER this audit lands; the audit itself does not
rename. The renames are zero-risk because:

1. Both old keys (`sites:v2`, `water:facilities`) have NO downstream readers
   in the codebase (verified via grep: only the cron-warm writers reference
   them).
2. Cron-warm is a pre-fill helper — failing to write to the wrong key is the
   same as not warming at all (no breakage; just a missed warm).
3. After the rename, the cron-warm tier and the live route tier point to the
   same canonical key, restoring intended warm behavior.
