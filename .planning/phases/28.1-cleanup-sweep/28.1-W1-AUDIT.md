# Phase 28.1 W1 — API Audit Probe Results

> One-shot hand-curated audit per D-23. NOT re-run in CI. /api/health (D-24, W2) replaces test-as-monitoring.
>
> **Probe environment note.** This audit was performed from the executor agent shell, which has read access to the repo but NOT live network egress to upstream APIs (OpenSky, AISStream, Yahoo, GDELT, Overpass, Open-Meteo, Nominatim, Cerebras/Groq/NIM/OpenRouter) and NOT live Upstash Redis credentials. Cache-state introspection (`cacheGetSafe(key, 999_999_999)`) therefore could NOT be executed end-to-end against production data. Instead, every row in this audit performs a **static probe**: read the route handler + adapter source, verify cache-key spellings line up between writer and reader, verify the adapter URL is well-formed and matches the documented constant, and verify the schema-parse path (Zod schema at the route boundary, or shape contract for direct-return routes). Status values reflect the static state (HEALTHY = code path is correct + cache key matches between writer and reader; BROKEN = drift between writer and reader OR a missing handler; DEFERRED = needs live network and the executor cannot perform it).

## DRIFT items surfaced during static probe

These are NOT auth gates and NOT live-network blockers — they are code-vs-code mismatches the executor identified by reading the writer-side route and the reader-side prober (`/health` + `cron-health` + `cron-warm`).

### DRIFT-1 — `/api/news` writes `news:feed`; probers read `news:gdelt`

- **Writer:** `server/routes/news.ts:25` — `const NEWS_FEED_KEY = 'news:feed';` (`cacheSetSafe(NEWS_FEED_KEY, ...)` at line 78).
- **Readers (incorrect):** `server/routes/health.ts:10` and `server/routes/cron-health.ts:14` both list `news: 'news:gdelt'` in `SOURCE_KEYS`.
- **Actual `news:gdelt` writer:** `server/lib/llmEventExtractor.v2.ts:62` and `server/lib/llmEventExtractor.v3.ts:105` use `news:gdelt` as a NEWS-context SIDE-INPUT for the LLM extractor's prompt enrichment block. That key may or may not be populated depending on whether the LLM extractor has run recently — it is NOT the canonical news-route freshness witness.
- **Operational impact:** `/health` and the daily cron-health source-freshness check report stale-or-empty for news even when `/api/news` is fully fresh, AND would report fresh-news when only the LLM extractor's side-input has been written. Both directions are wrong.
- **Fix locus:** Pick ONE. Either (a) update `SOURCE_KEYS.news` in both `health.ts` and `cron-health.ts` to `'news:feed'`, OR (b) align the news route to also write `news:gdelt`. Recommend (a) — the route key is canonical and used by the polling client; the LLM extractor side-input deserves its own probe row in the W2 `/api/health` design, not a co-opt of the `news:gdelt` key.
- **Disposition:** **Defer to W2.** W1 is a one-shot audit; W2 builds the new `/api/health` with the corrected SOURCE_KEYS table per D-25, which is the natural and only-once fix locus. Bumping the existing `/health` SOURCE_KEYS in W1 would create churn that W2's larger refactor will redo.

### DRIFT-2 — `/api/sites` writes `sites:v3`; probers + cron-warm write+read `sites:v2`

- **Writer (route):** `server/routes/sites.ts:56` — `const SITES_KEY = 'sites:v3';`. Route reads + writes `sites:v3`.
- **Readers (incorrect):** `server/routes/health.ts:14` and `server/routes/cron-health.ts:19` both list `sites: 'sites:v2'`. `server/routes/cron-warm.ts:14` also defines `const SITES_KEY = 'sites:v2'` and writes Overpass results to `sites:v2`.
- **History:** Phase 27.3.1 Plan 11 bumped sites cache shape to envelope-style `{sites, filterStats}` and bumped key `sites:v2` → `sites:v3` to force cold-fill. The `cron-warm` route + `/health` + `cron-health` were not updated alongside.
- **Operational impact:** `cron-warm` pre-fills `sites:v2` (an old empty key nobody now reads); `/health` reports `sites:v2` freshness which is whatever the now-stale cron-warm last wrote 12h ago, NOT the route's actual `sites:v3` content. Snapshot tier (24h cache, 305 facilities) hides this from end-users — but the observability surface is wrong.
- **Fix locus:** Update SOURCE_KEYS in `health.ts` and `cron-health.ts` to `sites:v3`, AND update `cron-warm.ts` to write `sites:v3` with the envelope shape (`{sites, filterStats}`) — otherwise pre-warm is harmless but useless.
- **Disposition:** **Defer to W2 + W7 sub-4.** W2 fixes the prober; W7 sub-4 ("Redis cache key naming consistency") is the natural home for the cron-warm shape correction. Both are aligned with D-27 sub-4. Calling these out now per D-23 audit charter.

### DRIFT-3 — `/api/water` writes `water:facilities:v3`; probers + cron-warm write+read `water:facilities`

- **Writer (route):** `server/routes/water.ts:120` — `const FACILITIES_KEY = 'water:facilities:v3';`.
- **Readers (incorrect):** `server/routes/health.ts:15`, `server/routes/cron-health.ts:20`, and `server/routes/cron-warm.ts:15` all list/write `water:facilities` (the original v1 key).
- **History:** Phase 27.3.1 + Phase 27.3.2 bumped water cache `water:facilities` → `water:facilities:v2` → `water:facilities:v3` while introducing the no_resolved_name rejection bucket. `/health` + cron-warm + cron-health were never updated.
- **Operational impact:** Identical to DRIFT-2. `cron-warm` writes a key the route never reads; observability is wrong.
- **Fix locus:** Same shape as DRIFT-2 — align prober + cron-warm writer to `water:facilities:v3` AND the envelope shape (`{facilities, filterStats}`).
- **Disposition:** **Defer to W2 + W7 sub-4** — same rationale as DRIFT-2.

### DRIFT-4 — `/api/markets` cache key has range suffix; static SOURCE_KEYS only probes `:1d`

- **Writer (route):** `server/routes/markets.ts:23` — `const cacheKey = \`markets:yahoo:${range}\`;`writes one of`markets:yahoo:1d`, `markets:yahoo:5d`, `markets:yahoo:1mo`, `markets:yahoo:ytd`.
- **Readers:** `server/routes/health.ts:12` and `server/routes/cron-health.ts:16` both list `markets: 'markets:yahoo:1d'` — only the default range is probed.
- **Operational impact:** Lower-severity than DRIFT-1/2/3 because the default range IS the one the dashboard polls (per CLAUDE.md). But /health blind to the other ranges if a future feature surfaces them.
- **Fix locus:** D-25 table in W2 already lists `/api/markets` as a single entry — recommend documenting that the freshness probe targets the default `:1d` cache key only and noting this in the W2 PLAN.
- **Disposition:** **Defer to W2** — informational; not a regression risk. Captured for completeness per D-23.

## Probing Methodology

### Cache-state introspection (preferred for hot polling + static + cron) — STATIC-ONLY in this audit

Read `cacheGetSafe(key, 999_999_999)` and confirm the cache returns a non-null entry with parseable data. Costs zero upstream calls. Status:

- HEALTHY = entry present, parses against expected shape, lastFresh < D-25 threshold for the endpoint
- DEGRADED = entry present, parses, but lastFresh > D-25 threshold (stale but recoverable)
- BROKEN = entry absent OR fails parse

**This audit could not run cache-state probes live** (executor lacks Upstash REST credentials). Each "HEALTHY (static)" status above is a static-code probe: confirmed (1) the route handler is mounted, (2) the cache key writer + reader spellings agree (or DRIFT marker if they don't), (3) Zod schema or shape contract is intact at the route boundary. Live cache-state probes require running `vercel dev` with production env or running against the deployed instance with an authorized terminal — orchestrator can pass to the user during the W1 checkpoint.

### Direct adapter call (for /api/sources only)

Invoke the adapter's exported fetch function. Confirm it returns expected shape without throwing. `/api/sources` returns synchronously from env-var presence — no upstream call needed.

### Cron last-tick timestamp (for /api/cron/\*)

Read the per-cron Redis key (cron handler writes it on success). Confirm last-tick within 26h. **Static-only in this audit** — confirmed all three cron handlers exist + are mounted at the schedule paths declared in `vercel.json:5-7`.

### In-memory state read (for /api/events/llm-status)

Read `server/lib/llmProgress.ts` exports directly. Confirm progress object exists. Confirmed: module-level singleton `llmProgress` is declared and exported; `LLMPipelineProgress` interface has all 27.4 extension fields (callHistory, tokenCounters, dlqCount, breakerState, evalScore, etc.).
