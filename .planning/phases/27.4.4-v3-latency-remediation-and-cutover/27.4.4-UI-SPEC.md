### Explicit Non-Goals (lock against speculative design)

The following surfaces were considered and **explicitly excluded** in CONTEXT.md or by inheritance:

- **No cutover button / modal in the app.** Cutover is operator-driven via `POST /api/events/llm-pipeline {version: 'v3'}` (curl / scripted). The Topbar pill is read-only post-27.4.1 (D-20 inheritance). Do NOT design a cutover-confirm dialog.
- **No production pipeline-version badge.** Pill stays dev-only. Do NOT promote the pill to production visibility.
- **No user-visible alert banners** for auto-rollback firing. Trigger 1/2 events are surfaced through the existing audit log + DevApiStatus, not via toast/banner UI.
- **No operator-approval UI in the app.** D-16's 4 approval checkpoints happen in PLAN.md / CUTOVER.md / executor-driven `STOP / AWAIT OPERATOR APPROVAL` steps — not via in-app prompts.
- **No forensic-snapshot UI.** D-19 snapshots are produced by `scripts/snapshot-v3-redis.ts`, written to disk under `.planning/phases/27.4.4-...`. No browser surface.
- **No bake-off matrix UI.** D-02/D-03 bake-off output lives in `27.4.4-XX-BAKEOFF.md`. No browser-rendered table.
- **No /api/eval-cron UI.** D-14 cron writes to existing Redis baseline key; if visible at all, it surfaces through the existing eval-score block (no new block in this phase).

If a planner or executor finds themselves designing any of the above, **stop** — that is out of scope and must be raised with the user as a scope-change request.

## Cell Specifications

These three cells are the entire UI deliverable of Phase 27.4.4. Each cell is appended to its host block after the existing per-provider rows, separated by `mt-1` only (no `border-t` — they share the host block's frame).

### Cell A — Pre-Warm (D-21)

**Host block:** `LatencyHistogramBlock`
**Position:** below the per-provider P50/P95/P99 rows, above the block's closing `</div>`.
**Source data fields** (added to `llmProgress` in this phase, A9-mirrored to `useLLMStatusPolling.ts`):

- `prewarmCount: number` — total pre-warm calls fired this run
- `lastPrewarmTs: number | null` — epoch-ms of most recent pre-warm
- `prewarmState: 'warm' | 'cold-fired' | 'unknown'` — derived from `Date.now() - lastNimCallTs`

**Layout (single row, 9px, tabular-nums):**

```
pre-warm: <state-badge> · count=<prewarmCount> · last=<relativeTime|"—">
```

**State-badge rules:**

| State        | Copy           | Tailwind                                                 |
| ------------ | -------------- | -------------------------------------------------------- |
| `warm`       | `warm`         | `bg-green-500/20 text-green-300 px-1 rounded text-[9px]` |
| `cold-fired` | `cold (fired)` | `bg-amber-500/20 text-amber-300 px-1 rounded text-[9px]` |
| `unknown`    | `—`            | `text-white/40 text-[9px]` (no chip background)          |

**Empty state:** when `prewarmCount === 0` AND `lastPrewarmTs === null`, render:

```
pre-warm: <state-badge> · count=0 · last=—
```

(No separate empty line — the row is informative even at zero. Showing `count=0` confirms the surface is wired and pre-warm has simply not been needed yet.)

**Why on the Latency block:** pre-warm exists to remove cold-start lag from p99. Co-locating it with latency lets the operator correlate "p99 dropped to 19s" with "pre-warm fired N times this run."

---

### Cell B — Adaptive Batch (D-04)

**Host block:** `RoutingTraceBlock`
**Position:** below the last-50 routing rows, above the block's closing `</div>`.
**Source data fields** (added to `llmProgress`, A9-mirrored):

- `adaptiveBatchStats.splitCount: number` — number of timed-out batches that were split into 1+1
- `adaptiveBatchStats.retrySuccess: number` — split-half retries that succeeded
- `adaptiveBatchStats.retryFail: number` — split-half retries that failed (and were DLQ-enqueued)
- `adaptiveBatchStats.dlqEnqueueCount: number` — entries written to DLQ with `reason: 'v3:adaptive-retry-fail'`
- `adaptiveBatchEnabled: boolean` — `env.V3_ADAPTIVE_BATCH === true`

**Layout (single row, 9px, tabular-nums):**

```
adaptive-batch: <enabled-badge> · split=<splitCount> · retry-ok=<retrySuccess> · retry-fail=<retryFail> · dlq=<dlqEnqueueCount>
```

**Enabled-badge rules:**

| Condition                                              | Copy         | Tailwind                                                 |
| ------------------------------------------------------ | ------------ | -------------------------------------------------------- |
| `adaptiveBatchEnabled === true` AND `splitCount > 0`   | `on (fired)` | `bg-amber-500/20 text-amber-300 px-1 rounded text-[9px]` |
| `adaptiveBatchEnabled === true` AND `splitCount === 0` | `on (idle)`  | `bg-green-500/20 text-green-300 px-1 rounded text-[9px]` |
| `adaptiveBatchEnabled === false`                       | `off`        | `text-white/40 px-1 text-[9px]` (no chip background)     |

**Numeric-cell color rules:**

| Field         | Default         | Threshold rule                                                                                                     |
| ------------- | --------------- | ------------------------------------------------------------------------------------------------------------------ |
| `split=`      | `text-white/80` | unchanged regardless of value                                                                                      |
| `retry-ok=`   | `text-white/80` | colorize `text-emerald-300` when `> 0`                                                                             |
| `retry-fail=` | `text-white/80` | colorize `text-rose-300` when `> 0`                                                                                |
| `dlq=`        | `text-white/80` | colorize `text-rose-300` when `> 0`; chip `bg-red-500/20 text-red-300` when `> 5` (matches Gate B DLQ≤5 threshold) |

**Empty state:** when `adaptiveBatchEnabled === false`, render the row with `off` badge and all counters at `=0` in `text-white/40`. **Do not hide the cell** — its presence at zero values confirms the wiring is live.

**Why on the Routing block:** adaptive batching is fundamentally a routing decision (split-this-batch vs send-as-one). Co-locating it with the routing trace puts retry-success vs retry-fail next to the primary-vs-fallback signal that operators read together.

### Cell C — Lineage Pre-Filter (D-18)

**Host block:** `SchemaStrictFailureBlock`
**Position:** below the per-provider failure rows, above the block's closing `</div>`.
**Source data fields** (added to `llmProgress`, A9-mirrored):

- `lineagePrefilterStats.hitCount: number` — groups skipped via lineage cache hit
- `lineagePrefilterStats.missCount: number` — groups that fell through to LLM call
- `lineagePrefilterEnabled: boolean` — `env.V3_LINEAGE_PREFILTER === true`

**Derived value:** `hitRate = hitCount / (hitCount + missCount)` formatted as `XX.X%` (one decimal). When denominator is 0, render `—%`.

**Layout (two-row cell — single label row + ProgressBar row):**

```
lineage-prefilter: <enabled-badge> · hit=<hitCount> · miss=<missCount> · rate=<hitRate>
[ProgressBar completed=hitCount total=(hitCount+missCount) barColor=#34d399]
```

The ProgressBar is exactly the existing `ProgressBar` component. Use `barColor='#34d399'` (emerald) for healthy hit rates; switch to `'#fbbf24'` (amber) when `hitRate < 0.20` AND `missCount > 50` (i.e., enabled but cache rarely hitting — operator should investigate cache-key drift).

**Enabled-badge rules:**

| Condition                                                           | Copy        | Tailwind                                                 |
| ------------------------------------------------------------------- | ----------- | -------------------------------------------------------- |
| `lineagePrefilterEnabled === true` AND `hitCount + missCount > 0`   | `on`        | `bg-green-500/20 text-green-300 px-1 rounded text-[9px]` |
| `lineagePrefilterEnabled === true` AND `hitCount + missCount === 0` | `on (idle)` | `bg-green-500/20 text-green-300 px-1 rounded text-[9px]` |
| `lineagePrefilterEnabled === false`                                 | `off`       | `text-white/40 px-1 text-[9px]` (no chip background)     |

**Empty state:** when `lineagePrefilterEnabled === false`, render the label row with `off` badge and `hit=0 · miss=0 · rate=—%` in `text-white/40`. **Omit the ProgressBar row** in this case (a 0/0 bar is visual noise). When enabled but pre-bake (`hit+miss === 0`), render an empty ProgressBar (`completed=0 total=1` to avoid divide-by-zero) in `text-white/20`.

**Why on the Schema-Strict Failure block:** lineage pre-filter and schema-strict failure are both "did we even need to call the LLM?" questions. Pre-filter answers "we skipped this group because we already have its enriched output." Schema-strict-fail answers "we called the LLM but had to throw the result out." Adjacent placement lets operators see total avoided work (skip + reject) at a glance.

## Empty States, Loading States, Error States

**Loading:** No skeleton. The cells either render `count=0`/`hit=0` placeholder text or an empty-state line; first poll completes within 1–2s and replaces placeholders. This matches every other v3 dashboard block.

**Error / network failure:** If `llm-status` poll fails entirely, the parent `EventsFiltersSectionV3` falls back to its existing failure UI (already specified in 27.4.3). New cells inherit this — no separate error path.

**Field-missing:** If the server has not yet shipped the new fields (e.g., during the brief deploy window between server and client), the cells render with the empty-state semantics above (`count=0`, badge=`unknown` or `off`). **No optional-chaining-into-undefined runtime errors.** Defensive default values:

```typescript
const prewarmCount = llmStatus.prewarmCount ?? 0;
const lastPrewarmTs = llmStatus.lastPrewarmTs ?? null;
const prewarmState = llmStatus.prewarmState ?? 'unknown';

const adaptiveStats = llmStatus.adaptiveBatchStats ?? {
  splitCount: 0,
  retrySuccess: 0,
  retryFail: 0,
  dlqEnqueueCount: 0,
};
const adaptiveEnabled = llmStatus.adaptiveBatchEnabled ?? false;

const lineageStats = llmStatus.lineagePrefilterStats ?? { hitCount: 0, missCount: 0 };
const lineageEnabled = llmStatus.lineagePrefilterEnabled ?? false;
```

This makes the cells safe to ship in a commit before the server-side instrumentation lands (though A9 discipline requires same-commit landing).

## Accessibility Notes (dev-only surface)

The dev dashboard is gated on `import.meta.env.DEV` and is not part of the production user surface. As such, the WCAG bar applied is "internal tooling readability" not "AA/AAA conformance":
