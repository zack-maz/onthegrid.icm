## Remediation Strategy

### Q1 — Primary remediation lever for Gate B

| Option                                | Description                                                         | Selected |
| ------------------------------------- | ------------------------------------------------------------------- | -------- |
| Model swap                            | Lock faster model; llama-3.3-70b at p50 7.7s → ~25-30min sequential | ✓        |
| Combo: model swap + adaptive batching | Belt-and-suspenders; adds code surface                              |          |
| Adaptive batching alone               | Doesn't address 929s p99; splitting still blows watchdog            |          |
| Looser watchdog with hard ceiling     | Doesn't help 929s outliers                                          |          |

**Decision:** D-01 — Model swap as primary lever.

### Q2 — Bake-off scope expansion

| Option                                 | Description                                                           | Selected |
| -------------------------------------- | --------------------------------------------------------------------- | -------- |
| Tier 1+2 with prompt-tuning            | qwen + llama-3.3 + nemotron + glm4.7 at 50 events; prompt-tune tier 2 | ✓        |
| Tier 1 only — minimum viable           | Just qwen + llama-3.3 at 50 events                                    |          |
| Full sweep including OpenRouter rescan | 5-8 candidates; most thorough                                         |          |
| Llama-3.3-70b focused validation only  | Single candidate; tightest feedback loop                              |          |

**Decision:** D-02 — Tier 1+2 with prompt-tuning at 50 events.

### Q3 — Winner selection criteria

| Option                              | Description                                         | Selected |
| ----------------------------------- | --------------------------------------------------- | -------- |
| Dual hard floors                    | within20km≥0.890 AND p95≤30s; tiebreaker lowest p99 | ✓        |
| Accuracy floor + latency tiebreaker | Permissive on speed                                 |          |
| Composite score formula             | Arbitrary weights; harder to defend in audit        |          |
| Latency floor + accuracy tiebreaker | Risks Gate A failure                                |          |

**Decision:** D-03 — Dual hard floors.

### Q4 — Adaptive batching contingency

| Option                                      | Description                                | Selected |
| ------------------------------------------- | ------------------------------------------ | -------- |
| Adaptive batching as opt-in defensive layer | V3_ADAPTIVE_BATCH env flag, default off    | ✓        |
| Adaptive batching always-on                 | Worse runtime if retries fail              |          |
| Skip — rely on existing safety net          | Risks another wasted 218min Gate B attempt |          |
| Dual-model concurrent racing                | Doubles request count; complexity          |          |

**Decision:** D-04 — Opt-in adaptive batching.

### Q5 — Pre-bake-off characterization

| Option                                        | Description                                              | Selected |
| --------------------------------------------- | -------------------------------------------------------- | -------- |
| Yes — instrumented v3 trace (20-batch)        | TTFB, token rate, generation vs network, max_tokens hits | ✓        |
| Skip — trust bake-off latency profile alone   | Faster but uncharacterized failure mode                  |          |
| Permanent instrumentation only — no preflight | Naturally captures during bake-off                       |          |
| Combine: instrument + 10-batch preflight      | Best of both                                             |          |

**Decision:** D-05 — Instrumented v3 trace preflight (20-batch).

### Q6 — max_tokens cap

| Option                                        | Description                                          | Selected |
| --------------------------------------------- | ---------------------------------------------------- | -------- |
| Yes, data-driven from preflight               | p99(tokens-out) + 20% buffer per model, ceiling 4096 | ✓        |
| Yes, conservative fixed cap (max_tokens=4096) | Single value, not data-driven                        |          |
| Aggressive fixed cap (max_tokens=2048)        | Risk: schema_fail rate spikes                        |          |
| No cap — rely on watchdog                     | Doesn't address reasoning-token explosion root cause |          |

**Decision:** D-06 — Data-driven max_tokens cap.

### Q7 — Tier 2 prompt-tuning budget

| Option                                | Description                          | Selected |
| ------------------------------------- | ------------------------------------ | -------- |
| 30min total time-budget across both   | Single 30min wall-clock; bounded     | ✓        |
| 3 attempts per candidate, no time cap | Could burn 30-60min just on tuning   |          |
| Single attempt only — fix or defer    | Misses candidates needing 2 attempts |          |
| Skip tier 2 — run baseline only       | Reverses D-02 prompt-tuning decision |          |

**Decision:** D-07 — 30min wall-clock budget for tier 2 prompt-tuning combined.

### Q9 — Add observability gates beyond original 4

| Option                                  | Description                                       | Selected |
| --------------------------------------- | ------------------------------------------------- | -------- |
| Add 3 observability gates               | schema_fail≤2%, p95≤30s, routingTrace≥90% primary | ✓        |

### Q10 — Run count

| Option                         | Description                      | Selected |
| ------------------------------ | -------------------------------- | -------- |
| 2 consecutive passes required  | Both must clear all 7 gates      | ✓        |
| Single run — original behavior | Doesn't validate reproducibility |          |
| 3 consecutive passes required  | Diminishing returns vs 2         |          |
| 2 runs with 1-hour gap         | Schedule complexity              |          |

**Decision:** D-10 — 2 consecutive Gate B passes.

### Q11 — Failure semantics

| Option                                         | Description                                  | Selected |
| ---------------------------------------------- | -------------------------------------------- | -------- |
| Strict: treat as overall fail, defer cutover   | Two consecutive passes is the bar            | ✓        |
| Allow 1 retry of Pass 2 only                   | Slippery slope                               |          |
| Best 2 of 3                                    | Masks intermittent regression                |          |
| Different operator action by which gate failed | Anti-Palantir-grade decisions under pressure |          |

**Decision:** D-11 — Strict failure semantics.
