## Summary

Phase 27.4.4 is a Palantir-grade reliability remediation phase: every reusable primitive landed in 27.4.3 (vendored router, v3 extractor with watchdog, observability dashboard, auto-rollback, eval harness, bake-off harness), and the only thing missing is a model that doesn't blow up at the long-tail. CONTEXT.md already locks 21 D-decisions; this RESEARCH closes the remaining technical-fidelity gaps the planner will need to author task-level work without re-deriving locked policy.

Key findings:

- **No new code surfaces.** Every extension point is an additive helper inside an existing file, with line-precise cites below.
- **NIM models behave OpenAI-compatibly through `https://integrate.api.nvidia.com/v1` but their structured-output stories diverge.** llama-3.3-70b uses standard `response_format: json_object` cleanly (D-01 leading candidate). Nemotron-3-super-120b-a12b and glm4.7 each have known shape/empty-content quirks in 27.4.3 Plan 03 evidence; the planner should pre-budget a single "envelope-shape" demo prompt for nemotron and a `guided_json` (`nvext` extension) experiment for glm4.7 — and stop when D-07's 30-min wall-clock fires.
- **Per-call instrumentation can land non-invasively in `freeClaudeRouter.callLLM()`.** TTFB and generation duration require the streaming path; the existing non-streaming call gives `usage.completion_tokens` for free, so token-emission rate falls out by dividing tokens by total `latencyMs`. Concrete shape below.
- **Vercel cron auth pattern: project DOES NOT YET use CRON_SECRET on `cron-warm`/`cron-health`** — they're un-authed. The planner must INTRODUCE the `Authorization: Bearer ${CRON_SECRET}` pattern for `/api/eval-cron` (D-14). Existing endpoints are `/api/cron/health` and `/api/cron/warm` mounted at `server/index.ts:84-85`; vercel.json declares both at `vercel.json:5-6`. Note the path scheme mismatch with CONTEXT.md: existing cron paths are `/api/cron/<name>` (the rewrite rule at `vercel.json:9` routes everything `/api/cron/:path*` → vercel-entry); CONTEXT proposes `/api/eval-cron` (single segment, NOT under `/api/cron/`) — verified that path falls under the same rewrite via `/api/:path*` at `vercel.json:10`, but consistency suggests `/api/cron/eval` may be preferable. Operator's call.
- **Upstash REST `/get/{key}` is binary-safe via `Upstash-Encoding: base64` header**, but the `@upstash/redis` SDK already in use (`server/cache/redis.ts:1-8`) is the cleaner path — no header munging needed. Snapshot script can use `redis.get<unknown>(key)` directly and write the JSON-encoded result to disk. The 6 keys in D-19 are well within Upstash REST size envelope (Plan 05 final snapshot was ~3MB worth of cached events; Upstash's documented practical body limit is generous for this scale).
- **Module-level `lastNimCallTs` (D-21) survives Vercel warm starts but resets on cold start.** The current rate-limiter `RollingWindow` instance at `freeClaudeRouter.ts:123` already follows this pattern — explicitly called out in `llmProgress.ts:6-7`. Pre-warm on cold start is the natural design: cold start resets `lastNimCallTs=0`, so the first `/api/events` call after cold-start triggers pre-warm precisely when needed. **No Redis backing required.**
- **Adaptive-batching test pattern is already established by 27.4.1 v2 tests.** The `withBatchWatchdog` mock pattern at `server/__tests__/lib/llmEventExtractor.v2.test.ts:60-63, 617-621, 656-662` shows exactly how to simulate a single timeout, then a passing batch on the next call — that's the unit-test surface for `splitBatchOnTimeout(batch, opts)` (D-04).
- **Schema-fail rate measurement is already wired in v3.** `schemaFailures` is incremented at two sites (`llmEventExtractor.v3.ts:579-586` malformed-JSON path and `:604-611` Zod-fail path) and exposed via `/api/events/llm-status` at `events.ts:635`. Rate = `(nvidia_nim.total + openrouter.total) / completedBatches` (operator pull-down for the per-pass threshold table).

**Primary recommendation:** Plan as a 2-plan sequence per CONTEXT specifics §"PLAN.md task structure sketch". Plan 01 is the **prep** (preflight + bake-off + winner-lock + 5 helper landings + dev dry-run); Plan 02 is the **cutover** (Gate A re-baseline + 2 Gate B passes + cutover POST + 27.4.2 UAT close). Atomic commits per task. The combined surface is ≈12+8=20 tasks, all ≤30-line code edits except `splitBatchOnTimeout` (≈80 lines) and `scripts/snapshot-v3-redis.ts` (≈120 lines).

### Candidate 3 — `nvidia/nemotron-3-super-120b-a12b` (tier 2, prompt-tunable)

- **NIM client config:** Same. NIM docs confirm OpenAI-compatible with `enable_thinking` chat-template kwarg + `reasoning_budget` for hard token ceiling [CITED: https://docs.api.nvidia.com/nim/reference/nvidia-nemotron-3-super-120b-a12b].

[CITED: NIM docs]
- **response_format:** `{type: 'json_object'}` is documented as accepted but NIM officially recommends `nvext.guided_json` for stricter shape enforcement [CITED: https://docs.nvidia.com/nim/large-language-models/1.1.0/structured-generation.html — "guided_json constrains output to a specific structure" vs "json_object enables the model to generate any valid JSON, including empty JSON"].
- **Plan 03 failure mode:** All 8 LLM-OK responses failed Zod with `events.0.groupKey: Required; events.0.location: Required` — model emits FLAT shape `{groupKey, location, ...}` instead of `{events: [{groupKey, location, ...}]}` envelope. [CITED: 27.4.3-03-BAKEOFF.md row 3 + Loser Deferral §2]
- **Best-bet prompt-tuning techniques (D-07, ranked by likelihood-to-unlock and lowest cost):**
  1. **Few-shot envelope demo + explicit "WRAP YOUR EVENTS ARRAY" demand** (highest yield per Plan 03 evidence + lowest token cost). Add to system prompt: `"Your output MUST be a single JSON object with a top-level 'events' array. Example: {\"events\": [{\"groupKey\": \"...\", \"location\": {...}, ...}]}. Do NOT emit a flat object with groupKey at the top level."` Cost: +~200 tokens system prompt; one bake-off run = ~10min. [BEST-BET]
  2. **`extra_body.nvext.guided_json` with the v3 JSON schema** — proper structured output guarantee, but the OpenAI SDK requires passing through `extra_body`: `client.chat.completions.create({model, messages, extra_body: {nvext: {guided_json: EVENT_EXTRACTION_SCHEMA_V3}}})`. Cost: ~10 lines of harness code in `bakeoff-v3-direct.ts` + one bake-off run. Higher ceiling (deterministic shape) but requires an SDK extra_body extension which the existing `OpenAI.chat.completions.create` call shape supports out-of-the-box. [SECOND-BEST]
- **Recommendation:** Try (1) first. If still failing within ~15min total wall-clock, switch to (2) with the rest of the budget. Defer if both fail.
- **Confidence:** MEDIUM — NIM docs are sparse on the nemotron+nvext.guided_json combo specifically; the broader claim that NIM supports `guided_json` is HIGH-confidence per NIM structured-generation doc.

## 3. Per-Call Instrumentation Pattern (D-05)

The existing `freeClaudeRouter.callLLM()` already captures `latencyMs` (`t0 = Date.now()` at `:327` and `Date.now() - t0` at `:338, :363`), `usage.prompt_tokens`/`completion_tokens` from response (`:347-353`), and writes them via the `recordLatency`/`accrueShadowCost` helpers (`:417-506`). For D-05 preflight characterization, add three additional captures.

**Three targets, smallest-diff approach:**

1. **TTFB (time-to-first-byte)** — requires the **streaming variant** of OpenAI SDK. The non-streaming call (`chat.completions.create({stream: false, ...})`) returns the full response in one promise resolution; first-byte time is indistinguishable from total time. Switch to streaming-only-during-preflight (`stream: true`) and record the timestamp of the FIRST `chunk` yielded by the iterator. Wrap conditional in `if (opts.captureTTFB) {...} else {...}` so production stays on non-streaming.
2. **Generation duration** — total wall clock minus TTFB.
3. **Token-emission rate** — `completion_tokens / generationDurationMs * 1000` tokens/sec.
4. **`<think>` block size** — measure raw response BEFORE `stripReasoningBlocks` runs; capture `(rawLength - strippedLength)` as approximate think-block bytes.
5. **max_tokens hit count** — check `response.choices[0]?.finish_reason` — `'length'` means the cap was hit. NIM exposes this via OpenAI-compat. Increment a counter per-model.

**Minimal TypeScript shape (illustrative, lands additively in `freeClaudeRouter.callLLM()`):**

```typescript
// freeClaudeRouter.ts — D-05 preflight instrumentation (gated on opts.captureTTFB)

interface CallTelemetry {
  latencyMs: number;
  ttfbMs: number | null; // null if not in capture mode
  genDurationMs: number | null;
  tokensIn: number;
  tokensOut: number;
  emissionRateTps: number | null; // tokens/sec
  reasoningBytes: number;
  finishReason: 'stop' | 'length' | 'tool_calls' | string | null;
  rawResponseBytes: number;
}

// Inside the for-attempt loop, after building the request:
const t0 = Date.now();
let firstByteTs: number | null = null;
let raw: string = '';
let usage: { prompt_tokens?: number; completion_tokens?: number } | undefined;
let finishReason: string | null = null;

if (opts.captureTTFB) {
  const stream = await p.client.chat.completions.create({
    model: p.model,
    messages,
    response_format: { type: 'json_object' },
    temperature: 0,
    max_tokens: MAX_TOKENS_PER_MODEL[p.model] ?? MAX_TOKENS_DEFAULT, // D-06
    stream: true,
    stream_options: { include_usage: true },
  });
  for await (const chunk of stream) {
    if (firstByteTs === null) firstByteTs = Date.now();
    const delta = chunk.choices[0]?.delta?.content ?? '';
    raw += delta;
    if (chunk.choices[0]?.finish_reason) finishReason = chunk.choices[0].finish_reason;
    if (chunk.usage) usage = chunk.usage;
  }
} else {
  const res = await p.client.chat.completions.create({
    model: p.model,
    messages,
    response_format: { type: 'json_object' },
    temperature: 0,
    max_tokens: MAX_TOKENS_PER_MODEL[p.model] ?? MAX_TOKENS_DEFAULT,
  });
  raw = res.choices[0]?.message?.content ?? '';
  usage = res.usage;
  finishReason = res.choices[0]?.finish_reason ?? null;
}

const latencyMs = Date.now() - t0;
const tokensIn = usage?.prompt_tokens ?? 0;
const tokensOut = usage?.completion_tokens ?? 0;
const stripped = stripReasoningBlocks(raw);
const reasoningBytes = raw.length - (stripped?.length ?? 0);

const telemetry: CallTelemetry = {
  latencyMs,
  ttfbMs: firstByteTs !== null ? firstByteTs - t0 : null,
  genDurationMs: firstByteTs !== null ? Date.now() - firstByteTs : null,
  tokensIn,
  tokensOut,
  emissionRateTps:
    firstByteTs !== null && tokensOut > 0
      ? (tokensOut / Math.max(1, Date.now() - firstByteTs)) * 1000
      : null,
  reasoningBytes,
  finishReason,
  rawResponseBytes: raw.length,
};
// existing recordLatency / accrueShadowCost calls below...
// PLUS for preflight: append telemetry to a /tmp/27.4.4-preflight-trace.jsonl file.
```

**Where it lands:** `server/lib/freeClaudeRouter.ts` `callLLM()` between current lines 326 and 393 (the per-attempt for loop). Streaming branch is opt-in via new `opts.captureTTFB?: boolean` parameter. Production callers don't pass it; only `scripts/bakeoff-v3-direct.ts --mode=characterize` does.

**Output sink:** `27.4.4-PREFLIGHT-CHARACTERIZATION.md` is the markdown summary; raw per-call JSONL goes to `/tmp/27.4.4-preflight-trace.jsonl` (mirrors Plan 03 `/tmp/27.4.3-03-bakeoff-direct-results.jsonl` convention at `bakeoff-v3-direct.ts:31`).

## 4. Vercel Cron Auth + crons[] Declaration Pattern (D-14)

### Existing project state (CRITICAL gotcha)

## 5. Upstash Redis Snapshot Wire Shape (D-19)

### Approach

Prefer the project's existing `@upstash/redis` SDK at `server/cache/redis.ts:1-8` over the raw REST API. The SDK is already configured, handles JSON encoding, and `redis.get<unknown>(key)` returns the deserialized value verbatim. Bypass the `cacheGet`/`cacheSet` envelope wrappers — those add `{data, fetchedAt}` structure for cache logic, but for forensic snapshots we want the raw key contents.

### Sample script structure

**File: `scripts/snapshot-v3-redis.ts` (NEW)**

```typescript
#!/usr/bin/env node
/**
 * Phase 27.4.4 D-19 — forensic Redis snapshot for v3 Gate B audit.
 *
 * Usage:
 *   tsx scripts/snapshot-v3-redis.ts --label=gate-b-pass-1-start
 *   tsx scripts/snapshot-v3-redis.ts --label=gate-b-pass-1-end
 *
 * Captures the 6 v3 keys at a moment in time + writes JSON file.
 */
import { writeFileSync, mkdirSync } from 'node:fs';
import { resolve, dirname } from 'node:path';
import { fileURLToPath } from 'node:url';
import { redis } from '../server/cache/redis.js';

const __dirname = dirname(fileURLToPath(import.meta.url));
const PHASE_DIR = resolve(
  __dirname,
  '../.planning/phases/27.4.4-v3-latency-remediation-and-cutover',
);

const KEYS = [
  'events:llm:v3',
  'events:llm:v3:partial',
  'events:llm-summary:v3',
  'events:llm-dlq',
  'events:llm-pipeline-audit',
  'events:llm-eval-baseline:v3',
] as const;

async function main(): Promise<void> {
  const labelArg = process.argv.find((a) => a.startsWith('--label='));
  if (!labelArg) {
    console.error('Usage: tsx scripts/snapshot-v3-redis.ts --label=<label>');
    process.exit(1);
  }
  const label = labelArg.split('=')[1]!;

  const snapshot: Record<string, unknown> = {};
  for (const key of KEYS) {
    try {
      // For DLQ (Redis Set), use smembers; for audit log (likely list), use lrange;
      // for everything else use get. Branch on key shape.
      if (key === 'events:llm-dlq') {
        snapshot[key] = await redis.smembers(key);
      } else if (key === 'events:llm-pipeline-audit') {
        snapshot[key] = await redis.lrange(key, 0, -1);
      } else {
        snapshot[key] = await redis.get<unknown>(key);
      }
    } catch (err) {
      snapshot[key] = { __error: String(err).slice(0, 200) };
    }
  }

  mkdirSync(PHASE_DIR, { recursive: true });
  const path = resolve(PHASE_DIR, `${label}.json`);
  const payload = {
    label,
    capturedAt: new Date().toISOString(),
    keys: KEYS,
    snapshot,
  };
  writeFileSync(path, JSON.stringify(payload, null, 2));
  console.log(`Snapshot written: ${path} (${JSON.stringify(payload).length} bytes)`);
}

main().catch((err) => {
  console.error('FATAL:', err);
  process.exit(1);
});
```

Pros: defense-in-depth even if operator forgets to swap DB. Cons: adds a code surface in lib files; introduces a second namespace operators have to remember.

#### Option C — Refuse-to-run guard

Add a startup check in the dry-run scripts (preflight, bake-off, snapshot) that verifies `process.env.UPSTASH_REDIS_REST_URL` does NOT contain a `prod`-tagged hostname OR is explicitly tagged `dev`. Refuse to run if the env doesn't match.

Pros: explicit failure. Cons: requires URL convention discipline (most Upstash URLs are randomly named).

### Recommendation

**Option A + Option C combined**:

1. PLAN Task 0 (D-20) starts with: "Operator confirms `.env.local` UPSTASH_REDIS_REST_URL is for dev DB, not prod" (operator approval gate).
2. Add a `--prod-confirm` flag requirement to `scripts/snapshot-v3-redis.ts` so accidental dev runs of the snapshot don't commit prod data into git.

### Confidence

HIGH on the risk diagnosis; MEDIUM on which mitigation is canonical for the project (no precedent in 27.4.x phase history for dev/prod Redis isolation).

### `lastNimCallTs` (D-21) classification

`lastNimCallTs` is operational — its purpose is "did we call NIM recently enough that the warm-state heuristic applies?" The semantic is:

- Cold start: `lastNimCallTs = 0` (initial value) → `Date.now() - 0` is always > 5min → pre-warm fires once on first batch loop. **This is the correct desired behavior** — cold start IS the case pre-warm targets.
- Warm start within active session: `lastNimCallTs` carries the timestamp of the last successful NIM call → pre-warm correctly skips when warm.
- Warm start across multi-hour idle: `lastNimCallTs` may be stale (e.g., 2h old); pre-warm correctly fires.

**No Redis backing required.** Adding a Redis mirror for `lastNimCallTs` would be over-engineering — cold start is exactly when pre-warm SHOULD fire, and the in-memory variable's behavior (init to 0 on cold start) makes it work without any persistence.

### Implementation guidance

- Initialize `let lastNimCallTs = 0;` at module-top in `freeClaudeRouter.ts` (matches the pattern used by `nvidiaNimWindow` at line 123).
- Update `lastNimCallTs = Date.now()` in `callLLM()` success branch at `:360-361` (right after `record(p.name as Provider, 'ok');`).
- `prewarmIfCold()` reads `lastNimCallTs` and decides; updates it on success.

### Confidence

HIGH — pattern explicitly documented in the codebase (`llmProgress.ts:6-7`); precedent established by 5+ existing module-level singletons.

## 11. Anti-Patterns from 27.4.3 Plan 05 Gate B FAIL

The planner MUST NOT repeat these. Derived from `.planning/phases/27.4.3-free-claude-code-routing/27.4.3-05-CUTOVER.md` lines 108-202 and `27.4.3-05-SUMMARY.md` lines 36-67.

### A1 — Trusting bake-off small-sample latency for production decisions

**What happened:** 10-event Plan 03 bake-off showed qwen p50 17.8s with 0 timeouts. Production at 196 batches showed p99 929s with 11 timeouts. The long-tail was invisible at small sample.

**Don't repeat:** Always require D-02's 50-event LLM-in-loop sample BEFORE locking a winner. The dual-floor at D-03 (within20km≥0.890 AND p95≤30s) is calibrated against this.

### A2 — Single Gate B run as cutover signal

**What happened:** Plan 05 had a single Gate B production smoke run. When it failed, there was no second-data-point to distinguish "model-specific long-tail surprise" from "transient infrastructure flake."

**Don't repeat:** D-10 mandates 2 consecutive passes. D-11 mandates strict failure semantics.

### A3 — Skipping pre-flight characterization

**What happened:** No D-05 equivalent existed in 27.4.3. Plan 05 ran the full Gate B production smoke against an uncharacterized model and discovered the failure mode in production. Per Plan 05's diagnosis: "11 batches blew through the 90s watchdog hard-kill — multiple times."

**Don't repeat:** D-05 preflight runs 20 batches in instrumented mode FIRST, exposes the long-tail signature BEFORE the full Gate B commits 218 minutes.

### A4 — No data-driven max_tokens cap

**What happened:** v3 had no per-model `max_tokens` configuration. Reasoning models (qwen) burned token budget on `<think>` blocks that exploded under production prompt complexity.

**Don't repeat:** D-06 enforces a per-model `MAX_TOKENS_PER_MODEL` from D-05 preflight measurements. Keeps worst-case latency bounded.

### A5 — Promoting OpenRouter to prod without quota analysis

**Why this matters even though OpenRouter wasn't promoted in 27.4.3:** D-12 explicitly defers OpenRouter prod promotion. The next phase MUST do quota analysis first; OpenRouter free tier is ~100-200 req/day per model and at production cadence (96 refreshes/day × 196 batches × cascade-on-NIM-fail) can exhaust in hours. **27.4.4 sticks to dev-only OpenRouter activation.**

### A6 — Rate-limit window contamination across bake-off candidates

**What happened (recovered):** First-pass `bakeoff-v3.ts` (DELETED, replaced by `bakeoff-v3-direct.ts`) ran candidates through `freeClaudeRouter.callLLM` — the per-Provider circuit breaker tripped on glm4.7's primary attempts and remained tripped, causing meta/llama-3.3-70b-instruct to receive 10/10 `nvidia_nim:skipped:breaker` decisions. **The breaker is correct production behavior; only the bake-off harness needed the bypass.** [CITED: 27.4.3-03-BAKEOFF.md "Anomalies / Notes" §1]

**Don't repeat:** `scripts/bakeoff-v3-direct.ts` is canonical. Don't re-introduce a freeClaudeRouter-based bake-off harness for cross-model comparison.

### A7 — Synthetic skip entries with wrong type contract

**What happened (recovered):** Watchdog soft-warn entries needed an exact field-set on `callHistory` to satisfy TS strict mode. Initial implementation drifted from the type contract.

**Don't repeat:** When extending `callHistory`/`routingTrace` with new entry types, mirror the EXACT field set documented at `llmProgress.ts:77-98`. **Why D-19 mandates start+end:** Without a start-of-run snapshot, post-mortem replay can't reconstruct what state the run BEGAN in vs ENDED in. If a v2 cache item polluted the v3 cache mid-run via the Pitfall 1 bridge, end-only snapshot can't tell. Start+end gives the diff.

**What works (preserve):** The Pitfall 1 graceful fallback at `events.ts:861-879` (v3→v2→v1→raw GDELT chain). This is what kept the user-facing map non-blank during Plan 05's Gate B failure. Phase 27.4.4 must NOT modify this code path; cutover relies on it as the safety net during the auto-rollback window.

### Pattern 1: Adaptive batch split-on-timeout (D-04)

```typescript
// server/lib/llmEventExtractor.v3.ts — D-04 adaptive helper
async function splitBatchOnTimeout(
  batch: EventGroup[],
  contextProducer: (g: EventGroup) => Promise<PromptContext>,
  routingCapture: (r: RoutingDecision[]) => void,
  batchIndex: number,
): Promise<EnrichedEventV3[]> {
  if (batch.length <= 1) {
    // Cannot split a single-group batch; DLQ-route it
    if (batch[0]) {
      await enqueueDLQ({
        id: batch[0].key,
        reason: 'v3:adaptive-retry-fail',
        lastError: 'batch already at minimum size; retry exhausted',
        timestamp: Date.now(),
      });
    }
    return [];
  }
  const half = Math.floor(batch.length / 2);
  const leftHalf = batch.slice(0, half);
  const rightHalf = batch.slice(half);

  const results: EnrichedEventV3[] = [];
  for (const sub of [leftHalf, rightHalf]) {
    const subContexts = await Promise.all(sub.map(contextProducer));
    const subPrompt = buildBatchUserPromptV3(subContexts);
    let subRouting: RoutingDecision[] = [];
    const subResult = await withBatchWatchdog(
      async () => {
        const r = await freeClaudeCallLLM(
          [
            { role: 'system', content: SYSTEM_PROMPT_V3 },
            { role: 'user', content: subPrompt },
          ],
          JSON.stringify(EVENT_EXTRACTION_SCHEMA_V3),
          { batchSize: sub.length },
        );
        subRouting = r.routing;
        return r.content;
      },
      {
        timeoutMs: env.LLM_BATCH_TIMEOUT_MS,
        softWarnMs: 60_000,
        batchIndex,
        label: 'v3-split',
        onTimeout: async () => {
          for (const g of sub) {
            await enqueueDLQ({
              id: g.key,
              reason: 'v3:adaptive-retry-fail',
              lastError: `split-half timed out after ${env.LLM_BATCH_TIMEOUT_MS}ms`,
              timestamp: Date.now(),
            });
          }
          // Stats counter increments
          const stats = llmProgress.adaptiveBatchStats ?? {
            splitCount: 0,
            retrySuccess: 0,
            retryFail: 0,
            dlqEnqueueCount: 0,
          };
          stats.retryFail += sub.length;
          stats.dlqEnqueueCount += sub.length;
          updateProgress({ adaptiveBatchStats: stats });
        },
      },
    );
    routingCapture(subRouting);
    if (!subResult) continue;
    try {
      const parsed = batchResponseV3.safeParse(JSON.parse(subResult));
      if (parsed.success) {
        results.push(...parsed.data.events);
        const stats = llmProgress.adaptiveBatchStats ?? {
          splitCount: 0,
          retrySuccess: 0,
          retryFail: 0,
          dlqEnqueueCount: 0,
        };
        stats.retrySuccess += parsed.data.events.length;
        updateProgress({ adaptiveBatchStats: stats });
      }
    } catch {
      // schema fail on split — counted via existing schemaFailures path
    }
  }
  return results;
}
```

```typescript
// server/lib/llmLineage.ts — D-18 group hash helper
import crypto from 'node:crypto';
import type { EventGroup } from './eventGrouping.js';

const GROUP_LINEAGE_KEY_PREFIX = 'events:llm:v3:lineage:';
const GROUP_LINEAGE_TTL_SEC = 7 * 24 * 3600;

export function computeGroupLineageHash(group: EventGroup): string {
  // Deterministic input: groupKey + sorted source URLs + total mention count.
  // Sort URLs to make hash insensitive to ordering noise from upstream.
  const sortedUrls = [...group.sourceUrls].sort().join('|');
  return crypto
    .createHash('sha256')
    .update(group.key)
    .update('|')
    .update(sortedUrls)
    .update('|')
    .update(String(group.totalMentions))
    .digest('hex');
}
```

## 16. Common Pitfalls

### Pitfall 1: Module-state assumption mismatch on Vercel

**What goes wrong:** Adding new module-level state without considering the cold-start reset can cause "first request after deploy is slow" or "stats counters look wrong."

**Why it happens:** Vercel Fluid Compute warm starts share module state, but cold starts (after idle, deploy, or scale-out) reset it. New developers forget this.

**How to avoid:** For state that must survive cold start: write through to Redis with `cacheSetSafe`. For state that's operational: leave it in-memory and design the semantics so cold-start reset is the desired behavior. D-21 pre-warm is the latter (cold-start = pre-warm fires = correct).

**Warning signs:** Test passing locally (state persists) but failing in prod (cold start resets).

### Pitfall 2: Bake-off harness contamination via shared circuit breaker

**What goes wrong:** Running multiple candidates through `freeClaudeRouter.callLLM` causes one model's failures to trip the breaker for the entire `nvidia_nim` provider, skipping all subsequent candidates.

**Why it happens:** Per-Provider breaker is by design correct for production; only the bake-off harness needs the bypass.

**How to avoid:** Use `scripts/bakeoff-v3-direct.ts` which calls NIM directly via OpenAI SDK (`bakeoff-v3-direct.ts:145-149`). DO NOT re-introduce a freeClaudeRouter-based bake-off harness.

**Warning signs:** Bake-off rows show `nvidia_nim:skipped:breaker` for late candidates after early failures.

### Pitfall 3: Two-key cache discipline drift

**What goes wrong:** Writing the partial-cache `LLMCachePayload` envelope to the terminal `events:llm:v3` key crashes every consumer with `events.map is not a function`.

**Why it happens:** Terminal key holds `ConflictEventEntity[]`; partial key holds `LLMCachePayload`. They're different shapes.

**How to avoid:** Reference CLAUDE.md's "Two-key discipline" pattern. Per `events.ts:847-852` `coerceCachedEvents` provides defense-in-depth, but the writer must respect the contract. New writes in this phase (D-04 adaptive split, D-18 pre-filter) MUST go to `events:llm:v3:partial` (observability) NOT `events:llm:v3` (terminal).

**Warning signs:** `/api/events` returns 500; logs show `TypeError: events.map is not a function`.

### Pitfall 4: A9 frontend↔server interface mirror miss

**What goes wrong:** Adding `prewarmCount` to server `LLMRunSummary` but not to client `useLLMStatusPolling.ts` mirror in the same commit causes "field-missing" defensive defaults to mask the real value during a deploy window.

**Why it happens:** Engineer commits server side, intends to "follow up with client commit later."

**How to avoid:** Use UI-SPEC's "Field-missing defensive defaults" pattern (`UI-SPEC.md:282-297`). But ALSO: same atomic commit. The cell renders `count=0` instead of crashing, but the operator sees no data — that's a regression.

**Warning signs:** Pre-warm cell shows `count=0` and `last=—` even after pre-warm has fired.

### Pitfall 5: Bake-off skipping resolver-only baseline persistence

**What goes wrong:** Multi-model bake-off runs the LLM-in-loop sample but doesn't persist the per-candidate resolver-only baseline at `events:llm-eval-baseline:v3:<sanitized-model>`.

**Why it happens:** `runEval({model})` is a separate invocation from the LLM-in-loop sample.

**How to avoid:** `bakeoff-v3-direct.ts:302-311` already does this — preserve the call when extending to `--limit=50`. Per-model baseline keys are 90d-TTL artifacts the planner references in BAKEOFF.md.

### Pitfall 6: Snapshot script overwriting prod cache

**What goes wrong:** Snapshot script accidentally calls `cacheSet` instead of `redis.get`, polluting prod state.

**Why it happens:** Copy-paste from a write-side example.

**How to avoid:** Read-only by construction. Use `redis.get<unknown>(key)` directly; never import `cacheSet` or `cacheSetSafe`. The `--prod-confirm` flag (Section 6 mitigation) is belt-and-suspenders.

### Pitfall 7: NIM model catalog drift mid-phase

**What goes wrong:** Bake-off relies on a model id that returns 404 between Plan 03 and 27.4.4 (e.g., NVIDIA deprecates `nvidia/llama-3.1-nemotron-ultra-253b-v1` between phases).

**Why it happens:** NVIDIA's catalog is dynamic; listed models can lose serving capacity.

**How to avoid:** Add `--validate-only` flag to `bakeoff-v3-direct.ts` for a 1-token-per-model availability check before the full bake-off run. If a model returns 404, defer (don't burn budget retrying).

### Pitfall 8: Tier 2 prompt-tuning rabbit hole

**What goes wrong:** Operator spends 2-3 hours iterating on prompts for nemotron + glm4.7 trying to unlock them; meanwhile the locked llama-3.3-70b winner is ready to ship.

**Why it happens:** Each iteration looks promising; the natural urge is "one more try."

**How to avoid:** D-07 wall-clock budget = 30 minutes TOTAL across both candidates. Operator logs start + end timestamps in BAKEOFF.md. When the timer fires, defer remaining candidates to next phase.
