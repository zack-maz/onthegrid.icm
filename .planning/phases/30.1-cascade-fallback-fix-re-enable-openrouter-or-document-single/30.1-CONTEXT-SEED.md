# Phase 30.1 — Context Seed (cascade fallback fix)

> Seed material for `/gsd-discuss-phase 30.1`. NOT a locked CONTEXT.md.
> Captures the bug Phase 30 surfaced but didn't fix. Run discuss-phase to convert this into locked decisions.

## What we discovered

The "cascade" advertised in `docs/architecture/llm-pipeline-reliability.md`
(NIM → OpenRouter) **does not exist in code**. The v3 extractor hardcodes
`skipOpenRouter: true` in both call sites:

- `server/lib/llmEventExtractor.v3.ts:622` (main batch path)
- `server/lib/llmEventExtractor.v3.ts:929` (split-half retry path)

Effect: OpenRouter is removed from `freeClaudeRouter.callLLM`'s provider
loop entirely. The "cascade" is a single-provider NIM-only pipeline.

## Evidence (2026-05-17 04:00 UTC cron)

After Phase 30 closed, the regular daily cron at 04:00 UTC fired and
demonstrated the failure mode Phase 30's operator-attended runs had
missed. Read from prod Redis `dev: events:llm-summary:v3`:

```json
{
  "errorTaxonomy": {
    "nvidia_nim": { "rate_limit": 39, "timeout": 0, ... },
    "openrouter": { "rate_limit": 0, "timeout": 0, ... }
  },
  "rateLimit": {
    "nvidia_nim": { "used": 45, "cap": 40, "window": "minute" },
    "openrouter": { "used": 0, "cap": 200, "window": "day" }
  },
  "routingTrace": [
    { "batch": 30, "provider": "nvidia_nim", "reason": "primary" },
    { "batch": 168..212, "provider": "nvidia_nim", "reason": "skipped:breaker" },
    ...
  ]
}
```

Interpretation: NIM hit its 40-RPM ceiling (45 used > 40 cap). Circuit
breaker opened. Batches 168-212 were "skipped:breaker" — dropped with
**zero attempts on OpenRouter**. OpenRouter's per-day budget was
completely untouched (0/200 used).

## Why skipOpenRouter exists (historical context)

From the comment at `freeClaudeRouter.ts:341-346` (Phase 27.4.4 Plan 02):

> "Free-tier OR rate-limits ~every call (~16 attempts × 16 rate_limit
> errors observed in dev), and a 100%-failing fallback is worse than no
> fallback: it amplifies the breaker error rate and burns the per-call
> retry budget on a guaranteed loser. v2 keeps OR enabled so the legacy
> rollback path is unchanged."

Two pieces of this reasoning are now stale:

1. **"v2 keeps OR for legacy rollback parity"** — v1/v2 pipelines were
   retired Phase 29 D-02. There is no v2 rollback path. The
   `skipOpenRouter` flag served the parallel-pipeline era; it has no
   counterpart caller anymore.

2. **"16/16 rate_limit observed in dev"** — that observation is from
   the Phase 27.4.4 dev run (~Mar 2026). It pre-dates Phase 29's
   cascade narrowing and may pre-date OpenRouter free-tier policy
   changes. **Untested in Phase 29's NIM+OR-only world.**

## Implications for Phase 30's already-shipped work

- **Plan 30-05's tuning** (BACKOFF [2000,8000,32000], RETRIES 3, JITTER 500)
  only affects within-NIM retry behavior. Once NIM's breaker opens, the
  new defaults are irrelevant — batches drop regardless.
- **Plans 30-02 and 30-06** (Run 1 + Run 2) both hit Path B with zero
  429s because they were operator-triggered during low-traffic windows.
  The 04:00 UTC daily cron hit the bad path. Path B observation in those
  runs is not representative of the production envelope.
- **Plan 30-07's architecture doc** describes a cascade that doesn't
  exist. Either the cascade needs to actually exist (remove skipOpenRouter)
  or the doc + ADR-0010 sub-block need to honestly state "NIM-only
  active; OpenRouter is dormant pending free-tier re-evaluation."
- **ADR-0010's "raw GDELT terminal fallback"** still holds at the
  service-degradation level (when LLM cache goes stale, /api/events
  serves raw GDELT). But the LLM cache going stale silently is a
  worse failure mode than openly degrading — the operator dashboard
  doesn't surface "NIM breaker tripped 50 batches dropped" in any
  prominent way.

## Open questions for `/gsd-discuss-phase 30.1`

1. **Re-test OpenRouter free-tier rate limits.** Has OpenRouter improved
   since Phase 27.4.4? Run an experiment: temp endpoint that fires N
   single-event OpenRouter calls and counts rate_limit responses. If
   <50% fail, OpenRouter is viable as fallback. If still >90% fail,
   it's not worth the latency.

2. **What's the right behavior when NIM breaker trips?**
   a. Try OpenRouter (if viable from #1)
   b. Drop the batch and let raw GDELT serve (current behavior)
   c. Pause new extractions for the rest of the cron window and resume
   next day (similar to SoftCap pause, more aggressive)
   d. Switch to a different model on NIM (cheaper / lower-cap-friendly)

3. **Should the dashboard surface "cascade degraded"?** Right now the
   API Health endpoint shows `llmEvents: healthy` even when 50/213
   batches were dropped (because the events written before the breaker
   tripped count as "healthy enough"). The freshness threshold + lastRun
   timestamp pattern hides catastrophic mid-run failures.

4. **Cost decision:** Paid OpenRouter (e.g. ~$0.10/1M tokens for Llama
   3.3 70B). The 04:00 cron processed 426 events. If each event costs
   ~$0.0001 via paid OR, full coverage = $0.04/day = $1.20/mo. Worth
   it as a backstop?

5. **What about NIM's rate-limit window itself?** Phase 30's tuning
   raised RETRY_ATTEMPTS 2→3 but didn't change the rolling-window
   limiter (`nvidiaNimWindow`). That limiter is what allowed `used: 45`
   to exceed `cap: 40` — meaning the limiter is letting batches through
   faster than NIM can absorb. Tighten the limiter? Make it adaptive
   based on retry-after headers?

## Suggested phase scope (operator's call in /gsd-discuss-phase 30.1)

**Minimum viable fix (small):**

- Document the single-provider reality in
  `docs/architecture/llm-pipeline-reliability.md` + ADR-0010 sub-block
  amendment.
- Add a Phase-31 carry-forward note: "Validate OpenRouter free-tier
  before re-enabling fallback."
- No code change. One commit.

**Right fix (medium):**

- Re-test OpenRouter free-tier with a temp test harness (no prod
  changes).
- If viable: remove `skipOpenRouter: true` from both v3.ts call sites.
  Redeploy. Observe next cron cycle.
- If not viable: document why, plan paid OR or rate-limit tightening
  as Phase 31 / Phase 32 work.
- 2-3 commits.

**Full fix (large):**

- Above + add dashboard surface for cascade-degraded state (operator
  sees "NIM breaker tripped, N batches dropped" prominently).
- Plus a watchdog-style alert when DLQ count > baseline for 24h.
- 5-8 commits. May warrant its own phase number rather than 30.1.
