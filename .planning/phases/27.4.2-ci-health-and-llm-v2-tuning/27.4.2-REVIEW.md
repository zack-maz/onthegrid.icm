## Warnings

### WR-01: `makeDefaults()` fixture in filters.test.ts is not type-checked and will silently drift

**File:** `src/__tests__/filters.test.ts:10-111`
**Issue:** The `makeDefaults(): FilterState` factory returns an object literal that omits required fields from the `FilterState` type defined in `src/stores/filterStore.ts:90-174`. Currently missing (verified by inspection):

- State fields: `showSites`, `enabledWaterTypes`, `showWater`, `waterNameFilter`, `showHighStress`, `showMediumStress`, `showLowStress`, `stressMin`, `stressMax`, `showHealthyWater`, `showAttackedWater`, `entityIdFilter`
- Actions: `togglePrecision`, `setEntityIdFilter`, `setEnabledWaterTypes`, `toggleWaterType`, `toggleShowWater`, `setWaterNameFilter`, `toggleShowHighStress`, `toggleShowMediumStress`, `toggleShowLowStress`, `setStressRange`, `toggleShowHealthyWater`, `toggleShowAttackedWater`, `toggleShowSites`

This is not flagged by `npm run typecheck` because `tsconfig.app.json` excludes `src/__tests__/`. Phase 27.4.2 P1 added `enabledPrecisions` precisely because of this drift hazard — but this same kind of D-03 surprise will recur for every new `FilterState` field until the fixture is type-checked.

The phase commit message frames the P1 fix as targeted; this finding flags that the structural cause (test files excluded from typecheck) is unresolved, not introduced by this phase.

**Fix:**

1. Either include `src/__tests__/` in a typechecked tsconfig project (`tsconfig.app.json` `exclude` removal, or a new `tsconfig.test.json` that extends app and adds tests to `include`), OR
2. Replace the hand-rolled fixture with `useFilterStore.getState()` after a `useFilterStore.setState(DEFAULTS)` call so the test consumes the real Zustand store and inherits any new fields automatically.

Option 2 is the cleaner long-term fix — `entityPassesFilters` only reads state, so the action stubs in `makeDefaults()` exist purely to satisfy the type. Drawing defaults from the store eliminates the entire stub block.

## Info

### IN-01: `getProviderOrder()` reads-and-returns mutable module state without test coverage

**File:** `server/adapters/llm-provider.ts:188-197`
**Issue:** The new `setProviderOrderOverride()` / `getProviderOrder()` pair is a wave-scoped mutable singleton (intentional per the comment at lines 180-187). The export contract is fine, but there is no unit test verifying that:

1. `setProviderOrderOverride(['groq', 'cerebras'])` actually flips the iteration order in `callLLM`
2. `setProviderOrderOverride(null)` restores the default
3. The override survives between calls within the same Node process

If a future refactor accidentally moves `_providerOrderOverride` into a function scope or replaces it with a useState-style getter, no test will catch it. Given the operator-runbook usage pattern (manual D-07 hang-recurrence flip), a silent break could cost incident-response time.

**Fix:** Add a short test in `server/__tests__/adapters/llm-provider.test.ts` that mocks `OpenAI` minimally and asserts the `providers` array iteration in `callLLM` follows the override when set.

### IN-02: `setProviderOrderOverride` accepts arbitrary `Provider[]` arrays — empty array silently disables LLM

**File:** `server/adapters/llm-provider.ts:190-192`
**Issue:** `setProviderOrderOverride([])` passes the type check but causes `callLLM` to immediately log `"both LLM providers unavailable — falling back to raw GDELT"` and return `null` without trying any provider. There is no validation that the override contains at least one element.

This is a low-impact footgun (an operator typo could disable LLM cluster-wide), but the function is explicitly designed for emergency runbook use, so a guardrail is warranted.

**Fix:**

```typescript
export function setProviderOrderOverride(order: readonly Provider[] | null): void {
  if (order !== null && order.length === 0) {
    throw new Error('setProviderOrderOverride: empty array would disable LLM; pass null to clear');
  }
  _providerOrderOverride = order;
}
```

### IN-03: `eval-replay.ts` swallows non-numeric `score.total` without typing

**File:** `scripts/eval-replay.ts:21`
**Issue:** `const ratio = score.total > 0 ? (score.within20km / score.total).toFixed(3) : 'n/a';` — `runEval()` returns an object whose shape is implicit at the call site. If `runEval` returns `{ total: 0 }` due to a fixture-load failure, the script prints `"within20km/total = n/a"` and exits 0, masking what looks like a successful run. The script's exit code is the only signal CI/wave runbook would consume.

**Fix:** Either log a warning + `process.exit(2)` when `total === 0`, or import `LLMEvalScore` from the harness and assert at the top of `main()`.

### IN-04: `cacheKey()` builds keys from a record with `undefined`-filtered values but no length validation

**File:** `server/lib/llmResolver.ts:49-59`
**Issue:** `cacheKey('poi', { country: undefined, landmark: undefined })` produces `geocode:fwd:constrained:poi:` — an empty-suffix key that would collide for every "no country, no landmark" call. With Plan 07 changes, `resolveViaPoiAmenity()` is gated by `if (!hierarchy.landmark) return null;` at line 206 so `landmark` is always defined when this branch executes — no current bug. However, a future caller adding a 7th branch could trip this.

This is purely defensive; not an active bug.

**Fix (optional):** Add `if (!ordered) throw new Error('cacheKey: no parts');` after the join, OR require at least one mandatory key in the function signature.
