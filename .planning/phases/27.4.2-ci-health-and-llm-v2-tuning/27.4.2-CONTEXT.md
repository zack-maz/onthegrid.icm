## Implementation Decisions

### Phase bundling and gating

- **D-01** Single bundled phase, single branch
  `feature/27.4.2-ci-health-and-llm-v2-tuning`. Plan waves run sequentially: CI
  health first, then LLM tuning. One STATE.md entry, one merge.
  - **Why:** Roadmap already reflects the bundle; the goal explicitly chains the
    two ("greening CI is the prerequisite so regression-watch during LLM tuning
    is trustworthy"). Splitting would add bookkeeping with no benefit.
  - **How to apply:** Branch from main after 27.4.1 lands; CI plans land before
    any tuning plan begins; do not interleave waves.

- **D-02** Strict CI gate before tuning. **No tuning commits land until `main` CI
  is fully green** — all filter tests pass, `npm audit` reports zero high-severity
  advisories, prettier reports clean, lint reports zero warnings.
  - **Why:** Tuning iterations measure regressions via the test suite. A
    half-broken suite produces false signals — we'd ship bad tunings or revert
    good ones.
  - **How to apply:** Last CI plan in the wave must explicitly verify all four
    gates (`npm test`, `npm audit`, `npm run format -- --check`,
    `npm run lint`) before the tuning wave is greenlit.

### CI remediation

- **D-03** Filter-test repair via fixture-factory extension. The actual count is
  not "32 distinct failures" — it's **544 failures from one root cause**:
  `filters.enabledPrecisions` (a 4-element array added in Phase 27) is missing
  from the test fixture builders, so every combined-filter assertion crashes at
  `filters.enabledPrecisions.length < 4`. Extend the fixture factory / defaults
  helper to include `enabledPrecisions` (default to all-4-precisions-enabled, the
  shipped runtime default). Single change should green all cascading cases.
  - **Why:** Smallest-diff fix; matches shipped runtime behavior; preserves the
    production contract that `enabledPrecisions` is non-nullable.
  - **How to apply:** Find the central fixture factory (likely in
    `src/__tests__/` test helpers or inline `defaultFilters` constant); add
    `enabledPrecisions: ['exact', 'neighborhood', 'city', 'region']` to the
    default. Do **not** make `filters.enabledPrecisions` optional in
    `src/lib/filters.ts` — that softens the production contract and risks
    silently disabling precision filtering at any missed call site.

- **D-04** `npm audit fix` without `--force`. Apply minor/patch bumps for all
  fixable advisories. Verify `npm test` and `npm run build` still pass post-bump.
  Accept any residual moderate-severity advisories that would require `--force`
  (major version jumps); document them in plan summary so a future phase can
  evaluate the breaking-change cost.
  - **Why:** Free of major-version risk; the three high-severity packages
    (flatted, path-to-regexp, picomatch) all have non-force fixes available per
    `npm audit` output.
  - **How to apply:** Single commit with `npm audit fix` output diff; do **not**
    chain it to other CI fixes so the dependency-bump diff is reviewable in
    isolation.

- **D-05** Format + lint mass-sweep with pre-commit guard. Single commit running
  `npm run format` (prettier write on all drift) followed by `npm run lint -- --fix`
  for auto-fixable warnings; manual fix for residual lint warnings in the same
  commit. Then add format+lint to `.husky/pre-commit` and/or `.lintstagedrc` so
  re-introduced drift fails the commit, not the CI run after.
  - **Why:** Mass sweep keeps the cosmetic-change diff isolated from behavioral
    work, easy to review. Pre-commit guard is what stops this debt from
    recurring next phase.
  - **How to apply:** Two commits — one for the mass sweep, one for the
    pre-commit hook update. CI gate verifies the hook actually runs by checking
    the husky version and presence of the format+lint command in the hook
    script.

### Hang-recurrence policy (operational ladder for tuning runs)

- **D-06** Hang-recurrence trigger: **`watchdogTimeoutCount ≥ 3` in a single
  pipeline run**. Tolerates isolated transient hangs (Cerebras under load
  occasionally hits the 90s gate even on healthy runs — ~1.6% rate is the
  noise floor at 184 batches) but flags sustained recurrence.
  - **Why:** Zero-tolerance is too brittle (one flaky batch aborts an otherwise
    good run); ratio-based 5% lets a degrading provider state leak through.
    Threshold of 3 is a sweet spot for the existing 184-batch run shape.
  - **How to apply:** Read `llmProgress.watchdogTimeoutCount` after every full
    run completes; if `≥ 3`, trigger the response in D-07 for the **next** run.
    Document the threshold in the tuning runbook.

- **D-07** Trigger response: **auto-flip Cerebras out of primary**. Set
  provider order to `[groq, cerebras]` for subsequent tuning runs (via env var
  override or in-memory setter on `llm-provider.ts`). Run continues — does not
  abort. Flip persists for the remainder of the tuning wave; restored to
  `[cerebras, groq]` at phase close.
  - **Why:** Cerebras hangs are the dominant failure mode (per 27.4.1 root
    cause). Groq has lower TPD (200K vs 1M) but is more responsive. Continuing
    with degraded throughput preserves the tuning iteration's data; aborting
    loses everything.
  - **How to apply:** Add a single in-memory toggle (no Redis persistence
    needed — wave-scoped, ops-managed). Document the flip in the tuning
    runbook with a one-line rollback (`unset LLM_PROVIDER_PRIMARY` or restart).

- **D-08** Pre-tuning baseline must complete with **`watchdogTimeoutCount = 0`**.
  If the first baseline-capture run trips the watchdog at all, retry until a
  clean run lands. Do **not** persist a noisy baseline to
  `events:llm-eval-baseline:v2`.
  - **Why:** Eval baseline is the comparator for "+5pp" judgments — it must be
    clean, otherwise tuning iterations are measured against drift, not signal.
  - **How to apply:** First plan in the tuning wave is "capture baseline"; it
    blocks downstream tuning plans until the baseline run is timeout-free. The
    runEval() harness is resolver-only (per A6/Pitfall 8) so it doesn't hit
    Cerebras at all — D-08 only applies to the full-production run that
    captures provenance counts and full-pipeline timing, not to the
    ground-truth replay.

### LLM v2 quality tuning

- **D-09** Success metric: **track all three distance gates (5km / 20km /
  100km), gate success on 20km.** "Beat v1 by ≥5pp" is measured at the 20km
  gate; the 5km and 100km counts are recorded for regression watch (a tuning
  that lifts 100km but drops 5km should be reverted unless the reasoning is
  documented).
  - **Why:** 20km matches the existing 27.4 D-25 deploy gate (within20km/total
    ≥ 0.8) — same threshold the production-flip already uses. Tracking all
    three preserves precision visibility.
  - **How to apply:** Confirm `runEval()` already reports
    `{within5km, within20km, within100km, total}` in `evalScore` (it does, per
    PIPELINE-ANALYSIS §9). Plan summaries record per-distance deltas after
    every iteration.

- **D-10** Split measurement: **eval score from ground-truth replay; fallback%
  from full production run.** runEval() is resolver-only, fast, deterministic,
  cheap (~1min Nominatim spaced 1/sec) — perfect for the inner tuning loop.
  But `provenanceCounts` only reflects real GDELT data, so
  `gdelt-actiongeo-fallback < 25%` requires a real 184-batch run, expensive
  but unavoidable.
  - **Why:** Ground-truth is curated (high-quality hierarchies) — it would
    skew provenance toward Branch 1–3 and mask real-world fallback rates.
    Full-production runs at 1–2 per tuning wave keep token spend manageable.
  - **How to apply:** Each tuning plan runs ground-truth replay before commit
    (eval-score gate). Wave-boundary plans run a full /api/events?force
    production trigger and measure provenance.

- **D-11** Lever priority order (all four selected, not all guaranteed to
  ship):
  1. **POI keyword expansion + amenity-mapping audit** — Branch 2
     (poi-amenity-nominatim) is the highest-leverage path for fallback
     reduction. Spot-check 10 POI inferences against Nominatim per §12 Q5;
     add missing keywords (drone base, airfield, refinery substation, etc.)
     and audit `POI_AMENITY_MAP` entries.
  2. **2-pass verify thresholds** — Branch 4 reranker triggers. Lower the
     250km gate to 150km to force more reranking on coarse hits; revisit
     WR-04 single-candidate auto-accept (§12 Q2 hypothesis: it may be
     accepting POI false positives like "Beirut, Oregon" for Beirut, Lebanon
     queries).
  3. **System prompt tightening** — rewrite `SYSTEM_PROMPT_V2` lines 84–114.
     Tighten landmark vs neighborhood guidance, add "do not invent landmarks"
     negative examples, sharpen the confidence rubric.
  4. **NEWS / TEMPORAL / BELLINGCAT block tuning** — §12 Q1, Q3, Q4
     hypotheses (window sizes, article counts, coord precision). Lowest
     leverage on resolver fallback; saved for last.
  - **Why:** Levers 1 and 2 directly target `gdelt-actiongeo-fallback`
    reduction (the harder of the two success criteria). Lever 3 affects
    extraction quality which propagates downstream. Lever 4 is fine-tuning
    that may already not be needed.
  - **How to apply:** One plan per lever category. Plan order = lever order.
    Stop early per D-13 if criteria met.

- **D-12** Tuning cadence: **micro-iteration**. Each lever change runs
  ground-truth replay (~1min) before commit; if eval score doesn't regress
  (per D-14), commit and move to the next sub-lever within that category.
  Full production runs only at wave-boundary checkpoints (after each lever
  category completes, ~3 production runs total budgeted).
  - **Why:** Maximum signal per iteration; trivial to bisect a regression.
    Batched/big-bang cadence loses attribution when accuracy moves.
  - **How to apply:** Each tuning sub-lever is its own atomic commit with the
    GT replay output captured in the commit message.

- **D-13** Tuning stop condition: **goal-driven**. As soon as eval score beats
  v1 by ≥5pp at 20km **AND** fallback drops below 25% on a full production
  run, the tuning wave is **done** — even if levers 3 and 4 are untouched.
  Untouched levers are captured as backlog todos via `/gsd-add-todo` for a
  future tuning phase.
  - **Why:** "Exhaust all 10 hypotheses" would inflate scope; the phase has a
    falsifiable success bar — stop when met.
  - **How to apply:** After every wave-boundary production run, check both
    criteria. If met, write a wave-summary, capture remaining levers as
    backlog, and proceed to phase close.

- **D-14** Per-lever revert policy: **GT-replay regression → revert that
  lever, document, move on.** A lever ships only if 20km eval doesn't
  regress. Allow neutral or improvement at 20km even if 5km moves slightly
  (track but don't gate on it). Do **not** require Pareto improvement across
  all three distances — too restrictive; many viable tunings would be
  rejected.
  - **Why:** Gate on the success metric (20km) so revert decisions are
    consistent with success criteria. Document negative results so future
    phases don't re-tread.
  - **How to apply:** Each plan summary records the GT replay before/after
    output for the lever. Reverts use atomic git revert; commit message
    cites the regression numbers and the §12 hypothesis being closed-out.

### Process

- **D-15** Commit cadence: one atomic commit per sub-lever (existing project
  convention). CI wave: one commit per category (fixture fix, audit fix,
  format sweep, lint sweep, hook update).
- **D-16** No new dependencies. All tuning is prompt + threshold + keyword
  level. Schema changes (Zod, JSON Schema) are out of scope per D-23 from
  27.4.
- **D-17** Test coverage: CI fixture fix is verified by the existing
  `filters.test.ts` going from 544 failures to 0. Tuning lever changes do
  **not** add new tests — the GT replay harness IS the test. POI keyword
  expansion may add a fixture in `llmResolver.test.ts` if a specific
  hypothesis warrants permanent regression coverage (planner's call).

- **Test fixtures via factory functions:** `src/__tests__/` patterns use

  survives warm starts but resets on cold. Hang-recurrence trigger (D-06) is
  per-run (`watchdogTimeoutCount`), not cross-run, so cold-start doesn't
  affect the policy.

## Specific Ideas

### Hang-recurrence runbook (illustrative shape)

```
# .planning/phases/27.4.2-.../tuning-runbook.md (write during first tuning plan)

## Pre-flight (before each tuning iteration)
- [ ] CI green on main (last check: <commit>)
- [ ] Cerebras + Groq token budgets <80% (check /api/events/llm-status)
- [ ] DLQ count baseline noted: <N>

## Per-iteration (per sub-lever)
1. Edit lever (one file, one constant or one block)
2. Run ground-truth replay: `npm run eval:replay` (or curl /api/events/llm-status?run=eval)
3. Capture before/after distance counts
4. If 20km regresses → revert, document, mark hypothesis in §12 closed-negative
5. If 20km ≥ baseline → commit with message:
   `feat(27.4.2): tune <lever> — eval 5km/20km/100km: A→B / C→D / E→F`

## Wave-boundary (after each lever category)
1. Trigger /api/events?force on the tuning branch
2. Wait for `llmProgress.stage === 'done'`
3. Check watchdogTimeoutCount === 0 → if not, retry per D-08
4. Check evalScore.within20km/total vs v1 baseline → ≥+5pp?
5. Check provenanceCounts.gdelt-actiongeo-fallback / total → <25%?
6. Both met → wave done; capture untouched levers as backlog; proceed to phase close

## Hang-recurrence response (D-07)
If watchdogTimeoutCount ≥ 3 in any run:
1. Set provider order to [groq, cerebras] for the rest of the wave
2. Note in plan summary: "Cerebras flipped out of primary at <commit> after <run-id>"
```
