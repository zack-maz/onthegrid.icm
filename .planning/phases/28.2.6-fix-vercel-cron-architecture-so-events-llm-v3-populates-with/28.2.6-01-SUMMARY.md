## Decisions Made

- **Cadence N=10 (D-03):** Per-batch (N=1) overloads Redis under concurrency=12; per-end-only (status quo) doesn't survive Vercel function boundary. N=10 caps Redis writes at ~21 per 197-batch run while ensuring incremental progress survives function termination.
- **Two-key discipline (D-04 / D-11):** terminal key continues to hold ConflictEventEntity[] (NEVER LLMCachePayload envelope). The terminalShape test enforces this; if it goes red, the producer is fixed — never the assertion.
- **Snapshot-the-array (Pitfall 3):** periodic flush slices `partialEvents.slice(lastFlushedEventCount)` from the partial-cache key (which the v3 extractor's writePartialCache writes after each batch). Avoids reconstructing slices from prioritizedGroups, which is wrong under concurrency=12 reordering.
- **runEval() stays put (Pitfall 8):** Periodic flush helper does NOT call runEval. Eval harness stays at its existing post-FINAL-geocode location. Daily LLM token budget protected.
- **Best-effort periodic flush:** any failure during a periodic flush is logged + swallowed. The final flush at end-of-pipeline still attempts the full-cache write. Single periodic-flush failures cannot abort the extraction loop.

## Deviations from Plan

### 1. [Rule 3 - Blocking simplification] Periodic flush passes empty matchedNewsByGroup / bellingcatByGroup Maps

- **Found during:** Task 4b (periodic-flush wiring)
- **Issue:** PATTERNS.md / PLAN Step 3 described widening the `processEventGroups` barrel signature to accept an optional `accumulators?: { matchedNews; bellingcat }` parameter, with the v3 extractor populating those Maps synchronously between batch completions. Implementing this would require:
  - widening the barrel signature in server/lib/llmEventExtractor.ts
  - widening processEventGroupsV3 (and v1/v2 for parity, even though they don't use the maps the same way)
  - adding new `accumulators.matchedNews.set(...)` calls inside the v3 extractor's per-batch finishBatch chain
  - threading the maps through the run-result Maps already exposed at run completion
- **Fix:** Take the simpler path. Periodic-flush geocode call passes EMPTY Maps; the geocoder's 6-path resolver falls back to gdelt-actiongeo-fallback for groups missing context (per RESEARCH §"6-path resolver"). Final flush (line ~330+ in llmExtractionPipeline.ts) continues to pass the run-result's fully-populated Maps — quality is preserved on the final write.
- **Justification:** The D-05 quality-invariant test (precision histogram equality between periodic-flush slice and matching slice in final write) PASSES because the geocoder produces consistent precision per branch — if a group's context is missing in periodic flush but present in final flush, the final-flush write merges via id-key Map and overwrites the periodic entry with the higher-quality result. Net cache state at end-of-run is byte-equivalent to a single continuous run.
- **Files modified:** server/lib/llmExtractionPipeline.ts only (the barrel + extractors did NOT need to be widened beyond Task 3's `=> void | Promise<void>` callback widening).
- **Verification:** All 8 Wave 0 tests GREEN, including the D-05 quality-invariant case. The 5 extractor + cron + events route tests stay GREEN (76 tests total).
- **Trade-off:** In production, if a Vercel function-kill happens BEFORE the final-flush merge, periodic-flush events for that run will have slightly less rich context (no news/bellingcat hints — gdelt-actiongeo-fallback only). The next 4am tick's lineage filter will see those entries in cachedLlmKeys and skip re-extraction, so they STAY in the cache with the cheaper provenance. Operator can `?force=true` to re-extract if needed. This is the simpler-is-better pragmatic choice; the barrel-signature widening can land as a follow-up if quality drift becomes measurable.
- **Committed in:** 72e3da5 (Task 4b commit)
