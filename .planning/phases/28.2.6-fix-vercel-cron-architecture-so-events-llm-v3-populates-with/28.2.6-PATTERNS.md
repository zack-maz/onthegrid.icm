**Analog:** `server/lib/concurrencyLimit.ts`

**Why this analog:** Both are ~30-LOC primitives with a single named export, no runtime deps beyond the project's standard surface, heavy JSDoc that documents WHY the project rolled it locally instead of pulling a package. **Imports / file-header pattern** (concurrencyLimit.ts L1-32):

```typescript
/**
 * Phase 27.4.4 Plan 02 — minimal pLimit-equivalent concurrency limiter.
 *
 * Caps simultaneous in-flight async tasks at `maxConcurrent`. Returns a
 * function that wraps a Promise-returning thunk; calling the wrapper
 * either runs the thunk immediately (if there's capacity) or queues it
 * until an in-flight task completes. The wrapper resolves with the
 * thunk's value (or rejects with its error).
 *
 * Why we don't use the npm `p-limit` package:
 *   - This is a 30-LOC primitive with a stable interface.
 *   - Adding a dependency for it touches package.json + lockfile and
 *     forces a re-audit; the existing dependency footprint is small
 *     and we'd rather keep it that way.
 * ...
 *
 * Concurrency safety:
 *   - JavaScript event loop is single-threaded; the inFlight counter and
 *     queue array reads/writes are atomic between awaits.
 */
```

**Shim body pattern** (RESEARCH §Pattern 1, verified against vercel/vercel source):

```typescript
import { waitUntil } from '@vercel/functions';

// Vercel's own getContext() probes globalThis[Symbol.for('@vercel/request-context')].
// Outside Vercel: getContext() returns {}, the optional chain at
// `getContext().waitUntil?.(promise)` evaluates to undefined, the promise IS
// NEVER STARTED. We need an explicit fallback for Express dev / Vitest.
const VERCEL_CTX = Symbol.for('@vercel/request-context');

export function safeWaitUntil(promise: Promise<unknown>): void {
  const hasVercelContext =
    typeof (globalThis as Record<symbol, unknown>)[VERCEL_CTX] !== 'undefined';
  if (hasVercelContext) {
    waitUntil(promise);
  } else {
    promise.catch((err) => {
      log.warn({ err }, 'waitUntil-fallback IIFE rejected (local dev)');
    });
  }
}
```

**Drift risk:**

- **If the shim throws on a rejected promise** (e.g., `await promise` instead of `promise.catch(...)`), the rejection propagates back to the cron route handler, which crashes the HTTP 200 response and breaks the dispatch contract. The `void`-IIFE pattern was specifically chosen to swallow rejections — preserve that semantics.
- **If `process.env.VERCEL` is used as the detection signal** instead of `Symbol.for('@vercel/request-context')`, the shim either fires `waitUntil` in tests where the build env var bleeds in, OR falls back-to-`promise.catch` on Vercel where the request context IS present but the env var is unreliable at request time (RESEARCH Pitfall 5).
- **If the shim re-throws TypeError on non-Promise input** to mirror `@vercel/functions`' own validation, callers passing a thenable that isn't `Promise.prototype` will crash; safer to type the parameter `Promise<unknown>` and rely on TS strict mode.
