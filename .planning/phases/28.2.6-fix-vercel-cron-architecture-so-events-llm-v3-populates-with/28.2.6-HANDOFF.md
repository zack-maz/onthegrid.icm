## The problem (one paragraph)

The Vercel cron at `/api/cron/refresh-events` uses a fire-and-forget IIFE (`void (async () => {...})()`) to run LLM extraction in the background after returning HTTP 200. On Vercel Fluid Compute, the function instance is killed the moment the response is sent — the background work never executes. We verified this on prod: forced the cron with `?force=true`, polled `/api/events/llm-status` five times across instances, every poll showed `stage: idle, callHistory: 0, dlqCount: 0`. Zero batches ran. The terminal cache key `events:llm:v3` stayed empty. The dashboard's new "Events (LLM)" health row, the `/api/health` `endpoints.llmEvents` field, and the prod-connectivity-audit.yml tier-green gate all sit downstream of that key — so they all stay `unknown` indefinitely.

Awaiting the IIFE inline (instead of fire-and-forget) keeps the function alive but hits a different ceiling: full v3 extraction is ~10 minutes wall time, and Vercel Hobby caps `maxDuration` at 300s. We tried this in commit `b016a5c`; the function timed out mid-extraction with 6 batches in the DLQ and the final terminal-key cacheSet at `llmExtractionPipeline.ts:386` unreachable. Reverted in `b4bf4a3`.

## Decision (locked 2026-05-07 via /gsd-discuss-phase 28.2.6)

**Resolution path: architecture refactor — incremental terminal-key write + Vercel `waitUntil` migration.**

Two coupled changes. Both must land together; neither works alone.

### Change A — Incremental terminal-key write

Modify `server/lib/llmExtractionPipeline.ts:386` so `events:llm:v3` (and the v2 / v1 fallbacks for other pipeline versions) gets `cacheSet`-ed periodically during extraction, not only at end-of-pipeline.

**Why both writes are needed.** Today the merged-key write happens once after the full extraction-then-geocoding pass. Within a single 300s function window we get partway through extraction batches, then the function aborts before reaching geocoding + the cache write. With incremental writes, even a partial 200s run leaves the gate-relevant key non-empty and the next cron tick (4am UTC) extends from where the previous one left off (the existing D-18 lineageHash pre-filter already handles the resume semantics).

**Specific contract details for the planner to lock in:**

- **Cadence.** Write every N batches (suggested N=10) rather than every single batch — keeps Redis write rate bounded under concurrency=12. Final write at end-of-pipeline still happens (no behavior change there); only adds intermediate writes.
- **Shape.** The terminal key continues to hold `ConflictEventEntity[]` (not the LLMCachePayload envelope used by `events:llm:v3:partial`). Plan 28.2.6 must NOT collapse the two-key discipline that CLAUDE.md Phase 27.4.1 calls out — `events:llm:v3` stays `ConflictEventEntity[]`; `events:llm:v3:partial` stays `LLMCachePayload`. The reader defense-in-depth helpers `toEntityArray` / `coerceCachedEvents` (commit `e26ceca`) stay as the safety net.
- **Geocoding interaction.** Today geocoding runs once after all extraction completes. Plan 28.2.6 needs to decide: geocode-per-batch-window (so partial writes are fully geocoded) OR write extraction-only entities and let geocoding fire on the next tick (less work per tick, but events sit in the cache un-geocoded for up to 24h). The discuss-phase user lean: **geocode-per-batch-window** — partial cache contents should always be self-consistent (extraction + geocoding done) so consumers never see half-enriched events. Confirm this in plan-phase.
- **Lineage hash interaction.** D-18 already partitions which groups need extraction by hashing the prior cache. Incremental writes mean the lineage filter sees more "already done" entries on re-runs, which is exactly the resume property we want. No code change needed in `groupLineageHash.ts`.
- **Test gate.** New vitest case in `server/__tests__/lib/llmExtractionPipeline.test.ts` (or analogous) asserting that two consecutive partial runs (e.g. 5 batches then function-kill, then 5 more batches) produce the same final state as one continuous run. This is the contract test that locks in the "no-state-loss across function boundaries" invariant.

### Change B — Vercel `waitUntil` migration

Replace `void (async () => {...})()` at `server/lib/llmExtractionPipeline.ts:203` with `waitUntil(...)` from `@vercel/functions`.

**Why.** Without this, Change A is academic — the function still dies the instant the response is returned, so the incremental writes never get a chance to run. `waitUntil` is Vercel's official mechanism for "let the function instance survive past the response so background work completes within the maxDuration budget."

**Specific contract details for the planner:**

- Install `@vercel/functions` (currently absent — `node_modules/@vercel/` only has `analytics` and `speed-insights`).
- The cron route currently does `await runRefreshExtraction(...)` and waits for the dispatch decision; the IIFE is the part that fires-and-forgets the actual work. Migration: keep `runRefreshExtraction`'s sync-decision return, but inside the helper change `void (async () => {...})()` to `waitUntil((async () => {...})())`. Returning a `dispatched: true` envelope quickly preserves the existing API shape; the background body now actually runs to completion (or to the maxDuration ceiling).
- Local dev fallback: `@vercel/functions`' `waitUntil` no-ops when not running on Vercel, so existing test mocks for the IIFE pattern continue to work without per-environment branches. Verify this on Express/Vitest before claiming the API is unchanged.
- The cron route's response shape stays the same: HTTP 200 in <500ms with `{ ok: true, dispatched: true, ... }`. Operator-side curl invocations don't need to change.

### Why both, not one or the other

- **Just Change A** (incremental writes, no waitUntil): function still dies in <1s after response. Incremental writes never execute. Verified empirically — pre-hot-fix #2 we saw `callHistory: 0` across 5 polls.
- **Just Change B** (waitUntil, no incremental writes): function stays alive up to 300s, runs as many batches as fit, then dies before reaching the single end-of-pipeline cache write. Cache stays empty. Same outcome as the awaited-IIFE attempt in `b016a5c`.
- **Both together**: function survives past response → runs batches → writes incrementally → next tick resumes via lineageHash pre-filter. Within 1-2 cron ticks the cache is fully populated. Subsequent prod-connectivity-audit.yml run shows `allTiersGreen=true`.

## What's intentionally out of scope

- **Vercel plan upgrade to Pro.** Considered as Path B in discuss-phase. Not chosen — operator preference for code-only fix.
- **Splitting extraction into N parallel cron routes.** Bigger refactor; the incremental-write + waitUntil combo gets us to green without sharding.
- **Optimizing extraction wall time below 10 min.** Concurrency, prompt size, batch size are all tunable, but they're 28.4+ scope. 28.2.6 only needs to make the existing 10-min extraction survive the function-boundary problem.
- **`@vercel/functions` adoption beyond this one call site.** Other cron routes (`cron-warm`, `cron-health`) currently work fine because their bodies are synchronous-await within the route handler — no fire-and-forget. Don't migrate them as part of this phase.
- **Changing the 4am UTC cron schedule.** Out of scope.

## Anti-patterns to avoid

- **Don't write `LLMCachePayload` envelopes to `events:llm:v3`.** That regression already happened once (Phase 27.4.1, fixed in commit `a5c8846`). Keep `events:llm:v3` as `ConflictEventEntity[]`. Use `events:llm:v3:partial` for envelope shape.
- **Don't `await` the IIFE instead of using `waitUntil`.** `await` blocks the response, makes the cron route's HTTP 200 take 5+ minutes, and the curl/Vercel-cron-trigger client may time out before the response arrives. `waitUntil` returns the response immediately AND keeps the body running. This is the canonical Vercel pattern.
- **Don't try to reach `allTiersGreen=true` in this phase.** That happens automatically after 1-2 cron ticks once the code lands. The success signal for 28.2.6 is "force-trigger of `/api/cron/refresh-events?force=true` followed by 4-min wait shows `events:llm:v3` non-empty AND `/api/health endpoints.llmEvents.status` flipped from `unknown` to `healthy`." The workflow run is downstream evidence, not a phase deliverable.
- **Don't refactor `groupLineageHash.ts` or `events:llm:v3:partial` semantics.** Both are working as designed; the partial-key writer + lineageHash pre-filter together provide the cross-tick resume semantics that make incremental writes safe.
- **Don't fold this into Phase 28.2.5's PR #11.** 28.2.5 is in code review for what shipped. 28.2.6 cuts a fresh branch from main after #11 merges.
