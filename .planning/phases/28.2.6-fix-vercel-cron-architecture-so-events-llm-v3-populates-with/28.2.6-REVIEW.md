## Summary

Both Plan 01 (incremental terminal-key writes) and Plan 02 (`safeWaitUntil` shim) are well-architected and correctly land the contracts described in CONTEXT/RESEARCH. The two-key discipline is preserved (terminal `events:llm:v3` holds `ConflictEventEntity[]`, partial `events:llm:v3:partial` holds `LLMCachePayload` envelopes). `runEval()` is correctly NOT called from intermediate flushes (Pitfall 8 satisfied). The `safeWaitUntil` shim is defensive on both paths — try/catch around `waitUntil`, `.catch` on the local-dev fallback, returns void to block accidental `await`. The findings below are mostly defensive-coding suggestions and one concurrency-related observation that is technically self-healing but worth documenting. No critical bugs, no security issues with the new env var, no test flakiness risks identified.

## Warnings

### WR-01: Periodic-flush no-op on v1 path is silently swallowed

**File:** `server/lib/llmExtractionPipeline.ts:361-365` (and v1 at `server/lib/llmEventExtractor.v1.ts`)
**Issue:** The pipeline computes `PARTIAL_KEY_ACTIVE = 'events:llm:partial'` for v1 (lines 361-365), but v1's `processEventGroups` (`llmEventExtractor.v1.ts`) never writes a partial cache. Every periodic-flush call on v1 reads a non-existent key, hits the `partialEvents` array check at line 388, and returns early. The cron path on the v1 rollback would NEVER persist incremental progress — the entire ~95-min run must complete for a single terminal write. If Vercel kills the function at 300s on v1, all work is lost.

This is acceptable per design intent (v1 is the rollback path and isn't expected to run on Vercel cron), but the current code silently swallows the no-op. A future operator forcing v1 via `POST /api/events/llm-pipeline {version: 'v1'}` would lose 4hr+ of work without any warning surface.

**Fix:** Either (a) add a v1-path log warning at extraction kick-off when `pipelineV2 || pipelineV3` is false but the cron triggered the run, OR (b) document the limitation explicitly in the helper:

```ts
// In runRefreshExtraction, before the safeWaitUntil call:
if (!pipelineV2 && !pipelineV3 && opts.triggeredBy === 'cron') {
  log.warn(
    'cron-triggered v1 extraction has no incremental flush — full run must complete within 300s or work is lost (rollback path; consider manual /api/events trigger instead)',
  );
}
```

### WR-02: Periodic flush reads partial cache without ordering guarantees under concurrency=12

**File:** `server/lib/llmExtractionPipeline.ts:380-451`
**Issue:** Under `LLM_V3_CONCURRENCY=12`, the v3 extractor's `finishBatch` interleaves `await onBatchComplete?.(c, totalBatches)` and `await writePartialCache(results, c, ...)` across multiple in-flight tasks. The periodic-flush callback reads `PARTIAL_KEY_ACTIVE` to discover what's "new since last flush", but the partial cache may LAG the in-memory `results` array — Task A's `onBatchComplete` (which reads partial cache) runs BEFORE Task A's own `writePartialCache` writes Task A's events. The flush therefore captures a stale snapshot.

Worst case under concurrency=12: when batch 10 triggers the flush, the partial cache may only reflect batches 1-9's events because batch 10's `writePartialCache` (line 576 of v3) hasn't run yet. The flush slices `partialEvents.slice(lastFlushedEventCount)` correctly for batches 1-9, but batch 10's events stay invisible until the NEXT flush at batch 20. This is self-healing — the next flush picks up the gap, and the final flush is a complete write of all `llmEntities`. **No events are permanently lost.**

The merge-by-id semantics in `mergeAndPersistLlmEntities` (line 125-130) further protect against duplicates if the slice window happens to overlap.

However, the comment block at line 336-356 claims "the cadence counter MUST live inside this callback closure so concurrency=12 batch-completion ordering races are serialized through finishBatch's monotonic ++completedBatchesCounter (Pitfall 2)" — this claim is correct for the COUNTER but does not address the **partial-cache-vs-in-memory-results lag**, which is a separate race. A reader inheriting this code may not realize the lag exists.

**Fix:** Add a code comment near line 386 documenting the lag explicitly:

```ts
// Under concurrency=12, partialEvents.length may lag the in-memory `results`
// array by up to (concurrency - 1) batches because Task A's onBatchComplete
// runs BEFORE Task A's writePartialCache. The lag is self-healing: the next
// flush picks up the gap, and the final flush is a complete write. Events
// are never permanently lost. Merge-by-id in mergeAndPersistLlmEntities
// further protects against any window overlap.
```

No code change required — the design is correct, just under-documented.

### WR-03: `cacheGetSafe` 999_999_999 ms TTL is a sentinel that future readers may not recognize

**File:** `server/lib/llmExtractionPipeline.ts:191, 227, 386`
**Issue:** Three call sites pass `999_999_999` as `logicalTtlMs` to `cacheGetSafe` to mean "accept any-age data". That's ~11.5 days, but the magic number obscures intent. A future reader changing the TTL semantics in `cacheGetSafe` could regress these call sites. (Note: pre-existing pattern at line 191/227, but Plan 01 added the third call site at line 386.)

**Fix:** Promote to a named constant near the top of the file:

```ts
/** Sentinel for "accept any age" — the partial-cache + raw-GDELT reads do
 *  not care about staleness; only the existence of the data matters. */
const TTL_ANY_AGE_MS = 999_999_999;

// then at line 386:
const partialCached = await cacheGetSafe<{...}>(PARTIAL_KEY_ACTIVE, TTL_ANY_AGE_MS);
```

## Info

### IN-01: `safeWaitUntil` Vercel detection happens at call time per invocation

**File:** `server/lib/safeWaitUntil.ts:64-65`
**Issue:** `globalThis[Symbol.for('@vercel/request-context')]` is checked on every call. This is correct (the global is request-scoped on Fluid Compute), but it does mean a single Vercel function invocation that calls `safeWaitUntil` BEFORE the request-context global is populated would silently use the local-dev path. In practice this won't happen because `runRefreshExtraction` is invoked from inside an Express route handler, by which time Vercel has set the global.

**Fix:** None required. Optionally add a one-line comment confirming the timing:

```ts
// VERCEL_CTX is populated by Vercel BEFORE the route handler runs, so any
// safeWaitUntil call from inside a handler sees it.
```

### IN-02: `safeWaitUntil` Vercel-path catch falls back to `.catch` but does NOT call `waitUntil` again

**File:** `server/lib/safeWaitUntil.ts:67-82`
**Issue:** When `waitUntil(promise)` itself throws (e.g., TypeError on non-Promise input), the shim falls back to `promise.catch(...)` to log late rejections. But this means the work runs as a normal unhandled IIFE — no Vercel function-instance extension. On Fluid Compute that effectively returns to pre-28.2.6 behavior for that single invocation: the work may be killed at `res.end()`.

This is the right tradeoff (better than crashing the cron route), but the comment "fall back to the local-dev catch path" understates the behavioral cost — production work would silently revert to the broken pattern this phase is fixing.

**Fix:** Strengthen the log warning and comment:

```ts
log.warn(
  { err: vercelErr },
  'CRITICAL: waitUntil threw on Vercel — work may be killed at res.end(). ' +
    'Investigate @vercel/functions input shape immediately.',
);
```

### IN-03: `safeWaitUntil` test for "invokes waitUntil when Vercel context is present" tests a stub, not the real probe

**File:** `server/__tests__/lib/safeWaitUntil.test.ts:57-65`
**Issue:** The test sets `globalThis[VERCEL_CTX] = { get: () => ({ waitUntil: mockWaitUntil }) }` to fake the Vercel context, and asserts `mockWaitUntil` is called with the promise. But the SUT does NOT invoke `globalThis[VERCEL_CTX].get().waitUntil()` — it imports `waitUntil` from `@vercel/functions` directly. The test passes only because `vi.mock('@vercel/functions', () => ({ waitUntil: mockWaitUntil }))` is also installed, mocking the import. The fake `globalThis[VERCEL_CTX].get()` shape is therefore not exercised by the production path; only its existence (`typeof !== 'undefined'`) is.

This is fine for the current contract, but the test fixture is misleading — it suggests the shim navigates `globalThis[VERCEL_CTX].get().waitUntil()`, which it does not.

**Fix:** Simplify the fake context to just `{}` to make the test fixture honest:

```ts
(globalThis as Record<symbol, unknown>)[VERCEL_CTX] = {}; // existence is what we probe
```

### IN-04: Test mocks `@vercel/functions` and `safeWaitUntil` simultaneously (defense-in-depth, but redundant under current SUT)

**File:** All three pipeline test files (`incrementalWrite.test.ts`, `terminalShape.test.ts`, `crossBoundary.test.ts`)
**Issue:** Each test mocks BOTH `@vercel/functions` (line 60-64 of terminalShape, etc.) AND `server/lib/safeWaitUntil.js` (line 74-78). The redundancy is defensible but worth noting that under the current pipeline SUT, only the `safeWaitUntil` mock is exercised — `@vercel/functions` is never imported by the path under test once `safeWaitUntil` is mocked. The `@vercel/functions` mock is dead code unless someone removes the `safeWaitUntil` mock.

**Fix:** None required — this is intentional and the comment explains it. Just a heads-up.
