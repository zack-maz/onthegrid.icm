# Phase 28.2.6: Fix Vercel Cron Architecture — Research

**Researched:** 2026-05-07
**Domain:** Vercel Fluid Compute function lifecycle + Express background-task patterns + LLM extraction pipeline incremental persistence
**Confidence:** HIGH (Vercel docs + verified package source + verified codebase reads)

## Summary

The phase is a surgical, two-line-class bug fix in a single helper (`server/lib/llmExtractionPipeline.ts`). Both changes (A: incremental terminal-key writes; B: `waitUntil` migration) are mechanically simple — the entire risk surface is in **the cross-cut interactions between the existing parallel batch loop, the `events:llm:v3` two-key discipline, and Vercel's serverless lifecycle**.

Critical empirical finding from documentation lookup: **`waitUntil` does NOT extend `maxDuration`. Promises passed to `waitUntil` share the function's `maxDuration` budget; if the function times out, the promises are cancelled** ([CITED: vercel.com/docs/functions/functions-api-reference/vercel-functions-package]). This means Change B alone gets us a 300s execution window after the response is sent — _not_ an unlimited budget. Change A (incremental writes every N batches) is what makes that bounded window safely resumable.

Critical local-dev finding: **`waitUntil` source is `getContext().waitUntil?.(promise)`** ([VERIFIED: github.com/vercel/vercel `packages/functions/src/wait-until.ts`]). Outside Vercel runtime `getContext()` returns `{}`, the optional-chain short-circuits, the call returns `undefined`, and the promise is **never run**. This means the local-dev/Vitest path needs a shim or a test-time mock that calls the promise eagerly — D-10's "no-op when not running on Vercel" is literally true, but "no-op" here means "the work doesn't run", which silently breaks Express dev. Plan must address this.

**Primary recommendation:** Single PR, two stages — Change A (incremental writes wired through the existing `onBatchComplete` callback path the v3 extractor already supports) lands first, then Change B (`waitUntil` migration with a 4-line dev shim that falls back to `void promise` when the Vercel context is absent). One vitest contract test asserting cross-function-boundary state preservation locks in the invariant.

### Pattern 1: `waitUntil` migration with local-dev shim (Change B)

**What:** Replace the bare `void (async () => {...})()` with a wrapper that calls `waitUntil` if the Vercel runtime is present and falls back to the `void`-IIFE when running locally (Express dev / Vitest).

**When to use:** Single call site for Phase 28.2.6 (`runRefreshExtraction:203`).

**Example (inline shape, no separate file):**

```typescript
// Source: github.com/vercel/vercel/packages/functions/src/wait-until.ts (verified 2026-05-07)
import { waitUntil } from '@vercel/functions';

// `waitUntil` is `getContext().waitUntil?.(promise)`. Outside Vercel,
// getContext() returns {}, the optional chain yields undefined, and the
// promise IS NEVER RUN. We need an explicit fallback for Express dev.
function safeWaitUntil(promise: Promise<unknown>): void {
  // Probe: Vercel injects a request-context global keyed by the symbol
  // 'Symbol.for(@vercel/request-context)'. Outside Vercel it's absent.
  const VERCEL_CTX = Symbol.for('@vercel/request-context');
  const hasVercelContext =
    typeof (globalThis as Record<symbol, unknown>)[VERCEL_CTX] !== 'undefined';

  if (hasVercelContext) {
    waitUntil(promise);
  } else {
    // Local Express dev / Vitest — the runtime won't be killed at res.end(),
    // so a bare unawaited promise (the prior pattern) runs to completion.
    // Catch swallows so a failure here doesn't escape as an unhandled rejection.
    promise.catch((err) => {
      log.warn({ err }, 'waitUntil-fallback IIFE rejected (local dev)');
    });
  }
}

// Call site at line 203 becomes:
safeWaitUntil(
  (async () => {
    // … existing IIFE body unchanged …
  })(),
);
```

[CITED: vercel.com/docs/functions/functions-api-reference/vercel-functions-package — "waitUntil() enqueues an asynchronous task to be performed during the lifecycle of the request… Promises passed to waitUntil() will have the same timeout as the function itself. If the function times out, the promises will be cancelled."]
[VERIFIED: source code at github.com/vercel/vercel `packages/functions/src/wait-until.ts` — implementation is `getContext().waitUntil?.(promise)` with a TypeError on non-Promise inputs.]

**Alternative shape (separate wrapper module, easier to mock in vitest):**

```typescript

  /* same logic */
```

### Pattern 2: Per-N-batch incremental flush via the existing `onBatchComplete` hook (Change A)

**What:** The v3 extractor already calls `onBatchComplete(completed, total)` after each batch (via `finishBatch` in `llmEventExtractor.v3.ts:569-573`). The pipeline today uses this callback only to update `llmProgress`. Hijack the same callback to drive the incremental terminal-key flush.

**When to use:** The natural insertion point for Change A — keeps the cadence counter aligned with the existing concurrency-12 race-safety contract (Phase 27.4.4 Plan 02 — `finishBatch` already gives `onBatchComplete` monotonically-increasing counts).

**Example:**

```typescript
// Source: existing pipeline at server/lib/llmExtractionPipeline.ts:269 (callback signature)
const FLUSH_EVERY_N = 10; // D-03
let batchesSinceLastFlush = 0;
const newlyEnrichedSinceLastFlush: EnrichedEventV3[] = []; // populated as batches complete
let lastFlushedIdx = 0; // index into prioritizedGroups for D-05 geocode-window

const extractResult = await processEventGroups(prioritizedGroups, async (completed, total) => {
  updateProgress({ completedBatches: completed, totalBatches: total });

  batchesSinceLastFlush++;
  if (batchesSinceLastFlush < FLUSH_EVERY_N) return;
  batchesSinceLastFlush = 0;

  // D-05: geocode-per-batch-window. Geocode only the events from the
  // batches completed since the last flush, then merge into terminal cache.
  // Geocoder requires the *groups* slice for ResolveContext — pull from
  // prioritizedGroups by completedBatches range.
  await flushIncrementalCache({
    llmCachedRef,
    LLM_EVENTS_KEY_ACTIVE,
    pipelineV3,
    pipelineV2,
    prioritizedGroups,
    windowStart: lastFlushedIdx,
    windowEnd: completed, // exclusive — completed batches × batchSize
  });
  lastFlushedIdx = completed;
});
```

**Important subtlety:** Under concurrency=12, batch N may complete BEFORE batch N-1. `finishBatch` in `llmEventExtractor.v3.ts:569` rotates through `++completedBatchesCounter` so the callback receives monotonic counts, BUT the events in `results` may be from any of the in-flight batches. The geocode-window slice MUST be defined by _which events have been added to `results` since last flush_, not by `completed × BATCH_SIZE` over `prioritizedGroups`. Two viable techniques:

1. **Snapshot-the-array approach** (recommended for simplicity): At each flush, snapshot `results.length` from the prior flush. Geocode `results.slice(prevSnapshot, currentLength)`. Trust the v3 extractor's existing race-safety contract — `results.push(...)` calls happen synchronously between awaits.
2. **Per-batch event tagging approach**: Plumb a third callback arg through `onBatchComplete` that delivers the just-validated batch's events directly. Requires changing `processEventGroups`'s signature — bigger touch.

Snapshot-the-array (option 1) is the smaller, safer change.

### Pattern 3: Cross-function-boundary state preservation contract test (D-07)

**What:** A vitest test that simulates two consecutive partial runs of the pipeline (e.g., 5 batches → mid-run kill → 5 batches in second run) and asserts the final terminal-key state matches what a single continuous 10-batch run would have produced.

**When to use:** Mandatory per D-07. Locks in the "no-state-loss across function boundaries" invariant so future refactors can't silently regress.

### Anti-Patterns to Avoid

- **Writing `LLMCachePayload` envelopes to `events:llm:v3`** — D-04 / D-11 hard block. The terminal key holds `ConflictEventEntity[]`. ## Common Pitfalls

### Pitfall 1: `waitUntil` silently no-ops in local dev / Vitest

**What goes wrong:** Engineer pushes Change B, runs `npm run dev:server`, hits the cron endpoint manually with curl, sees HTTP 200 in <500ms. Polls `/api/events/llm-status`. `stage: idle, callHistory: 0` — same symptom as the Vercel-prod bug. Wrongly concludes the fix doesn't work.
**Why it happens:** `getContext()` returns `{}` outside Vercel; `waitUntil?.(promise)` short-circuits to `undefined`; the promise is never started. Express dev keeps the function alive, but no one's running the work.
**How to avoid:** Mandatory `safeWaitUntil` shim that detects the Vercel context (via the `Symbol.for('@vercel/request-context')` global) and falls back to `promise.catch(...)` for local. See Pattern 1 above. Verified during research by reading the `@vercel/functions` source [VERIFIED: github.com/vercel/vercel/blob/main/packages/functions/src/wait-until.ts] — the optional-chain at the call site is the silent-no-op gate.
**Warning signs:** Local dev shows `dispatched: true` immediately and `/api/events/llm-status` returns `stage: idle` after the first hit. Same surface symptom as the prod bug.

### Pitfall 2: Concurrency=12 batch-completion ordering ≠ batch-index ordering

**What goes wrong:** Engineer wires the cadence counter as `if (batchIndex % 10 === 0)` inside the per-batch closure. Under concurrency=12, batches complete out of order — flushes fire in clusters (3-4 simultaneous), then dry spells, then more clusters. Race: an earlier-indexed batch may complete _after_ a later-indexed batch's flush has already written to cache, then write a clobber.
**Why it happens:** Phase 27.4.4 Plan 02 (CLAUDE.md "Parallel v3 Batch Processing" section) established that `Math.floor(i / BATCH_SIZE)` ≠ completion order. The shared `completedBatchesCounter` flowing through `finishBatch()` is the only monotonic source.
**How to avoid:** Drive `batchesSinceLastFlush` from inside the existing `onBatchComplete` callback path (which already receives `completed` from `finishBatch`'s monotonic counter). Don't introduce a parallel counter that ticks on a per-task basis.
**Warning signs:** Tests pass at concurrency=1 but fail intermittently at concurrency=12. Cache content fluctuates between flushes.

### Pitfall 3: Geocode-window slicing under reordered batch completion

**What goes wrong:** Engineer slices `prioritizedGroups[lastFlushedIdx * BATCH_SIZE : completed * BATCH_SIZE]` as the geocode window. Under concurrency=12, the events that have been pushed to `results` since the last flush DON'T necessarily correspond to that group-slice — they correspond to whichever batches happened to finish in that interval.
**Why it happens:** `processEventGroupsV3:608` does `results.push(...validated.data.events)` from each batch's resolution. The push order tracks completion order, not batch-index order.
**How to avoid:** Use the snapshot-the-array technique: capture `results.length` (or hand the inner extractor a callback that exposes the raw `results` slice). Geocode the slice `results.slice(prevSnapshot, currentLength)` directly. Don't try to reconstruct the slice from `prioritizedGroups`.
**Warning signs:** Some events end up un-geocoded after the final flush; the per-event resolver throws "group key not found" or returns GDELT-centroid fallbacks for events that should have hit the resolver's higher-quality branches.

### Pitfall 4: Forgetting the merge-by-id when writing intermediate cache

**What goes wrong:** Engineer writes `cacheSetSafe(LLM_EVENTS_KEY_ACTIVE, newWindow.map(toEntity), TTL)` for the intermediate flush. The cache loses every event from prior cron ticks that should have been preserved.
**Why it happens:** The existing final write at line 386 already builds `llmMergeMap` from `llmCachedRef.data` (line 376) and overlays new events. The intermediate write must do the same.
**How to avoid:** Extract a small helper `mergeAndPersist(newEntities, llmCachedRef, key)` that wraps the lines 374-388 pattern. Call it from both the periodic-flush hook AND the final-flush block. Final write becomes a degenerate case of the helper (window = all enriched events from this run).
**Warning signs:** After the first incremental flush, the cache holds _fewer_ events than it did before the cron run started.

### Pitfall 5: `safeWaitUntil` shim using stale Node feature detection

**What goes wrong:** Engineer reaches for `process.env.VERCEL === '1'` as the Vercel-detection signal. This is set during build, but in some local-test scenarios (e.g., importing `@vercel/functions` triggers some self-detection) the env var may not be set even when the runtime IS Vercel-aware.
**Why it happens:** `process.env.VERCEL` is a build-time env signal, not a runtime context signal.
**How to avoid:** Use the `Symbol.for('@vercel/request-context')` global probe — that's what the package's `getContext()` itself uses. The fallback wraps `waitUntil` with a `try/catch` that treats _any_ throw OR no-op-undefined as "context unavailable, fall back to promise.catch."
**Warning signs:** Test suite shows `waitUntil` calls in environments that should be Vercel; or the fallback fires on a real Vercel function.

### Pitfall 6: TS `noUncheckedIndexedAccess` regression in new code

**What goes wrong:** Engineer writes `const ev = results[i]` inside the new flush helper without the existing `if (!ev) continue` guard, fails `tsc --strict` (project uses `noUncheckedIndexedAccess`).
**Why it happens:** The Phase 27.4.4 normalization sweep (28.1 W7) explicitly enforced this rule across server-side code. New code lands under the same TS configuration.
**How to avoid:** Mirror the existing `for (let i = 0; i < events.length; i++) { const ev = events[i]; if (!ev) continue; ... }` pattern in `llmEventExtractor.v3.ts:1176-1178`. CLAUDE.md "Phase 27.4.1 V1 TS cleanup" section is the canon.
**Warning signs:** `npx tsc --noEmit` errors reference unchecked array access; `npm run typecheck` fails.

### Pitfall 7: Bundle commit forgotten

**What goes wrong:** Source change lands in `server/lib/llmExtractionPipeline.ts`. PR opens. Reviewer approves. Operator merges, runs `vercel --prod`. Prod deploys old `api/vercel-entry.js` because `npm run build` was never run on the branch.
**Why it happens:** The `api/vercel-entry.js` bundle is committed (NOT generated at deploy time per project convention — Vercel deploys the file directly from git). The bundle is a build artifact tracked in git.
**How to avoid:** After source changes land, run `npm run build` and commit the regenerated `api/vercel-entry.js` in the same PR (or as a follow-up before the merge gate). This pattern is well-established — every Phase 28.2.x PR includes a bundle commit.
**Warning signs:** PR diff doesn't include `api/vercel-entry.js`; post-deploy smoke shows the same broken behavior.

### Pitfall 8: Eval harness re-run inside the IIFE multiplies token spend per run

**What goes wrong:** The current IIFE at lines 320-325 + 352-358 runs `runEval()` once after each pipeline finishes (geocoder-only per Pitfall 8 of Phase 27.4 docs). If incremental flushes incorrectly call `runEval()` per flush, daily token spend goes through the roof.
**Why it happens:** The existing pattern is "extract → geocode → eval → cache." Adding intermediate "extract → geocode → cache" should NOT include "→ eval" or it doubles/triples the daily eval cost.
**How to avoid:** `runEval()` stays in its current location (after the FINAL geocode-and-cache, before `updateProgress({stage:'done'})`). The intermediate-flush helper does NOT call `runEval()`.
**Warning signs:** `events:llm-eval-baseline:v3` shows a sudden uptick in writes per cron tick; LLM token budget hits the soft cap unexpectedly.

### `waitUntil` source (the Vercel runtime contract)

```typescript
// Source: github.com/vercel/vercel/blob/main/packages/functions/src/wait-until.ts (verified 2026-05-07)
import { getContext } from './get-context';

export const waitUntil = (promise: Promise<unknown>) => {
  if (promise === null || typeof promise !== 'object' || typeof promise.then !== 'function') {
    throw new TypeError(`waitUntil can only be called with a Promise, got ${typeof promise}`);
  }

  return getContext().waitUntil?.(promise);
};
```

```typescript
// Source: github.com/vercel/vercel/blob/main/packages/functions/src/get-context.ts (verified 2026-05-07)
export const SYMBOL_FOR_REQ_CONTEXT = Symbol.for('@vercel/request-context');

export function getContext(): Context {
  const fromSymbol: typeof globalThis & {
    [SYMBOL_FOR_REQ_CONTEXT]?: { get?: () => Context };
  } = globalThis;
  return fromSymbol[SYMBOL_FOR_REQ_CONTEXT]?.get?.() ?? {};
}
```

[VERIFIED 2026-05-07] These two snippets are the entire surface area of "what `waitUntil` does." On Vercel, `getContext()` returns the request-bound context with a real `waitUntil` method. Outside Vercel (Express dev, Vitest, anything else), `getContext()` returns `{}` and the optional-chain at `getContext().waitUntil?.(promise)` evaluates to `undefined` — the promise is never invoked.
