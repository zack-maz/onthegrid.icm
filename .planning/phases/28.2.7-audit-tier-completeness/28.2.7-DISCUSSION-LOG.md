## R2 — `llm:lastProgress` write-through location

### Q1: Where should the llmProgress → Redis write-through live?

| Option                            | Description                                                                                                                                                 | Selected |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| In `llmProgress.ts` setters       | `resetProgress()` and `updateProgress()` each call `cacheSetSafe('llm:lastProgress', ...)`. Centralized; couples singleton to Redis but degrade-open holds. | ✓        |
| At extraction-pipeline call sites | Explicit `cacheSetSafe` at the 2-3 call sites that set `startedAt`/`completedAt`. Keeps `llmProgress.ts` pure but scatters write-through.                   |          |
| Single helper `persistProgress()` | Helper in `llmProgress.ts`, called by both. Compromise — cleaner test isolation.                                                                            |          |

**User's choice:** In `llmProgress.ts` setters (Recommended)
**Notes:** Smallest write surface (2 mutators), single concern per module, easy to test.

### Q2: On which state changes does the write-through fire?

| Option                      | Description                                                                                        | Selected |
| --------------------------- | -------------------------------------------------------------------------------------------------- | -------- |
| Only on transitions         | Fire on `startedAt`-set + `completedAt`-set. ~2 Redis writes per run.                              | ✓        |
| On every `updateProgress()` | Every partial merge fires `cacheSetSafe`. ~50–200 writes per run for batch progress probe ignores. |          |
| Transitions + final batch   | Fire on transitions plus last batch flush.                                                         |          |

**User's choice:** Only on transitions (Recommended)
**Notes:** Probe reads `completedAt ?? startedAt`; mid-run batch updates don't change probe output.

## R1 — `cron:lastTick:<name>` writers

### Q1: When does each cron handler write its tick key?

| Option                             | Description                                                                                 | Selected |
| ---------------------------------- | ------------------------------------------------------------------------------------------- | -------- |
| After body succeeds                | Tick written only when status 200 path. Probe shows `unknown` if cron crashed.              | ✓        |
| Top of try (after auth)            | Tick recorded BEFORE body runs. Crash mid-body still leaves a fresh tick — operator misled. |          |
| Always at handler exit (`finally`) | Tick written regardless of body success. "Handler ran" vs "cron worked".                    |          |

**User's choice:** After body succeeds (Recommended)
**Notes:** Honest signal; operator gets `unknown` when cron didn't actually do its job.

### Q2: How does cron-warm handle partial success?

| Option                    | Description                                                                          | Selected |
| ------------------------- | ------------------------------------------------------------------------------------ | -------- |
| Tick on partial-or-better | Promise.allSettled returns `'partial'` (one ok) or `'ok'` (both ok). Tick on either. | ✓        |
| Tick only on full success | Tick fires only when both sites + water Overpass fetches succeed.                    |          |
| Tick always, log partial  | Tick on every invocation; partial state surfaces only via `logger.warn`.             |          |

**User's choice:** Tick on partial-or-better (Recommended)
**Notes:** "Did the cron tick run" vs "did everything succeed"; per-source freshness covered by cache-backed probes.

### Q3: Where does refresh-events-cron's tick write go?

| Option                          | Description                                                                               | Selected |
| ------------------------------- | ----------------------------------------------------------------------------------------- | -------- |
| In the route handler            | Tick at `refresh-events-cron.ts` after `runRefreshExtraction` returns. Helper stays pure. | ✓        |
| Inside `runRefreshExtraction()` | Helper writes the tick. Cleaner if helper grows callers, but cron-tick is route-level.    |          |

**User's choice:** In the route handler (Recommended)
**Notes:** Cron-tick semantics are a route concern, not a helper concern.

## TTL constant unit + naming

### Q1: How do we name the TTL constants given cacheSetSafe takes seconds?

| Option                                      | Description                                                                                | Selected |
| ------------------------------------------- | ------------------------------------------------------------------------------------------ | -------- |
| `*_TTL_SEC = 604800`                        | Constant name matches API unit. No conversion. Matches existing `SITES_REDIS_TTL_SEC` etc. | ✓        |
| `*_TTL_MS = 604800000 + /1000 at call site` | Honor SPEC's literal name; convert at each call. Three drift sites.                        |          |
| `*_TTL_MS = 604800000 + helper toSec()`     | Convert via shared helper. Slightly more ceremonious.                                      |          |

**User's choice:** `*_TTL_SEC = 604800` (Recommended)
**Notes:** Deliberate override of SPEC's `_TTL_MS` wording; value (7 days) unchanged.

### Q2: Where do the two TTL constants live?

| Option                        | Description                                                                                    | Selected |
| ----------------------------- | ---------------------------------------------------------------------------------------------- | -------- |
| Co-located with their writers | `CRON_LASTTICK_TTL_SEC` in `healthSources.ts`; `LLM_LASTPROGRESS_TTL_SEC` in `llmProgress.ts`. | ✓        |
| Both in `healthSources.ts`    | Single "audit-tier knobs" file. Loses locality with `llmProgress.ts`.                          |          |
| Both in new `auditTtl.ts`     | Dedicated file. New file for ~6 lines.                                                         |          |

**User's choice:** Co-located with their writers (Recommended)
**Notes:** Each constant lives near its usage cluster.

## R2 — `probeLlmStatus()` read fallback shape

### Q1: Read order in `probeLlmStatus()`?

| Option                          | Description                                                                                        | Selected |
| ------------------------------- | -------------------------------------------------------------------------------------------------- | -------- |
| Redis first, in-memory fallback | `cacheGetSafe('llm:lastProgress')` first; on null/throw fall back to singleton. Solves cold-start. | ✓        |
| In-memory first, Redis fallback | Read singleton first; only hit Redis on null. Defeats R2's purpose.                                |          |
| Read both, take max(timestamp)  | Defends against drift; more complex.                                                               |          |

**User's choice:** Redis first, in-memory fallback (Recommended)
**Notes:** Cold-start case is exactly when singleton is null AND Redis has the timestamp.

### Q2: What freshness when both null?

| Option                        | Description                                                                         | Selected |
| ----------------------------- | ----------------------------------------------------------------------------------- | -------- |
| `freshnessMs: null → unknown` | Preserve existing contract. Honest.                                                 | ✓        |
| `freshnessMs: 0 → healthy`    | Mirror probeProbeOnly. Wrong contract — llmStatus tracks pipeline, not process.     |          |
| Bias to fresh deploy          | Healthy if Redis reachable + key missing + deploy < 26h. Adds new state dependency. |          |

**User's choice:** `freshnessMs: null → unknown` (Recommended)
**Notes:** First cron run within 26h flips it green; no artificial bias.

### Q3: Backfill singleton from Redis on probe?

| Option                   | Description                                                                               | Selected |
| ------------------------ | ----------------------------------------------------------------------------------------- | -------- |
| No, read-only probe      | Probe stays pure. Singleton becomes consistent via next pipeline run.                     | ✓        |
| Yes, backfill from Redis | Probe writes singleton when Redis fresher. Adds write-side concern; saves ~50ms hot path. |          |

**User's choice:** No, read-only probe (Recommended)
**Notes:** Avoids "probe mutates state" surprise; minimal probe logic.

## Closeout — smaller items

### Q1: What value does each cron handler write to `cron:lastTick:<name>`?

| Option                                  | Description                                                        | Selected |
| --------------------------------------- | ------------------------------------------------------------------ | -------- |
| `Date.now()` as the value               | Stored as `{data: <epoch>, fetchedAt: <epoch>}`. Self-documenting. | ✓        |

**User's choice:** `Date.now()` as the value (Recommended)
**Notes:** Probe handles both `entry.data` and `entry.lastFresh`; explicit timestamp at write site is self-documenting.
