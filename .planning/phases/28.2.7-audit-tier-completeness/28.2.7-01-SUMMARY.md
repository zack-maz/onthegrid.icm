# Phase 28.2.7 Plan 01: cron:lastTick writers Summary

**Redis writers for cron:lastTick:{health,warm,refresh-events} with 7-day TTL, honest-failure semantics (no tick on body throw), and 6 vitest contract tests.**

## Performance

- **Duration:** 12 min
- **Started:** 2026-05-08T04:21:27Z
- **Completed:** 2026-05-08T04:33:48Z
- **Tasks:** 4
- **Files modified:** 5 (4 source + 1 existing test mock parity fix)

## Accomplishments

- `CRON_LASTTICK_TTL_SEC = 604_800` constant added to `server/lib/healthSources.ts` co-located with SOURCE_KEYS, FRESHNESS_THRESHOLDS_MS, and TIER_BY_ENDPOINT (CONTEXT D-07 audit-tier knobs file).
- Three cron handlers now write their per-cron `cron:lastTick:<name>` Redis key with `Date.now()` after body work succeeds, flipping `probeCronTick` from perma-`unknown` to `healthy` on first cron tick.
- `cron-health` writes after both eval blocks (`runEval` + `runAdversarialEval`) and the source-freshness loop complete — exactly matching CONTEXT D-03 "after body succeeds" boundary.
- `cron-warm` writes on partial-or-better (`results.some(r => r.status === 'fulfilled')`) so transient Overpass timeouts on one upstream don't surface as cron-tier red. Full failure (both rejected) leaves tick unwritten — probe stays `unknown`, the honest signal.
- `refresh-events-cron` writes inside the `try` block, after `log.info` and before `res.status(200).json`. The `catch` block does NOT write the tick, so a NIM throttle / extraction failure correctly leaves the probe at `unknown`. Helper `runRefreshExtraction` in `server/lib/llmExtractionPipeline.ts` is unmodified per CONTEXT D-05 (helper has non-cron callers; cron-tick semantics are a route-level concern).
- 6 vitest contract tests pin the writer contract: 1 cron-health (success-path write), 3 cron-warm (both succeed, partial, both reject), 2 refresh-events-cron (success-path write + honest-failure skip).
- Full vitest suite: 2180 passed (baseline 2174 + 6 new), 2 skipped, 19 skipped, 5 todo. `tsc --noEmit` exits 0.
