## Fixed Issues

### WR-01: Stale `startedAt` in Redis can mask a more-recent in-memory completion

**Files modified:** `server/routes/health.ts`
**Commit:** `2873314`
**Applied fix:** Replaced `redisLatest ?? memLatest` in `probeLlmStatus()` with a `Math.max(redisLatest, memLatest)` form that handles either-side-null cases first, then takes the freshest of the two. Comment explicitly documents the crashed-run-`startedAt` failure mode that motivated the change. Verification: persistence test suite (7 cases) re-ran clean, including the "Redis throws + memory fresh" degrade-open case which already exercised the memory-fallback path that this fix preserves.

### WR-02: `updateProgress({completedAt, errorMessage})` writes the same shape as success

**Files modified:** `server/lib/llmProgress.ts`
**Commit:** `c3e8bd9`
**Applied fix:** Wrapped the existing `partial.completedAt !== undefined` write-through guard with an `isErrorTermination` check that inspects `partial.stage === 'error'`, the merged singleton's `llmProgress.stage === 'error'`, and `llmProgress.errorMessage !== null`. Three-way OR catches the case where the partial only carries `completedAt` but a prior batch update had already set `stage: 'error'`. Brings `llm:lastProgress` write-discipline into alignment with the `cron:lastTick:*` "tick fires only on success" contract from cron-health.ts:114-118 (cf. cron-lasttick.test.ts:212-222 honest-failure case). All 7 existing persistence tests still pass — none of them exercised the error-termination path, so the new guard is dead code under the current suite (would be follow-up coverage in a future iteration; deliberately not added here since WR-02's fix scope is the source-side guard, not new test coverage).

### WR-03: Missing test coverage for cron-warm TTL argument and refresh-events `?force=true` Bearer interaction

**Files modified:** `server/__tests__/routes/cron-lasttick.test.ts`
**Commit:** `6c09a04`
**Applied fix:** Two test additions. (1) The cron-warm "both succeed" case now asserts `cacheSetSpy.toHaveBeenCalledWith('cron:lastTick:warm', expect.any(Number), 604_800)` — TTL drift would now fail loudly, mirroring the cron-health and refresh-events-cron cases. (2) New case `'rejects ?force=true with wrong Bearer; runRefreshExtraction NOT called (WR-03)'` sets `mockEnv.CRON_SECRET = 's3cret'`, sends `Authorization: Bearer wrong` with `?force=true`, and asserts status 401 + `runRefreshExtraction` not called + tick not written. Tightens the auth-before-force ordering invariant. Suite went from 6 → 7 cases, all green.

### WR-04: Bearer auth uses string `===` instead of constant-time compare

**Files modified:** `server/routes/cron-health.ts`, `server/routes/refresh-events-cron.ts`
**Commit:** `7a7f71e`
**Applied fix:** Both files now import `timingSafeEqual` from `node:crypto` and replace the plain `if (auth !== expected)` body with the same `Buffer.from` + length-check + `timingSafeEqual` pattern used by `server/middleware/dashboardAuth.ts:55-64` and `server/middleware/rateLimit.ts:81-86`. Length check fires before `timingSafeEqual` per the Node.js contract (the helper throws on mismatched buffer lengths). Length is not the secret, only the bytes are, so an early-exit on length is safe. The asymmetric IN-04 carried-forward issue (cron-warm has no auth gate at all) is deliberately left untouched — it's an info-tier finding out of scope for this fix pass. All existing 401-on-wrong-Bearer test cases continue to pass with the constant-time compare; the WR-03 test added in the prior commit also exercises this gate.
