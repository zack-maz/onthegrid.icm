# Phase 28.2.7: Audit-tier Completeness — Specification

**Created:** 2026-05-07
**Ambiguity score:** 0.0825
**Requirements:** 3 locked

## Goal

Make `prod-connectivity-audit.yml` exit 0 with `allTiersGreen=true` against a healthy prod by writing the missing `cron:lastTick:*` keys, persisting `llm:lastProgress` to Redis (so it survives Vercel cold starts), and fixing `probeProbeOnly()` to mirror `probeSources()`'s honest-stub contract.

## Background

Phase 28.2.6 (PR #12, merged 2026-05-07) cleared the dominant `critical[llmEvents]: unknown` blocker by getting `events:llm:v3` to populate within Vercel's 300s `maxDuration` ceiling via `safeWaitUntil` + incremental terminal-key writes. That fix worked: `/api/health` now reports `critical: 4 healthy / 0 unknown`. But the next prod-connectivity-audit.yml run (https://github.com/zack-maz/onthegrid.icm/actions/runs/25529308448) returned `allTiersGreen: false` because three OTHER tiers — pre-existing latent bugs masked by the higher-priority blocker — are now the dominant signals:

- **`cron` tier** (cronHealth, cronWarm, cronRefreshEvents): all `unknown`. `probeCronTick(name)` reads Redis key `cron:lastTick:<name>` (server/routes/health.ts:186) but **no handler in the codebase ever writes that key** — confirmed via grep: 1 reader, 0 writers. The probe will return `unknown` forever regardless of whether crons actually run.

- **`non-critical[llmStatus]`** (was healthy 30 min after we triggered the cron, now unknown): `probeLlmStatus()` (server/routes/health.ts:127) reads `llmProgress.completedAt ?? llmProgress.startedAt` from an **in-memory singleton** in the Node process. Vercel Fluid Compute reuses instances opportunistically — when `/api/health` requests route to a fresh/different instance from the one that ran the cron, the singleton is `null` and the probe returns `unknown`.

- **`probe-only` tier** (authCheck, geocode): both `unknown`. `probeProbeOnly()` (server/routes/health.ts:167) returns `{ freshnessMs: null, hadError: false }`. Per `deriveStatus(null, 0, false)` (server/lib/healthSources.ts:134) → `'unknown'`. The probe is broken by construction: it never exercises the actual middleware/endpoint AND mathematically can't return `healthy` with its current shape. The contract should mirror `probeSources()` (health.ts:143) — both probes are pure config-introspection with no upstream call to fail, so "always healthy when the process is running" is the correct contract.

Three independent fixes, each <30 LOC, no shared files between them. Phase 28.3 (k6 load test) is blocked on `allTiersGreen=true`, which requires all three.

## Requirements

1. **`cron:lastTick:<name>` writers in all three cron handlers**: Each Vercel cron handler writes its own tick timestamp to Redis on every invocation.
   - Current: 0 writers in codebase. `cron:lastTick:health`, `cron:lastTick:warm`, `cron:lastTick:refresh-events` all unset, so `probeCronTick` reads `null` → `unknown`. Confirmed via `grep "cron:lastTick" server/` returning only the reader at health.ts:186.
   - Target: Each of `server/routes/cron-health.ts`, `server/routes/cron-warm.ts`, and `server/routes/refresh-events-cron.ts` writes `cacheSetSafe(\`cron:lastTick:${name}\`, Date.now(), CRON_LASTTICK_TTL_MS)`at handler start (after Bearer auth, before the actual cron body), where`CRON_LASTTICK_TTL_MS = 7 _ 24 _ 60 \* 60_000` (7 days).
   - Acceptance: After deploy, fire any cron handler manually (e.g. `?force=true`); within 5s, `cacheGetSafe('cron:lastTick:health' | 'cron:lastTick:warm' | 'cron:lastTick:refresh-events', 999_999_999)` returns a number (epoch ms). After firing all three, `/api/health` reports `cron: { healthy: 3, degraded: 0, unhealthy: 0, unknown: 0 }`.

2. **`llm:lastProgress` Redis-backed persistence**: The LLM extractor writes its last-progress timestamp to Redis with each batch flush; `probeLlmStatus()` reads from Redis instead of the in-memory `llmProgress` singleton.
   - Current: `probeLlmStatus()` (health.ts:127) reads `llmProgress.completedAt ?? llmProgress.startedAt` from a module-level singleton. The singleton is reset to `{startedAt:null, completedAt:null}` on cold start. Verified: same prod URL returned `llmStatus: healthy` immediately after the cron, then `llmStatus: unknown` 30 min later when a different function instance served `/api/health`.
   - Target: `llmProgress` writes through to Redis key `llm:lastProgress` on every state change (TTL = `LLM_LASTPROGRESS_TTL_MS = 7 * 24 * 60 * 60_000`). `probeLlmStatus()` reads Redis first, falls back to in-memory singleton if Redis is unavailable. Schema: `{ startedAt: number | null, completedAt: number | null }`.
   - Acceptance: Trigger the cron once. Wait 60s for the function instance to be reused or recycled. Hit `/api/health` until the request lands on a fresh instance (verified by absent in-memory state — could check via x-vercel-id header churn). The fresh instance's response shows `llmStatus.status: healthy` because Redis read succeeds. Specific test: vitest-level test that writes `llm:lastProgress` directly to mock Redis, instantiates a fresh `llmProgress` singleton (no in-memory state), calls `probeLlmStatus()`, and asserts `freshnessMs !== null`.

3. **`probeProbeOnly()` honest-stub reporting**: The probe returns `freshnessMs: 0` (matching `probeSources()`) so `deriveStatus(0, 0, false)` derives to `healthy`.
   - Current: `probeProbeOnly()` (health.ts:167) returns `{ freshnessMs: null, lastSuccessTs: Date.now(), hadError: false, errorReason: null, latencyMs: 0 }`. Plugged into `deriveStatus(null, 0, false)` (healthSources.ts:134) — first guard `if (freshnessMs === null) return 'unknown'` fires, so authCheck + geocode are perma-unknown. The `lastSuccessTs: Date.now()` is set but never consulted because freshnessMs is the discriminant.
   - Target: Change `freshnessMs: null` → `freshnessMs: 0`. With threshold = 0 (per healthSources.ts:79-80), `deriveStatus(0, 0, false)` evaluates `0 <= 0` → returns `'healthy'`. The contract becomes "process is running iff probe is healthy" — same shape as `probeSources()` which is the established canon for config-introspection probes.
   - Acceptance: Vitest unit test asserts `probeProbeOnly()` returns `freshnessMs: 0` AND `deriveStatus(probeProbeOnly().freshnessMs, 0, false) === 'healthy'`. Live: `/api/health` reports `probeOnly: { healthy: 2, unhealthy: 0, unknown: 0 }` (authCheck + geocode both healthy).

## Boundaries

**In scope:**

- 3 cron handlers gain `cacheSetSafe('cron:lastTick:<name>', Date.now(), 7d)` at handler start
- `llmProgress` schema gains write-through to Redis key `llm:lastProgress` (7d TTL); `probeLlmStatus()` reads from Redis with in-memory fallback
- `probeProbeOnly()` shape change: `freshnessMs: null` → `freshnessMs: 0`
- Vitest contract tests for each fix (3 test files, ~5-10 assertions each)
- Unchanged behavior for already-healthy tiers (critical, static, non-critical except llmStatus)

**Out of scope:**

- Synthetic-request exercise of authCheck/geocode middleware — explicitly rejected in spec interview (option (b) honest-stub locked over option (a) middleware exercise; would add ~30 LOC + ~5ms latency per /api/health for marginal failure-mode coverage)
- Cron-route hydration of pipeline override (Phase 999.4 backlog item from 28.2.6 deploy debug) — different bug, different fix; doesn't affect tier-green
- Renaming or restructuring existing Redis keys — Phase 28.1 W7 audit pinned all load-bearing keys; this phase only ADDS new keys
- Migration to a different probe architecture (e.g. push-based instead of pull-based) — premature optimization; current architecture is fine once the 3 latent bugs are fixed
- Runbook for operator-side cron observability dashboards — separate UI concern, not gate-relevant
- Changing the freshness thresholds in `FRESHNESS_THRESHOLDS_MS` — current thresholds are correct; the bug is missing data, not wrong thresholds

## Constraints

- **Single PR per the existing decimal-phase pattern.** Plans 01/02/03 land together so the audit signals collectively flip green in one deploy boundary. Avoids the "fix one tier, audit still red, fix next tier" multi-PR thrash that 28.2.6+28.2.7 already represents.
- **No new env vars.** All TTLs locked in code as named constants (`CRON_LASTTICK_TTL_MS`, `LLM_LASTPROGRESS_TTL_MS`); no operator-tunable surface needed at this scope.
- **`cacheSetSafe` is the only Redis write API.** Matches Phase 27.4.x convention; never use `redis.set` directly.
- **Redis read failures must degrade-open.** Per RESEARCH §Pattern 1 + Phase 28.1 W2 contract: if Redis is unreachable, `probeLlmStatus()` falls back to the in-memory singleton (still `healthy` if same instance ran cron); `probeCronTick()` returns `unknown` (correct — we don't actually know). Never `throw` from a probe.
- **Vitest baseline 2174 passes** must stay green. Each fix lands with new tests that ADD to the count.
- **Vercel Fluid Compute writeUntil semantics** apply to Plan 02's `llm:lastProgress` writes — wrap inline writes in `safeWaitUntil` if they happen post-`res.end()` (likely not the case since these are extractor-internal, but verify).
- **TTL = 7 days** for both new Redis key families (operator-locked). Matches existing `audit:connectivity:last-result` and `operator:audit-log` conventions; comfortable margin over the 26h freshness threshold.
