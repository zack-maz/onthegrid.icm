## Phase Boundary

Phase 28.3 is the **load test** child of the v1.4-closeout umbrella. It runs **third** in the 28.x sequence (D-02): cleanup (28.1) and sync (28.2) have merged, the codebase and prod surface are stable, now validate that production handles 1–300 concurrent users with measurable PASS/FAIL signal.

Scope is exactly two bands of work:

1. **Performance optimization layer** (D-19) — add `s-maxage` CDN headers to `/api/*` responses with per-endpoint TTLs so Vercel CDN absorbs the bulk of reads at 300 VU. Redis fires only on cache miss + warm-up cron path. This is the "client/server relationship improvement" the user asked for.
2. **k6 load test** (D-15 through D-21) — discrete tier sweep at 50/100/150/200/250/300 VU, full-browser-loop polling per VU, PASS/FAIL bar at 300 VU steady-state, four metrics families measured beyond PASS/FAIL.

## Implementation Decisions (filtered from umbrella for 28.3 scope)

### Phase Shape & Sequencing

- **D-01:** Phase 28 split into three child phases. **For 28.3:** depends on 28.2 merged to main; this phase's close = milestone v1.4 close.
- **D-02:** Sequence is **cleanup → sync → load**. **For 28.3:** the load test runs against the cleaner, synced code so the numbers are trustworthy and bisectable.

### Performance Optimization Layer

- **D-19:** **Edge cache + Redis fallback architecture.** Add `s-maxage` CDN headers to `/api/*` responses with per-endpoint TTLs:
  - `/api/flights`: **5s**
  - `/api/ships`: **30s**
  - `/api/markets`: **60s**
  - `/api/events`, `/api/news`: **900s (15 min)**
  - `/api/sites`, `/api/water`: **86400s (24h)**
  - `/api/sources`: TBD during PLAN drafting (Claude's discretion — currently cold; may flip if 28.2's auth changes affect it).

  Vercel CDN absorbs the bulk of reads at 300 VU; Redis only on cache miss + warm-up cron. Trade-off accepted: every VU sees the same edge-cached payload within the s-maxage window — polling parity is automatic.

  **Constraint:** D-19 layer lives ABOVE Redis, never replaces it. The cache-bridge fallback chain (Pitfall 1 in 27.4.x) must continue to function with the new edge layer.

### k6 Load Test Methodology

- **D-15:** **k6 runs from GitHub Actions runner.** Reproducible, free, results land as PR artifacts, easy to gate phase close on a green run. Single-region North America egress accepted. The `scripts/load-test.js` from Phase 21.3 is the starting point. NOT a new cron entry (Hobby cap = 3, already at 3).
- **D-16:** **Discrete tier sweep**: six separate runs at 50 / 100 / 150 / 200 / 250 / 300 VU. Each tier holds 5 minutes steady-state after a 60s ramp. Output: latency-vs-VU curve, breakpoint identification. Total wall-time ~45 minutes per full sweep.
- **D-20:** **Full browser-loop polling per VU.** Each k6 VU runs a "browser session": at t=0 fires site/water/sources/markets/flights/ships/events/news fetches, then polls flights every 5s, ships every 30s, markets every 60s, events every 15min, news every 15min. Mirrors a real multi-tab browser. Roughly 0.27 req/s/VU → ~81 RPS at 300 VU. Replaces Phase 21.3's scenario-split shape.
- **D-21:** **Polling parity automatic from D-20 + D-19.** D-20 ensures all simulated users poll all endpoints; D-19 edge cache ensures all VUs within a given s-maxage window see byte-identical responses. Eliminates the "user A sees stale flights, user B sees fresh" divergence concern.

### PASS/FAIL Bar & Metrics

- **D-17:** **PASS/FAIL bar** (measured at 300 VU steady-state):
  - p95 < 500ms on hot endpoints (`/api/events`, `/api/flights`).
  - p99 < 1500ms.
  - Error rate < 1%.
  - No 5xx spikes.
  - **Cache hit ratio > 90%** — non-negotiable. Validates that Upstash + s-maxage actually absorb the load instead of cascading to upstream.

  All five must pass to close 28.3 (and therefore close v1.4).

- **D-18:** **Metrics measured beyond PASS/FAIL** (all four required):
  - Per-endpoint latency breakdown (p50/p95/p99 per endpoint, tagged in k6).
  - Rate-limit hit count (429 responses) — validates 28.2's D-04 Bearer-bypass landed correctly.
  - Vercel function cold-start frequency (first-request-per-VU latency tracked separately) — validates the warm-up cron sufficiency.
  - Upstash Redis cache hit ratio — read from Upstash dashboard during the run, attached to test artifact.

### Claude's Discretion (for 28.3)

- Specific TTL value for `/api/sources` if D-19 includes it.
- The exact handoff between k6's `setup()` (for once-per-VU init fetches at t=0) and the polling phase loop.

<specifics>
## Specific Ideas

- "Balancing Redis" — operator concern about cache load distribution at 300 VU. Resolved by D-19 edge-cache architecture (Vercel CDN absorbs the bulk; Redis only on miss).
- "Making sure all users are polling everything" — operator concern about data parity across simulated users. Resolved by D-20 full-browser-loop-per-VU + D-19 edge cache.
- The cache-hit threshold (>90%) in D-17 is the most important PASS/FAIL signal — it proves the architecture, not just the throughput.
- The 5-minute steady-state per tier (D-16) is intentional: long enough that warm cache + cold start frequency converge, short enough that the full sweep stays under an hour.
