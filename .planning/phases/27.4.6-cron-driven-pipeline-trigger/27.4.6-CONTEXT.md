# Phase 27.4.6: Cron-Driven Pipeline Trigger — Context

**Gathered:** 2026-04-29 (initial scaffold) → 2026-04-29 (post-/gsd-discuss stress-test)
**Status:** Ready for replanning — D-08..D-11 added, existing 01-PLAN.md needs update
**Source:** 27.4.4 Plan 02 HANDOFF + /gsd-discuss session 2026-04-29

## Phase boundary

Move the LLM enrichment pipeline trigger out of `/api/events` and into a
Vercel cron. Today, the first request to `/api/events` after a cache miss
or 15-min cooldown fires a fire-and-forget extraction that takes ~95 min
at `LLM_V3_CONCURRENCY=1`. That user pays for the cold start. Subsequent
requests get the (eventually) cached result, but the first-user latency
profile is bad.

Goal: `/api/events` becomes a pure cache reader. A new
`/api/cron/refresh-events` route runs the same extraction on a schedule
(server-side, no user request needed). Pipeline stays warm; users always
see the most-recent cached result instantly.

### Falsifiable success bar

1. **Cache-only `/api/events`** — the route NEVER triggers extraction.
   Cache miss returns whatever fallback exists (raw GDELT, in-memory, or
   `{events: [], degraded: true}`). The fire-and-forget block at
   `events.ts:~1019-1130` is deleted.
2. **Cron-driven refresh** — `vercel.json` includes a `/api/cron/refresh-events`
   cron entry. Manual invocation with the `CRON_SECRET` Bearer header
   triggers a full v3 extraction and writes to `events:llm:v3`.
3. **Verified end-to-end on prod** — after merge, a manually-invoked
   cron run produces `events:llm:v3` with non-zero count (when NIM is
   healthy). Subsequent `/api/events` reads serve from cache without
   triggering extraction.
4. **No user-visible regression** — `/api/events` continues to serve
   events (from cache or raw GDELT fallback). Map never goes blank.

## Decisions (locked at scaffold)

### D-01: Cron schedule = once daily at `0 4 * * *` (4am UTC)

- Vercel Hobby plan caps crons at 1/day (surfaced in 27.4.4 HANDOFF as
  anti-pattern #14).
- 4am UTC = 11pm ET / 8pm PT — low-traffic window in user's timezone.
- GDELT updates every 15 min, but a 24h-old conflict event is still
  relevant for the dashboard's audience (numbers-over-narratives).
- If hourly refresh becomes important, the alternative is upgrading to
  Vercel Pro ($20/mo) or adding a self-hosted scheduler. Out of scope
  for this phase.

### D-02: Single dispatch per cron tick — no parallel pipeline runs

- `events:llm-process-ts` Redis key (existing 15-min cooldown) acts as
  a mutex even at 1/day cadence — safer than removing the cooldown.
- If a cron tick fires while a manual extraction is already in flight,
  the cooldown short-circuits the cron and logs `cron_skipped:cooldown`.
  Acceptable.

### D-03: `/api/events?backfill=true` keeps its escape hatch

- The existing query param triggers GDELT backfill (raw events, no LLM).
- This stays as a manual-recovery operator tool — useful when prod
  cache is empty AND the cron hasn't fired yet AND you want immediate
  raw events.
- It does NOT trigger LLM extraction in the new model. LLM is cron-only.

### D-04: Reuse the v3 extraction code path verbatim

- `processEventGroupsV3` + `geocodeEnrichedEventsV3` + cache writes are
  unchanged. The cron route just calls the same fire-and-forget block
  that `/api/events` used to call — extracted into a shared helper.
- Zero re-implementation. Pure refactor.

### D-05: Cron auth via existing `CRON_SECRET`

- Mirrors `/api/cron/eval` and `/api/cron/health` patterns. Vercel
  attaches `Authorization: Bearer ${CRON_SECRET}` to scheduled invocations.
- Manual ops invocations work too — operator runs
  `curl -H "Authorization: Bearer $CRON_SECRET" .../api/cron/refresh-events`.
- CRON_SECRET is already set in both `.env.local` and Vercel prod env.

### D-06: Telemetry preserved

- `llmProgress` singleton stays the same. The cron-fired extraction
  populates `stage`, `completedBatches`, `totalBatches`, `dlqCount`,
  etc. exactly as before. DevApiStatus dashboard works unchanged.
- The cron run shows up in `routingTrace` and call history just like
  a request-fired run did.

### D-07: Rollback strategy

- The cron route is additive. If broken, delete the cron entry from
  `vercel.json` and revert `events.ts` to keep the fire-and-forget path.
- Cron-health folding (D-09) reverts by removing the `runEval()` call
  from the health handler — eval-cron route file is preserved (still
  callable manually) so a vercel.json swap re-enables scheduled eval.
- A dedicated rollback flag (env var) is OUT OF SCOPE — the surface area
  is small enough that a code revert is the appropriate rollback.

### D-08: NIM-throttle at cron time = accept failure, no retry

- When the 4am UTC tick fires while NIM is in throttle (HANDOFF documents
  ~7-min p99 latency, ~24h recovery window), the watchdog kills batches,
  DLQ fills, breaker trips. Cron returns 200 with the failure recorded in
  `llmProgress.dlqCount` + DLQ Redis set.
- `/api/events` continues serving raw GDELT fallback (per Pitfall 1
  graceful-degrade bridge). Map never goes blank.
- Next cron tick is 24h later. If that also fails, operator notices via
  dashboard `llm-status` and triggers manually (see D-11).
- Pre-flight NIM probe + skip + retry-marker patterns are deferred to a
  future phase if multi-day extraction failures become a felt operational
  pain. Don't pre-build it.
- **Why simple wins:** the existing telemetry (DLQ, breaker, llm-status)
  already surfaces the failure mode. Adding pre-flight logic is more code
  to test and maintain for a degenerate case the user can fix in 30 seconds
  with a manual `?force=true` curl.

### D-09: Eval-drift folds into cron-health (frees a slot for refresh-events)

- Hobby plan caps at 3 cron entries. `cron-warm` is NOT vestigial — it
  pre-warms `sites:v2` (3-day TTL, 721 Overpass entries) and
  `water:facilities` (Overpass water adapter); dropping it means cold
  60s+ Overpass fetches every 3 days for the first user. Cannot drop.
- Instead, fold the eval-drift call (`runEval()` from
  `server/lib/llmEvalHarness.ts`) into the existing
  `server/routes/cron-health.ts` GET handler.
- Eval runs daily on cron-health's schedule (`0 0 * * *`), decoupled from
  refresh-events extraction success. If 4am refresh-events fails (D-08),
  eval still runs at midnight UTC the next day.
- The dedicated `server/routes/eval-cron.ts` POST route is preserved for
  manual operator invocation, just removed from `vercel.json`.
- Final `vercel.json` cron entries: `cron-health` (0 0), `cron-warm`
  (0 12), `cron-refresh-events` (0 4) — all once daily, Hobby-compliant.

### D-10: Cron self-heals on cold cache (eliminates first-deploy gap)

- Inside `runRefreshExtraction`, before the cooldown check, probe
  `cacheGetSafe('events:llm:v3', maxAgeSec: very-large)`. If the cache
  is empty (no entry OR entry has zero events), bypass the 15-min cooldown
  and fire the extraction immediately.
- This means the FIRST invocation of the cron route after a fresh deploy
  always produces a populated cache, regardless of when the deploy happened
  relative to the next 4am UTC tick.
- The cron route fires once on first manual operator trigger (Plan Task 5
  Step 2) — that invocation now also serves as the first-deploy heal.
- After cache is populated, subsequent invocations (next 4am UTC tick or
  manual force) honor the normal cooldown.
- **Why this matters:** Plan Task 5's manual curl is operator-discipline.
  This decision makes the cold-start case structurally self-healing —
  if operator forgets the manual curl, the next 4am tick fixes it
  instead of waiting another 24h.

### D-11: Operator force-trigger via `?force=true` query param

- `GET /api/cron/refresh-events?force=true` with valid `Authorization:
Bearer ${CRON_SECRET}` triggers extraction even when the 15-min
  cooldown is active.
- Without `?force=true`, the route honors the cooldown (returns
  `dispatched: false, reason: 'cooldown'`).
- Auth gate is the same `CRON_SECRET` check used for the unflagged path
  — the param is a behavior modifier, not a privilege escalation.
- Adds ~5 LOC to the cron route handler. The existing
  `runRefreshExtraction({forceCooldown: ...})` helper option (Task 1)
  already supports this — just pipe it from the query param.
- Use cases: post-bug-fix re-extraction, post-cache-flush warm-up,
  testing during deploys. Replaces the alternative of `redis-cli del
events:llm-process-ts` (which requires Redis credentials at the
  operator's terminal).

## Anti-patterns (carry-forward + new)

Carrying forward from 27.4.4 HANDOFF anti-patterns 1-16. Specifically
load-bearing for this phase:

- **#13** — don't wrap route registration in `if (NODE_ENV !== 'production')`.
  The new cron route should always register; auth gate handles env diffs.
- **#14** — Vercel Hobby cron 1/day cap is in effect. D-01 picks 4am UTC.
- **#16** — Long-gap deploys surface bundling drift. After this phase
  ships, run `vercel build` locally before pushing if it's been >7 days.

New for 27.4.6:

- **#17 NEW: Don't rely on `/api/events` to trigger extractions.** Once
  the cron is live, the route is cache-only. Anyone reading `events.ts`
  later should NOT add fire-and-forget extraction logic back into the
  read path. The pattern is: cache-read in route, write-trigger in cron.
- **#18 NEW: Cron should respect `events:llm-process-ts` cooldown.** If
  a manual extraction (e.g., operator runs `?backfill=true` then triggers
  a manual LLM run via the dashboard replay endpoint) is already in flight,
  the cron must short-circuit, not stack a parallel run.

## Discussion log (2026-04-29 /gsd-discuss session)

The initial scaffold (D-01..D-07) covered happy-path mechanics. Stress-test
surfaced four outcome-shaping gray areas the scaffold left implicit. Each
discussion below captures the question, alternatives considered, and why
the chosen path won.

### Gray area 1 → D-08 (NIM-throttle at cron time)

**Question:** When the 4am UTC tick lands during NIM's documented 24h
throttle window, the entire daily extraction is wasted. Do we add backoff?
Pre-flight probe? Just accept?

**Alternatives weighed:**

- (A) Accept failure, no retry — chosen
- (B) Pre-flight NIM probe + skip with `dispatched: false, reason: 'nim_unhealthy'`
- (C) Pre-flight probe + write `events:llm-cron-retry-due` Redis key + dashboard badge
- (D) Defer to 27.4.7+ if it becomes felt pain

**Why A:** Existing telemetry (DLQ, breaker, llm-status) already surfaces
the failure. The probe option (B) saves a cooldown slot but doesn't fix the
root cause; operator still has to manually re-trigger. Building the retry
queue (C) is real engineering for a case that resolves in 30s with a manual
`?force=true` curl (now possible per D-11). Choosing simple keeps the cron
mechanism legible.

### Gray area 2 → D-09 (Eval-cron drop)

**Question:** Hobby plan caps at 3 crons. Original plan dropped cron-eval.
Eval-drift then runs only inside refresh-events extraction; if extraction
fails (gray area 1), eval doesn't run. Tight coupling. Acceptable?

**Alternatives weighed:**

- (A) Accept the coupling (original plan)
- (B) Drop cron-warm instead — REJECTED after verifying warm pre-warms
  sites:v2 (3-day TTL) + water:facilities; cold Overpass fetches every
  3 days is unacceptable
- (C) Fold eval into cron-health — chosen
- (D) Upgrade Vercel Pro ($20/mo) — out of scope

**Why C:** Decouples eval from extraction success while preserving the
3-cron budget. cron-health already runs daily with a Redis ping +
freshness check; adding `runEval()` is ~25 lines. Eval drift detection
remains structurally independent of NIM availability.

### Gray area 3 → D-10 (First-deploy gap)

**Question:** After this phase ships, `events:llm:v3` may be empty for
up to 24h until the next 4am tick. Plan Task 5 has a manual curl, but
operator might forget. Harden against forgetting?

**Alternatives weighed:**

- (A) Just document in CLAUDE.md + deploy checklist
- (B) Self-healing first run on /api/events — REJECTED, defeats cache-only purity
- (C) Cron self-heals on cold cache — chosen
- (D) Skip, doc-only

**Why C:** The cron handler is already the canonical entry point for
extractions. Adding "if cache is empty, ignore cooldown and run" is ~10
lines and structurally fixes the cold-start case without leaking
fire-and-forget back into `/api/events`. Operator manual-curl on deploy
becomes belt-and-suspenders rather than mandatory.

### Gray area 4 → D-11 (Ops force-trigger)

**Question:** Plan Task 1 adds `forceCooldown?: boolean` to the helper
but the cron route doesn't expose it. How do operators bypass the 15-min
cooldown after a bug fix or cache flush?

**Alternatives weighed:**

- (A) `?force=true` query param, auth-gated — chosen
- (B) Separate POST endpoint with `DASHBOARD_PASSWORD` (different scope)
- (C) No force surface — operator runs `redis-cli del events:llm-process-ts`
- (D) Use existing `/api/events/llm-replay` endpoint

**Why A:** Cheapest path (~5 LOC). CRON_SECRET already protects the
route. The force semantics is a behavior modifier on the existing
operation, not a different operation — query param is the natural
surface. Option B's auth split is over-engineering for a 1-operator
project. Option C requires Redis credentials at the operator's terminal
(an extra dependency for a routine ops task).
