# Phase 27.4.6: Cron-Driven Pipeline Trigger — Context

**Gathered:** 2026-04-29
**Status:** Ready for planning
**Source:** 27.4.4 Plan 02 HANDOFF (cutover-live state surfaced this as the natural next step)

## Phase boundary

Move the LLM enrichment pipeline trigger out of `/api/events` and into a
Vercel cron. Today, the first request to `/api/events` after a cache miss
or 15-min cooldown fires a fire-and-forget extraction that takes ~95 min
at `LLM_V3_CONCURRENCY=1`. That user pays for the cold start. Subsequent
requests get the (eventually) cached result, but the first-user latency
profile is bad.

Goal: `/api/events` becomes a pure cache reader. A new
`/api/cron/refresh-events` route runs the same extraction on a schedule
(server-side, no user request needed). Pipeline stays warm; users always
see the most-recent cached result instantly.

### Falsifiable success bar

1. **Cache-only `/api/events`** — the route NEVER triggers extraction.
   Cache miss returns whatever fallback exists (raw GDELT, in-memory, or
   `{events: [], degraded: true}`). The fire-and-forget block at
   `events.ts:~1019-1130` is deleted.
2. **Cron-driven refresh** — `vercel.json` includes a `/api/cron/refresh-events`
   cron entry. Manual invocation with the `CRON_SECRET` Bearer header
   triggers a full v3 extraction and writes to `events:llm:v3`.
3. **Verified end-to-end on prod** — after merge, a manually-invoked
   cron run produces `events:llm:v3` with non-zero count (when NIM is
   healthy). Subsequent `/api/events` reads serve from cache without
   triggering extraction.
4. **No user-visible regression** — `/api/events` continues to serve
   events (from cache or raw GDELT fallback). Map never goes blank.

## Decisions (locked at scaffold)

### D-01: Cron schedule = once daily at `0 4 * * *` (4am UTC)

- Vercel Hobby plan caps crons at 1/day (surfaced in 27.4.4 HANDOFF as
  anti-pattern #14).
- 4am UTC = 11pm ET / 8pm PT — low-traffic window in user's timezone.
- GDELT updates every 15 min, but a 24h-old conflict event is still
  relevant for the dashboard's audience (numbers-over-narratives).
- If hourly refresh becomes important, the alternative is upgrading to
  Vercel Pro ($20/mo) or adding a self-hosted scheduler. Out of scope
  for this phase.

### D-02: Single dispatch per cron tick — no parallel pipeline runs

- `events:llm-process-ts` Redis key (existing 15-min cooldown) acts as
  a mutex even at 1/day cadence — safer than removing the cooldown.
- If a cron tick fires while a manual extraction is already in flight,
  the cooldown short-circuits the cron and logs `cron_skipped:cooldown`.
  Acceptable.

### D-03: `/api/events?backfill=true` keeps its escape hatch

- The existing query param triggers GDELT backfill (raw events, no LLM).
- This stays as a manual-recovery operator tool — useful when prod
  cache is empty AND the cron hasn't fired yet AND you want immediate
  raw events.
- It does NOT trigger LLM extraction in the new model. LLM is cron-only.

### D-04: Reuse the v3 extraction code path verbatim

- `processEventGroupsV3` + `geocodeEnrichedEventsV3` + cache writes are
  unchanged. The cron route just calls the same fire-and-forget block
  that `/api/events` used to call — extracted into a shared helper.
- Zero re-implementation. Pure refactor.

### D-05: Cron auth via existing `CRON_SECRET`

- Mirrors `/api/cron/eval` and `/api/cron/health` patterns. Vercel
  attaches `Authorization: Bearer ${CRON_SECRET}` to scheduled invocations.
- Manual ops invocations work too — operator runs
  `curl -H "Authorization: Bearer $CRON_SECRET" .../api/cron/refresh-events`.
- CRON_SECRET is already set in both `.env.local` and Vercel prod env.

### D-06: Telemetry preserved

- `llmProgress` singleton stays the same. The cron-fired extraction
  populates `stage`, `completedBatches`, `totalBatches`, `dlqCount`,
  etc. exactly as before. DevApiStatus dashboard works unchanged.
- The cron run shows up in `routingTrace` and call history just like
  a request-fired run did.

### D-07: Rollback strategy

- The cron route is additive. If broken, delete the cron entry from
  `vercel.json` and revert `events.ts` to keep the fire-and-forget path.
- A dedicated rollback flag (env var) is OUT OF SCOPE — the surface area
  is small enough that a code revert is the appropriate rollback.

## Anti-patterns (carry-forward + new)

Carrying forward from 27.4.4 HANDOFF anti-patterns 1-16. Specifically
load-bearing for this phase:

- **#13** — don't wrap route registration in `if (NODE_ENV !== 'production')`.
  The new cron route should always register; auth gate handles env diffs.
- **#14** — Vercel Hobby cron 1/day cap is in effect. D-01 picks 4am UTC.
- **#16** — Long-gap deploys surface bundling drift. After this phase
  ships, run `vercel build` locally before pushing if it's been >7 days.

New for 27.4.6:

- **#17 NEW: Don't rely on `/api/events` to trigger extractions.** Once
  the cron is live, the route is cache-only. Anyone reading `events.ts`
  later should NOT add fire-and-forget extraction logic back into the
  read path. The pattern is: cache-read in route, write-trigger in cron.
- **#18 NEW: Cron should respect `events:llm-process-ts` cooldown.** If
  a manual extraction (e.g., operator runs `?backfill=true` then triggers
  a manual LLM run via the dashboard replay endpoint) is already in flight,
  the cron must short-circuit, not stack a parallel run.
