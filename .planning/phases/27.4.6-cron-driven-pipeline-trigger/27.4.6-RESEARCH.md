## Existing fire-and-forget block to delete

`server/routes/events.ts:~1019-1130` (line numbers approximate — verify
during implementation). The block lives inside the `/api/events` GET
handler and looks like:

```ts
// 15-min cooldown via events:llm-process-ts
const lastProcessTs = await cacheGetSafe('events:llm-process-ts', ...);
if (!lastProcessTs || Date.now() - lastProcessTs > 15 * 60_000) {
  // fire-and-forget — does not block the response
  void (async () => {
    await cacheSetSafe('events:llm-process-ts', Date.now(), ...);
    const groups = groupGdeltRows(rawCache.data);
    const extraction = await processEventGroupsV3(groups);
    if (extraction.events) {
      const geocoded = await geocodeEnrichedEvents(extraction);
      // ... cache write to events:llm:v3
    }
  })();
}
```

The block must be EXTRACTED, not deleted — both the new cron route and
(maybe) the dev-only manual-replay path will call it.

## Existing cron patterns to mirror

Three crons already in `vercel.json`:

```json
{ "path": "/api/cron/health", "schedule": "0 0 * * *" },
{ "path": "/api/cron/warm", "schedule": "0 12 * * *" },
{ "path": "/api/cron/eval", "schedule": "0 4 * * *" }
```

But Hobby plan caps at 1/day per cron. We have 3 already. **Adding a 4th
will fail the deploy** with the same error 27.4.4 HANDOFF saw on the
initial cutover push.

### Options

**A. Inline cron-warm + cron-eval into refresh-events** — single cron
runs the warm + eval + extraction sequence at 4am UTC. Loses
independent scheduling control but stays under the cap.

**B. Replace cron-eval with refresh-events** — eval runs as a
post-extraction step inside refresh-events anyway (per 27.4 Plan 08
D-20 the eval harness fires resolver-only after geocoding). The
existing cron-eval route becomes redundant.

**C. Stay at 3 crons, drop one of the existing** — least disruptive.
Choose between cron-health (just pings), cron-warm (pre-warms LLM
client), cron-eval (runs runEval).

**Recommended: B.** The eval harness is already wired into the
extraction pipeline (server/routes/events.ts fire-and-forget block runs
runEval after geocodeEnrichedEvents). Promoting the extraction itself
to a cron means eval fires automatically.

`vercel.json` becomes:

```json
{ "path": "/api/cron/health", "schedule": "0 0 * * *" },
{ "path": "/api/cron/warm", "schedule": "0 12 * * *" },
{ "path": "/api/cron/refresh-events", "schedule": "0 4 * * *" }
```

(Drops eval-cron entry. The eval-cron Express route can stay registered
for manual invocation but won't have a schedule.)

## Cooldown interaction (D-02)

`events:llm-process-ts` Redis key currently:

- Set at the start of each fire-and-forget extraction
- Checked at the start to prevent re-entry within 15 min

After the cron promotion:

- Cron runs at 4am UTC. Sets the timestamp.
- If an operator manually triggers a replay extraction at 4:05am via the
  dashboard, the 15-min cooldown blocks it. Operator sees a "cooldown
  active" log.
- Acceptable — cooldown is the existing behavior.

If the operator wants a forced re-extraction, the explicit path is:

1. Delete `events:llm-process-ts` via `clear-llm-cache-dev.ts` (dev) or
   a small ops helper (prod) — TBD.
2. Re-trigger.

A `?force=true` cron query param could bypass the cooldown for emergency
re-runs. Out of scope for this phase but worth noting as a follow-up.

## Test surface

New file: `server/__tests__/routes/refresh-events-cron.test.ts`. Three
test cases:

1. **Without `Authorization: Bearer`** — returns 401.
2. **With wrong Bearer** — returns 401.
3. **With correct Bearer + cooldown elapsed** — fires extraction, returns
   200 with `{ ok: true, dispatched: true }`.
4. **With correct Bearer + cooldown active** — short-circuits, returns
   200 with `{ ok: true, dispatched: false, reason: 'cooldown' }`.
5. **With CRON_SECRET unset** — returns 503 (matches eval-cron pattern).

Existing tests for `/api/events` stay unchanged — the cache-read path
is untouched. The fire-and-forget block being deleted is currently NOT
asserted by any test (it's all integration-level and skipped under test
mode), so removing it has no test-side cost.

## Risks

1. **Eval harness removal from cron-eval may surprise an existing watcher.**
   Anyone monitoring the `events:llm-eval-baseline:v3` key for daily
   updates will still see them — eval still fires inside refresh-events.
   But the cron tick TIMING shifts from "midnight UTC" to "4am UTC".
   Worth noting in CLAUDE.md.

2. **Cooldown can cause silent skips.** If a manual extraction lands at
   3:50am UTC and the cron tick fires at 4:00am, the cron skips with
   `cooldown:active`. The dashboard shows no fresh data until the next
   tick (24h later). Mitigation: log clearly + add `lastCronRunAt` to
   `llmProgress` so the dashboard surfaces the skip.

3. **First-deploy gap.** Between deploying this phase and the first 4am
   UTC tick, the cache may not refresh. Mitigation: run a manual
   extraction immediately after deploy via the cron URL with the Bearer
   header. Add this step to the resumption recipe.
