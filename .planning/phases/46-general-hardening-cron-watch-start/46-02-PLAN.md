<objective>
HARD-02 server tier: add cron first-tick + missed-run detection to `/api/health` (999.3) without an external SaaS and without widening the health status enum. Three deliverables: (1) a hardcoded `CRON_SCHEDULE_GRACE_MS` table in `healthSources.ts` (3 crons, each `{expectedIntervalMs, graceMs}`) mirroring `FRESHNESS_THRESHOLDS_MS` (per D-04); (2) a pure `deriveCronRunState` helper returning `'unknown' | 'missed' | 'healthy'` layered ON TOP of the unchanged 4-state `deriveStatus` ladder (per D-06); (3) a `missedRun` SIBLING field on the cron endpoint rows of the `/api/health` response + matching `.optional()` schema — surfacing the D-05 three-state semantics (`unknown` = pre-first-tick, `missed` = null OR stale past `expected+grace` after first fire, `healthy` = within grace) via /api/health.

THE LOAD-BEARING INVARIANT (RESEARCH Landmine 1/2, Pitfall 1): `missed` is NEVER a value in the 4-member `healthStatusEnum`. It is a sibling field. `prod-connectivity-audit.yml:208` hardcodes `okCron = ["healthy","degraded"].includes(tierStatus.cron)` — a `missed` status on the cron tier would flip `allTiersGreen=false` and regress the LLM-RELI-07 milestone-close acceptance gate. The audit never reads the sibling field. A task that edits `healthStatusEnum`, `tierRollupSchema`, or `deriveStatus`'s return type is WRONG.

Purpose: distinguish "never fired yet" (unknown) from "fired before but now silently stopped" (missed) — the actual missed-run signal 999.3 asks for; Phase 47's load test reads this to confirm crons survived load.
Output: schedule+grace table + deriveCronRunState + missedRun sibling field + schema (.optional()) + tests pinning the audit-gate safety.
</objective>
