## Decisions Made

- **Stay at "critical" tier for llmEvents.** Per RESEARCH Open Question 1 + CONTEXT Deferred Ideas: introducing a `'critical-llm'` sub-tier would require a Zod schema bump in `healthSchema.ts` (the `healthTierEnum` currently has 5 values) AND a `buildSummary()` refactor in `server/routes/health.ts` (the summary aggregator hard-codes the 5 known tiers). The current implementation gives the operator the right signal (gate flags fallback) without that overhead. If a future operator-driven need surfaces (e.g., wanting the LLM tier to NOT trigger HealthBanner toast separately from the raw events tier), the sub-tier can be added then.
- **IIFE inside the rows[] array literal (not a top-level helper) for Events (LLM).** Same rationale as Plan 01: the projection is consumed once, the existing Events row uses an inline shape that diverges from the `...spread` pattern without going through a helper, and a top-level helper would need to thread `aggregateHealth + eventQuality` through props. The IIFE is consistent with the file's existing style.
- **Counts (eventQuality.llmCount) stay store-sourced; only freshness comes from health-aggregate.** Same model as Plan 01's Precip row: counts describe content quality, not freshness. Health-derived fields (status / lastSuccessTs / lastErrorReason) describe the cache key's freshness; the count of LLM events visible to the user is a content metric served independently from the eventStore.
- **Tests 11/12 adapted to the rendered-row pattern.** The plan's literal `screen.getByText('Events (raw)')` / `screen.getByText('Events (LLM)')` matchers would have failed because the rows[] array is no longer DOM-rendered (Polling Stores section deleted in `cc3b388`, 2026-05-06 — see Plan 01 Deviation #1). Adapted to assert the rendered API Health table rows (`data-testid="all-apis-row-/api/events"` + `data-testid="all-apis-row-events:llm:v3"`), which is the operator-visible signal of the split. Source-level verification of the `'Events (raw)'` / `'Events (LLM)'` literals happens via grep in the verification phase per the acceptance criteria. The plan's `<behavior>` intent is preserved: both rows visible, with the LLM row reflecting fallback when v3 is cold.
- **Test 4 made regression-resilient.** The prior `expect(c.healthy + c.degraded + c.unhealthy + c.unknown).toBe(3)` was hard-coded against the original 3 critical-tier endpoints (flights/ships/events). Plan 02 adds `llmEvents` as the 4th, breaking the assertion. Updated to derive the count from `TIER_BY_ENDPOINT.filter(t === 'critical').length` so future critical-tier additions don't need to touch this assertion.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Blocking] Test 4 in health.test.ts was hard-coded to assert critical-tier sum === 3, breaking when llmEvents was added as the 4th critical entry**

- **Found during:** Task 2 GREEN — Test 4 failed with `expected 4 to be 3` after PROBE_STRATEGIES.llmEvents was wired and the response started carrying the new endpoint.
- **Issue:** The test's intent was "every critical-tier endpoint shows up in summary.critical". Hard-coding the count to 3 made it brittle: the moment a new critical-tier endpoint is added (which Plan 02 D-06 intentionally does), the test fails despite the contract being met.
- **Fix:** Derive the expected count from `TIER_BY_ENDPOINT.filter(t === 'critical').length` so the test stays green for any future critical-tier addition while still asserting that the summary aggregator counts every critical endpoint that ran a probe.
- **Files modified:** `server/__tests__/routes/health.test.ts` (Test 4 body — derive count instead of hard-coding 3; new assertion `expectedCriticalCount`)
- **Verification:** All 11 tests in the route suite pass; Test 4 itself passes against the new contract; Tests 1/2/3/5a/5b/5c/6/7/8 also pass.
- **Committed in:** `0bf3efc` (Task 2 commit, alongside the PROBE_STRATEGIES.llmEvents wiring that triggered the Test 4 break)

**2. [Rule 3 — Blocking] Test 11/12 literal `screen.getByText('Events (raw)' / 'Events (LLM)')` matchers would have failed because the rows[] array is no longer DOM-rendered**
