## Phase Boundary

Two-band scope, both required for phase close:

**Band A — three named code/wiring fixes** (the operator's reported symptoms):

1. **LLM events monitoring gap** — `events:llm:v3` is not in `SOURCE_KEYS` (`server/lib/healthSources.ts:34-47`). API Health tab cannot tell an operator whether `/api/events` is serving enriched LLM-extracted events or has bridged to raw GDELT fallback (`server/routes/events.ts:701-731`). Fix: add to registry + new dedicated row in DevApiStatus.
2. **Weather tooltip precipitation coverage** — `WeatherOverlay.tsx:77-93` `findNearestPrecip()` uses a 2° (~200km) Manhattan cutoff against `waterStore.rawPrecipData`. Wide swaths of the Iran bbox sit outside any sample's catchment so the precip block of the tooltip silently empties. Fix: widen cutoff + show distance hint in tooltip; verify hydration runs even when only the Weather layer (not Water) is toggled on.
3. **Precipitation in API dashboard** — `waterPrecip` is in `FRESHNESS_THRESHOLDS_MS` (line 69) and `TIER_BY_ENDPOINT` (line 96) but missing from `SOURCE_KEYS` (line 34-47). The DevApiStatus `Precip` row reads from `waterStore` selectors instead of `/api/health` aggregate, so it can't surface freshness drift the way other endpoints do. Fix: add to `SOURCE_KEYS`, switch the row to consume from `/api/health`.

**Band B — "all tiers green" gate that 28.3 depends on.** Define and prove a green-light bar against PROD using the existing 28.2 W6 audit workflow as the evidence mechanism. 28.3 PR cannot merge until the most recent run of the workflow shows all-green per the bar in D-03.

**Out of scope for 28.2.5:**

- Edge cache layer / `s-maxage` headers — that's 28.3 D-19. Don't pre-stage it here.
- k6 load test — that's 28.3 D-15/16/20.
- Bilinear interpolation across the precip raster (Band A item 2 alternative) — explicitly deferred per D-05.
- LLM eval-baseline freshness as a quality gate — explicitly deferred per D-06.
- Rewriting any data adapter (open-meteo, GDELT, ADS-B). All three Band-A symptoms are wiring/registry, not adapter bugs.
- Changes to the cron schedule (Hobby cap = 3, untouched).
- Continuous baseline tracking (already deferred at the umbrella level).

**Branch discipline:** Own feature branch (`feature/28.2.5-api-green-gate` per `feedback_branch_per_phase.md`). Close = merge to main. After merge, 28.3 is unblocked.

## Implementation Decisions

### Phase Shape & Sequencing

- **D-01:** Phase 28.2.5 is inserted between 28.2 (complete 2026-05-06) and 28.3 (not yet started). It blocks 28.3.
  - **Why:** The operator surfaced three symptoms ("LLM pipeline isn't visibly producing events", "weather tooltip drops precip at most x,y", "precip not surfaced in API dashboard") that — combined — mean a 1–300 VU load test against the current prod surface would measure latency on a half-broken data path. The numbers wouldn't bisect cleanly back to the load. Better to land a green snapshot first.
  - **How to apply:** ROADMAP.md gets a new `### Phase 28.2.5:` entry between 28.2 and 28.3. Phase 28.3's `Depends on:` line gets `Phase 28.2.5` appended. Umbrella 28-CONTEXT.md sequence note (D-02) extends from "cleanup → sync → load" to "cleanup → sync → green-gate → load".

- **D-02:** Hybrid scope (Band A + Band B). NOT a pure-fix phase, NOT a pure-gate phase.
  - **Why:** A pure-fix phase wouldn't prevent regression on the 50+ other endpoints that could quietly drift before 28.3. A pure-gate phase would land a tooling improvement without addressing the three symptoms the operator already reported. Hybrid keeps both honest.
  - **How to apply:** Plan splits into Band A (per-fix atomic commits) and Band B (gate definition + workflow extension + evidence in PR). Both must be green before close.

### Green-Light Definition (Band B)

- **D-03:** Tiered green bar — critical-tier MUST be `'healthy'`, non-critical/static MAY be `'degraded'`, probe-only MUST return 200, cron MUST be within 26h.
  - The five tier groups come straight from `server/lib/healthSources.ts` `TIER_BY_ENDPOINT` (lines 87-106). No new tiers introduced.
  - Concrete pass map at gate-check time:
    - `critical`: `flights`, `ships`, `events` → status === `'healthy'` (within freshness threshold)
    - `non-critical`: `markets`, `news`, `weather`, `waterPrecip`, `sources`, `llmStatus` → status ∈ {`'healthy'`, `'degraded'`}
    - `static`: `sites`, `water` → status ∈ {`'healthy'`, `'degraded'`} (48h thresholds already lenient)
    - `probe-only`: `authCheck`, `geocode` → 200 OK
    - `cron`: `cronHealth`, `cronWarm`, `cronRefreshEvents` → freshness ≤ 26h (covers daily-cron skew)
  - **Why:** Critical-tier strictness protects the load-test signal (those are the endpoints under highest VU pressure). Non-critical leniency reflects prod realities (Yahoo Finance returns stale on weekends; Cerebras NIM occasionally throttles). Two rules to remember; the planner can encode this as a JSON manifest the workflow consumes.
  - **How to apply:** Implementation lives in the W6 workflow extension (D-09) — a new step parses `/api/health` JSON and asserts the tier map above. Single source of truth; the bar is data, not code-duplicated logic.

- **D-04:** Gate verification = `/api/health` JSON response AND DevApiStatus row matches the JSON state.
  - **Why:** D-03 alone catches transport-layer health but misses wiring drift between the server response and the dashboard rendering — which is exactly the failure mode that lets all three Band-A symptoms exist today. Layering the dashboard match catches future drift.
  - **How to apply:** PR description for 28.2.5 includes (a) workflow run link showing tier-green assertion passed, (b) operator screenshot of API Health tab matching the JSON state. The screenshot is manual; the JSON assertion is mechanical.

### Weather Tooltip Fix Path (Band A item 2)

- **D-05:** Widen `findNearestPrecip` cutoff AND surface a "nearest sample, X km away" hint in the tooltip.
  - Current: 2° Manhattan distance (~200km) cutoff at `WeatherOverlay.tsx:77-93`.
  - Target: widen to ~4° (~400km) so every Iran-bbox position resolves a hit. The widening is a behavior tradeoff (showing a more distant sample = lower spatial precision), so the tooltip MUST disclose the distance to the user. Format suggestion: `"30-day: 12 mm — nearest sample 320 km away"` when distance > existing-tight-cutoff, plain `"30-day: 12 mm"` when within ~100km.
  - Hydration verification is implicit: the planner MUST confirm `useWaterPrecipPolling` fires on AppShell mount regardless of water-layer toggle (the precip data has to exist for the widened cutoff to find anything). This is a quick read of `src/components/layout/AppShell.tsx` + `src/hooks/useWaterPrecipPolling.ts`.
  - **Why:** The user picked widening + UI honesty over verify-only because verify-only depends on `useWaterPrecipPolling` already being wired correctly (which we expect but haven't confirmed) AND on the 2° cutoff being satisfiable from sparse data. Belt-and-suspenders is wasted scope; widening + distance hint addresses the user-visible symptom directly.
  - **How to apply:** Single commit per Band-A pattern. Files touched: `WeatherOverlay.tsx` (cutoff + format string), maybe `findNearestPrecip` returns `{ value, distanceKm }` instead of bare value. Hydration verification is a planner check, not a code change unless the verification fails.

### LLM Pipeline Gate (Band A item 1 + Band B integration)

- **D-06:** Visible + populated. Add `events:llm:v3` to `SOURCE_KEYS` with a 26h freshness threshold; require status ∈ {`'healthy'`, `'degraded'`} at gate-check time. If empty at gate-check, run `GET /api/cron/refresh-events?force=true` (Bearer-gated, exists per Phase 27.4.6) and wait for it to land before merging.
  - **Why:** Visible-only would let 28.3 launch on top of pure-fallback (raw-GDELT-only) data, which defeats the whole point of having an LLM pipeline. Eval-baseline-fresh (the third option) is overkill for a load-test prereq — extraction quality is a separate quality-gate phase, deferred (see Deferred Ideas).
  - 26h threshold reasoning: cron is daily at 4am UTC; 24h would race the cron skew, 26h gives 2h buffer. Matches the existing `cronHealth` / `cronWarm` / `cronRefreshEvents` thresholds for symmetry.
  - **How to apply:** Three discrete edits in `healthSources.ts`: add `llmEvents: 'events:llm:v3'` to `SOURCE_KEYS`, `llmEvents: 26 * 60 * 60_000` to `FRESHNESS_THRESHOLDS_MS`, `llmEvents: 'critical'` to `TIER_BY_ENDPOINT`. (Tier = critical because D-06's "must be populated" promotes it from observability-only to gate-relevant.) Force-trigger logic lives in the workflow (D-09), not in the route — the route already supports `?force=true`.

- **D-07:** API Health tab distinguishes enriched-vs-fallback via TWO rows: `Events (raw)` (probes `events:gdelt`) and `Events (LLM)` (probes the new `events:llm:v3` SOURCE_KEYS entry from D-06).
  - **Why:** Single-row-with-badge looked denser but obscures the cache-bridge state when both keys are warm. Two rows give the operator a one-glance read: "raw=healthy + LLM=healthy" = enriched, "raw=healthy + LLM=unknown" = fallback active. Matches the existing pattern in DevApiStatus where related concerns get sibling rows.
  - **How to apply:** The existing `Events` row in `DevApiStatus.tsx` keeps its label but renames internally to `Events (raw)`. New `Events (LLM)` row sits directly below it. Both consume from the `/api/health` aggregate response via the existing per-endpoint indexing — no new wiring beyond the row definition.

### Precipitation Registry Fix (Band A item 3)

- **D-08:** Add `waterPrecip: 'water:precip'` to `SOURCE_KEYS` (line 46-47 of `healthSources.ts`); switch the DevApiStatus `Precip` row from `waterStore` selectors to `/api/health` aggregate consumption.
  - **Why:** `waterPrecip` already has a `FRESHNESS_THRESHOLDS_MS` entry (line 69, 12h) and a `TIER_BY_ENDPOINT` entry (line 96, non-critical) — it's literally the only one in the registry that lacks the `SOURCE_KEYS` line. The omission is doc/wiring drift from when the W2 health system was built. The DevApiStatus row falling back to `waterStore` selectors is the visible symptom.
  - **How to apply:** Single line in `healthSources.ts` (the `// DRIFT-N` comment style established in W2 should be reused: `// DRIFT-4: waterPrecip was in thresholds + tier but missing from SOURCE_KEYS — operator-reported in 28.2.5.`). DevApiStatus row update is small — switch from `useWaterStore(s => s.precipMatched)` etc. to consuming the same `health.waterPrecip` field every other row uses.

### Evidence Mechanism (Band B)

- **D-09:** Extend `.github/workflows/prod-connectivity-audit.yml` (built in 28.2 W6) with a new step that fetches `/api/health` and asserts the D-03 tier-green bar. Workflow fails LOUDLY if any critical=unhealthy or non-critical=unhealthy.
  - The existing sidecar `audit:connectivity:last-result` Redis key (7d TTL) absorbs the new assertion result without schema change — the JSON shape just gains an `allTiersGreen: boolean` field plus `tierStatus: { critical: 'healthy', ... }`. Pinned by the existing W-3 contract test in `server/routes/__tests__/audit-status.test.ts` (planner extends the test).
  - The merged API Health tab's audit-result banner picks up the new field automatically once the schema bumps; no new UI surface.
  - **Why:** Reuses 28.2 W6 infrastructure verbatim instead of building a parallel mechanism. The workflow already runs against PROD with a Bearer secret and writes a sidecar that the dashboard reads — that's exactly what this gate needs. Re-runnable from the GitHub Actions UI before 28.3 merge means an operator can re-prove green at any moment.
  - **How to apply:** New step in the existing YAML workflow. New JSON field in audit-status response shape (existing test enforces). Audit doc location: `.planning/phases/28.2.5-api-green-gate/28.2.5-W{N}-AUDIT.md` if waves materialize.

- **D-10:** Gate target = PROD only. Dev-side verification of the three Band-A fixes is by normal vitest + manual smoke; the "all tiers green" gate runs against `otg-iran-monitor.vercel.app` only.
  - **Why:** 28.3 load-tests prod, so the gate that unblocks 28.3 must measure prod. Dev's lower-fidelity data (no live ADS-B credentials, possibly missing Bearer) would produce false fails on static-tier endpoints and false passes elsewhere. Cleanest split: dev for unit-level evidence (the 3 fixes work in code), prod for integration-level evidence (the gate is satisfied).
  - **How to apply:** Workflow trigger stays as `workflow_dispatch` (manual). Operator runs it once before opening the 28.2.5 PR (proves the fixes landed in prod), once again right before 28.3 merge (proves the gate held). Both runs link in their respective PRs.

### Claude's Discretion

- The audit JSON schema extension shape — whether `allTiersGreen` is a top-level boolean, a nested `tiers: { allGreen, byTier }` object, or both (D-09 leaves room).
