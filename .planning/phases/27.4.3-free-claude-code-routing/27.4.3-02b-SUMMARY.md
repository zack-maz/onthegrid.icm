## B-2 lineage evidence (sample expectations after a v3 run)

```bash
$ redis-cli HGETALL events:llm:v3:lineage:llm-v3-2026-04-26_iran_tabriz
1) "prompt"          -> "<full SYSTEM_PROMPT_V3 + userPrompt>" (capped 32k)
2) "response"        -> "<JSON content from freeClaudeRouter>" (capped 32k)
3) "parsed"          -> "<stringified Zod-validated event>" (capped 32k)

5) "provenance"      -> "gdelt-actiongeo-fallback"
6) "resolverPath"    -> "pre-resolve"
```

## Decisions Made

See frontmatter `key-decisions` for the full set. Highlights:

1. **Lineage timing** — Captured at extract-time (post-Zod-validation, pre-resolver) with placeholder coord + 'pre-resolve' resolverPath. Plan literal text said "after per-event resolve" but the LLM-decision lineage is COMPLETE at extract; the resolver is a separately-observable downstream step.
2. **enrichedV3ToEntities** — Created as sibling of enrichedV2ToEntities rather than parameterizing. Risk-isolates the v3 cutover; future v3-specific data fields won't regress v2 rendering.
3. **3-way pipeline dispatch** — Replaced `isPipelineV2()` boolean with `getPipelineVersion()` returning `'v1'|'v2'|'v3'` discriminator. Single source of truth, no helper drift.
4. **onSoftWarn callHistory shape** — Fixed the previous executor's draft which used `ts:` instead of `timestamp:` and missed `durationMs/ok/batchSize`. Now matches the LLMPipelineProgress.callHistory element type exactly.
5. **Eval harness model arg** — Sanitizes `/` → `_` so OpenRouter-style ids (`moonshotai/kimi-k2.5`) produce conventional single-segment Redis keys.
6. **Test 11 update** — Tracked as Rule 1 deviation: the existing test asserted the v2 baseline key which the plan's Task 6 explicitly bumps to v3. Test had to flip in lockstep with the production code change.
