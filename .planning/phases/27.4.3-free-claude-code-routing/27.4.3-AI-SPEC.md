## 1. System Classification

**System Type:** Extraction (structured event-attribute extraction from GDELT raw rows + few-shot reasoning over Bellingcat / news / temporal context)

**Description:**
The v3 enrichment pipeline ingests raw GDELT v2 rows (CAMEO-coded conflict events scraped from global news every 15 minutes), groups them by date + CAMEO root + 50km proximity, and routes each group through a free-tier LLM (NVIDIA NIM primary, OpenRouter fallback) to extract structured fields: refined event type (5-value ontology — `airstrike` / `on_ground` / `explosion` / `targeted` / `other`), normalized location hierarchy (country / admin1 / city / neighborhood / landmark + confidence), casualty estimates, actor identification, and a one-paragraph reasoning trace. A 6-path resolver (own-site-snapshot, POI-amenity Nominatim, Nominatim direct, Nominatim 2-pass verified, GDELT ActionGeo fallback, Bellingcat coord passthrough) then converts the LLM-emitted hierarchy into a coordinate with provenance, never accepting LLM-emitted lat/lng directly. The user is the single operator running an Iran-conflict OSINT dashboard for personal intelligence; "good" means a `runEval()` resolver-only score of ≥0.890 within20km on the locked 50-event ground-truth corpus (= 27.4.2 baseline 0.940 minus 5pp tolerance), zero watchdog timeouts on a 184-batch production run, and DLQ ≤ 5 entries.

**Critical Failure Modes:**

1. **Hallucinated coordinates** — LLM emits a lat/lng that doesn't match the GDELT row's ActionGeo bounding region, or the resolver returns a coord with a misclassified provenance bucket (one of 6 enums). Drops events on the wrong city / wrong country, breaking the auditability narrative ("why did this event get coord X?") that the Palantir-grade DevApiStatus is designed to answer.
2. **Schema rejection cascade** — non-strict-mode LLM (NVIDIA NIM / OpenRouter free models) emits malformed JSON or violates the Zod `enrichedEventAny` v3 contract. With v3 dropping OpenAI strict-JSON-Schema mode (D-10), the entire batch can be rejected post-parse, leaving GDELT rows un-enriched for that wave. Tracked as observability metric (D-12 block 4).
3. **Watchdog hang with late resolve** — provider stalls past the 90s hard kill; if AbortController + generation-counter guard from 27.4.1 D-09 isn't preserved verbatim, a late resolve clobbers `events:llm:v3` cache with stale data. The two-key discipline (`events:llm:v3` terminal vs `events:llm:v3:partial` observability-only) is non-negotiable.
4. **Provider-cap exhaustion with silent fall-through** — NVIDIA NIM 429s past backoff retries + OpenRouter daily exhaust simultaneously. Cascade falls through to raw GDELT (the graceful-degradation contract from 27.4 D-29) without operator visibility. The Rate-Limit Headroom Gauge (D-12 block 3) and Routing Trace block (D-12 block 1) must surface this before it becomes a silent map-quality regression.
5. **Severity-weighted error compounding** — an `airstrike` (typeWeight 10) hallucinated to a wrong city has 3.3× the dashboard impact of a misclassified `other` event (typeWeight 3). Eval gate 0.890 within20km is corpus-wide; a model that scores 0.890 by acing low-severity events but missing airstrikes ships an unacceptably bad system. Mitigation: severity-stratified scoring as a deferred observability nicety.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Open-Source Conflict Intelligence (OSINT) — geo-spatial event extraction and verification. Sits at the intersection of OSINT investigative journalism (Bellingcat, NYT Visual Investigations), conflict-monitoring data infrastructure (ACLED, ISW, GDELT), and personal-use intelligence dashboards. The system is a structured-extraction layer over GDELT raw rows whose output (refined coordinates, event-type classification, casualty estimate, provenance trace) is rendered on a 2.5D map and ranked into severity-weighted notification cards for a single operator monitoring the 2026 US-Iran / Israel-Iran / Houthi-strikes / Iraq-Iran / Lebanon theaters in near-real-time.

**User Population:** Solo operator (the dashboard owner) running a personal real-time intelligence dashboard during active hostilities. Decisions made on the dashboard surface: where to direct further investigation; which events to share with peers (informally, via screenshot or link); which markets to watch (oil futures + airline-traffic correlations with strike clusters); whether a key site (Natanz, Fordow, Hudaydah, Strait of Hormuz) is under attack. **NOT a public-facing system** — no general-public consumers, no third-party API, no editorial-publication pipeline, no humanitarian-triage downstream. The aspirational peer audience for output quality is the OSINT analyst community (Bellingcat-grade investigators, Eyes-on-the-Middle-East verification volunteers, ISW analysts) — what they would accept on a publicly-shared screenshot is the calibration mental model.

**Stakes Level:** **High** (deliberately not Critical). The dashboard is single-operator and decisions made are informational/curatorial — not operational. A wrong coord misleads the operator's mental model and possibly a peer-shared link, but does not cascade into airstrike targeting, humanitarian dispatch, or an editorial publication pipeline. However, Iran-conflict OSINT is a high-profile public-discourse domain where being publicly wrong (sharing a screenshot an analyst can disprove) damages the operator's credibility and the dashboard's value as a personal tool. Stakes are above-medium because of the OSINT community red-team feedback loop, below-mission-critical because no third party acts on the output without the operator's editorial intermediation.

**Output Consequence:** Concrete failure cascades when the LLM is wrong:

- **Wrong coord** → marker drops in wrong city/region → operator misreads which sub-theater the event hit → operator might share that misread to a peer or post a screenshot publicly → public correction by an OSINT analyst → loss of dashboard credibility and re-evaluation cost on the operator's part.
- **Wrong event type** (e.g., airstrike misclassified as on_ground) → wrong icon (jet vs explosion vs crosshair) + wrong threat-weight (10 vs 8 vs 3 in `src/lib/severity.ts`) → cluster heatmap miscolors → severity score wrong → notification severity miscalibrated → operator misses a high-severity event buried under low-severity noise.
- **Wrong provenance bucket** (e.g., resolver reports `nominatim-verified-2pass` for a coord that was actually `gdelt-actiongeo-fallback`) → operator can't trace why the coord was chosen → auditability narrative breaks → operator can't defend the call when challenged on the OSINT community's accuracy norms.
- **Schema rejection cascade** → batch loses 2 events → `events:llm:v3` cache thinned → Pitfall 1 bridge falls back to v2 (best case) or raw GDELT (worst case) → map shows raw GDELT lat/lng (often country-centroid level — Iran 32.0°N 53.0°E, Iraq 33.0°N 44.0°E) → events visually mass at country center, severely degraded UX. Per [GDELT Codebook V2.0](http://data.gdeltproject.org/documentation/GDELT-Event_Codebook-V2.0.pdf), country-centroid placement is a documented GDELT behavior when ActionGeo cannot resolve below country granularity — not a bug, but a degradation we are explicitly buying out of by enriching with the LLM.

### Known Failure Modes in This Domain

These are the failure modes specifically observed in conflict-OSINT geocoding pipelines, not generic LLM hallucination patterns.

1. **Country-centroid trap.** When the model can't pin a city below admin1, it (or the resolver) defaults to the GDELT ActionGeoLat / ActionGeoLng — which for un-resolvable locations is often the ISO-country centroid (Iran 32.0,53.0; Iraq 33.0,44.0; Yemen 15.5,47.5; Lebanon 33.85,35.85). Multiple events cluster visually at country center as if a single mass attack hit Tehran/Baghdad. Per [GDELT codebook](http://data.gdeltproject.org/documentation/GDELT-Event_Codebook-V2.0.pdf), this is documented GDELT behavior. **Mitigation:** v2/v3 prompt includes "do not return country-centroid coords; if uncertain return city or region precision with appropriate confidence"; resolver `gdelt-actiongeo-fallback` provenance bucket is treated as an explicit observability signal, not a normal path.

2. **Strike-platform conflation (rocket vs airstrike).** A "rocket landed in Tel Aviv" headline is `explosion`, not `airstrike` — there is no aerial delivery platform attribution in a Houthi/Hezbollah ballistic launch. LLMs trained on news corpora overweight "airstrike" because it's the more frequent headline word. The 5-type ontology only works if the platform-attribution distinction is enforced. **Mitigation:** ontology definitions in system message + a few-shot worked example contrasting an Israeli jet strike on Tehran (airstrike) with a Houthi missile launch on Eilat (explosion). Also surfaces in the D-08 bake-off — model picks must demonstrate this distinction on the corpus.

3. **Casualty inflation from headline language.** Headlines say "dozens dead" / "scores killed" — LLM transcribes literally as `killed: 24` when the article body says "at least 5". This is the most-cited OSINT error per [ACLED fatalities methodology](https://acleddata.com/methodology/fatalities). **Mitigation:** explicit prompt instruction "always use the lower-bound from the most cautious source; if sources disagree, use `unknown=true`"; eval rubric flags any event where `killed` exceeds the lower-bound across the cited sources by >50%.

4. **Persian-script transliteration collapse.** Non-Latin scripts (فارسی, العربية, کوردی) in the NEWS block confuse models that aren't strongly multilingual. The high-frequency failure is collapsing mid-frequency Iranian cities (Sirjan, Bandar Abbas, Sanandaj, Yazd) into the high-frequency anchor (Tehran). Per [The Transliteration Problem in OSINT](https://www.osintcombine.com/post/the-transliteration-problem-in-osint), without input-vs-output validation, transliteration errors cascade through the intelligence cycle. **Mitigation:** model selection criterion in D-08 bake-off (kimi-k2.5 multilingual MoE > llama-3.3-70b on this dimension); ground-truth corpus deliberately includes events at mid-frequency Iranian cities (gt-XXX entries at Bandar Abbas, Sirjan, etc.) as a regression check.

5. **Stale event-time from GDELT publish-time.** GDELT row DateTime is publish time, often hours to days after the event. Without grounding to news-headline date or temporal cues ("yesterday", "early this morning") in the NEWS block, the model emits publish-time as event-time. **Mitigation:** the TEMPORAL block in v2/v3 prompt explicitly anchors the model to the last-3-events-in-region within ±72h; eval flags any `event_at` more than 24h after the source-article publish time.

6. **Bellingcat-coord-override miss.** When `extractBellingcatGeo()` (server/lib) returns a verified coord (e.g., a Bellingcat investigation has already geolocated the strike at landmark precision), that coord should pass through as `provenance='bellingcat-coord-passthrough'` with `confidence=1.0` and the LLM should not "improve" it with a guess. The known failure is models occasionally re-emitting their own Tehran-anchor when a Bellingcat-verified Mashhad coord is in the prompt. **Mitigation:** prompt rule "Bellingcat-verified coords are CANON; if BELLINGCAT BLOCK contains a coord hint for the event, pass it through unchanged"; `.strict()` Zod schema rejects any LLM-emitted `lat/lng` field outright (the LLM emits hierarchy only — coord comes from the resolver).

7. **Schema-fail-as-silent-zero.** When Zod rejects a batch (malformed JSON, missing required field, type mismatch), all events in the batch go to the DLQ — `events:llm:v3` cache loses those events for that wave. Per [LLM hallucinations and failures](https://www.evidentlyai.com/blog/llm-hallucination-examples), silent-failure modes are the hardest to detect because the system "appears to work". **Mitigation:** D-12 block 4 "Schema-Strict Failure Rate" surfaces per-provider Zod-fail % so a regression is visible; per-event retry budget (2 attempts, 1s/4s exp backoff) gives one recovery shot before DLQ-routing.

### Regulatory / Compliance Context

**Regulatory burden is minimal for this personal-use deployment.** Source-attribution discipline (GDELT / Bellingcat / Nominatim citations) is the primary externally-facing concern, and is already enforced via the 6-bucket provenance enum at the schema level.

- **No EU AI Act applicability** — the system is not on the high-risk list (no biometric identification, no employment screening, no critical-infrastructure operation, no law-enforcement use, no education / public-service decisioning). It is a personal informational dashboard.
- **No HIPAA / GDPR / PCI** — no PII collected; the only personal data passing through the system is public-figure names appearing in news headlines (named commanders, political leaders), which are journalistic-fair-use territory and not regulated personal data.
- **Source attribution / fair use** — primary data sources have known licensing posture: GDELT is open data (public domain); Bellingcat content is CC-BY-NC for some published investigations (attribution required, non-commercial use compliant); Nominatim is ODbL-licensed (attribution required — already surfaced in the `/api/geocode` route response). News headlines are surfaced in the NEWS block prompt context and shown at the article-title level in the detail panel — incidental fair use, no full-text reproduction.
- **Export-control awareness** — Iran is a sanctioned country under US OFAC / EU sanctions regimes. The dashboard is purely informational (consumes public news; emits no technology, no data transfer to Iran, no operational targeting). No export-controlled IP transfer; no sanctioned-party transaction. Nominatim and OSM data are open-license and not export-controlled.
- **OSINT community norms (informal but real)** — public dashboard screenshots circulating in the OSINT Twitter/Bluesky community are subject to peer red-team correction. This is the binding accuracy floor in practice, even though it is not a formal regulatory regime. The eval rubric (above) calibrates against this floor.

## 2. Framework Decision

**Selected Framework:** free-claude-code (vendored TypeScript port, MIT license) — provider routing primitives + rolling-window rate limiter + 429 exponential backoff + `<think>`-tag stripper, layered over the OpenAI Node SDK as the wire layer.

**Version:** Pin to upstream `Alishahryar1/free-claude-code` commit SHA — to be selected by the planner at the start of the vendor plan and recorded in the header of `server/lib/freeClaudeRouter.ts`. No git submodule, no Python runtime in the deploy surface.

**Rationale:**
Vendoring upstream logic in-process beats hosting the upstream uvicorn FastAPI proxy as a separate service: zero new infrastructure to monitor, Vercel-serverless compatible (uvicorn isn't), and per-batch latency is unchanged because we skip the HTTP hop. Vendoring also beats writing against the OpenAI SDK directly because we inherit free-claude-code's tested rolling-window rate limiter (40 req/min for NVIDIA NIM), 429 backoff cascade, and `<think>`-block stripper for reasoning models like kimi-k2.5 — primitives we'd otherwise reimplement and re-debug. NVIDIA NIM is the locked primary provider (D-07): 40 req/min free, no documented daily token cap, OpenAI-compatible (drop-in via `new OpenAI({ baseURL })`), best free quota in the upstream catalog. This replaces the v2 Cerebras+Groq cascade entirely (D-03) — not a side-by-side experiment — with v1+v2 extractors retained only as rollback paths per D-17/D-18.

**Alternatives Considered:**

| Framework                                                              | Ruled Out Because                                                                                                                                                               |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Run upstream uvicorn FastAPI proxy on Render Free / Oracle Always Free | Adds a new service to monitor, doesn't fit Vercel serverless deploy surface, no operational gain over in-process vendoring (D-01)                                               |
| Direct OpenAI Node SDK against NVIDIA NIM with no vendoring            | Loses upstream's tested rolling-window rate limiter + 429 backoff + reasoning-block stripper — would need to reimplement and re-debug all three primitives ourselves (D-02)     |
| OpenRouter as primary provider                                         | Free-tier daily caps too tight (~50-200 req/day per model) for the sustained 184-batch refresh pattern; only viable as fallback in the cap-cascade (D-09)                       |
| Cerebras-primary + free-tier-fallback hybrid                           | Contradicts D-03 ("free-claude-code is our main form of routing to free LLM calls") and the user-stated intent of removing paid escape hatches from the v3 path                 |
| Anthropic Claude direct (or any paid provider)                         | Rejected per D-03 no-paid-escape-hatch policy; v3 graceful degradation is raw GDELT, never a paid LLM                                                                           |
| Git submodule + Python runtime on Vercel                               | Python on Vercel serverless is awkward and defeats the in-process integration goal (D-01 supporting rationale)                                                                  |
| Multi-provider parallel race (call N providers, take first valid)      | Not needed — D-06 establishes rate limits aren't binding for our 184-batch sequential pattern; sequential cascade is sufficient                                                 |
| Keep OpenAI strict JSON Schema mode                                    | Forces back onto paid providers (NVIDIA NIM + OpenRouter free models don't reliably support strict mode); contradicts D-03/D-10. Zod gives equivalent runtime safety post-parse |

**Vendor Lock-In Accepted:** Partial. Vendoring upstream pins us to free-claude-code's logical contract (rate-limit shape, fall-through order, reasoning-strip regex). Mitigated by three properties: (a) MIT license — no usage restrictions, (b) we own the TypeScript port so upstream drift can never block our deploy and we cherry-pick fixes at our cadence, (c) the wire layer is the OpenAI Node SDK, so swapping providers is a `baseURL` change — not a framework migration. ### Entry Point Pattern

The router is a single async function `callLLM` that the v3 extractor calls per batch. The cascade is internal — callers pass `messages + schemaText + opts` and get back `{ content, routing }`.

```typescript
// Excerpt: the minimum running shape of server/lib/freeClaudeRouter.ts
//
// Vendored from https://github.com/Alishahryar1/free-claude-code (MIT)
// Pin: <commit-sha — planner fills>
// Adapted from upstream `proxy/main.py` (rolling window + cascade) and
// `providers/openai_compat.py` (NVIDIA NIM + OpenRouter client wrappers).

export type FreeProvider = 'nvidia_nim' | 'openrouter';

export interface RoutingDecision {
  provider: FreeProvider;
  model: string; // slash-prefixed: 'moonshotai/kimi-k2.5'
  reason: 'primary' | `fall_through:${string}`; // D-12 block 1 surfaces verbatim
  timestamp: number; // Date.now()
}

export type RouterErrorBucket =
  | 'rate_limit' // 429 + Retry-After
  | 'timeout' // watchdog (hard) or per-call timeout (soft)
  | 'malformed_json' // content not parseable
  | 'schema_fail' // Zod rejection — caller-side, taxonomy-mirrored here
  | 'network' // ENOTFOUND / ECONNRESET / EAI_AGAIN
  | 'upstream_500'
  | 'other';

const NVIDIA_NIM_BASE = 'https://integrate.api.nvidia.com/v1';
const OPENROUTER_BASE = 'https://openrouter.ai/api/v1';

// 40 req/min sliding window per upstream proxy/main.py:80-135.
class RollingWindow {
  private timestamps: number[] = [];
  constructor(
    private readonly capacity: number,
    private readonly windowMs: number,
  ) {}
  canRequest(now = Date.now()): boolean {
    this.evict(now);
    return this.timestamps.length < this.capacity;
  }
  consume(now = Date.now()): void {
    this.evict(now);
    this.timestamps.push(now);
  }
  // Observability for D-12 block 3 (Rate-Limit Headroom Gauge).
  used(now = Date.now()): number {
    this.evict(now);
    return this.timestamps.length;
  }
  private evict(now: number): void {
    const cutoff = now - this.windowMs;
    while (this.timestamps.length > 0 && this.timestamps[0]! < cutoff) this.timestamps.shift();
  }
}

const nvidiaNimWindow = new RollingWindow(40, 60_000);
// OpenRouter free-tier caps daily, not per-minute; track via a separate counter
// keyed at `llm:tokens:openrouter:YYYY-MM-DD` (mirror of v2's llmTokenBudget).

export async function callLLM(
  messages: OpenAI.Chat.ChatCompletionMessageParam[],
  schemaText: string, // D-10: included in prompt, NOT response_format
  opts: { batchSize?: number; modelOverride?: string; signal?: AbortSignal } = {},
): Promise<{ content: string | null; routing: RoutingDecision[] }> {
  const decisions: RoutingDecision[] = [];
  const cascade: FreeProvider[] = ['nvidia_nim', 'openrouter'];

  for (const provider of cascade) {
    if (provider === 'nvidia_nim' && !nvidiaNimWindow.canRequest()) {
      decisions.push({
        provider,
        model: '-',
        reason: 'fall_through:nvidia_nim_window_full',
        timestamp: Date.now(),
      });
      continue;
    }
    const client = getClientFor(provider); // OpenAI({ apiKey, baseURL })
    if (!client) continue;
    const model = pickModel(provider, opts.modelOverride); // D-08 winner; provider-aware remap

    if (provider === 'nvidia_nim') nvidiaNimWindow.consume();
    const t0 = Date.now();
    try {
      const res = await client.chat.completions.create(
        {
          model,
          messages,
          response_format: { type: 'json_object' }, // D-10: NEVER 'json_schema' on free tier
          temperature: 0,
          max_tokens: 2048,
          stream: false, // pitfall 6: NIM defaults can flip this
        },
        { signal: opts.signal }, // mandatory — see Pitfall 4 + Section 4b.2
      );
      const raw = res.choices[0]?.message?.content ?? null;
      const reasoningContent =
        // Some NIM-hosted reasoning models tuck reasoning into a side-channel
        // field on the message object. Strip it so JSON.parse only sees JSON.
        (res.choices[0]?.message as { reasoning_content?: string } | undefined)?.reasoning_content;
      const stripped = stripReasoningBlocks(raw, reasoningContent);
      decisions.push({ provider, model, reason: 'primary', timestamp: Date.now() });
      logger.info({ provider, model, durationMs: Date.now() - t0 }, 'free-claude-code call ok');
      return { content: stripped, routing: decisions };
    } catch (err) {
      const bucket = classifyError(err);
      logger.warn({ err, provider, model, bucket }, 'free-claude-code call failed');
      decisions.push({
        provider,
        model,
        reason: `fall_through:${provider}_${bucket}`,
        timestamp: Date.now(),
      });
      // Increment per-provider taxonomy counter via updateProgress (D-14).
      // continue to next provider on retryable errors; break on policy errors.
    }
  }

  // All free providers exhausted → caller falls back to raw GDELT (27.4 D-29).
  return { content: null, routing: decisions };
}

// D-11 — strip BOTH inline <think>...</think> tags AND a side-channel
// reasoning_content field before JSON.parse. Regex uses [\s\S] (NOT .) so
// multi-line reasoning blocks match.
export function stripReasoningBlocks(
  content: string | null,
  reasoningContent?: string,
): string | null {
  if (content === null) return null;
  let out = content.replace(/<think>[\s\S]*?<\/think>/g, '');
  if (reasoningContent) out = out.replace(reasoningContent, '');
  // Some models prefix `reasoning_content: ...\n` directly into the content.
  out = out.replace(/^reasoning_content:[^\n]*\n/m, '');
  return out.trim();
}
```

### Common Pitfalls

1. **NVIDIA NIM JSON-mode quirk — `'json_schema'` is not supported on free tier.**
   The free-tier endpoint accepts `response_format: { type: 'json_object' }` (loose JSON guarantee) but does NOT reliably accept `response_format: { type: 'json_schema', json_schema: {...} }` — strict mode is silently ignored or returns `wrong_api_format`. **Fix per D-10:** include the JSON Schema as instruction text inside the user message, validate post-parse with Zod (`enrichedEventAnyV3.safeParse`). The runtime contract is unchanged from v2; only the wire-level enforcement relaxes. See [NVIDIA NIM API Reference](https://docs.nvidia.com/nim/large-language-models/latest/api-reference.html).

2. **Reasoning-block emission — `<think>` tags AND/OR `reasoning_content` field.**
   kimi-k2.5, kimi-k2-thinking, and deepseek-r1-class models emit reasoning in two ways simultaneously: (a) inline `<think>...</think>` blocks in the message content, AND (b) a separate `reasoning_content` field on the message object. Strip BOTH before JSON.parse. The regex is `/<think>[\s\S]*?<\/think>/g` — note `[\s\S]` (not `.`) so multi-line blocks match without a `dotAll` flag. Per D-11 + Section 4b helper. Models occasionally emit malformed `<think>` blocks (unclosed); the regex is non-greedy and tolerant.

3. **OpenRouter daily-cap surprise — not a per-minute rate limit.**
   Free-tier OpenRouter models (model ID suffix `:free`) impose a _daily_ request cap of ~50 req/day for accounts under $10 in credits, ~1000 req/day for accounts ≥$10 (per [OpenRouter rate limits docs](https://openrouter.zendesk.com/hc/en-us/articles/39501163636379-OpenRouter-Rate-Limits-What-You-Need-to-Know)). 429 is returned with `X-RateLimit-Reset` pointing to the next-day midnight UTC. Treat it as a fall-through trigger to raw-GDELT degradation (no retry-after sleep — that would block for hours). Track daily counter at `llm:tokens:openrouter:YYYY-MM-DD` (48h TTL), mirror of v2's `llmTokenBudget`. **Failed attempts still count** against the daily quota — don't retry the same model after a 429.

4. **Late-resolve clobber — AbortController is mandatory.**
   Timed-out NVIDIA NIM calls can resolve 10+ min after the 90s watchdog fires, especially under thinking-mode load. Without `AbortController.signal` threaded into `client.chat.completions.create({ signal })`, the OpenAI SDK keeps the underlying fetch alive, the response eventually returns, and (without the late-resolve guard inside `withBatchWatchdog`) clobbers the partial cache or DLQ entries written for that batch. Verbatim from 27.4.1 D-12 — `withBatchWatchdog`'s `timedOut` closure flag already drops late returns; v3 must additionally call `abortCtl.abort()` inside `onTimeout` so the underlying fetch is killed and provider budget is preserved.

5. **Provider model-id format mismatch — slash-prefixed but different prefixes.**
   NVIDIA NIM model IDs are `<org>/<model>` (e.g. `moonshotai/kimi-k2.5`, `meta/llama-3.3-70b-instruct`, `z-ai/glm4.7`) per [NVIDIA NIM model catalog](https://build.nvidia.com/moonshotai/kimi-k2.5). OpenRouter uses different prefixes for the same logical models (e.g. `moonshotai/kimi-k2:free`, `meta-llama/llama-3.3-70b-instruct:free`, `openai/gpt-oss-120b:free`). The router MUST do a per-provider model-name remap inside `pickModel(provider, modelOverride)` — NEVER pass an NVIDIA NIM ID to OpenRouter or vice versa (returns 404 on the model). This is unlike Cerebras + Groq (v2) where both used the same `gpt-oss-120b` shape.

6. **NVIDIA NIM streaming default — force `stream: false` explicitly.**
   Some NVIDIA NIM-hosted models default to `stream: true` even when the request body omits the field. The OpenAI SDK then expects an SSE response and the non-streamed JSON path returns malformed payloads. Always pass `stream: false` explicitly in `chat.completions.create` for the extraction path — we want a single full response and we're already wrapping with `withBatchWatchdog` for timeout discipline. Per [NVIDIA NIM API reference](https://docs.api.nvidia.com/nim/reference/llm-apis).

**Tool Use:**

None for the LLM itself — extraction does not use OpenAI function-calling / tool-use. The 6-path resolver (`server/lib/llmResolver.ts`) is provider-independent and runs **after** the LLM returns:

- v3 LLM returns the structured location _hierarchy_ `{ country, admin1, city, neighborhood, landmark, confidence }` (the LLM never emits lat/lng — `.strict()` Zod rejects extra keys per existing v2 contract).
- The resolver translates that hierarchy into a coordinate by trying the 6 paths in order: `own-site-snapshot` → `poi-amenity-nominatim` → `nominatim-direct` → `nominatim-verified-2pass` → `gdelt-actiongeo-fallback` → `bellingcat-coord-passthrough`.
- The resolver is **unchanged** from v2 — the only thing that swaps in v3 is the upstream LLM source, not how its output is geocoded. This is load-bearing: provenance buckets and resolver branches stay testable against the same eval harness.

## 4b. AI Systems Best Practices

> Cross-cutting patterns, framed for Phase 27.4.3 (TypeScript / OpenAI Node SDK / NVIDIA NIM + OpenRouter cascade).

### Structured Outputs without Pydantic — Zod

We're TypeScript, not Python; the equivalent of Pydantic + retry-on-validation-failure is Zod. The v3 schema is a new branch on the existing discriminated union at `server/lib/llmSchema.ts` — it mirrors v2's shape (D-10: only the wire-level enforcement relaxes, not the runtime contract).

```typescript
// server/lib/llmSchema.ts — v3 branch additions (illustrative; mirrors v2 shape)
import { z } from 'zod';
import { GEOCODE_PROVENANCE_VALUES, locationHierarchyV2 } from './llmSchema.js';

// .strict() is the load-bearing guard — same as v2. ANY extra key (including
// lat/lng/coordinates the LLM might hallucinate despite the system prompt)
// fails safeParse and the event gets routed to the DLQ. This is D-05.
export const enrichedEventV3 = z
  .object({
    schemaVersion: z.literal('v3'),
    groupKey: z.string(),
    location: locationHierarchyV2, // identical to v2 — strict, NO lat/lng
    type: z.enum(['airstrike', 'on_ground', 'explosion', 'targeted', 'other']),
    confidence: z.number().min(0).max(1),
    // TRANSFORM (not max) — Cerebras qwen taught us in v2: rejecting a 250-char
    // reasoning over the 200 limit nukes the whole batch. Truncate instead.
    reasoning: z.string().transform((s) => (s.length > 200 ? `${s.slice(0, 197)}…` : s)),
    weaponType: z
      .enum(['airstrike', 'drone', 'missile', 'artillery', 'small_arms', 'IED'])
      .nullable(),
    targetType: z.enum(['military', 'infrastructure', 'civilian', 'leadership']).nullable(),
    timeOfDay: z
      .string()
      .regex(/^([01]\d|2[0-3]):[0-5]\d$/)
      .nullable(),
    durationMinutes: z.number().int().nonnegative().nullable(),
    actors: z.array(z.string()),
    severity: z.enum(['critical', 'high', 'medium', 'low']),
    summary: z.string(),
    casualties: z.object({
      killed: z.number().int().nullable(),
      injured: z.number().int().nullable(),
      unknown: z.boolean(),
    }),
    sourceCount: z.number().int(),
  })
  .strict();

export const batchResponseV3 = z.object({
  events: z.array(enrichedEventV3),
});

// Discriminated union — extend the existing enrichedEventAny:
export const enrichedEventAnyV3 = z.discriminatedUnion('schemaVersion', [
  enrichedEventV1, // existing
  enrichedEventV2, // existing
  enrichedEventV3, // NEW
]);
```

**Framework integration:** the OpenAI Node SDK has no native Zod hook (unlike LangChain's `.with_structured_output()` or LlamaIndex's `PydanticOutputParser`). The validation is manual but standardized:

```typescript
const parsed = JSON.parse(stripped); // throws → catch → DLQ 'v3:malformed'
const validated = batchResponseV3.safeParse(parsed); // .success: boolean
if (!validated.success) {
  /* DLQ 'v3:schema_fail' + log issues.slice(0,3) */
}
results.push(...validated.data.events);
```

**Retry logic:** v2's pattern stays — per-event retry budget is **2 attempts** with **1s / 4s exponential backoff + ±250ms jitter** (mirror of `BACKOFF_MS = [1000, 4000]` + `JITTER_MS = 250` from `server/adapters/llm-provider.ts:14-22`). On Zod fail, the entire batch (BATCH_SIZE=2 events) goes to DLQ with `reason: 'v3:schema_fail'` and execution continues to the next batch — never abort the run on a single bad batch. Retries happen at the **provider level** inside `freeClaudeRouter.callLLM` (transient errors → retry same provider; policy errors → fall through to next provider). Schema-fail rate is surfaced in DevApiStatus block 4 (D-12) so the planner can re-prompt or pick a different model in the bake-off if it spikes >5%.

### Async-First Design

Express request handlers + `withBatchWatchdog` Promise.race + `AbortController` end-to-end. Three constraints to honor:

1. **AbortController.signal MUST thread end-to-end.** The OpenAI SDK accepts `{ signal }` as the second argument to `chat.completions.create`. Without it, a 90s watchdog timeout fires, returns `null` to the caller, but the underlying `fetch` keeps running — late-resolves 10+ min later (consuming provider rate-limit budget for nothing). v3 must:
   - Create one `AbortController` per batch in the v3 extractor.
   - Pass `signal` down through `callLLM` opts → `client.chat.completions.create({ signal })`.
   - Call `abortCtl.abort()` inside `withBatchWatchdog`'s `onTimeout` callback.
     The watchdog's late-resolve guard (`timedOut` closure flag) drops late returns at the JS level; the `abort()` call kills the network fetch at the TCP level.

2. **Stream vs. await — always `stream: false` for extraction.** The OpenAI SDK supports streaming via `stream: true`, but we want a single fully-validated JSON object — chunked SSE responses would force us to buffer the whole stream anyway and cope with mid-stream `<think>` tag closures spanning chunks. v2 uses await; v3 inherits. (Streaming would be appropriate for a UX-facing chat surface — not relevant here.)

3. **The one common mistake — `Promise.race` without late-resolve guard.** A naive `Promise.race([fetchPromise, timeoutPromise])` lets the loser keep running. The 27.4.1 `withBatchWatchdog` already guards this via the `timedOut` closure flag + `workPromise.catch(() => {})` to suppress unhandled-rejection on late-arriving rejections. **Do not rewrite this primitive — wrap it.** See `server/lib/llmExtractorWatchdog.ts:74-138` for the canonical pattern.

### Prompt Engineering Discipline

**System vs. user prompt separation** — copy v2's `SYSTEM_PROMPT_V2` near-verbatim into `SYSTEM_PROMPT_V3` with two changes:

- Update the schema-version reference if any (none currently).
- Add explicit "Output JSON only — no preamble, no `<think>` blocks in final output, no markdown code fences" guidance. Reasoning models may still emit them; `stripReasoningBlocks` handles the `<think>` case, but explicit instruction reduces frequency.

**User prompt structure** (per event batch, 2 events) — verbatim v2 builder:

```

CAMEO Code: ...

Actors: X vs Y
Goldstein Scale: ...
```

**Few-shot:** keep v2's pattern — 1-2 worked examples in the system message (preserved verbatim from v2's `SYSTEM_PROMPT_V2`). Dynamic retrieval via the NEWS / BELLINGCAT / TEMPORAL blocks above is the heavier lift; static few-shot stays static.

**Token-budget discipline (`max_tokens: 2048` mandatory, never unbounded):** NVIDIA NIM free tier returns 4xx if `max_tokens` is too high relative to prompt size + model context, but the more common failure is silently truncated JSON when the model runs out of output budget mid-event. 2048 covers BATCH_SIZE=2 events at ~1024 tokens each (matches v2). Surface truncated-JSON rate as part of D-12 block 4 (Schema-Strict Failure Rate) so a retroactive bump to 3072 is data-driven, not guessed.

### Context Window Management

This is structured extraction (not RAG, not conversation, not autonomous-loop), so no chunking / summarisation / compaction logic is needed:

- BATCH_SIZE=2 keeps prompt+output under 8k tokens per call → trivial inside NVIDIA NIM kimi-k2.5's 256k context.
- The NEWS block is **tier-tagged** (T1/T2/T3 source-quality bucket via `getSourceTier`) and **±24h time-windowed** — already in v2 at `server/lib/llmEventExtractor.v2.ts:286-310`, copy verbatim. This implicitly bounds the prompt size: capping at 5 articles × 160-char title-slice = ≤800 chars per event.
- The TEMPORAL block caps at 3 prior events × 120-char summary slice = ≤360 chars per event.
- The BELLINGCAT block caps at 3 hits × 160-char title-slice = ≤480 chars per event.

**Total worst-case prompt size per BATCH_SIZE=2 batch ≈ 4k tokens** — under all candidate models' context windows.

**Alert Thresholds:**

- **Auto-rollback triggers (no human action required at trigger time; audit-log entry written):**
  - `watchdogTimeoutCount ≥ 3` per run (CONTEXT.md D-17 trigger 1) → fires `setPipelineOverride('v2')`.
  - Eval-at-20km drop ≥5pp from cutover baseline (CONTEXT.md D-17 trigger 2) → fires `setPipelineOverride('v2')`.
  - Both write to `events:llm-pipeline-audit` Redis list (90d TTL) with `trigger: 'auto:*'` + reason text.

- **Operator soft-alerts (banner in DevApiStatus, no auto-action; review at next operator session):**
  - Schema-rejection rate per provider sustained >5% for 24h.
  - OpenRouter daily cap >80% (per `llm:tokens:openrouter:YYYY-MM-DD` counter) — leading indicator that NVIDIA NIM is taking too many fall-throughs.
  - Shadow cost >$30/day = materially above $24/day target = NVIDIA NIM degraded path.
  - DLQ count >10 entries (current contents of `events:llm-dlq`).

- **Cron failure alerts:**
  - Nightly `npm run eval:replay` cron fails to write `events:llm-eval-baseline:v3:nightly:YYYY-MM-DD` for >2 consecutive days → operator-visible banner in DevApiStatus.

**Smart Sampling Strategy (which interactions surface for human review):**

- **Auto-flagged in DLQ for human review (every occurrence):**
  - Any event with `suspect: true` (set by guardrails O-4 / O-6 above).
  - Any event with provenance bucket mismatch (precision='exact' + provenance='gdelt-actiongeo-fallback' = country-centroid risk).
  - Any batch with all-events Zod-fail.
  - Any event where the Bellingcat-coord-override guardrail (O-5) fired.

- **Operator daily review (~5 minutes):**
  - Open DevApiStatus → glance pipeline pill (M-1) + eval-at-20km sparkline (M-2) + watchdog count (M-3) + DLQ tail (M-7).
  - If any out-of-band, click into D-13 lineage drill-down for the specific event.

- **Operator weekly review (~15 minutes):**
  - Review provenance distribution (M-4) for resolver-path-collapse risk.
  - Review per-provider error taxonomy (M-5) for degraded-provider patterns.
  - Review shadow-cost trend (M-6) — is the architecture still earning its keep?
  - Decide if cascade reorder or model-pick re-run is warranted.

- **Reproducibility-hash spot-check (monthly; eval dim #10):**
  - Pick 5 random enriched events from `events:llm:v3:lineage:*`.
  - Re-run via `POST /api/events/llm-replay/:groupKey` (dev-only endpoint, dual-gated per 27.4 Pitfall 6).
  - Diff `(coord, provenance, type)` against original. If diff > 0, investigate non-determinism (likely model-side stochasticity at temperature=0 — should be 0 — or upstream model-version drift).

- **Quarterly Persian/Arabic subset audit (eval dim #8 / Section 1b mode #4):**
  - Manual review of 20 events from the non-Latin source subset of the GT corpus.
  - Compare resolver output against operator's reading of the source articles.
  - Calibrates the model-pick decision longitudinally — if `within20km` on the subset has dropped below 0.80, schedule a 27.5+ bake-off rerun with the latest NVIDIA NIM catalog.
