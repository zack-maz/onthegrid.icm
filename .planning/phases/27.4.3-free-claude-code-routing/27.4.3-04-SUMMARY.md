## Decisions Made

(See `key-decisions` frontmatter above for the full 6-bullet list. Highlights below.)

1. **DrillDownBlock under V3** — Rule 2 deviation: the plan literal said the v3 composer should NOT mount DrillDownBlock because "DrillDownRow auto-detects v3 fields under the existing event-list block." But the version-routed render switch REPLACES the v2 composer with V3 when v3 is active, so the existing v2 event-list block is gone. Without DrillDownBlock under V3, the entire D-13 lineage UX surface (reasoningTrace + lineageHash) is unreachable. Mounting DrillDownBlock under V3 restores the surface while preserving graceful degradation when v1/v2-cached events come through.
2. **ProgressBar additive extension** — kept the existing repo's ProgressBar structure (h-1 flex-1 bg-white/10 + the inline % counter span). Plan literal text used a different shape; preserved repo conformance and only added the new optional `barColor` prop.
3. **DevApiStatusV3.test.tsx pattern** — mirrors existing `devApiStatusEventsSection.test.tsx` (named import + module-level mutable mock + uiStore.setState before render). Plan template suggested `vi.mocked()` + default import + `vi.fn()` reassignment; chose existing-file conformance over plan literal.
4. **Topbar v3 pill test fetch stub** — uses `vi.stubGlobal('fetch')` instead of MSW. Avoids dragging an MSW dependency into the project for a single test, and is consistent with how other Topbar/DevApi tests treat /api/* (mock at the hook level or stub fetch in test scope).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 — Missing critical functionality] DrillDownBlock not mounted under EventsFiltersSectionV3**

- **Found during:** Task 6 verification (running the new lineage-chip regression test, which initially failed because `screen.getByTestId('drill-down-expand')` returned null)
- **Issue:** The plan's `<action>` for Task 4 said "LineageDrillDown extension is rendered inside DrillDownRow under the existing event-list block (DrillDownRow auto-detects v3 fields). No separate block here." This was true for the design where v3 was supposed to STACK on top of v2. But Task 4's render switch REPLACES the v2 composer with V3 when v3 is active (the JSX is `v3 ? <V3/> : v2 ? <V2/> : null`, not `<V2/>{v3 && <V3/>}`). Without DrillDownBlock under V3, the entire D-13 lineage UX surface is unreachable.
- **Fix:** Mounted `<DrillDownBlock llmStatus={llmStatus} />` at the bottom of `EventsFiltersSectionV3`. DrillDownRow's existing v3 lineage extension (added in Task 3) auto-detects the optional fields, so v1/v2-cached events under the same composer surface degrade gracefully (no chips render). Updated the plan acceptance criterion's Task 6 lineage test to expand `drill-down-expand` then `drill-down-row-toggle` so the lineage chips become visible.
- **Files modified:** `src/components/ui/DevApiStatus.tsx` (Task 4 commit `1aacc6a` would be the right place; landed in Task 6 commit `9e621c0` because the gap was found during test runtime).
- **Verification:** Test 7 (`renders DrillDownRow lineage extension when reasoningTrace + lineageHash are populated`) now passes; the cyan hash chip + reasoning trace block both render.
- **Committed in:** `9e621c0` (atomic with Task 6 test creation)
