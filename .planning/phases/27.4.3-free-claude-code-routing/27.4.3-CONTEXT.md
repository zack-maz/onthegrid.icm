# Phase 27.4.3: free-claude-code Routing Evaluation - Context

**Gathered:** 2026-04-25
**Status:** Ready for planning
**Source:** Discussion-driven gray-area resolution (2026-04-25 session, post-27.4.2 close)

<domain>
## Phase Boundary

This phase delivers a v3 enrichment pipeline that replaces the manual
Cerebras+Groq cascade in `server/adapters/llm-provider.ts` with
free-claude-code-mediated free-LLM routing as the **sole** primary path,
plus a Palantir-grade observability extension to DevApiStatus that exposes
every routing decision, latency profile, rate-limit headroom, error taxonomy,
provenance lineage, and pipeline-version flip event.

**Falsifiable success bar:**

1. **Eval parity** — `runEval()` resolver-only score ≥ 0.890 within20km
   (= 27.4.2 Plan 07 baseline 0.940 minus 5pp tolerance). Captured against
   the locked 50-event ground-truth corpus at
   `.planning/eval/ground-truth-events.json`.
2. **One clean production run** — 184 batches end-to-end with
   `watchdogTimeoutCount = 0` and `provenanceCounts` populated, so
   `gdelt-actiongeo-fallback` rate is measurable.
3. **Cutover** — v3 promoted to default via runtime override. Pipeline pill
   in Topbar shows `v3`. 27.4.2 HUMAN-UAT.md tests 1+2 (full 184-batch
   production run + post-fix fallback% measurement) executed on v3 and
   ticked off.

**Hard out-of-scope** (per ROADMAP and prior phases):

- Phase 27.4.4 — `depthTest` TS drift in `useEntityLayers.ts` (deck.gl v9)
- Phase 27.4.5 — LLM flight-recorder Redis ring buffer
- Phase 27.3.3 — romanization of non-Latin water names
- Vercel preview deploy failure
- Ground-truth corpus expansion beyond 50 events
- Cerebras model swap back to gpt-oss-120b on tier upgrade
- Adding paid-provider escape hatch to v3 (Cerebras/Groq are entirely
  removed from the v3 path; v3 degrades to raw GDELT, not to paid LLM
  providers)
- Bumping the Zod schema (events:llm-schema-v3 with new fields) — the
  schema lock from 27.4 D-23 is preserved; only the wire-level strict-mode
  contract relaxes

<decisions>
## Implementation Decisions

### Integration shape (Area 1)

- **D-01** Vendor in-process (no proxy hop). Port the relevant
  free-claude-code Python modules — translation layer, per-provider
  rate-limit primitives, NVIDIA NIM + OpenRouter client wrappers — to
  TypeScript under `server/lib/freeClaudeRouter.ts`. The v3 extractor
  calls these functions directly; no uvicorn server, no http hop, no
  Python runtime in our deploy surface.
  - **Why:** free-claude-code is MIT-licensed, designed as a long-running
    FastAPI proxy that does not fit Vercel serverless. Vendoring the
    _logic_ — not the FastAPI wrapper — gives us its tested rate-limit
    handling and provider-routing decisions without any new infra.
    Calling functions in-process from llm-provider.ts is materially
    simpler than hosting a separate service and adds zero latency.
  - **How to apply:** Pin to a specific upstream commit (record SHA in
    the new file's header). Document which Python modules were ported
    so future updates can be re-applied. No git submodule, no Python
    runtime in deploy.

- **D-02** Vendoring scope is **logic only**, not the Discord/Telegram
  bot or CLI-flavored helpers. Port:
  - Provider client config (NVIDIA NIM `https://integrate.api.nvidia.com/v1`,
    OpenRouter `https://openrouter.ai/api/v1`)
  - Per-provider rolling-window rate limiter (40 req/min for NVIDIA NIM)
  - Reactive 429 exponential backoff
  - `<think>`-tag stripper / `reasoning_content` parser
  - Heuristic tool-call parser (defer; not used by extraction path)
    Do **not** port:
  - FastAPI / uvicorn server
  - Anthropic ↔ OpenAI message-shape translator (we already use OpenAI
    SDK natively; no need for the Anthropic-shape layer)
  - Discord bot, Telegram bot, claude-pick CLI

### Pipeline cascade shape (Area 2)

- **D-03** v3 replaces Cerebras+Groq entirely. The v3 extractor calls
  **only** `freeClaudeRouter.callLLM(...)` — no Cerebras, no Groq, no
  paid-LLM escape hatch. If all free-tier providers exhaust, v3
  degrades to raw GDELT per the existing graceful-degradation contract
  (27.4 D-29).
  - **Why:** User's stated intent: "free-claude-code is our main form of
    routing to free LLM calls for enrichment, not our current process."
    Adding paid fallback would dilute that. Map never goes blank — the
    raw-GDELT fallback handles the worst case.
  - **How to apply:** v3 extractor (`server/lib/llmEventExtractor.v3.ts`)
    imports from `freeClaudeRouter`, never from `llm-provider.ts`.
    Cerebras/Groq paths in `llm-provider.ts` remain shipped (v2 still
    callable via runtime override) but are not reached by v3.

- **D-04** v3 is a new schema-version with separate cache keys.
  - `events:llm:v3` — terminal cache, `ConflictEventEntity[]` shape
    (same as v2 per the v2-key two-key discipline from 27.4.1 D-09)
  - `events:llm:v3:partial` — observability-only `LLMCachePayload`
    envelopes per batch
  - `events:llm-summary:v3` — run summary (extends LLMRunSummary
    with v3-specific fields — see D-21)
  - `events:llm-eval-baseline:v3` — eval baseline (90d TTL)
  - `events:llm-pipeline-override` — accepts `'v1' | 'v2' | 'v3' | null`
    via `POST /api/events/llm-pipeline`
  - **Why:** Cache-key versioning on shape change is canon (27.4.1 D-09).
    A pipeline-version bump that shares cache keys would risk
    cross-version contamination during the v2↔v3 cutover window.
  - **How to apply:** Bump cache key constants in `server/routes/events.ts`
    - `server/lib/llmProgress.ts`. Mirror the two-key discipline:
      terminal key reads through `coerceCachedEvents()` defense-in-depth
      helper (per 27.4.1 commit `e26ceca`); partial key writes after every
      batch never serve users.

- **D-05** v1/v2 graceful-fallback bridge (Pitfall 1) preserved.
  Order: v3 → v2 → v1 → raw GDELT. If `events:llm:v3` cache empty AND
  v3 extractor errors out, server falls back to `events:llm:v2`, then
  `events:llm` (v1), then raw GDELT. Map never goes blank — same
  contract as today, extended with v3 at the top.
  - **How to apply:** Add v3 read in the `/api/events` cache-fallback
    chain, before v2.

### Provider selection + rate-limit feasibility (Area 3)

- **D-06** Rate-limit feasibility verdict: **NOT a binding constraint**
  for our usage pattern. Sequential 184-batch run @ ~30s/batch =
  ~92 min total = ~2 req/min sustained avg. NVIDIA NIM caps at
  40 req/min = 57.6k req/day. /api/events refresh on 15min cooldown
  caps at 96 runs/day. Even worst case = 184 × 96 = 17.6k req/day,
  well below the daily implicit cap.
  - **How to apply:** No special-casing needed for normal operation.
    The rolling-window throttle (D-01 ported logic) is defensive.

- **D-07** Primary provider: **NVIDIA NIM only** at first ship.
  - Endpoint: `https://integrate.api.nvidia.com/v1`
  - 40 req/min free, no documented daily token cap
  - OpenAI-compatible (drop-in via `new OpenAI({ baseURL })`)
  - **Why:** Best free quota of any provider in the free-claude-code
    catalog. OpenAI-compatible endpoint means zero translation layer
    needed. Stable per upstream README.
  - **How to apply:** New env var `NVIDIA_NIM_API_KEY` (free key from
    `build.nvidia.com/settings/api-keys`). Document in `.env.example`.

- **D-08** Model selection: **multi-model eval, pick winner.** Inner
  loop runs `runEval()` resolver-only against a candidate set of
  NVIDIA NIM models, picks the one closest to 0.940 within20km.
  Candidates to evaluate (in priority order):
  1. `moonshotai/kimi-k2.5` — MoE, strong multilingual & structured
     output (best fit for Persian/Arabic place-name extraction)
  2. `z-ai/glm4.7` — free-claude-code's default, recent (2025)
  3. `meta/llama-3.3-70b-instruct` — known baseline for OSS reasoning
  4. Whatever else NVIDIA NIM ships in their catalog at the time of
     evaluation (planner can iterate)
  - **Why:** Eval is the only authoritative comparator. We don't pick
    on benchmarks — we pick on this specific 50-event corpus.
  - **How to apply:** `npm run eval:replay -- --model=<id>` extends the
    existing eval-replay script to take a `--model` flag. Run all
    candidates, capture per-distance scores in plan summary, lock the
    winner in v3 config. Loser models become deferred (Phase 27.5+).

- **D-09** Cap fall-through cascade (defense): **NVIDIA NIM → OpenRouter
  free models → raw GDELT.** No Cerebras, no Groq, no DeepSeek (paid).
  Fall-through triggers on:
  - Rate-limit 429 + exhausted backoff retries
  - Sustained 5xx on the primary
  - Daily quota exhaustion (per-provider counter via D-01 vendored
    primitive)
  - **Why:** Honors D-03 ("free-claude-code is the only path") while
    giving operational headroom. OpenRouter free models have tight
    daily caps (~100-200 req/day per model on free tier) — only viable
    as fallback, not primary.
  - **How to apply:** Cascade defined in `freeClaudeRouter.callLLM()`.
    Order: `[nvidia_nim, openrouter_free]`. On exhaust, return null
    (raw GDELT degradation kicks in upstream — same contract as v2).

### Schema strict mode handling (Area 4)

- **D-10** Drop OpenAI strict JSON Schema mode for v3.
  `response_format: { type: 'json_object' }` only; the JSON Schema is
  included in the prompt as instruction text (system message + user
  message). Zod schema in `server/lib/llmSchema.ts` continues to validate
  post-parse — same defense-in-depth as v1/v2 already do.
  - **Why:** NVIDIA NIM's OpenAI-compatible endpoint and OpenRouter's
    free models do **not** reliably support strict JSON Schema mode —
    only OpenAI's hosted models and Anthropic's Claude 3.5+ do.
    Attempting strict mode would force us back onto paid providers,
    contradicting D-03. Zod gives us identical runtime safety.
  - **How to apply:** New `EVENT_EXTRACTION_SCHEMA_V3` constant
    (textual JSON Schema reference in prompt) in `freeClaudeRouter.ts`.
    The Zod `enrichedEventAny` discriminated union grows a `v3` branch
    (mirrors v2 shape; only the wire-level enforcement changes, not
    the runtime contract). Schema-rejection rate becomes a tracked
    observability metric (D-19).

- **D-11** Strip `<think>` blocks pre-Zod. Reasoning models (kimi-k2.5,
  deepseek-r1) emit `<think>...</think>` blocks and/or
  `reasoning_content` fields that pollute the JSON parse path.
  freeClaudeRouter does the strip before handing the response to the
  v3 extractor.
  - **Why:** Matches the existing 200-char `reasoning` field truncation
    pattern in v2 (`server/lib/llmSchema.ts`). Zod sees only the
    structured JSON output. Adds ~10 lines.
  - **How to apply:** New helper
    `stripReasoningBlocks(content: string): string` in freeClaudeRouter.
    Regex: `/<think>[\s\S]*?<\/think>/g` + `.replace(/^reasoning_content:[^\n]*\n/m, '')`.
    Tested as first thing the parser does.

### Palantir-grade observability (Area 5)

- **D-12** New DevApiStatus blocks for v3 (gated on
  `schemaVersion === 'v3' && import.meta.env.DEV`):
  1. **Routing Trace block** — last 50 routing decisions. Each row:
     `[timestamp] batch=N → provider=nvidia_nim | model=kimi-k2.5 | reason=primary` (or `reason=fall_through:nvidia_nim_429`).
     Click row → expands to the prompt + response + parsed event.
     Sources: D-13 lineage.
  2. **Latency Histogram block** — P50 / P95 / P99 per provider over
     last 100 calls. Sparkline. Color-codes when P99 crosses watchdog
     warn threshold (60s).
  3. **Rate-Limit Headroom Gauge** — live "NVIDIA NIM 32/40 req/min
     used (60s rolling window)" + "OpenRouter daily 47/200 req used".
     Visual fill bar. Triggers fall-through prediction when ≥80%.
  4. **Schema-Strict Failure Rate block** — per-provider count of
     responses that failed Zod parse, broken down by failure mode
     (malformed JSON, missing required field, type mismatch).

- **D-13** Provenance lineage drill-down per event. Click any enriched
  event in DevApiStatus event drill-down → see:
  - Full prompt (system + user)
  - Raw response text
  - Parsed JSON
  - Chosen coord + provenance bucket
  - Resolver path taken (which of the 6 branches)
  - `<think>` reasoning trace (if present)
  - Reproducibility hash: `sha256(prompt || model || event_id)` — copy
    button so the same decision can be replayed via /api/events/llm-replay
  - **Storage:** Redis key `events:llm:v3:lineage:{eventId}`,
    bounded set capped at 500 entries (LRU eviction), 7-day TTL.
  - **Why:** Auditability is the core Palantir-grade ask. "Why did this
    event get coord X?" must be answerable from the dashboard alone.

- **D-14** Per-provider error taxonomy. Bucket errors into:
  - `rate_limit` (429 + Retry-After header set)
  - `timeout` (90s watchdog hard kill)
  - `malformed_json` (response not valid JSON)
  - `schema_fail` (Zod rejection)
  - `network` (ENOTFOUND / ECONNRESET / EAI_AGAIN)
  - `upstream_500` (provider 5xx)
  - `other` (catchall — surfaces in dashboard with raw-error preview)
    Counters per provider per UTC day; rolls into `events:llm-summary:v3`.
  - **Why:** Drives routing-policy decisions over time. "NVIDIA NIM has
    18% timeout rate this week → deprioritize."
  - **How to apply:** Extend `LLMRunSummary` interface with
    `errorTaxonomy: Record<Provider, Record<ErrorBucket, number>>`.
    `freeClaudeRouter.callLLM` classifies on every failure; counter
    increments via existing `updateProgress()` pattern.

- **D-15** Pipeline-version flip audit log. Every v1 ↔ v2 ↔ v3 flip
  (auto OR manual) recorded with:
  - timestamp (ISO)
  - from-version → to-version
  - trigger (`auto:eval_drop` | `auto:watchdog_recurrence` |
    `manual:operator_post`)
  - operator (env-tagged: dev / production / cron)
  - reason (free-text on manual flips, structured on auto)
  - **Storage:** Redis key `events:llm-pipeline-audit`, bounded list of
    last 200 entries (LREVERSE pattern), 90-day TTL.
  - **Surface:** "Recent Flips" block in DevApiStatus.
  - **Why:** Compliance + debugging. Pairs with D-16 cutover and
    D-17/D-18 rollback triggers — every flip leaves a trace.

### Cutover and rollback (Area 5 cont.)

- **D-16** Cutover gate (v3 → default pipeline):
  - **Gate A** (eval parity): `runEval()` resolver-only score
    `within20km/total ≥ 0.890` against the 50 GT events. Captured to
    `events:llm-eval-baseline:v3` with timestamp.
  - **Gate B** (production smoke): one full 184-batch production run
    with:
    - `watchdogTimeoutCount === 0`
    - `provenanceCounts` populated (no all-zero bug)
    - DLQ count ≤ 5 entries (matches Plan 07 baseline shape)
    - End-to-end completion within 120 min (1.3× v2's ~92min)
  - **Both must hit before** `POST /api/events/llm-pipeline {version: 'v3'}`
    is run as the default-flip. Pipeline pill in Topbar updates to v3.
  - **Why:** Mirrors 27.4.2 D-13 stop-condition shape. Eval-only gate
    misses production failure modes (hangs, rate-limit edge cases);
    production-only gate misses model-quality regressions.

- **D-17** Auto-rollback ladder. Both triggers fire automatically once
  v3 is the default pipeline:
  - **Trigger 1**: `watchdogTimeoutCount ≥ 3` in a single run → flip
    pipeline override back to v2; record D-15 audit entry with
    `trigger: 'auto:watchdog_recurrence'`.
  - **Trigger 2**: Re-run of `runEval()` (scheduled or on-demand)
    drops ≥5pp from the v3 cutover-gate score → flip back to v2;
    record audit entry with `trigger: 'auto:eval_drop'`.
  - Auto-flip implementation: existing `setPipelineOverride()` (in
    `server/config.ts:230-242`, mirror of 27.4.2 P6 D-07) called
    inside the v3 extractor on trigger detection. Redis cross-worker
    coherence already preserved.

- **D-18** Manual rollback always available. `POST
/api/events/llm-pipeline {version: 'v2', reason: '...'}` accepted
  at any time. Redis override has 7-day TTL. Pipeline pill in Topbar
  reflects the override (read-only post-27.4.1 D-20).

### Cost / budget tracking (Area 5 cont.)

- **D-19** Both consumption + shadow-cost tracked.
  - **Consumption tracking** (free-tier %): per-provider rolling
    counter — "NVIDIA NIM 17/40 req/min, 2.1k/day used", "OpenRouter
    47/200 daily req on kimi-k2.5". Drives D-09 fall-through.
  - **Shadow-cost** (what it would have cost on paid): per-call,
    `tokens_in × $0.20/M + tokens_out × $0.40/M` (Cerebras qwen
    benchmark rate, Cerebras paid pricing as of 2026-04). Daily roll-up
    in DevApiStatus. Quantifies "free-claude-code saved $X today" —
    material when justifying the architecture in roadmap audits.
  - **Storage:** counters in `events:llm-summary:v3` and
    `events:llm-cost-shadow:v3` (90d ring).

### Known constraints

- **NVIDIA NIM 40 req/min** — non-binding for our sequential 184-batch
  pattern (D-06). Headroom gauge in dashboard is operational, not
  load-bearing.
- **OpenRouter free model daily caps** — typically ~100-200 req/day per
  model. Only viable as fallback per D-09. Multiple OpenRouter
  models can be cycled to expand effective daily ceiling, but this
  is planner's discretion.
- **Vercel cold-start eviction** — module-level state (rate-limiter
  windows, circuit breaker) survives warm starts but resets on cold.
  Per-run watchdog count is not cross-run, so cold-start doesn't
  affect D-17 trigger 1.
- **Vendoring without Python runtime** — TypeScript port must replicate
  free-claude-code's rate-limiter behavior. Reference Python source
  during planning; document deviations.
- **`<think>`-block stripping** — must run before any JSON parse,
  including the JSON Schema validation step. Reasoning models
  occasionally emit malformed `<think>` blocks (unclosed) — strip
  is regex-tolerant per D-11 helper.

### Cutover sequence (D-16 → D-17 → D-18)

```
# Pre-cutover (in dev / staging)
1. Run multi-model bake-off:
   for model in [kimi-k2.5, glm4.7, llama-3.3-70b]:
     npm run eval:replay -- --model=<model>
2. Pick winner (closest to 0.940 within20km, ≥0.890 floor)
3. Lock winner in freeClaudeRouter config

# Cutover gate (D-16)
1. POST /api/events?force=true with LLM_PIPELINE_V3=true
2. Wait for completion (~92-120 min)
3. Check /api/events/llm-status:
   - watchdogTimeoutCount === 0
   - provenanceCounts populated
   - DLQ ≤ 5 entries
4. Run final eval:
   npm run eval:replay (against v3 winner model)
   → within20km/total ≥ 0.890

# Cutover (manual, intentional)
1. POST /api/events/llm-pipeline {version: 'v3', reason: 'cutover-gate-met'}
2. Verify Topbar pill = v3
3. Watch DevApiStatus for 24h:
   - Routing Trace populating
   - Latency P95 stable
   - Rate-limit headroom not pegged
   - Schema-fail rate < 5%

# Auto-rollback triggers (D-17, automatic; no operator action)
- If watchdogTimeoutCount ≥ 3 in any run → flip to v2 + audit entry
- If scheduled re-runEval drops ≥ 5pp from v3 cutover-gate score
  → flip to v2 + audit entry

# Manual rollback (D-18)
POST /api/events/llm-pipeline {version: 'v2', reason: '<free-text>'}
```

## Deferred Ideas

### Captured for backlog (`gsd-add-todo`)

- **Time-series eval-at-20km tracking** (`events:llm-eval-history:v3`,
  ring buffer 90d) — observability nicety; not required for v3 ship.
  Surface in DevApiStatus as sparkline if eval drift becomes a concern.
- **Schema v3 fork with optional fields** — relaxed Zod contract for
  partial enrichments. Wait until v3 production data shows whether
  the strict v2 schema causes salvageable enrichments to be lost.
- **DeepSeek paid-tier as an explicit escape hatch** — currently
  rejected per D-03 (no paid fallback in v3). Re-evaluate if
  free-tier failure rate is unacceptably high.
- **A/B production split (50/50 v2/v3)** — rejected because it
  contradicts D-03 "replace entirely". Could be revisited as a
  feature-flag-driven rollout strategy if cutover risk is too high.
- **Multi-provider race (parallel calls)** — rejected per D-07/D-09
  (sequential cascade is sufficient given non-binding rate limits).
- **Per-provider circuit breakers** (extending `llmCircuitBreaker.ts`
  Provider type with `'nvidia_nim' | 'openrouter'`) — current sliding
  window is per-`Provider`; the type union grows but the algorithm
  stays. Planner's call whether this is in scope or its own micro-plan.
- **v1 / v2 retirement** — explicitly out of scope per D-21. v1+v2
  remain shipped as rollback paths. Retirement is a future phase
  once v3 has proven stable for 30+ days.
- **Bumping Zod schema to v3** — out of scope per the schema lock
  inheritance from 27.4 D-23. Strict-mode contract relaxation
  (D-10) is at the wire level only.
- **Cloudflare Workers AI provider** (per upstream issue #169) —
  could expand the free-tier surface beyond NVIDIA NIM + OpenRouter
  but adds complexity. Defer until upstream merges.
- **MiniMax-M2.7 provider** (per upstream issue #156) — same as above.

### Considered alternatives (rejected)

- **Run real uvicorn proxy on Oracle Cloud Always Free / Render free**
  — rejected; vendoring in-process is materially simpler, fits Vercel,
  doesn't add a new service to monitor. (D-01)
- **Direct providers via OpenAI SDK without vendoring free-claude-code
  logic** — rejected; we lose the tested rate-limit handling and
  reasoning-block stripping. Hybrid approach would be vendoring
  light, which is what we picked.
- **Git submodule + Python runtime** — rejected; Python on Vercel is
  awkward, defeats the in-process integration goal.
- **OpenRouter primary** — rejected per D-07; daily caps too tight
  for primary load.
- **Multi-provider race (parallel)** — rejected; not needed given
  rate limits aren't binding.
- **Keep strict JSON Schema mode** — rejected per D-10; would force
  back onto paid providers.
- **Per-provider strict-mode capability gate** — rejected per D-10
  in favor of uniform Zod validation.
- **Eval-only cutover gate (skip production-run smoke)** — rejected
  per D-16; misses production-only failure modes.
- **A/B in production for 7 days** — rejected; doubles spend during
  comparison window, contradicts D-03.
- **Manual-only rollback** — rejected per D-17; auto-triggers catch
  failures faster than human dashboards.
- **Free-tier consumption tracking only (no shadow cost)** —
  rejected per D-19; shadow cost is the value-attribution narrative.
