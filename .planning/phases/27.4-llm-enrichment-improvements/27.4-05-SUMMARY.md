# Phase 27.4 Plan 05: Layered resolver — POI amenity + two-pass verify Summary

Wired Plan 03's two stub branches into functional implementations. POI amenity path hits Nominatim with a structured {amenity, countrycodes, viewbox} query and country-filters by address.country_code. Two-pass verify triggers on sanity gate (precision<=city OR distance>250km), fetches 5 candidates, sends them to the LLM reranker with a strict {pick, reasoning} schema. All three Nominatim paths are cache-first (Redis geocode:fwd:constrained:*) and share a 1-req/s module-level throttle spacer.

## What Shipped

### Task 1 — D-03 POI amenity branch

- `POI_AMENITY_MAP` (21 entries) translates POI keywords to canonical Nominatim `amenity` query strings. `nuclear -> nuclear power plant`, `airbase -> military airbase`, `port of -> port`, etc.
- `inferAmenity(landmark)` returns the canonical amenity string for a landmark that contains a POI keyword; uses longest-first keyword match so `naval base` wins over the standalone `naval`.
- `resolveViaPoiAmenity(hierarchy)`:
  - Gates on `hierarchy.landmark && inferAmenity !== null`
  - Hits Redis cache with `geocode:fwd:constrained:poi:amenity=<a>|country=<cc>|landmark=<l>` stable key
  - Calls `forwardGeocodeConstrained(landmark, {amenity, countrycodes: cc ?? ME_COUNTRY_CODES, viewbox: ME_VIEWBOX, addressdetails: true, limit: 3})`
  - Filters results by `address.country_code === cc` (cross-country rejection)
  - Caches hit OR `{miss: true}` under 30d redis TTL / 30d logical TTL
- `resolveViaNominatimDirect(hierarchy)` also rewritten to use `forwardGeocodeConstrained` (picks up D-02 22-country viewbox constraint) + shares the same cache + throttle.

### Task 2 — D-04 two-pass verify branch

- `rerankerResponseSchema` (Zod strict): `{pick: integer 1-5, reasoning: string <=100}`
- `RERANKER_JSON_SCHEMA` (JSON Schema): mirror of the Zod schema with `additionalProperties: false` — passed to `callLLM` via `response_format: json_schema` strict mode.
- `RERANKER_SYSTEM_PROMPT`: "You are picking the geocoding result most consistent with a conflict-event description. Output only JSON matching the schema. Do NOT invent coordinates."
- `buildRerankerUserPrompt(hierarchy, candidates, ctx)`: renders hierarchy string + ctx.summary (first 400 chars) + up to 3 ctx.articleTitles (first 140 chars each) + numbered candidate list with lat/lng/display_name/type.
- `shouldTriggerTwoPassVerify(hierarchy, hit, ctx)`:
  - FIRES when `derivePrecision(hierarchy) === 'region' || 'city'`
  - FIRES when `haversineKm(hit, centroid) > 250`
  - Otherwise returns false (direct hit accepted without verify)
- `resolveViaVerifiedTwoPass(hierarchy, ctx)`:
  - Cache-first with `geocode:fwd:constrained:verify:*` key
  - Calls `forwardGeocodeConstrained(query, {limit: 5, addressdetails: true, countrycodes + viewbox})`
  - Early-returns null if fewer than 2 candidates (pointless to rerank a single hit)
  - Calls `callLLM` with `RERANKER_SYSTEM_PROMPT + buildRerankerUserPrompt(...)` and `RERANKER_JSON_SCHEMA`
  - JSON.parse -> `rerankerResponseSchema.safeParse` -> pick-index bounds check (0 <= idx < candidates.length)
  - Falls through on any failure; direct-hit fallback handled by the dispatcher
- Dispatcher flow updated: after `resolveViaNominatimDirect` returns a hit, check `shouldTriggerTwoPassVerify`; if yes, run verify and prefer verify result; if verify fails, fall back to direct hit; otherwise continue to bellingcat/gdelt.

### Shared infrastructure

- `throttleNominatim()` — module-level 1-req/s spacer via `lastNominatimCallMs`. Every Nominatim call site (POI, direct, verify) awaits this first.
- `cacheKey(kind, parts)` — stable deterministic key builder that sorts keys alphabetically. Prevents `amenity=x|country=y` vs `country=y|amenity=x` collisions.
- `__resetThrottleForTests()` exported test helper — resets `lastNominatimCallMs = 0`. Required because the module-level state accumulates across vitest `it()` blocks in the same file, causing throttle waits that interact with `mockResolvedValueOnce` consumption order.

## Deviations from Plan

### [Rule 3 - Blocking issue] Module-level throttle state accumulated across tests

The plan did not anticipate that the module-level `lastNominatimCallMs` would poison test isolation. The first POI amenity test (in the new describe block) timed out waiting on the throttle long enough that `mockResolvedValueOnce` was consumed by the WRONG dispatch call — the POI branch received `[]` (the default), and the Natanz hit went to the direct branch instead. Visible symptom: 1 test fail out of 31, test duration 2016ms (≈ 2 consecutive 1s throttle waits instead of the expected 1 wait).

Fix: added `__resetThrottleForTests()` exported from `server/lib/llmResolver.ts` and called from every `beforeEach`. Pattern mirrors the existing `__resetSitesSnapshotCacheForTests` and `__resetSnapshotCacheForTests` test-only helpers already established in sitesSnapshot.ts and waterSnapshot.ts. No production behavior change.

Files modified:
- `server/lib/llmResolver.ts` — added `export function __resetThrottleForTests()` (4 lines)
- `server/__tests__/lib/llmResolver.test.ts` — added `__resetThrottleForTests()` call at top of 3 `beforeEach` blocks (3 lines)

Tracked as: `[Rule 3 - Blocking issue] Added test-only throttle reset`
