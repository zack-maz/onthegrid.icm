# Phase 27.4: LLM Enrichment Improvements - Context

**Gathered:** 2026-04-20
**Status:** Ready for planning

<domain>
## Phase Boundary

Raise the LLM-enriched event pipeline to Palantir-grade accuracy and observability. Three coupled deliverables:

1. **Geolocation accuracy** — layered resolver (structured hierarchy + regional-constrained Nominatim + POI-type specialist + sanity-gated 2-pass verify) replaces today's single-shot extract-and-geocode.
2. **Richer extraction** — prompts fed with cross-matched news titles, Bellingcat OSINT blocks, and prior-event temporal context; output schema extends with confidence + reasoning, weapon/target classification, and time-of-day / duration.
3. **Dedicated Events section in DevApiStatus** — pipeline waterfall, precision/confidence histograms, per-event drill-down with prompt replay, LLM call log with token/cost tracking, accuracy eval harness, geocoding provenance, deviation/outlier detection.

Ships with flag-gated rollout, bounded retry + DLQ, tracked token budget, and cache-version bump (`events:llm` → `events:llm:v2`).

**Out of scope (deferred):**

- Scraped article bodies (HTTP fragility + legal gray area; revisit if news-title accuracy insufficient)
- LLM fine-tuning or custom model hosting
- Multi-language prompt variants
- User-facing (non-dev) accuracy indicators on the production UI — dev panel only

</domain>

<decisions>
## Implementation Decisions

### Geolocation Accuracy (layered resolver)

- **D-01:** LLM output replaces single `location.name` with a structured place hierarchy: `{ country, admin1, city, neighborhood, landmark, confidence }`. Confidence is 0–1 numeric. Each hierarchy field nullable; LLM emits only what it can justify from source text. Precision indicator (`exact | neighborhood | city | region`) is derived from the deepest non-null field.
- **D-02:** Every Nominatim call is constrained by `countrycodes=IR,IQ,SY,LB,IL,PS,JO,EG,SA,AE,BH,KW,OM,QA,YE,TR,AF,PK,TM,AZ,AM,GE` plus a Middle East viewbox. Eliminates "Damascus, Maryland" class misses at zero extra cost.
- **D-03:** POI-type specialist path: when the extracted landmark has a facility flavor (nuclear / military / port / airbase / dam / reservoir), the resolver first checks the project's own `sites:overpass` and `water:facilities:v3` snapshots for a name match within country. On miss, queries Nominatim with an amenity/landuse filter. Named-facility events (Natanz, Bandar Abbas, Dimona) should near-perfect-match via this path.
- **D-04:** Sanity gate: after resolution, if the coord falls outside the GDELT ActionGeo bounding box + 250 km tolerance, OR if precision ≤ `city`, trigger the two-pass verify — Nominatim returns top-5 candidates (already constrained by D-02), LLM is asked to pick the one consistent with the source text. Bounded to the ambiguous subset so cost stays predictable.
- **D-05:** Reject geocode-in-prompt (where LLM emits coordinates directly). Preserves Phase 27 D-05 "never invent coordinates." LLM stays on names; geocoding stays deterministic.

### Prompt Input Enrichment

- **D-06:** News cache cross-match — each event group joins against `news:gdelt` by time (±24h) and location proximity (haversine, radius tied to group's centroid uncertainty). Matched article titles + snippets are inserted into the prompt, tagged by source tier (Tier 1 gold / Tier 2 silver / Tier 3 bronze via existing `sourceTiers.ts`). Zero new I/O.
- **D-07:** Bellingcat OSINT block — when `extractBellingcatGeo`-matched articles exist for the group, they render as a separately-tagged high-trust section in the prompt (distinct from general news). Bellingcat prose frequently contains lat/lng which the LLM can pass straight into `landmark`.
- **D-08:** Temporal context block — last 3–5 enriched events in same region (within bbox + 72h) included in prompt as lightweight context. Helps name-consistency ("the Jobar substation" vs one-off mentions). Pulled from `events:llm:v2` cache, zero new I/O.
- **D-09:** Defer scraped article bodies. Revisit in future phase if accuracy still gaps after D-06–D-08 land.
- **D-10:** `BATCH_SIZE` drops `8 → 2` groups per call. Richer input per group demands full LLM attention per event bundle. (Phase 27.2 D-02 decided 8→4 but did not ship; 27.4 goes further.)

### Extraction Output Schema

- **D-11:** `location` object replaced with structured hierarchy per D-01.
- **D-12:** Add `confidence: number` (0–1) and `reasoning: string` (≤200 chars) per event. `reasoning` cites which signals led to the location pick — makes every event auditable in DevApiStatus drill-down.
- **D-13:** Add `weaponType: 'airstrike' | 'drone' | 'missile' | 'artillery' | 'small_arms' | 'IED' | null` and `targetType: 'military' | 'infrastructure' | 'civilian' | 'leadership' | null`. Enables threat-class filtering and pattern detection.
- **D-14:** Add `timeOfDay: 'HH:MM' | null` (UTC) and `durationMinutes: number | null`. Extracted when articles mention strike times; gives timeline precision beyond GDELT's midnight-UTC stamp.

### DevApiStatus Events Section (Palantir-grade UI)

- **D-15:** New dedicated section below existing per-source rows. Collapsible. Rendered dev-only (same `NODE_ENV !== 'production'` gate as today).
- **D-16:** Pipeline waterfall + throughput — horizontal timeline bar per stage (grouping → llm-processing → geocoding → done) with per-stage durations. Adjacent readouts: batches/min, geocodes/min, current concurrency.
- **D-17:** Precision + confidence distribution — histogram bars for precision buckets (exact / neighborhood / city / region), confidence buckets (0–.2, .2–.4, .4–.6, .6–.8, .8–1), source-tier distribution (gold/silver/bronze), and casualty-bearing event count.
- **D-18:** Per-event drill-down — expandable list of recent N (default 50) enriched events. Each row shows: place hierarchy, precision, confidence, reasoning, weapon/target, LLM tokens in/out, geocoding provenance path, sources. Click to copy full prompt+response JSON for debugging.
- **D-19:** LLM call log + token/cost — rolling log of last N (default 20) LLM calls: provider (cerebras/groq), model, tokens in/out, duration, success/fail, batch size. Cumulative run totals for the day. Driven by existing `llmProgress.ts` extended with a call-history array.

### Palantir-Grade Extras

- **D-20:** Accuracy eval harness — manually curated ground-truth set of 20–30 known events (verified coords from Bellingcat/ISW) committed to the repo. On every LLM run the harness quietly re-extracts the ground-truth set and reports accuracy at 5km / 20km / 100km thresholds in DevApiStatus. Precision-drift alarm: a baseline score is written to Redis, deltas surface in the dashboard.
- **D-21:** Prompt replay / shadow mode — DevApiStatus button "re-extract with current prompt" on any cached event. Shows side-by-side old vs new extraction. Enables prompt iteration without touching production cache.
- **D-22:** Geocoding provenance — every event records which resolver path produced its coord: `own-site-snapshot` | `poi-amenity-nominatim` | `nominatim-direct` | `nominatim-verified-2pass` | `gdelt-actiongeo-fallback` | `bellingcat-coord-passthrough`. Shown per-event in drill-down, aggregated as a pie chart in the Events section.
- **D-23:** Deviation / outlier detection — events are flagged "suspect" when any of: confidence < 0.5, precision = `region`, resolved coord > 100km from GDELT ActionGeo, or all source URLs are Tier 3. Suspect count + filterable list surface in DevApiStatus for spot-checking.

### Rollout Strategy

- **D-24:** Env var `LLM_PIPELINE_V2` toggles old vs new extraction pipeline. Default off in prod, on in dev.
- **D-25:** Prod flip gated on eval harness hitting ≥ 80% of ground-truth events within 20 km. Gate enforced by `/api/events/llm-status` returning eval score; deploy ritual checks it before flipping.
- **D-26:** Old v1 extractor code preserved under `server/lib/llmEventExtractor.v1.ts` for one phase as rollback path. Deleted in 27.5.
- **D-27:** Reject shadow mode (doubles daily token load; eval harness gives accuracy signal without the cost). Reject hard cutover (no rollback path on regression).

### Error Handling + Retry Budget

- **D-28:** Per-event retry budget = 2 attempts (same provider, exponential backoff 1s / 4s).
- **D-29:** Provider fallback chain Cerebras → Groq → raw GDELT (preserves 27 D-06 graceful degradation).
- **D-30:** Events exhausting all retries go to Redis dead-letter set `events:llm-dlq` with `{id, reason, lastError, timestamp}` payload. DLQ count + recent entries surface in DevApiStatus for manual triage.
- **D-31:** Circuit breaker: if a provider's error rate exceeds 30% in its last 10 calls, pause that provider for 5 minutes; fall through to next provider in chain.

### Token Budget + Rate Limits

- **D-32:** Track daily tokens per provider in Redis under `llm:tokens:{provider}:YYYY-MM-DD` (TTL 48h). Incremented on each successful call.
- **D-33:** Soft cap at 80% of daily limit (Cerebras 800K / Groq 160K) → pause new-event processing, keep serving cached LLM events.
- **D-34:** Hard cap at 95% of daily limit (Cerebras 950K / Groq 190K) → switch provider; if both hard-capped, disable LLM pipeline for the day, serve raw GDELT.
- **D-35:** Near soft cap, prioritize new + high-severity events over reprocessing older ones.
- **D-36:** DevApiStatus renders per-provider budget bar `cerebras: 230K/1M (23%) ∙ groq: 15K/200K (7.5%)` inside the Events section.

### Cache Versioning + Schema Evolution

- **D-37:** Bump cache key `events:llm` → `events:llm:v2`. Similarly `events:llm-summary` → `events:llm-summary:v2`. Old v1 keys are ignored and age out naturally via Redis TTL.
- **D-38:** Dev file cache follows same versioning: `dev-llm-cache.json` → `dev-llm-cache-v2.json`.
- **D-39:** LLM summary payload gains `schemaVersion: 'v2'` so DevApiStatus can display which schema is serving the map.
- **D-40:** Rollback path: setting `LLM_PIPELINE_V2=false` flips the resolver back to v1 code; v1 cache is regenerated on the next miss (same pattern as today).

### Claude's Discretion

- Exact LLM prompt wording and few-shot examples (planner will draft; iterate against eval harness)
- Ground-truth event set curation (Claude proposes candidates from Bellingcat/ISW archives; user signs off before committing)
- Histogram visual styling in DevApiStatus (match existing per-source row aesthetic)
- Circuit breaker sliding-window implementation (array vs counter)
- Whether retry backoff uses jitter
- DLQ size cap and eviction policy
- Exact copy format for "copy prompt+response JSON" button (pretty JSON vs compact)

<specifics>
## Specific Ideas

- "Palantir-grade" means: every event pin is auditable (who extracted it, what sources, what confidence, what resolver path), every pipeline run is measurable (accuracy score, token cost, throughput), every failure is actionable (DLQ with reason, deviation flags). Not polish — load-bearing observability.
- The eval harness is the north-star metric. Without a ground-truth set, we're guessing whether the pipeline improved. Curate 20–30 events with verified coords (Bellingcat, ISW war maps), commit to `.planning/eval/ground-truth-events.json`, run on every LLM invocation.
- DevApiStatus is the single-pane-of-glass. Every decision in this phase should surface there — not scattered across logs, Redis keys, and code. If you can't see it in the panel, it effectively doesn't exist.
- The POI specialist path (D-03) is the accuracy multiplier for this app specifically. Named facilities (Natanz, Dimona, Bandar Abbas, Al Udeid) are what the user cares about most — they map onto the existing sites/water overlays. Hitting these accurately ≥ 95% of the time is more valuable than marginal gains on generic city-level events.
- Flag-gated rollout (D-24) must land before any other change touches production. Everything else can ship behind the flag and iterate safely.

</specifics>
