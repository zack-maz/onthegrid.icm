# Phase 27.4: Code Review Report

**Reviewed:** 2026-04-20
**Depth:** standard
**Files Reviewed:** 34
**Status:** issues_found

## Summary

Phase 27.4 delivers a substantial LLM enrichment pipeline overhaul. The architecture is sound and the threat-model concerns from the phase brief are largely handled correctly. The dual-gate on `/llm-replay`, the D-05 `.strict()` enforcement in the v2 Zod schema, the Nominatim viewbox/countrycodes defaults, the DLQ `lastError` 500-char cap, and the resolver provenance tagging are all implemented correctly. The eval harness correctly calls only the resolver, never `callLLM` directly, satisfying A6/Pitfall 8.

One critical issue is present: the `forwardGeocode` (unconstrained, legacy) function is still called directly from `llmEventExtractor.v1.ts` without any geographic constraint, creating a geographic-scope bypass for the v1 pipeline path that will remain active during the rollout window. A group of warnings cover a throttle gap in the two-pass verify path, a DLQ eviction bug under concurrent write races, a batch-count progress tracking discrepancy, and an unchecked integer overflow in the DLQ eviction loop. Three info items cover code quality.

## Critical Issues

### CR-01: v1 extractor calls unconstrained `forwardGeocode` — geographic bypass during rollout window

**File:** `server/lib/llmEventExtractor.v1.ts:2`
**Issue:** The v1 extractor (preserved as rollback path per D-26, active when `LLM_PIPELINE_V2=false`) imports and calls `forwardGeocode` — the unconstrained legacy adapter — not `forwardGeocodeConstrained`. During the rollout window where both pipelines may be exercised (D-40 rollback scenario), the v1 path can resolve place names to coordinates outside the Middle East viewbox. The D-02 security requirement ("eliminate 'Damascus, Maryland' class misses") is not enforced for v1. While the v2 path correctly uses `forwardGeocodeConstrained` via `llmResolver.ts`, the v1 path is also reachable in production (`LLM_PIPELINE_V2=false` is the default per `.env.example`).

**Fix:**

```typescript
// In server/lib/llmEventExtractor.v1.ts — replace the unconstrained import:
// BEFORE:
import { forwardGeocode } from '../adapters/nominatim.js';

// AFTER:
import { forwardGeocodeConstrained } from '../adapters/nominatim.js';
import { ME_VIEWBOX, ME_COUNTRY_CODES } from '../lib/meBounds.js';

// And replace any forwardGeocode(placeName, countryCode) call with:
const [result] = await forwardGeocodeConstrained(placeName, {
  countrycodes: countryCode ?? ME_COUNTRY_CODES,
  viewbox: ME_VIEWBOX,
  limit: 1,
});
// result is undefined if empty array; treat null the same as before
```

## Warnings

### WR-01: Throttle not applied on the two-pass verify Nominatim call — can burst to 2 req/s

**File:** `server/lib/llmResolver.ts:372-376`
**Issue:** In `resolveViaVerifiedTwoPass`, `throttleNominatim()` is called before the constrained fetch for the top-5 candidate list. However, this function is triggered only when `resolveViaNominatimDirect` has already called `throttleNominatim()` for the direct query. The direct query sets `lastNominatimCallMs = Date.now()` (line 42), then the two-pass verify immediately calls `throttleNominatim()` again. If the direct query is cache-served (no actual Nominatim HTTP call) but still calls `throttleNominatim`, the elapsed-time calculation may be satisfied before the two-pass call fires, meaning two HTTP requests reach Nominatim within the same second when the direct query was a cache hit. The Nominatim usage policy caps at 1 req/s. Under load, two requests can land simultaneously (one from the direct path and one from the verify path).

The root cause: `throttleNominatim()` is called before checking the Redis cache in `resolveViaNominatimDirect`. If the cache miss occurs AND verify is triggered, the next Nominatim call (verify's top-5) may land within 1s of the previous one because `lastNominatimCallMs` was set by the first `throttleNominatim()` call, and the cache lookup + short JSON parse fills enough of the gap on fast Redis but not on slow connections.

**Fix:** Move the `throttleNominatim()` call in both Nominatim-calling functions to immediately before the `fetch()` call rather than before the cache-check:

```typescript
// Pattern to apply in both resolveViaNominatimDirect and resolveViaVerifiedTwoPass:
// After cache miss is confirmed, before the fetch:
const cached = await cacheGetSafe<...>(key, ...);
if (cached?.data) {
  // cache hit — no throttle needed, no Nominatim call
  if ((cached.data as { miss?: boolean }).miss) return null;
  return cached.data as SnapshotHit;
}
// Only throttle here — after confirming we will actually hit Nominatim
await throttleNominatim();
const candidates = await forwardGeocodeConstrained(...)
```

### WR-02: DLQ eviction JSON re-stringify may not match the stored sadd payload — srem silently no-ops

**File:** `server/lib/llmDLQ.ts:56-58`
**Issue:** The eviction loop at line 57-58 serializes entries to remove via `JSON.stringify(e)` on each parsed `DLQEntry`. However, the payload originally stored in Redis was serialized from the `capped` object at line 44 (`JSON.stringify(capped)`). If the JSON.stringify output for `e` (deserialized and re-serialized) does not byte-for-byte match the original stored string (e.g. due to key ordering differences in the Redis storage layer or Upstash REST encoding), the `srem` call silently no-ops and the DLQ never shrinks below `DLQ_MAX`. Redis set members are compared by byte equality; `JSON.stringify` object key ordering is insertion-order in V8 but there is no guarantee the round-trip matches the original stored string when Upstash serializes/deserializes the payload.

**Fix:** Store a canonical serialization and use the raw members string directly for `srem`:

```typescript
// Replace the toRemove construction:
const toRemove = parsed.slice(0, size - DLQ_MAX).map((e) => e.__raw as string); // store raw string alongside parsed

// Alternatively, use the raw strings from `all` (already available):
const rawAll = await redis.smembers(DLQ_KEY);
const withParsed = rawAll
  .map((raw) => ({ raw, parsed: parseEntry(raw) }))
  .filter((x): x is { raw: string; parsed: DLQEntry } => x.parsed !== null);
withParsed.sort((a, b) => a.parsed.timestamp - b.parsed.timestamp);
const toRemove = withParsed.slice(0, size - DLQ_MAX).map((x) => x.raw);
if (toRemove.length > 0) await redis.srem(DLQ_KEY, ...toRemove);
```

### WR-03: Progress `totalBatches` computed with `BATCH_SIZE=8` (v1) in fire-and-forget block when v2 is active

**File:** `server/routes/events.ts:800`
**Issue:** When the v2 pipeline is active (`isPipelineV2() === true`), the fire-and-forget block sets `totalBatches` using `Math.ceil(prioritizedGroups.length / 8)` — hardcoded to 8, the v1 batch size. The v2 extractor uses `BATCH_SIZE = 2` (exported from `llmEventExtractor.v2.ts`). This causes the `/api/events/llm-status` progress bar in DevApiStatus to display the wrong total batch count (4x too high), potentially showing "2 / 50 batches" when in fact there are only 13. The `completedBatches` count reported by `onBatchComplete` callbacks uses the actual v2 batch index, so the ratio will appear to stall.

**Fix:**

```typescript
// In server/routes/events.ts — replace the hardcoded 8:
import { BATCH_SIZE as BATCH_SIZE_V2 } from '../lib/llmEventExtractor.v2.js';

// Then:
const effectiveBatchSize = pipelineV2 ? BATCH_SIZE_V2 : 8;
updateProgress({
  stage: 'llm-processing',
  totalBatches: Math.ceil(prioritizedGroups.length / effectiveBatchSize),
});
```

### WR-04: `resolveViaVerifiedTwoPass` caches a miss when only 1 candidate returned, but single-candidate results are usable

**File:** `server/lib/llmResolver.ts:379-382`
**Issue:** The two-pass verify branch guards `if (candidates.length < 2)` before running the LLM reranker, returning null and caching a miss. This is intentional for the 2-pass use-case, but it means that when the Nominatim top-5 query returns exactly 1 result (unambiguous match), the code caches a miss and falls through to the Bellingcat or GDELT fallback instead of accepting the single high-confidence candidate. This is a conservative design choice, but combined with the cache-miss write, it means a query that would correctly resolve via a single Nominatim result is permanently (for 30 days) routed to the lower-quality GDELT fallback for the same location hierarchy query, even if the single candidate is correct.

**Fix:** Accept a single-candidate result directly without LLM reranking — the whole point of the 2-pass is disambiguation; one candidate needs no disambiguation:

```typescript
if (candidates.length === 0) {
  await cacheSetSafe(key, { miss: true }, GEOCODE_CACHE_REDIS_TTL_SEC);
  return null;
}
if (candidates.length === 1) {
  // Single unambiguous result — accept without LLM reranking
  const first = candidates[0]!;
  const hit: SnapshotHit = { lat: first.lat, lng: first.lng, displayName: first.displayName };
  await cacheSetSafe(key, hit, GEOCODE_CACHE_REDIS_TTL_SEC);
  return hit;
}
// 2+ candidates: run LLM reranker
```

## Info

### IN-01: `forwardGeocode` (unconstrained) has no rate-limiter; test comment acknowledges caller responsibility but v1 extractor does not honour it

**File:** `server/__tests__/adapters/nominatim-forward.test.ts:74-98`
**Issue:** The test for `forwardGeocode` contains a comment "the rate limiting is enforced at the caller level in geocodeEnrichedEvents." Inspection of `llmEventExtractor.v1.ts` shows the v1 geocoder calls `forwardGeocode` sequentially in a loop without any throttle. The v2 path uses `throttleNominatim()` inside `llmResolver.ts`. The v1 loop in `geocodeEnrichedEvents` (v1) has no sleep between iterations, potentially firing N Nominatim requests in rapid succession during geocoding of a full batch. This is acceptable for the personal/dev context but warrants documentation.
**Fix:** Add a 1-second delay between Nominatim calls in `geocodeEnrichedEvents` (v1) to match the Nominatim usage policy, or add a comment acknowledging the intentional omission for the rollback-only path.

### IN-02: `ME_VIEWBOX` format inconsistency with Nominatim docs comment

**File:** `server/lib/meBounds.ts:13`
**Issue:** The comment states "Viewbox format per Nominatim docs: [lng1, lat1, lng2, lat2]" but `ME_VIEWBOX = [30, 15, 70, 42]` places (west=30, south=15, east=70, north=42). Nominatim's `viewbox` parameter expects `left,top,right,bottom` which is `left=west, top=north, right=east, bottom=south` — making the correct order `[west, north, east, south]` = `[30, 42, 70, 15]`. The current value `[30, 15, 70, 42]` is `[west, south, east, north]` which is the bounding box, not Nominatim's expected viewbox order. This may cause Nominatim to treat the viewbox as inverted (south > north in the wrong positions). Verify the Nominatim API handles the current ordering correctly.
**Fix:** Verify with a Nominatim test call. If the ordering is wrong, correct to `[30, 42, 70, 15]` and update the comment to match the actual parameter order used.

### IN-03: `shouldPauseNewEvents` checks EITHER provider at soft-cap — overly conservative for v2

**File:** `server/lib/llmTokenBudget.ts:137-146`
**Issue:** `shouldPauseNewEvents` returns true when _either_ provider reaches the 80% soft cap. Because the v2 callLLM adapter tries Cerebras first then Groq, exhausting Cerebras-soft-cap should not pause processing if Groq is still under its soft cap — there is a healthy fallback. The current logic pauses all new LLM processing when Cerebras hits 800K/day even though Groq has 160K available. This is conservative (as noted in comments) but for a solo-dev system where missed events are costly, the OR logic may cause unnecessary pipeline pauses.
**Fix:** Consider changing to `budgetState('cerebras', cerebrasUsed) === 'soft' && budgetState('groq', groqUsed) === 'soft'` (AND instead of OR) so processing only pauses when both providers are constrained — mirroring the hard-cap behavior in `callLLM` which skips a provider individually but falls through to the next.
