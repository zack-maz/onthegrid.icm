## 3. The Gate-Swap Contract (D-06)

This section is the load-bearing part of Phase 28.2's UI surface. Every promoted field follows the same mechanical rule:

**Before:** `{import.meta.env.DEV && <FieldOrBlock />}`
**After:** `{shouldRenderDashboard() && <FieldOrBlock />}`

`shouldRenderDashboard()` is imported from `@/lib/dashboardAuth` (already exported at `src/lib/dashboardAuth.ts:52`). The helper returns `import.meta.env.DEV || hasDashboardKey()` — meaning every promoted field renders identically in dev (current behavior preserved) AND in prod-with-Bearer (new behavior), and is hidden in prod-without-Bearer (current behavior preserved).

**Same render. Same styling. Same copy. Same spacing. Same color.** The promoted fields look byte-for-byte identical to today's dev render; only the visibility predicate changes.

### 3.1 EntityTooltip — Event ID stub

**Current dev block** (`src/components/map/EntityTooltip.tsx:125`):

```tsx
{
  import.meta.env.DEV && (
    <span style={{ color: '#6b7280', fontSize: '8px', marginLeft: '4px' }}>
      {entity.id.slice(0, 12)}
    </span>
  );
}
```

**Phase 28.2 contract:** swap predicate to `shouldRenderDashboard()`. Inline `<span>` styling preserved verbatim:

- Color `#6b7280` (gray-500) — preserved.
- Font size `8px` — preserved (intentionally smaller than the parent tooltip's `11px` body to read as a tertiary debug subscript).
- Left margin `4px` — preserved.
- Truncation to `entity.id.slice(0, 12)` — preserved.

### 3.2 EventDetail — Event ID row

**Current dev block** (`src/components/detail/EventDetail.tsx:56`):

```tsx
{
  import.meta.env.DEV && <DetailValue label="ID" value={entity.id} />;
}
```

**Phase 28.2 contract:** swap predicate to `shouldRenderDashboard()`. The `DetailValue` component's existing styling (label + value row, `px-3 py-1`, label `text-[10px] uppercase tracking-wider`, value tabular-nums on the right) is preserved verbatim.

The full `entity.id` is shown (not truncated like the EntityTooltip subscript) — this mirrors the current dev behavior. No change to truncation rules.

### 3.3 EventDetail — Confidence + Geo Precision rows

**Current dev block** (`src/components/detail/EventDetail.tsx:165`):

```tsx
{
  import.meta.env.DEV && d.confidence != null && (
    <div className="mt-2 border-t border-white/5 pt-2">
      <DetailValue label="Confidence" value={d.confidence.toFixed(3)} />
      {d.geoPrecision && <DetailValue label="Geo Precision" value={d.geoPrecision} />}
    </div>

```

**Phase 28.2 contract:** swap predicate to `shouldRenderDashboard()`. The wrapper styling is preserved verbatim:

- `mt-2` — top margin 8px (separates from preceding "Source" section).
- `border-t border-white/5 pt-2` — top divider with 8px padding above the rows. The `border-white/5` color (white at 5% alpha) is intentionally subtle — it reads as "internal subdivider", not "new section".
- `Confidence` value formatted to 3 decimals via `.toFixed(3)`.
- `Geo Precision` value is the raw `geocodeProvenance` enum string (e.g. `nominatim-verified-2pass`) — no remapping, no humanization. This is operator surface, not user surface.

### 3.4 WaterFacilityDetail — OSM ID row

**Current row** (`src/components/detail/WaterFacilityDetail.tsx:117`):

```tsx
<DetailValue label="OSM ID" value={String(facility.osmId)} />
```

**Caveat — already always-rendered.** Unlike the three EventDetail/Tooltip surfaces, the OSM ID row in WaterFacilityDetail is currently rendered regardless of `import.meta.env.DEV`. The 28-CONTEXT.md D-06 list names it as a graduation target, but the surface inspection above confirms it does NOT carry a `DEV` gate today.

**Phase 28.2 contract:** the planner has two paths and must pick one before writing the gate-swap commit:

**Path A — preserve current behavior (recommended):** OSM ID row remains always-rendered, no gate added. The CONTEXT D-06 entry is treated as documenting the existing surface's classification ("OSM ID is operator-tier, currently leaks to all users — but it's been there since Phase 15 and removing it is a regression risk on a load-test-adjacent phase").

**Path B — apply the Bearer gate:** wrap the row in `{shouldRenderDashboard() && <DetailValue ... />}`. This is the literal D-06 contract reading; cost is one row disappearing from public WaterFacilityDetail panels.

**Decision deferred to planner.** Either path is contract-compliant for this phase. Whichever path the planner picks must be committed atomically with a one-line CONTEXT.md note (D-06 clarification) and a UAT-trace screenshot before merge.

### 3.5 Render parity test contract

The gsd-executor must verify the gate swap is byte-equivalent in dev. For each of the four surfaces:

1. Snapshot dev render BEFORE gate swap (`vitest run` — snapshot test or visual screenshot).
2. Apply gate swap.
3. Snapshot dev render AFTER gate swap.
4. Diff the two snapshots — they MUST be byte-identical. Any difference = bug, fix it.
5. Add a Bearer-prod render snapshot (mock `localStorage` with the Bearer key set) — this MUST match the dev snapshot byte-for-byte.
6. Add a no-Bearer prod render snapshot (mock `import.meta.env.DEV === false` + no Bearer) — the promoted block MUST be absent.

This three-snapshot test applies per surface. Total: 12 snapshots across 4 surfaces. Path B for §3.4 adds 3 more snapshots (15 total).

## 4. Surface-Integrity Invariant (Non-Regression)

This invariant comes from CONTEXT D-07 and is the load-bearing surface principle that Phase 28.2 must NOT regress.

> **Whenever `shouldRenderDashboard()` is true, the operator dashboard surface (DevApiStatus modal trigger in Topbar, the merged API Health tab, Water tab, Sites tab, Events tab, plus the read-only Topbar pipeline pill) is ALWAYS visible — regardless of layer-toggle state, regardless of cold-start cache state, regardless of which entity (if any) is selected.**

This was established in Phase 27.4.6 (which dropped the prior `useLayerStore.activeLayers.has('water')` gate that hid the Water tab on cold start, and the prior `schemaVersion === 'v2' && import.meta.env.DEV` gate that hid the Events tab on cold start). The fix was: **dashboard surface is decoupled from layer-state and from data-state.**

### Invariant assertions (planner: code these as vitest tests)

For each of the 4 tabs (API Health / Water / Sites / Events) under each of these conditions, the tab MUST render:

| Condition                                        | API Health | Water  | Sites  | Events | Topbar Pill |
| ------------------------------------------------ | ---------- | ------ | ------ | ------ | ----------- |
| Dev + cold cache + no layers active              | render     | render | render | render | render      |
| Bearer-prod + cold cache + no layers active      | render     | render | render | render | render      |
| Bearer-prod + warm cache + Water layer off       | render     | render | render | render | render      |
| Bearer-prod + warm cache + Events filter cleared | render     | render | render | render | render      |
| No-Bearer prod + warm cache                      | hidden     | hidden | hidden | hidden | hidden      |

The lone gate is `shouldRenderDashboard()`. No other predicate participates in tab visibility.

### Single-poll contract preserved (Phase 28.1 W2)

Phase 28.1 W2 established `HealthStatusProvider` as the single source for `/api/health` polling — `HealthBanner` + `DevApiStatusAllApisTab` consume from one provider instance, one poll cycle per interval. **Phase 28.2's W5 merge MUST preserve this.** The merged `apiHealth` tab consumes via `useHealthStatusContext()` only — it MUST NOT call `useHealthStatus()` directly. Test 7 in `src/components/providers/__tests__/HealthStatusProvider.test.tsx` enforces "TWO consumers inside ONE provider → exactly ONE `/api/health` call per cycle" and remains the gating test.

`HealthBanner` is intentionally NOT gated by `shouldRenderDashboard()` — D-26 only gates the merged tab. This is correct: HealthBanner is a public-tier critical-outage signal (no operator data leaked), the merged tab is the operator's drill-down. Two surfaces, two visibility rules, one provider.

### 5.3 Four new diagnostic blocks (D-23)

Per AI-SPEC §7 these blocks live on the merged API Health tab. The visual primitives are inline and reuse existing Tailwind utilities + existing block-styling patterns from the current `DevApiStatusAllApisTab`. **No new components, no new color tokens, no new typography.**

#### 5.3.1 Tier-grouped summary banner

**Position:** top of the API Health tab, above the per-endpoint table.

**Structure:** single horizontal row.

**Copy template:** `15 of 16 healthy · 1 degraded · 0 unhealthy` followed by a per-tier breakdown line `critical: 5/5 · non-critical: 9/10 · cron: 1/1`.

No new color tokens. Reuse `colorBridge.ts` exports.

#### 5.3.2 Per-endpoint quality metrics

**Position:** inside each expanded row's JSON dump area, ABOVE the JSON dump.

**Per-endpoint copy:**

| Endpoint        | Quality metrics shown                                                                             |
| --------------- | ------------------------------------------------------------------------------------------------- |

#### 5.3.3 Per-endpoint manual retry button (Bearer-gated UI)

**Position:** inside each expanded row, below the quality metrics block.

**Visual:** small inline button, `text-xs px-2 py-0.5 rounded border border-white/10 hover:bg-white/5`. Existing button-pattern in DevApiStatus.

**Copy:** `Refresh now` (NOT "Retry" — refresh is what the operator wants; retry implies failure).

**Disabled state:** while a refresh is in-flight, button shows `Refreshing...` with no spinner glyph (text-only — keep visual budget tight; the next-poll countdown tick already provides motion in the row).

**Bearer gate:** the button itself only renders when `shouldRenderDashboard()` is true (the merged tab is already gated, so the button inherits — but it's worth restating here that this surface is operator-only, never user-facing).

**Cache-bust mechanic:** Claude's discretion at planning time per CONTEXT (direct store action vs. cache-bust query param vs. dedicated route).

#### 5.3.4 Recent-fetch sparkline

**Position:** inside the per-endpoint table row (NOT the expanded view) — a compact 10-dot strip in the rightmost column before the chevron.

**Visual:** flex row of 10 small dots, 4px diameter, 2px gap. Each dot represents one entry from `recentFetches[]`, oldest-left → newest-right.

**Color encoding:**

- ok = green (reuse `#22c55e` via colorBridge `--color-site-healthy`).
- fail = red (reuse `#ff3b30` via colorBridge `--color-event-airstrike`).
- empty slot (fewer than 10 fetches in store) = `bg-white/10` placeholder dot (existing utility).

**Implementation primitive:** inline `<div className="flex gap-0.5">` of `<span className="w-1 h-1 rounded-full" style={{backgroundColor: ...}} />`. NO SVG, NO new chart helper — keep the visual budget as tight as the data allows.

**No tooltip on hover.** The sparkline is a glance signal; the JSON dump in the expanded row carries the full timestamp+latency+status detail.

### 5.4 W6 connectivity-audit banner (D-25)

**Position:** below the tier-grouped summary banner, above the per-endpoint table.

**Visual:** a single horizontal bar, padding `px-3 py-1.5`, rounded `rounded`. Color:

- All endpoints connecting → `bg-green-500/10 border border-green-500/20 text-green-400` (existing utility set used elsewhere in the modal).
- Any endpoint not connecting → `bg-red-500/10 border border-red-500/20 text-red-400`.

**Copy:**

The audit result is sourced from a lightweight Redis sidecar key (planner picks key + TTL). The banner reads via `/api/health` extension or via a dedicated `/api/audit-status` route — Claude's discretion at planning time.

**Color:** amber — `bg-amber-500/10 border border-amber-500/20 text-amber-400`. (NOT red — quota-hit is expected operator behavior, not an error.)

Already specified in §5.4 above.
