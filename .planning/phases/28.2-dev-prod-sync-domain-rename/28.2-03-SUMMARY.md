## Decisions Made

- **Cap value 50 is hard-coded, not env-tunable** — CONTEXT D-09 explicitly says "no new env-tunable surfaces" for this phase. The cap is a threat-model parameter (the daily-token-budget exhaustion mitigation calibrated against Cerebras 1M/day free-tier), not an operator-tunable knob. If the cap ever needs to move, it's a planned phase change (PR + commit), not a Vercel env redeploy.
- **operator:audit-log is a NEW Redis key namespace, distinct from the existing events:llm-pipeline-audit** — pipelineAudit captures from→to provenance with a `trigger` discriminator (manual:operator_post / auto:eval-drop / etc) used by rollback automation. operatorAudit captures the SHA-256 Bearer fingerprint for the AI-SPEC §7 dashboard surface. The two log slightly different facts at slightly different cadences; coexisting is correct, not duplicative.
- **Adversarial harness reuses runEval's resolver-only pattern (per A6 / Pitfall 8)** — running the full LLM extractor against the 10-entry fixture would add ~20K tokens/day, well within budget on a healthy day but costly on a degraded day. Resolver-only execution exercises the defensive layers being measured (Zod-strict + viewbox constraints + non-leakage) at zero token cost. The token-budget hard-cap short-circuit is defense-in-depth.
- **8-test matrix for adversarial harness instead of the planned 7** — added Test 3b (LEAK criterion) alongside the planned Test 3 (BLOCK criterion). The BLOCK + LEAK pair establishes the PASS rubric symmetrically; either alone would leave a gap. Plan 05's robustness row consumes the leaked count, so the LEAK-side asserter mirrors the BLOCK-side asserter.
