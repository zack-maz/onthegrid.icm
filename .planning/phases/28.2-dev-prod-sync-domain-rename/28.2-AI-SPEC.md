## 1. System Classification

**System Type:** Extraction (with light enrichment) — existing pipeline. **No new AI system is built in this phase.** Phase 28.2 only graduates two existing operator-control endpoints from `dev-only` to `Bearer-gated prod`.

**Description:**
GDELT v2 conflict event rows → grouped by date+CAMEO root+50km proximity → batch-of-2 LLM extraction (Cerebras qwen-3-235b primary, Groq gpt-oss-120b fallback, optional NVIDIA NIM v3 path) → Zod-validated 5-type ontology (`airstrike`/`on_ground`/`explosion`/`targeted`/`other`) → 6-path hierarchical location resolver → cached at `events:llm:v3` Redis key. Operator-control endpoints `POST /api/events/llm-pipeline` (runtime v1/v2/v3 swap) and `POST /api/events/llm-replay/:groupKey` (single-group re-extraction with current prompt) are the surfaces graduating in 28.2 per D-08 — they let the operator drive the pipeline from a deployed dashboard during incidents without a CLI session.

**Critical Failure Modes (focus on what 28.2 introduces or amplifies):**

1. **Map serves blank events.** Pitfall 1 bridge already protects via `events:llm:v2 → events:llm → raw GDELT` graceful degradation. 28.2 must not regress this — Bearer-gating endpoints does not change the read path, but `/llm-replay` runtime mistakes could.
2. **Cache poisoning via `/llm-replay` writing terminal cache.** Pitfall 6 dual-gate (NODE_ENV !== 'production' check + in-handler 404 + never-write-cache) MUST remain intact when graduating to Bearer-gated prod. Loss of this guarantee = unbounded cache corruption.
3. **Cost runaway via operator-triggered re-extraction loops.** Bearer-authenticated operator can repeatedly POST `/llm-replay/:groupKey`, each call burning ~2K input tokens against the daily budget. Existing token-budget primitive (Cerebras 1M/day, Groq 200K/day, soft 0.8 / hard 0.95) protects but doesn't rate-limit per-operator. New attack surface: single Bearer compromise → daily budget exhausted within minutes.
4. **Operator runtime version-swap mistake.** `POST /llm-pipeline {version: 'v1'}` flips production to a deprecated extractor; if operator forgets to revert, prod serves stale enrichment indefinitely. Mitigation today: 7-day Redis TTL on `events:llm-pipeline-override` auto-clears. Phase 28.2 graduates the endpoint to prod, so this becomes a real failure mode for the first time.
5. **Prompt-injection via NEWS/BELLINGCAT enrichment blocks at re-extraction time.** v3 extractor's prompt includes adjacent NEWS articles (tier-tagged from `news:gdelt`, ±24h window). If a hostile actor seeds GDELT with an adversarial news article, `/llm-replay` will re-extract using the poisoned prompt context, returning attacker-controlled output. Pre-28.2 this was a dev-only concern; post-28.2 the attack vector is reachable via Bearer auth.

## 1b. Domain Context

**Industry Vertical:** Open-source intelligence (OSINT) / conflict monitoring. Sub-vertical: real-time geospatial event extraction from public news + state-event databases.

**User Population:** Solo operator (project author) monitoring the US-Iran conflict (active since 2026-02-28 per `WAR_START`). Personal dashboard; not multi-tenant; no public consumer surface beyond a Bearer-gated read-only operator view.

**Stakes Level:** Medium. Not life-critical (no ops decisions are made directly from this dashboard), but accuracy matters for situational awareness — wrong location classification (e.g., region instead of city precision) misleads spatial reasoning; wrong type (`airstrike` mislabeled as `on_ground`) breaks toggle-driven filters.

**Output Consequence:** A wrong extraction surfaces a misplaced dot on the map, mistyped event in the EventDetail panel, or false-positive in the threat-cluster heatmap. No automated downstream action is triggered. The operator visually inspects → cross-references with primary GDELT row + actor metadata → decides whether to trust.

### What Domain Experts Evaluate Against

OSINT practitioners evaluate event-extraction systems against these axes (drawn from the existing 50-event ground-truth set + GDELT documentation + Bellingcat field-investigation patterns):

| Dimension                   | Good (analyst accepts)                                                                                                                                                                         | Bad (analyst flags)                                                                                               | Stakes                                                                          | Source                                  |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | --------------------------------------- |
| **Location precision**      | Coordinates within 5km of true incident location, with `precision: 'exact'` flag matching                                                                                                      | Coordinates >100km off; `precision: 'exact'` claimed but coords are city-centroid                                 | High — drives spatial heatmap accuracy                                          | Phase 27.4 ground-truth set             |
| **Type classification**     | 5-type ontology applied correctly (airstrike vs on_ground vs explosion vs targeted vs other)                                                                                                   | Mass conflation: everything tagged `other`; or aggressive misclassification (peaceful protest tagged `airstrike`) | High — drives toggle filtering + threat-weight scoring                          | CAMEO codebook + project's CONTEXT D-13 |
| **Confidence calibration**  | `confidence: 0.4` events fail more than `confidence: 0.9` events at the 5km bar                                                                                                                | All events claim 0.95 confidence (uncalibrated)                                                                   | Medium — currently informational, dev-only display                              | Phase 27.4 D-17                         |
| **Provenance traceability** | Every event has a `geocodeProvenance` enum (own-site-snapshot / poi-amenity-nominatim / nominatim-direct / nominatim-verified-2pass / gdelt-actiongeo-fallback / bellingcat-coord-passthrough) | Coords appear without provenance                                                                                  | High — debugging false positives requires knowing which path produced the coord | Phase 27.4 6-path resolver design       |
| **Casualty extraction**     | Numeric casualty counts (`fatalities`, `injuries`) match the GDELT NumMentions-weighted average ±20%                                                                                           | Missing counts when source articles state them; or hallucinated counts when articles are silent                   | Medium — counters block in dashboard                                            | GDELT actor codes                       |

### Known Failure Modes in This Domain

1. **LLM-emitted coordinates that bypass the resolver.** The Zod schema `.strict()` rejects coords at extraction time (Phase 27.4 D-05); any model that "helpfully" emits lat/lng strings causes batch-wide DLQ instead of pollution.
2. **Single-actor saturation.** A high-volume actor (e.g., MIL_USA appearing in 60% of GDELT rows on a busy day) skews type weights toward whatever that actor is associated with.
3. **Stale event re-emission.** GDELT re-publishes the same incident across 4–8 hours of update files. The eventGrouping primitive dedups, but watchdog-timed-out batches can produce stale enrichment that bypasses dedup if cached at terminal key.
4. **Region-name ambiguity.** "Tehran" → city, "Tehran Province" → region; "South Khorasan" → province, "Khorasan" → contested historical region spanning 3 modern countries. Resolver's 6-path hierarchy handles via `confidence` + admin1/admin2 chain; fragile if hierarchy is incomplete.
5. **Iran/Iraq/Israel typos** — character-level swaps in upstream wire-service copy cascade through GDELT into prompt context. Existing harness has 5+ ground-truth examples for this class.

### Regulatory / Compliance Context

None applicable. Personal dashboard, no PII processed, no automated decision-making, no regulated industry (healthcare/finance/legal). The data sources (GDELT, OSM, Bellingcat) are all public-by-design.

The only compliance-adjacent concern: **export-control / dual-use research**. Geospatial event extraction at the precision used here (5km city-level) is on the edge of dual-use territory but well below thresholds requiring registration (no defense-grade resolution, no real-time targeting, no integration with kinetic systems).

## 2. Framework Decision

**Selected Framework:** OpenAI SDK (TypeScript) with provider cascade — **existing, locked in Phase 27.4.** No new framework selected in 28.2.

**Version:** `openai@^4.x` (currently in `package.json`). Provider routing via `baseURL` swap in `server/adapters/llm-provider.ts`. Cerebras + Groq + (optional) NVIDIA NIM all expose OpenAI-compatible chat-completions endpoints.

**Rationale:**

- TS-native — no Python sidecar; single bundle deploys to Vercel Functions
- Single SDK across all three providers via `baseURL` swap (Cerebras: `api.cerebras.ai/v1`, Groq: `api.groq.com/openai/v1`, NIM: `integrate.api.nvidia.com/v1`)
- Zod for structured output (TS-native, no Pydantic equivalent needed)
- Free tier on all three providers covers daily budget at current Iran-conflict event volume

**Alternatives Considered:**

| Framework     | Ruled Out Because                                                                                                                                                                      |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| LangChain JS  | Too much abstraction for extraction-only workload; chain composition adds latency without benefit at batch-of-2 fan-out; 27.4 era avoided supply-chain churn                           |
| Vercel AI SDK | Was not yet GA when Phase 27 started; the project's `claude.md` knowledge update notes it as the modern Vercel default — revisit in a future phase if/when migration cost is justified |
| LlamaIndex TS | RAG-oriented, not extraction-oriented; would force reframing the problem as retrieval-then-extract                                                                                     |

**Vendor Lock-In Accepted:** Partial. The `baseURL` swap pattern means swapping providers is mechanical; swapping the SDK itself (e.g., to Vercel AI SDK) is a 1-day refactor. Acceptable lock-in.

### Entry Point Pattern

```typescript
// server/adapters/llm-provider.ts (current)
export async function callLLM(opts: CallLLMOpts): Promise<LLMCallResult> {
  const providers: Provider[] = ['cerebras', 'groq']; // NIM optional via env
  for (const provider of providers) {
    if (!isAvailable(provider)) {
      callHistory.push({ provider, model: 'skip-no-client', skipReason: 'no_client' });
      continue;
    }
    if ((await budgetState(provider)) === 'hard') {
      callHistory.push({ provider, model: 'skip-budget', skipReason: 'hard_cap' });
      continue;
    }
    if (!circuitBreaker(provider).isAvailable()) {
      callHistory.push({ provider, model: 'skip-breaker', skipReason: 'breaker' });
      continue;
    }
    return await callWithRetry(provider, opts); // 2 attempts × 1s/4s exp + jitter
  }
  throw new AllProvidersFailedError();
}
```

### Key Abstractions

| Concept                     | What It Is                                                     | When You Use It                                                   |
| --------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------- |
| Provider cascade            | Cerebras → Groq → (NIM) failover with budget + breaker gates   | Every LLM call routes through `callLLM()`                         |
| Batch grouping              | `eventGrouping.ts` clusters GDELT rows by date+CAMEO root+50km | Pre-extraction; reduces API calls 10-50x                          |
| Watchdog wrapper            | `withBatchWatchdog()` 90s hard kill + 60s soft warn            | Wraps every batch Promise; protects against zombie Cerebras calls |
| Resolver hierarchy          | `resolveLocation(hierarchy, ctx)` 6-path dispatcher            | Per-event after extraction; produces coord + provenance           |
| Zod schema with `.strict()` | Rejects LLM-emitted coords + extra keys at parse time          | Every batch result validated before cache write                   |

### Common Pitfalls

1. **`maxLength` in JSON Schema breaks Cerebras qwen.** Removed from `EVENT_EXTRACTION_SCHEMA_V2.reasoning`; truncation is enforced post-parse via Zod transform.
2. **Two-key discipline on Redis writes.** Terminal `events:llm:v3` (consumers iterate as array) vs. observability `events:llm:v3:partial` (envelope `{events, progress, complete}`). Crossing them = `events.map is not a function` everywhere downstream.
3. **Cerebras `gpt-oss-120b` is paid-tier.** Open Cerebras tier serves `qwen-3-235b-a22b-instruct-2507` only. Misconfigured model env → `model_not_found`.
4. **Pitfall 6 dual-gate on `/llm-replay`.** Endpoint registered ONLY when `NODE_ENV !== 'production'` AND in-handler 404 if production AND no Bearer. Phase 28.2 adds Bearer-gated prod path; the in-handler 404 must still trigger when Bearer absent.
5. **Race-safety relies on JS event-loop single-thread.** `llmProgress.x = (llmProgress.x ?? 0) + 1` evaluates synchronously between awaits. Concurrent v3 batches (Plan 02) rely on this.

## 4. Implementation Guidance

**Model Configuration:**

- Cerebras: `qwen-3-235b-a22b-instruct-2507` (open tier), `temperature: 0.0`, `response_format: { type: 'json_schema', json_schema: EVENT_EXTRACTION_SCHEMA_V2 }`
- Groq: `openai/gpt-oss-120b` (free tier), same params
- (Optional) NVIDIA NIM v3: `qwen2.5-72b` via NIM, same params, ~40 req/min ceiling

**Core Pattern:**

- Batch size: 2 groups per call (down from v1's 8) — Pitfall: NIM concurrent throttle
- Concurrency: `LLM_V3_CONCURRENCY=12` parallel batches (FIFO limiter, no `p-limit` dep) — drives 197-batch dev runs from ~95 min → ~10 min
- Trigger: `POST /api/cron/refresh-events` daily 4am UTC (Hobby cron cap = 3); operator override via `?force=true` with valid Bearer

**Tool Use:**

- Forward geocoder: Nominatim with server-owned ME viewbox + 22 country codes (T-27.4-04-01 contract — never user-overridable)
- POI mode: `amenity=` for site-resolved entries
- Cache: `geocode:fwd:constrained:v2:<hash>` Redis 30-day logical / 90-day hard TTL

**State Management:**

- Terminal cache: `events:llm:v3` (Redis 7-day TTL, served to /api/events read path)
- Observability cache: `events:llm:v3:partial` (Redis envelope, populated per-batch during run)
- Token budget: `llm:tokens:{provider}:YYYY-MM-DD` (48h TTL, soft 0.8 / hard 0.95 caps)
- DLQ: `events:llm-dlq` Redis SADD bounded 200 entries, 7d TTL
- Pipeline override: `events:llm-pipeline-override` Redis 7-day TTL (operator-set v1/v2/v3 pin)

**Context Window Strategy:**

- Per-batch input: 2 grouped events + matched NEWS (±24h, tier-tagged) + Bellingcat coord candidates + 3 most-recent TEMPORAL events in same region (72h)
- Typical input: ~3-5K tokens; output: ~500-800 tokens
- Cerebras context: 32K (qwen-3-235b) — comfortable headroom

## 4b. AI Systems Best Practices

> Pre-filled from existing Phase 27.4 patterns. TypeScript codebase — Pydantic equivalent is **Zod**.

### Structured Outputs with Zod (Pydantic equivalent for TS)

```typescript
// server/lib/llmSchema.ts (current)
const enrichedEventV2 = z
  .object({
    type: z.enum(['airstrike', 'on_ground', 'explosion', 'targeted', 'other']),
    hierarchy: z.object({
      country: z.string(),
      admin1: z.string().nullable(),
      city: z.string().nullable(),
      neighborhood: z.string().nullable(),
      landmark: z.string().nullable(),
      confidence: z.number().min(0).max(1),
    }),
    fatalities: z.number().int().nonnegative().nullable(),
    injuries: z.number().int().nonnegative().nullable(),
    reasoning: z.string().transform((s) => (s.length > 200 ? s.slice(0, 197) + '…' : s)),
  })
  .strict(); // .strict() rejects LLM-emitted coords (Phase 27.4 D-05)

export const enrichedEventAny = z.discriminatedUnion('schemaVersion', [
  z.object({ schemaVersion: z.literal('v1') /* ... */ }),
  z.object({ schemaVersion: z.literal('v2') /* ... */ }).extend(enrichedEventV2.shape),
]);
```

**Validation failure handling:** Per-event Zod failures truncate `reasoning` (transform, don't reject) so a single overly-verbose model output doesn't DLQ the entire batch. Schema-fail at the discriminated union level routes to `events:llm-dlq` with `reason: 'schema_validation_failed'`.

### Async-First Design

- All extractor functions return `Promise<EnrichedEventV2[]>`; no callbacks
- `Promise.race` watchdog wrapper protects every batch — late-resolving Cerebras calls (after timeout) are AbortControlled and their results discarded via generation-counter check
- `Promise.all(tasks)` with concurrency limiter for parallel batch dispatch (Plan 02)
- Streaming NOT used — extraction is single-shot JSON, no token-by-token consumer

### Prompt Engineering Discipline

- System prompt: extraction rubric + 5-type ontology + hierarchy schema (locked, version-controlled)
- User prompt: GDELT row(s) + NEWS context + BELLINGCAT candidates + TEMPORAL events (assembled per-batch)
- Few-shot: NOT used — wastes tokens vs. structured output schema
- Token budget: ~3-5K input per batch; daily ceiling enforced at `llmTokenBudget.ts`

### Context Window Management

Extraction-only system — no conversation history, no agent compaction. Per-batch input is bounded:

- 2 GDELT events × ~500 tokens each = 1K
- NEWS ±24h window, top-K=8 articles × ~300 tokens = 2.4K
- BELLINGCAT coord candidates × ~50 tokens × 5 candidates = 250
- TEMPORAL last-3 events × ~200 tokens = 600
- **Total ceiling per batch: ~4.3K input + ~800 output = ~5.1K tokens** (well under Cerebras 32K limit)

### Cost and Latency Budget

- Per-batch latency p50: ~27s (Cerebras qwen-3-235b at typical input size)
- Per-batch cost: $0 on Cerebras free tier (1M tokens/day) and Groq free tier (200K tokens/day)
- Daily extraction (~150-200 batches): ~$0/day at current free-tier limits
- Caching: Redis `geocode:fwd:constrained:v2:*` 30-day TTL eliminates re-resolution of repeated locations; Redis `events:llm:v3` 7-day TTL serves all consumers without re-extraction
- Sub-task routing: NOT used — batch-of-2 is the smallest viable unit; further fan-out increases coordination overhead more than it saves

## 5. Evaluation Strategy

| **Per-Bearer replay quota**                          | More than **50 `/llm-replay` calls per 24h** from the same Bearer fingerprint (SHA-256 truncated to 8 hex chars) | HTTP 429 with `Retry-After` header pointing to the rolling-window reset. Implementation: Redis `INCR operator:replay-quota:{bearerFingerprint}:{YYYY-MM-DD}` with 48h TTL on first set; check-then-INCR pattern in the route handler (not middleware — middleware runs before Bearer parse). **Cheaper than rate-limiter middleware extension** per scope-constraint guidance: ~6 lines of Redis logic, no new primitive. Rationale: 50 replays/day × ~2K input tokens = 100K tokens/day worst case, ~10% of Cerebras free-tier 1M/day budget — well below any blast-radius concern even under full quota exhaustion. |
| **Operator-action audit log**                        | Every successful `/llm-pipeline` and `/llm-replay` request                                                       | Redis `SADD operator:audit-log {timestamp, bearerFingerprint, operation, args, result}` bounded set, ~500 entries cap (oldest evicted via `SCARD` check + `SPOP` raw-string srem), 30d TTL. Synchronous write before HTTP response — the audit trail completeness rubric (§5) gates this.                                                                                                                                                                                                                                                                                                                             |
| **UI-side confirm modal on non-default version pin** | `POST /llm-pipeline {version: 'v1' \| 'v2'}` (not `'v3'`, not `null`) from the dashboard                         | `DashboardAuthModal`-style confirm modal in the operator UI before the POST fires. Bypass via direct `curl` is intentional (operator scripts must work).                                                                                                                                                                                                                                        |

**Smart Sampling Strategy:**

- **Every operator-triggered replay diff** → written to `events:llm-replay-log` Redis bounded set (~200 entries cap, 30d TTL) with `{groupKey, oldExtraction, newExtraction, bearerFingerprint, timestamp}`. Non-blocking; written after the HTTP response is sent. Operator can post-hoc audit "what did I change last Tuesday?" without touching the terminal cache. This is observability-only — never read by the `/api/events` serving path (Pitfall 6 dual-gate stays absolute).
- **Every operator-triggered version swap** → already covered by the audit log (§6). Rotation policy: bounded 500 entries cap, 30d TTL.
- **Adversarial test set re-run on demand** — when the operator suspects a poisoned context (e.g., a flagged news article in the DLQ), they can `POST /api/events/llm-eval/adversarial-rerun` (Bearer-gated, no rate limit — single-operator project, manual cadence only) to re-execute the ~10-entry set immediately rather than waiting for the next cron tick.
- **NO smart sampling for accuracy degradation** — that's Phase 27.4's `runEval()` 50-event harness territory; 28.2 inherits unchanged.
