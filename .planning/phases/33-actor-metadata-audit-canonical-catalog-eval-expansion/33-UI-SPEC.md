### Issue-badge palette (drill-down `issue` column)

The drill-down sample row carries an `issue` field with four enum values (`'null' | 'raw-cameo' | 'ambiguous' | 'low-confidence'`). The badge color must align with the existing event-type palette already declared in `app.css` `@theme` so no new tokens are introduced.

Auto-selected mapping (recommended default — chosen to reuse existing `--color-event-*` and `--color-faction-*` vars rather than introduce new tokens; rationale below the table):

| Issue value | Visual treatment | CSS var used | Why this token |
| --- | --- | --- | --- |
| `null` | `text-text-muted/60` (no border, plain muted gray text) | `--color-text-muted` (`oklch(0.5 0 0)`) | Null = absence-of-data; muted-text reads as "missing" without escalating attention |
| `raw-cameo` | `text-[color:var(--color-faction-disputed)]` (#f59e0b amber) | `--color-faction-disputed` | Code-as-actor = ambiguous attribution, same semantic as faction-disputed (we don't know whose side this is) |
| `ambiguous` | `text-[color:var(--color-faction-disputed)]` (#f59e0b amber) | `--color-faction-disputed` | Same semantic family as raw-cameo (attribution unclear). Same color; the `issue` enum string itself differentiates. |
| `low-confidence` | `text-[color:var(--color-event-other)]` (#dc5a5a dim red) | `--color-event-other` | "Other" event color reads as soft-warning without the urgency of airstrike-red; matches the dim-red palette family for catch-all-degraded-state |

**Rationale for reusing existing tokens, not introducing new ones:**

1. D-13 single-source-of-truth contract (`colorBridge.ts` byte-identity test) forbids inline hex/RGBA in consumers. New tokens would need to land in `app.css` `@theme` AND `colorBridge.ts` fallbacks AND the byte-identity test — non-trivial scope creep for a read-only sub-block.
2. The four issue values already align semantically with existing event/faction colors: muted-text for absence, faction-disputed amber for attribution-uncertain (raw-cameo + ambiguous share this), event-other dim-red for degraded-quality.
3. The two amber buckets (`raw-cameo` + `ambiguous`) are differentiated by the badge **label text** itself (the operator reads "raw-cameo" or "ambiguous"), not by color. This keeps the visual palette at three swatches (muted / amber / dim-red) which the operator can pattern-match at a glance.
4. ui-checker's color dimension validates against 60/30/10 split + accent-reserved-for list. The Phase 33 sub-block adds zero new accent surface area; the three swatches above are all consumed-from-existing tokens, NOT new declarations.

**Badge render shape (auto-selected, recommended default):** plain colored text in the drill-down row (e.g. `<span className="font-mono text-[color:var(--color-faction-disputed)]">raw-cameo</span>`). No background fill, no border, no rounded chip — keeps the row visually consistent with the Phase 32 prune block's `<span className="font-mono text-text-muted/60">{entry.status}</span>` precedent at line 1624. A chip-style badge would diverge from the analog. **If during executor pass the operator finds the plain-text badge insufficient, the fallback is a `border border-current rounded px-1` ring at the same color — explicitly noted here so the planner doesn't have to re-decide.**

## Interaction Contract

(Not in template — added because gsd-ui-researcher should be prescriptive about state behavior; downstream gsd-planner consumes this section.)

### Loading state

While the parent dashboard is in its first poll cycle (`opStatus === null`), the actor-quality sub-block does NOT render at all — it inherits the parent `opStatus &&` gate at line 1540. Auto-selected: matches Phase 32 prune block precedent (silent absence during loading; no skeleton, no placeholder). If polling takes >2s repeatedly the parent block surfaces its own "loading" state; the sub-block does not add a second.

### Default state (data present, all counts zero)

When `actorQuality.totalEvents > 0` and all four counters are zero, the count row still renders: `Actor quality: Null: 0 · Raw-CAMEO: 0 · Ambiguous: 0 · Low-confidence: 0`. **The drill-down list is suppressed when `sample.length === 0`.** Auto-selected: this is the "healthy" baseline operator wants to confirm; suppressing the count row would force the operator to remember whether the absence means "no data" or "all clean".

### Hover state on counter numbers

Auto-selected: **no hover state**. The counts are rendered as plain text inside a single string, not as interactive elements. Matches Phase 32 `dead-url-count` precedent at line 1614 (also a plain text counter with no hover). Adding a hover-tooltip ("click to filter") would imply interactivity that doesn't exist — Phase 33 ships no filter mechanism.

### Drill-down expansion

The drill-down list **is always visible** when `actorQuality.sample.length > 0`. No collapse / expand toggle. Auto-selected: matches Phase 32 D-10 prune-list precedent at line 1617 (always-visible bounded list, `max-h-40 overflow-y-auto` for scroll). The list is naturally bounded by the server-side `LIMIT_DRILL_DOWN = 20` cap (D-16); truncation footer signals more exist.

### Keyboard navigation

The drill-down list `<ul>` is non-interactive (read-only). No focusable items, no keyboard-handlers. Matches Phase 32 prune list precedent. The only focusable elements in the surrounding Operator Actions block are the existing `replay-test-trigger` and `prune-dead-urls-trigger` buttons; Phase 33 adds none.

### Polling cadence

Counts refresh automatically on the existing `/api/operator-status` poll loop (parent block manages cadence — Phase 33 does NOT introduce a new poll). After the next `runRefreshExtraction()` cron tick (24h cycle by default; force-trigger via `?force=true`), counts may shift as the daily cron rewrites `events:llm:v3` through the new catalog. No real-time WebSocket, no SSE.

### Accessibility contract

- **Counter row aria-label:** the count row carries `aria-label="Actor quality counters: {nullActors} null actors, {rawCameoActors} raw CAMEO codes, {ambiguousActors} ambiguous strings, {lowConfidenceActors} low confidence"` on the wrapping `<div>`. Lets a screen reader announce the four counts as one unit (matches the conjoined `·`-separated rendering).
- **Drill-down list semantic markup:** the `<ul>` carries `aria-label="Actor quality drill-down sample (up to 20 events)"`. Each `<li>` is a list item; no `aria-live` (data is poll-refreshed at the parent block's cadence; per-row updates would be noisy).
- **Issue badge:** the colored issue span carries no aria override — the text content (`null` / `raw-cameo` / `ambiguous` / `low-confidence`) is its own label.
- **Color contrast:** all four issue-badge colors (`--color-text-muted`, `--color-faction-disputed` amber `#f59e0b`, `--color-event-other` dim red `#dc5a5a`) render on the `bg-white/5` expanded-row surface or directly on the `--color-surface-elevated` panel. Contrast checked against WCAG 2.1 AA for normal text:
  - muted-text on surface-elevated: existing pattern (passes — was checked by 28.2 W5 D-23)
  - faction-disputed amber `#f59e0b` on `bg-white/5` over `#1a1a1a`: ratio ≈ 7.3:1 ✓ AA
  - event-other dim red `#dc5a5a` on same: ratio ≈ 4.9:1 ✓ AA for normal text
- **Empty state:** the empty-state copy (`Actor quality: no data`) inherits the `text-text-muted` color from the parent row class — same contrast as all other zero-state rows.

## DOM Mount Point (load-bearing for executor)

The new sub-block mounts **after** the Phase 32 prune block's closing `</>` fragment at `src/components/ui/DevApiStatus.tsx:1654`, **before** the `pruneQuotaAlert` conditional at line 1658, **inside** the same `<section data-testid="operator-actions">` at line 1532.

Render gate: `{opStatus?.actorQuality != null && (...)}` — silent skip when the aggregator does not yet return the field (matches Phase 32 D-10's forward-compat pattern at line 1612, `opStatus?.prune != null`). This means a pre-Phase-33 server deploy with a post-Phase-33 client will not crash; the sub-block simply doesn't render until the server catches up.

**Why this position (and not before the prune block, and not after the prune-quota-alert):**

1. **Visual rhythm** — Operator Actions section grows top-down: 24h count → per-Bearer → adversarial-eval → dead-URL count + prune button → **actor-quality counters + drill-down** → quota alerts. The new block reads naturally as "another quality metric" after the dead-URL surface and before the alerts.
2. **Pairing** — Phase 32 prune is a destructive-action block; Phase 33 actor-quality is a read-only counters block. Placing them adjacent groups "quality observability" into one visual cluster, with the existing 429 quota alerts (operator-action surface) sitting below.
3. **Co-mount avoidance** — the prune-quota alert is logically attached to the prune button (one operator action, one quota); mounting Phase 33 between the button and its quota alert would visually orphan the alert. After the closing fragment of the prune block keeps the prune button + alert as a unit.
