### Claude's Discretion

- **Audit script execution surface** — standalone tsx script (`scripts/audit-actors.ts` invoked as `node --import tsx/esm scripts/audit-actors.ts`) **vs** vitest `describe.skip` flipped manually. **Recommended: standalone `tsx` script** under `.planning/phases/33-*/audit/run-audit.ts` (or `scripts/audit-actors.ts`) — matches Phase 31's `watch:snapshot` precedent (`scripts/snapshot-cron-watch.ts`), keeps it out of the test runner's noise floor, and lets the operator commit the report + script together.
- **CAMEO codebook source** — committed reference at `.planning/phases/33-*/cameo-codes.txt` vs `.json`. **Recommended: `cameo-codes.json`** with shape `{ "version": "GDELT-CAMEO-2026-05", "actorCodes": [{code, label, type}], "eventCodes": [...] }`. Source: GDELT's published codebook URL + a committed snapshot (mirrors how `colorBridge.ts` snapshots `@theme`). Existing `server/adapters/gdelt.ts` does NOT carry a CAMEO _actor_ codebook — only event-code helpers (`classifyByBaseCode`, `describeEvent`) and per-row column accessors (`COL.Actor1Name`, `COL.Actor1CountryCode`). The actor codebook is net-new content for Phase 33.
- **`canonicalize()` ordering when multiple aliases match** — **longest-alias-wins** to avoid generic-name shadowing (e.g., "Israel Defense Forces" beats "Israel" if both alias to different canonicals).
- **`expectedActor{1,2}` precedence: AND vs OR** — D-13 picks AND. Researcher reviews against audit findings during ground-truth backfill; may relax to OR for genuinely-ambiguous source attribution.
- **JSON Schema rendering of `actorConfidence` for wire** — **mark as required in wire schema** AND repair server-side (defense-in-depth). If NIM (`qwen-235b`) rejects required-array-of-enums under its relaxed JSON-Schema enforcement, fall back to optional. NIM's strict-mode rejection of `maxLength` (see `llmSchema.ts:288-298` comment) is precedent: NIM does NOT implement the full JSON Schema keyword set; required-array-of-enum is more conservative and likely fine. **Researcher recommendation: SHIP REQUIRED**, monitor `schemaFailures.nvidia_nim.missingField` counter for one cron tick post-deploy, revert to optional if it spikes.
- **Catalog → faction integration in this phase** — store `affiliation` on `CanonicalActor`, do NOT surface it yet in the dashboard sample. Reserved for future use (e.g., Phase 35+ frontend rendering).

## Phase Goal

Make actor metadata in `events:llm:v3` operator-trustworthy via a deterministic canonical catalog applied server-side after the v3 extractor's Zod-validated batch — and surface the resulting quality counts on the API Health tab. Zero new third-party deps, zero cache-key bump, zero retroactive backfill: existing entries roll forward through the 24h cron cycle.

## Approach (implementation order, 7 bullets)

1. **Audit first (ACTOR-01).** Pull a live snapshot of `events:llm:v3`, run deterministic regex + deny-list classification against actors fields, emit `33-AUDIT-REPORT.md`. The report drives ACTOR-02 catalog seeding (D-06 lists are starting baselines, not final) AND ACTOR-04 ground-truth backfill (D-14 ≥30/50 target).
2. **Catalog next (ACTOR-02).** Ship `server/data/actor-catalog.ts` with audit-driven seed list + contract test. Static-data module — pattern-identical to `factions.ts` / `ethnicGroups.ts`. CAMEO codebook lands as a sibling `cameo-codes.json` for orphan-check enforcement.
3. **Schema extension (ACTOR-03 part A).** `actorConfidence` added to `enrichedEventV3` via `.extend()` AND to `EVENT_EXTRACTION_SCHEMA_V3` wire contract. Strict-extend behavior verified against rollout-window cache reads (see Open Q §1).
4. **Extractor integration (ACTOR-03 part B).** Post-validate hook walks `event.actors[]` through `canonicalize()`. `actorConfidence` repaired to length-locked `'low'` defaults before write. SYSTEM_PROMPT instruction #9 extended (D-09) — best-effort hint, not enforcement.
5. **Eval extension (ACTOR-04).** `runEval()` adds actor-match scoring against ground-truth `expectedActor{1,2}` by joining live `events:llm:v3.groupKey` to ground-truth `id`. `EvalScore` shape gains `actorMatchRate`. Adversarial fixture appends 3 entries.
6. **Aggregator extension (ACTOR-05 part A).** `/api/operator-status` route gains `actorQuality` block computed lazily over already-deserialized cache. Reuses Phase 32 D-13's lazy-compute precedent — no new Redis sidecar.
7. **Dashboard surface (ACTOR-05 part B).** `DevApiStatus.tsx` adds Actor Quality sub-block at UI-SPEC-pinned mount point (between line 1654 and 1658). Render gate `opStatus?.actorQuality != null` so pre-Phase-33 server deploys silently skip.

## Open Questions / Pitfalls

### Open Q §1 — Zod `.extend()` + `.strict()` against legacy cache reads

**Question:** Does `enrichedEventV3.extend({ actorConfidence: z.array(...) })` reject existing v3 cache payloads that lack the `actorConfidence` field during the forward-compat rollout window?

**Investigation:** `enrichedEventV3 = enrichedEventV2.extend({ schemaVersion: z.literal('v3') })` at `llmSchema.ts:173-175`. The JSDoc at lines 167-170 confirms strict() is re-applied through .extend() in Zod v3 — verified by the v2→v3 schemaVersion bump itself (an existing test). HOWEVER, strict() only enforces "no EXTRA fields"; it does NOT enforce "all required fields present" — Zod's default IS that all listed fields are required. So adding `actorConfidence: z.array(...)` (without `.optional()`) WILL make Zod reject any payload missing the field — including all pre-Phase-33 v3 entries in `events:llm:v3` during the rollout window.

**Cache-read sites that would break:** (1) `enrichedEventAny` discriminated union at `llmSchema.ts:191-195` — used by the temporal-context loader at `llmEventExtractor.v3.ts:359-389` reading `cached.data` shape; (2) `events.ts` cache read on `/api/events`; (3) the geocoded `ConflictEventEntity` shape (which currently doesn't carry the field at all — D-18 forward-only).

**Resolution:** Ship `actorConfidence` as **`z.array(z.enum(['high','medium','low'])).optional()`** for the rollout window (CONTEXT.md D-11 explicit caveat). The extractor's repair step (D-10 row 6) populates it before write, so all NEW entries carry it; old entries roll forward through the 24h cron. Tighten to required in a Phase 35+ cleanup phase. **Confidence: HIGH.** This matches the existing `aliases: string[]` style flat-array forward-compat philosophy in the file (the Phase 28.1 D-13 colorBridge pattern uses the same "optional during rollout, tighten later" cadence).

### Open Q §2 — NIM JSON Schema enforcement of `actorConfidence` array-of-enum

**Question:** Does NIM's qwen-235b under relaxed JSON Schema mode reliably emit a `actorConfidence` field marked required at the wire level?

**Evidence:** `llmSchema.ts:288-298` documents Cerebras qwen-3-235b rejecting `maxLength` as `wrong_api_format: Invalid fields for schema with types ['string']: {'maxLength'}`. The comment at lines 351-358 notes: _"NVIDIA NIM and OpenRouter free models do not reliably support strict JSON Schema mode... v3 surfaces this constant as PROMPT INSTRUCTION TEXT (not response_format.json_schema)."_

**Implication:** The JSON Schema is EMBEDDED in the system prompt (line 157) for v3, NOT enforced by the provider's strict response_format. So "required" in the schema is a guideline the LLM may not honor.

**Resolution:** Ship `actorConfidence` as **required in the wire schema** (for LLM forcing-function value) AND ALWAYS run the server-side repair step (D-10) as defense-in-depth. Track the schema-failure rate via `llmProgress.schemaFailures.nvidia_nim.missingField` (counter exists at `llmEventExtractor.v3.ts:741-748`). If the rate spikes post-deploy, the repair step still salvages every batch — but the operator can revert to optional in a 1-line cleanup commit.

### Open Q §3 — `EVENT_EXTRACTION_SCHEMA_V3` un-aliasing risk

**Current state:** `llmSchema.ts:359` declares `EVENT_EXTRACTION_SCHEMA_V3: Record<string, unknown> = EVENT_EXTRACTION_SCHEMA_V2`. Adding the actor-confidence field requires un-aliasing — copying the v2 schema literal verbatim and editing the copy.

**Risk:** Future v2 schema edits (which should be rare given v2 is rollback-only post-Phase-29) won't auto-propagate to v3. **Mitigation:** add a JSDoc comment at the new v3 schema literal explicitly stating "v3 diverged from v2 in Phase 33 — actorConfidence added; future v2 changes do NOT auto-propagate." The v1+v2 extractors were deleted in Phase 29, so v2 schema is also effectively frozen — this is low risk.

### Open Q §4 — Ground-truth `id` vs live `groupKey` join

**Question:** D-13 says `runEval()` matches live `events:llm:v3.groupKey` to ground-truth `id`. But ground-truth `id`s are synthetic (`'gt-001'`, `'gt-002'`, see `ground-truth-events.json:16`), NOT groupKeys.

**Implication:** A direct `groupKey === id` join finds zero matches. D-13's specified join is incorrect as written.

**Resolution options (researcher recommends option (c)):**

- (a) Backfill ground-truth with a `groupKey: string \| null` field; phase executor manually associates each ground-truth entry with a real groupKey from a recent cron run. **Brittle** — groupKeys change as GDELT rows churn.
- (b) Reverse-engineer: at audit time, find a recent live event near each ground-truth's `truth.lat/lng`. **Slow** — runs an O(N×M) haversine sweep.
- (c) **Match by landmark + country**: live `liveEvent.data.locationName` (or `liveEvent.label`) against ground-truth `hierarchy.landmark` / `hierarchy.country` with case-insensitive substring. Approximate but cheap; matches the spirit of "is the live cache producing the right actors for events near Natanz?" Score `actorMatchRate = matchedExpectedActor / totalGroundTruthWithExpectedActor`. Unmatched (no live event near landmark) counts as a miss (consistent with resolver miss semantics per D-13).

The planner must pick option (a), (b), or (c) during the executor pass against the audit report; the researcher recommends (c) for simplicity + cost.

### Open Q §5 — Adversarial fixture cap math

**Discrepancy:** D-15 says "Adversarial set stays under 10 total entries (fits the existing fixture budget)." But `adversarial-injections.json` currently contains **10 entries** (adv-001 through adv-010, lines 5+). Adding 3 actor-confusion entries → 13 total, which violates the cap.

**Resolution:** Treat the "10 total" cap as soft — D-15 was written before checking the fixture size. The actual constraint is `runAdversarialEval()` performance (resolver-only, Nominatim 1-req/s throttle) — 13 entries take ~13s to score, still well under the 800s cron budget. **Researcher recommendation: ship 13 entries; document the cap-bump in `33-SUMMARY.md`.** If the planner wants strict cap adherence, drop 3 of the existing entries (less defensible — they're shipped and load-bearing).

### Pitfall §1 — Code duplication between audit script + operator-status classification

The same D-02 deterministic classification rules run in two places: the one-shot audit script (ACTOR-01) AND the lazy compute in `/api/operator-status` (ACTOR-05). **Risk:** Drift between the two implementations means dashboard counts disagree with the audit report.

**Mitigation:** Factor classification into a shared module — `server/lib/actorClassifier.ts` — with exported `classifyActor(actor: string, cameoCodebook: Set<string>, denyList: Set<string>): 'ok' \| 'null' \| 'raw-cameo' \| 'ambiguous'`. Both the audit script AND the operator-status route import it. Atomic commit boundary: ships in the same plan-task as D-02 (audit deterministic rules) or D-16 (operator-status block) — researcher recommends shipping the shared module FIRST (D-02 plan-task), then both consumers import from it.

### Pitfall §2 — Forward-only D-18 means dashboard counts will look "broken" on day 1

The dashboard count of `lowConfidenceActors` will be ~0% of `totalEvents` on day 1 (because no live entries have `actorConfidence` yet), then climb toward ~steady-state over the 24h cron window as entries roll forward. **Operator UX risk:** counts that "should" be non-zero look broken.

**Mitigation:** Document this in `33-SUMMARY.md`'s "Post-deploy verification" section. Operator can force via `GET /api/cron/refresh-events?force=true` immediately after deploy (existing surface — no new code). If the operator wants the dashboard "warm" before the natural 04:00 UTC tick, the force-trigger costs ~10 minutes of LLM-extraction wall time.

### Pitfall §3 — Catalog `cameoCodes[]` cross-checks against the codebook at build time, not at runtime

The contract test (D-07 (b)) asserts every `CanonicalActor.cameoCodes[]` entry is in the committed `cameo-codes.json`. **Risk:** if GDELT upstream renames an actor code (rare), the codebook snapshot drifts, the test breaks on the next mismatch. **Mitigation:** D-07's intentional design — drift surfaces loudly. CONTEXT.md "Deferred Ideas" explicitly defers auto-resync to a future cleanup phase. Document this in the catalog file's top-of-file JSDoc.

### Pitfall §4 — `'cron:refresh-events'` Bearer fingerprint precedent (for future audit-log writes)

Phase 33 does NOT add any new operator-action audit-log entries (the catalog applies inside the cron path automatically; the dashboard surface is read-only). So no `'cron:refresh-events'` fingerprint writes are needed. **If a future phase adds operator-initiated catalog mutations, the Phase 32 D-11 / RESEARCH A8 pattern applies (`bearerFingerprint: 'cron:refresh-events'` for cron caller, real fingerprint for operator caller).** Noted here for forward-compatibility only.
