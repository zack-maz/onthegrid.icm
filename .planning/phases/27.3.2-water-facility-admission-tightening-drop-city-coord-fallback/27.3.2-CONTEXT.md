# Phase 27.3.2: Water Facility Admission Tightening — Drop City/Coord Fallbacks

**Gathered:** 2026-04-19
**Status:** Ready for planning

<domain>
## Phase Boundary

Tighten water facility admission so every admitted non-desalination facility carries a real Latin OSM name. Drop any OSM element whose `name` / `name:en` / `operator` chain all fail the `isLatin` script check. Desalination remains exempt from the tightening (sparse OSM coverage, strategic importance) and is the sole facility type where the server synthesizes a fallback label (city or coord) when no Latin name is available. Kill the client-side fallback chain in `src/lib/waterLabel.ts` entirely — labels flow from server to client unchanged. Regenerate `src/data/water-facilities.json` under the new rule and bump the Redis key so deploys flush stale entries.

Scope is **tighten admission + move all label synthesis to the server + simplify the client + regenerate snapshot**. Romanization of Persian / Arabic / Georgian names is intentionally deferred to Phase 27.3.3.

</domain>

<decisions>
## Implementation Decisions

### Admission Rule

- **D-01: Strict Latin-label admission for non-desalination.** A non-desal facility admits only when `extractLabel(tags, facilityType)` would return a non-bare string — i.e. `name` / `name:en` / `operator` has a non-empty trimmed value AND passes the `isLatin` script check. OSM elements whose only usable name tags are non-Latin (Persian, Arabic, Georgian, Cyrillic, etc.) are rejected even when `hasName(tags)` returns true under the R-03 D-05 rule.
- **D-02: River-match rescue killed.** The 4 river-resolved bare-label facilities currently admitted under the original framing ("admit if Latin name OR linkedRiver") are also dropped. This keeps the rule dead-simple: admit iff the OSM tags produce a Latin label. `linkedRiver` remains as post-admission enrichment for the detail panel but is no longer an admission signal.
- **D-03: Desalination exempt.** Desalination continues to admit on `hasName(tags)` alone (existing R-02 Plan 04 exemption from the 2-of-3 compound gate). The new Latin-label requirement does NOT apply to desalination. All 15 currently-admitted desal remain, including the 5 with non-Latin-only names. Rationale: desal OSM coverage is sparse (~63 raw elements across the ME); dropping the 5 non-Latin entries would cost real strategic infrastructure coverage (Jeddah, Basra, Doha area, 2 coastal). Rule consistency yields to data scarcity.

### Rejection Bucket

- **D-04: New bucket `no_resolved_name`.** Added to both `WaterFilterStats.rejections` (summed view) and `WaterFilterStats.byTypeRejections[label]` (per-type view). Placed between `no_name` and `duplicate` in schema ordering so it reads as a progressive strictness continuation. The Zod schema (`server/schemas/cacheResponse.ts` `waterFilterStatsSchema`) is extended under `.strict()` — both the summed shape and the inner per-type shape add the field.
- **D-05: Decision ordering in `computeAdmissionDecision`.** Insert the new check AFTER step 3 (`no_name`) and BEFORE step 4 (non-desal compound 2-of-3). The new step:
  ```
  if (facilityType !== 'desalination' && !hasLatinLabel(tags)) {
    return { verdict: 'reject', bucket: 'no_resolved_name' };
  }
  ```
  This preserves existing first-match-wins semantics and keeps desal on its own admission track. `hasLatinLabel(tags)` is a new exported helper in `server/adapters/overpass-water.ts` that returns true iff any of `name:en` / `name` / `operator` is non-empty trimmed AND passes the existing `isLatin` regex.

### Server-Side Label Synthesis (Desalination Only)

- **D-06: `extractLabel` gains a narrow desal-only synthesis branch.** For the 5 exempt non-Latin desal, the server now synthesizes the display label at normalization time so the client never needs to re-derive anything. Resolution order inside `extractLabel`:
  1. If `name:en` is non-empty and Latin → title-cased `name:en`
  2. Else if `name` is non-empty and Latin → title-cased `name`
  3. Else if `operator` is non-empty and Latin → title-cased `operator`
  4. **NEW:** Else if `facilityType === 'desalination'` AND `nearestCity` resolved → `"Desalination Plant near {nearestCity.name}"` (150km lookup via existing `findNearestCity`)
  5. **NEW:** Else if `facilityType === 'desalination'` (no nearest city) → `"Desalination Plant at {lat}°, {lng}°"` (abs-value + N/S + E/W, 2 decimals — mirrors old client coord fallback format)
  6. Else → bare `FACILITY_TYPE_LABELS[facilityType]` (never reached for non-desal post-admission gate)
- **D-07: `extractLabel` signature change.** The function gains `(lat: number, lng: number, nearestCity: ReturnType<typeof findNearestCity>)` parameters. `normalizeWaterElement` must reorder to compute `findNearestCity` BEFORE `extractLabel` (already computed before `computeAdmissionDecision`, so passing through is mechanical).

### Client Simplification

- **D-08: `src/lib/waterLabel.ts` collapses to a single one-line read.**
  ```typescript
  export function getWaterFacilityDisplayName(facility: WaterFacility): string {
    return facility.label?.trim() || FACILITY_TYPE_LABELS[facility.facilityType];
  }
  ```
  Delete: `WATER_TYPE_LABELS` (duplicate of server `FACILITY_TYPE_LABELS` — import from server types instead), `NEAR_UNKNOWN_RE`, `GENERIC_TYPE_RE`, the 3-branch `linkedRiver` / `nearestCity` / coord fallback chain, the sentinel comments, and the D-10 audit scaffolding. Keep the file exporting `getWaterFacilityDisplayName` — same name, same contract (returns a non-empty human-readable display string), trivial implementation.
- **D-09: `FACILITY_TYPE_LABELS` becomes the single source of truth for type labels.** Imported from `server/adapters/overpass-water.ts` by the client instead of duplicating. Already exported; no server change needed.
- **D-10: Delete `src/lib/__tests__/waterLabel.test.ts` D-10 audit case.** The "GENERIC_TYPE_RE reachable via non-Latin-only-name" test is dead post-tightening — desal now carries a synthesized label from the server, and non-desal facilities with non-Latin names are rejected at admission. Replace the test file with coverage of the one-liner: (a) Latin-named facility returns raw label, (b) undefined label returns FACILITY_TYPE_LABELS fallback, (c) synthesized desal label passes through unchanged.

### Cache Invalidation

- **D-11: Redis key bump `water:facilities:v2` → `water:facilities:v3`.** Mirrors the Plan 11 (27.3.1) v1→v2 bump. Forces a cold snapshot-tier fill on first post-deploy request, so stale cached entries carrying the old 436-facility shape get replaced atomically. No migration logic. Sites key (`sites:v3`) unchanged — sites are untouched by this phase.

### Snapshot Regeneration

- **D-12: Regenerate `src/data/water-facilities.json` after code lands.** `npm run refresh:water` script (Plan 05 + Plan 09 of 27.3.1) runs against live Overpass + Redis, writes the new shape via atomic tempfile+rename. Expected outcome: 436 → ~304 facilities (240 dams + 49 reservoirs + 15 desalination). Commit regenerated JSON in the same commit as the `extractLabel` / `computeAdmissionDecision` changes — mirrors Plan 10 pattern.
- **D-13: Snapshot label fields change shape.** Admitted dams/reservoirs now always carry Latin names (no bare "Dam" / "Reservoir" labels). The 5 exempt desal carry server-synthesized `"Desalination Plant near {city}"` or `"Desalination Plant at {lat}°,{lng}°"` strings. Verify post-regeneration: zero facilities where `label` matches the `GENERIC_TYPE_RE` pattern from the now-deleted client safety net.

### Observability

- **D-14: DevApiStatus Water Filters section renders `no_resolved_name` bucket.** Mirror the existing bucket rendering pattern:
  - Summed view: add a row between `no_name` and `duplicate` in the "Total rejections" block of `src/components/ui/DevApiStatus.tsx` `WaterFiltersSection`.
  - Per-type view: add to the "Rejections by Type" block so each of `dams` / `reservoirs` / `desalination` shows its own `no_resolved_name` count (desal will always be 0 by construction — that's useful data proving the exemption is working).
- **D-15: Existing 7 rejection buckets keep current ordering.** Only insert one new entry. Don't restructure the panel.

### Test Coverage

- **D-16: Regression tests.** Add to `server/__tests__/overpass-water.test.ts`:
  - Non-desal dam with Latin `name:en` → admits.
  - Non-desal dam with Persian-only `name` → rejects to `no_resolved_name`.
  - Non-desal reservoir with non-Latin `name` + `linkedRiver` (within 20km of Tigris) → rejects to `no_resolved_name` (verify D-02 river-rescue kill).
  - Desalination with non-Latin `name` + no `nearestCity` → admits, `label === "Desalination Plant at {lat}°, {lng}°"`.
  - Desalination with non-Latin `name` + `nearestCity = Jeddah` → admits, `label === "Desalination Plant near Jeddah"`.
  - `computeAdmissionDecision` unit tests cover the new `no_resolved_name` branch ordering (after `no_name`, before desal-exempt compound).
- **D-17: `src/lib/__tests__/waterLabel.test.ts` coverage.** Replace the current D-10 audit scaffolding with:
  - Latin-named facility → returns raw `facility.label` trimmed.
  - Undefined / empty `facility.label` → returns `FACILITY_TYPE_LABELS[facility.facilityType]` (defensive fallback — shouldn't occur in production snapshots).
  - Synthesized desal label ("Desalination Plant near Jeddah") passes through unchanged.

### Deferred

- **D-18: Romanization deferred to Phase 27.3.3.** User directive: "deferring romanization of persian/arabic names and readding those facilities in pipeline for phase 27.3.3." Added to ROADMAP.md during this phase. Scope for 27.3.3 will be: add a transliteration step to `extractLabel` (ICU4C / `@sindresorhus/transliterate` / LLM synthesis) so Persian `سد سعد` becomes `Saad Dam` and re-admits under the D-01 Latin-label gate. Expected impact when 27.3.3 lands: snapshot count climbs from ~304 back toward ~430.

## Existing Code Insights

### Reusable Assets

- `isLatin(str)` (server/adapters/overpass-water.ts line ~357) — the script-check used by `extractLabel`. New `hasLatinLabel` helper reuses it verbatim.
- `findNearestCity(lat, lng)` (line ~449) — already runs inside `normalizeWaterElement` before `computeAdmissionDecision`. Reused for desal label synthesis (D-06 step 4).
- `FACILITY_TYPE_LABELS` (line ~405) — already exported. Client imports for its one-liner fallback.
- `computeAdmissionDecision` (line ~704) — first-match-wins decision function. Adding a new ordered branch is straightforward; `AdmissionVerdict` union already has `{ verdict: 'reject'; bucket: keyof WaterFilterStats['rejections'] }` and will pick up the new bucket automatically once the type is extended.
- `stats.byTypeRejections[entry.label]` initialization (line ~866) — the per-type bucket object literal already mirrors the summed shape; extend both lock-step (D-04).
- `waterFilterStatsSchema` `.strict()` Zod schema — the 27.3.1 Plan 11 Redis envelope pattern already round-trips this shape; adding a field requires updating both TypeScript and Zod together or the schema parse will fail on the new key. No other shape-change work needed.

### Established Patterns

- **Strict admission + post-admission enrichment.** `linkedRiver` / `nearestCity` / `capacity` / basin stress all compute at admission time regardless of admission outcome — costs a few dozen microseconds but keeps the code path uniform. 27.3.2 preserves this: no early-exit reordering to skip enrichment work for rejected elements.
- **First-match-wins rejection.** `computeAdmissionDecision` short-circuits on the first failing check. New `no_resolved_name` step slots in naturally.
- **Redis key bump on shape change.** Plan 11 v1→v2 established the pattern. No migration, no union-type read logic — just bump the key, let the snapshot tier refill.
- **Per-type rejection bucket initialized with all keys as zero.** `fetchFacilityType` seeds all 7 buckets before the first `normalizeWaterElement` call. Extending to 8 buckets is a single-line literal change.
- **Desalination exemption pattern.** Established in Plan 04 for the D-06 compound gate. 27.3.2 extends the same exemption pattern to the new Latin-label check — consistent decision architecture.

### Architectural Tension to Watch

- **Label synthesis now lives in two places — `extractLabel` for Latin names and the narrow desal fallback.** Single file, single function, but two conceptual paths. Worth a brief JSDoc comment explaining that the desal-only branches are the sole intentional generic-label synthesis in the codebase.
- **`linkedRiver` enrichment no longer gates admission, but still populates on admitted facilities.** The detail panel keeps showing "Sits on the Tigris" info. No-op from the client's perspective, but worth noting in the plan so reviewers don't think `linkRiver()` has become dead code.

## Specific Ideas

- **User directive verbatim (from 27.3.1-HUMAN-UAT.md Gap 2):** "yes... but I want to remove city and coord fallbacks and just drop those facilities." The rule is unambiguous; the discussion only refined the edge cases (desal exemption, safety-net disposition, bucket naming).
- **"Drop facilities with no label"** (user response during 27.3.2 discussion). Selected strict admission over the original "Latin name OR linkedRiver" framing — kills the 4 river-rescue admissions. Rationale: cleanest code, one-rule-to-remember.
- **"cleanest and most resilient code"** (user response on client safety-net disposition). Led to the combined pattern: server owns all label synthesis (including the narrow desal fallback), client is a one-liner read, Redis key bump handles cache freshness.
- **Desal exemption carved through by precedent** — the existing R-02 D-06 2-of-3 exemption for desalination extends cleanly to this Latin-label check. Consistent decision architecture: desal is the single "sparse-OSM-coverage" carve-out across both compound gate and label-script gate.
- **27.3.3 phase created during this discussion** — romanization of Persian / Arabic / Georgian names, re-admitting the dropped ~129 facilities (non-desal bare-label) under the existing D-01 gate after transliteration. Added to ROADMAP.md as a real phase, not just a deferred-idea note.
