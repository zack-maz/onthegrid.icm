## Known gap (user-accepted at Task 3 checkpoint)

Three desal entries have bare `"Desalination Plant"` labels because their OSM `name` tag is literally that phrase. `hasLatinLabel` passes (all ASCII), so `extractLabel` returns the tag verbatim without firing the synthesis branches. Plan 07 removed the client-side `GENERIC_TYPE_RE` guard in `src/lib/waterLabel.ts` under the assumption that the server owns all label synthesis — but the server-side branches only trigger when `hasLatinLabel` FAILS, not when it trivially passes on a generic string.

**User decision:** Accept and ship. Rare OSM-authoring pattern, note for follow-up if UX surfaces it.

**Proposed fix for a future patch (not this phase):** Extend `extractLabel` with a post-Latin-check `GENERIC_OSM_NAME_RE = /^(dam|reservoir|desalination(\s+plant)?)$/i` guard that treats bare generic names as missing and cascades into the desal synthesis branches. For non-desal, this would drop the 3 elements entirely (turning them into `no_resolved_name` rejections), which is consistent with D-01 intent. Scope ~5 lines in `server/adapters/overpass-water.ts`.
