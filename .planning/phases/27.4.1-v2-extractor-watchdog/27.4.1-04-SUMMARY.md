## Watchdog hook shape (D-11/D-12/D-13)

Identical contract to the shape v2 will apply in Plan 03:

```ts
const content = await withBatchWatchdog(
  () => callLLM(messages, EVENT_EXTRACTION_SCHEMA, { batchSize: batch.length }),
  {
    timeoutMs: env.LLM_BATCH_TIMEOUT_MS,   // 90s default (D-01/D-03)
    softWarnMs: 60_000,                     // D-02
    batchIndex,
    label: 'v1',                            // <-- only differs from v2
    onTimeout: async () => {
      for (const g of batch) {
        await enqueueDLQ({
          id: g.key,
          reason: 'timeout_watchdog',       // D-04
          lastError: `v1 batch ${batchIndex} exceeded ${env.LLM_BATCH_TIMEOUT_MS}ms`,
          timestamp: Date.now(),
        });
      }
      updateProgress({
        watchdogTimeoutCount: (llmProgress.watchdogTimeoutCount ?? 0) + 1,  // D-06
      });
    },
    onSoftWarn: (elapsedMs) => {
      /* append synthetic 'watchdog-soft-warn' entry to callHistory (D-02) */
    },
  },
);
```

On v1 watchdog timeout: `content` is `null`, the existing `if (content === null) { continue; }` branch fires, and the loop moves to the next batch without blocking further work.

## Decisions Made

- **D-14 audit before fix:** Followed the plan's mandatory audit step. Classifying 3 errors first (one per hypothesized category) confirmed that Category C was a downstream effect of Category B, which meant a single fix path (D-15) closed all 20 errors without touching the Zod schema or introducing non-null assertions. Saved an estimated ~15 min of speculative schema-tightening work.
- **v1 scope limit (no per-batch cache):** Per CONTEXT D-07, per-batch `cacheSetSafe` is scoped to v2 only. v1 is the rollback path that operators rarely use; doubling v1's maintenance surface for cache-write symmetry was explicitly out-of-scope. If a future incident proves v1 is actively used for long runs, that's 27.4.2+ scope expansion.
- **Typed-entry idiom for callHistory soft-warn append:** During Task 3, the inline object literal `{provider: 'cerebras', ...}` triggered TS2322 widening against the array element type (which has optional `skipReason`). Rather than cast or restructure, declared the entry as `NonNullable<typeof llmProgress.callHistory>[number]` before the spread. This is a clean TS pattern that preserves type safety without changing the shape of `LLMPipelineProgress.callHistory`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] TS2322 widening on callHistory append in onSoftWarn hook**

- **Found during:** Task 3 (watchdog wrap), immediately after initial edit.
- **Issue:** `[{provider: 'cerebras', ..., timestamp: Date.now()}, ...history].slice(0, 20)` was inferred as a union array mixing the inline literal (no `skipReason`) and `...history` entries (with optional `skipReason`), which TS refused to assign to `LLMPipelineProgress['callHistory']` (1 error).
- **Fix:** Declared the soft-warn entry as a variable typed `NonNullable<typeof llmProgress.callHistory>[number]` before the spread. This gives the array element the exact union-compatible shape without a cast.
- **Files modified:** `server/lib/llmEventExtractor.v1.ts` (in the same Task 3 edit).
- **Verification:** `npx tsc --noEmit -p tsconfig.server.json 2>&1 | grep -c llmEventExtractor.v1` = 0.
- **Committed in:** `34ef37f` (Task 3 commit).

The fix strategy was unaffected — one `if (!g) continue;` + one `if (!entity) continue;` still closes all 13 Category A errors.
