# Phase 27.4.1 Plan 03: V2 Extractor Watchdog Integration Summary

**Wave 2 integration plan — wires the Plan 01 withBatchWatchdog helper + cacheSetSafe into `processEventGroupsV2`. Each successful batch now writes an LLMCachePayload envelope to `events:llm:v2`, hung Cerebras calls hit a 90s hard-kill and their groups are DLQ-routed with `reason='timeout_watchdog'`, and the final write carries `complete: true` so readers can detect end-of-run. Closes Phase 27.4's shipped P0 defect (one hung call losing 45+ minutes of LLM work).**

### Task 1 — processEventGroupsV2 integration (commit `e34e992`)

- Added imports for `cacheSetSafe`, `withBatchWatchdog`, `updateProgress`, `llmProgress`, and `env` to `server/lib/llmEventExtractor.v2.ts` — matches the Plan 01 public API.
- Exported new `LLMCachePayload` type (D-08) with template-literal `progress: \`${number}/${number}\`` so malformed callers trip the compiler, not the runtime.

- Added `writePartialCache(events, completed, total, complete)` module-private helper — single write path with 4 call sites (null content, zod fail, success, final) so progress/complete/generatedAt semantics can't drift.
- Rewrote the `processEventGroupsV2` for-loop body:
  - Wrapped `callLLM` in `withBatchWatchdog` with `timeoutMs: env.LLM_BATCH_TIMEOUT_MS`, `softWarnMs: 60_000` (hard-coded per D-02).
  - Composed `onTimeout` hook: for-loops the batch and DLQ-enqueues each group with `reason: 'timeout_watchdog'`, then bumps `watchdogTimeoutCount` via `updateProgress`.
  - Composed `onSoftWarn` hook: prepends a synthetic `{provider: 'cerebras' as const, model: 'watchdog-soft-warn', durationMs: elapsedMs, ...}` entry to `llmProgress.callHistory` so DevApiStatus shows an amber marker.
  - Added `writePartialCache(results, batchIndex + 1, totalBatches, false)` after each of the three batch-termination paths (null content, zod fail, success).
- Added a final `writePartialCache(results, totalBatches, totalBatches, true)` call after the loop (D-10) so readers can detect end-of-run.
- `V2ExtractionRun` return shape unchanged — no changes to the extractor's public contract.

## Known Gotchas (for Plan 04 + downstream operators)

1. **Envelope shape collision with the existing route writer.** The route handler's fire-and-forget block (`server/routes/events.ts:1016`) writes a plain `ConflictEventEntity[]` to `events:llm:v2` after the full pipeline finishes (extraction → geocoding → merge). The v2 extractor's per-batch writes write `LLMCachePayload` envelopes. During an active run, the cache is an envelope object; after the run completes and the route handler's terminal `cacheSetSafe(...)` fires, the cache reverts to a plain array. This is the shape transition the plan's Change 4 note describes.

   **D-09 risk:** the reader at `server/routes/events.ts:675-678` reads `events:llm:v2` as `ConflictEventEntity[]` and the Pitfall 1 bridge gate at line 685 is `if (pipelineV2 && !llmCached?.data)` — which is truthy-data gated, not array-shape gated. If an envelope is read on a concurrent `/api/events` request during active processing, `normalizeEventTypes` would `.map` on a non-array object and throw. Per plan scope (`server/routes/events.ts` untouched), this is an accepted window during rollout — the Phase 27 LLM cooldown (`events:llm-process-ts` 15-min key) + serverless cold-start characteristics make concurrent-during-processing reads rare. Partial-v2-to-user is explicitly deferred per D-09.

2. **Plan 04 (v1 integration) needs to mirror this exact shape.** If Plan 04 writes a `LLMCachePayload`-shaped envelope to `events:llm` (the v1 key), v1 readers will hit the same non-array risk. Keep the envelope type exported from `llmEventExtractor.v2.ts` so Plan 04 can reuse it. Consider whether v1 needs a similar envelope at all — the P0 was specifically v2-shipped.
