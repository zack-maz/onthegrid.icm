## Watchdog signature (canonical)

```ts
export interface BatchWatchdogOptions {
  timeoutMs: number;          // D-01 default 90_000
  softWarnMs: number;         // D-02 default 60_000 (soft-only; log, non-terminating)
  batchIndex: number;         // log / error correlation
  label: string;              // 'v1' | 'v2'
  onTimeout: () => Promise<void>;        // caller composes DLQ + progress
  onSoftWarn?: (elapsedMs: number) => void;
}

export async function withBatchWatchdog<T>(
  batchFn: () => Promise<T>,
  opts: BatchWatchdogOptions,
): Promise<T | null>;
```

Contract:

- Returns `T` on success.
- Returns `null` on hard-timeout (after `onTimeout` is awaited).
- Rethrows if `batchFn` rejects before timeout (identical to pre-watchdog behavior for non-timeout errors).
- A batch promise that resolves/rejects AFTER the timeout is silently discarded — `onTimeout` is not called again, no return clobbers the `null` the caller already has (D-05).

## 4 tested behaviors

1. **Success path** — `batchFn` resolves in 10ms with `timeoutMs=100, softWarnMs=1000`; `onTimeout` + `onSoftWarn` never invoked.
2. **Hard-timeout path** — `batchFn` never resolves; fake timers advance by `timeoutMs=50`; result is `null`, `onTimeout` called exactly once. Subsequent late-resolve does not re-invoke `onTimeout`.
3. **Soft-warn path** — `batchFn` resolves at 80ms with `softWarnMs=50, timeoutMs=200`; `onSoftWarn` called once at 50ms with `elapsedMs=50`, then resolves with the correct value; `onTimeout` never called.
4. **Late-resolve clobber-prevention (D-05)** — After hard-timeout fires at 30ms, firing the late resolver at 100ms+ does not flip the `onTimeout` invocation count past 1.

## Decisions Made

- **Watchdog stays free of redis/progress imports.** The `onTimeout` hook is caller-composed (Wave 2 will write `async () => { await enqueueDLQ({...reason:'timeout_watchdog'}); updateProgress({ watchdogTimeoutCount: n+1 }); }`). This keeps the helper trivially unit-testable (no redis mock needed inside the test for the helper itself) and preserves the one-module-one-responsibility boundary.
- **`onSoftWarn` + `onTimeout` hook errors are swallowed + logged, not propagated.** Rationale: the watchdog's job is to keep the batch loop alive. If a telemetry hook throws, re-raising would cascade into the same P0 the phase is fixing (one hung call kills the loop). Logs are present for diagnosis.
- **`buildSummary()` NOT updated with `watchdogTimeoutCount`.** Per CONTEXT D-06, the field is live-progress-only for DevApiStatus — no cold-start persistence requirement. Leaving `buildSummary` untouched avoids a hidden coupling between this plan and `LLMRunSummary` consumers. A future plan can promote the field to the summary if needed.
