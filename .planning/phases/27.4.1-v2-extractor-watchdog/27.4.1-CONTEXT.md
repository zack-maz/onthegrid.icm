<decisions>
## Implementation Decisions

### Watchdog (P0)

- **D-01** Default batch timeout: **90 seconds hard**. Cerebras's healthy-but-slow regime under "high traffic" reaches 60s+; 90s catches true hangs with margin without false-positive DLQ'ing legitimate slow batches.
- **D-02** Soft-warn threshold: **60 seconds**. When a batch crosses 60s but completes successfully, log the entry to `callHistory` with an amber status marker so we have real p95 data to re-tune on without redeploys.
- **D-03** Env var override: **`LLM_BATCH_TIMEOUT_MS`**. Authoritative value comes from env; fallback to 90000 if unset. Allows in-incident tuning without code change.
- **D-04** Timeout action: **DLQ-route the timed-out group with `reason: 'timeout_watchdog'`** + continue processing. Preserves existing DLQ semantics — the group enters normal retry/exclusion pipeline. Do NOT silently skip or retry inline.
- **D-05** Watchdog mechanism: **`Promise.race([batchCall(), timeoutPromise])`**. The lost call's eventual resolution must NOT clobber the cache. Use an abort signal or generation counter to prevent the resolved-late Promise from writing to Redis.
- **D-06** Watchdog telemetry: **`llmProgress.watchdogTimeoutCount`** field incremented on each timeout. Surface in existing DevApiStatus pipeline waterfall.

### Cache write granularity

- **D-07** Write frequency: **every successful batch**. At our scale (~200KB array, ~184 batches) per-batch serialization cost is <1ms — negligible. Maximum durability wins.
- **D-08** Cache envelope shape: **`{events: [...], progress: 'N/M', complete: boolean, generatedAt: ISO8601}`**. The new `progress` and `complete` fields let readers tell a partial snapshot from a final one. The existing `fetchedAt` semantics on the outer `CacheEntry<T>` wrapper stay unchanged.
- **D-09** Reader semantics: **unchanged — Pitfall 1 bridge stays as-is**. When `events:llm:v2` is non-empty but `complete: false`, `/api/events` STILL serves v1 cache if populated, per existing graceful-degradation contract. Partial-v2-to-user is deferred to a future phase. This keeps 27.4.1 focused on durability, not UX.
- **D-10** Final write: when all batches complete, set `complete: true` and write one final time so readers can detect completion without inspecting progress math.

### v1 extractor symmetry

- **D-11** Apply watchdog to BOTH v1 and v2: **shared helper `server/lib/llmExtractorWatchdog.ts`** exports a `withBatchWatchdog(batchFn, options)` function that wraps any per-batch Promise with timeout + DLQ routing + telemetry updates.
- **D-12** Rationale: the rollback path must be reliable. If v2 breaks and operators flip `LLM_PIPELINE_V2=false` (or POST to `/llm-pipeline`), v1 must not exhibit the same defect. Asymmetric reliability on a rollback path is a footgun.
- **D-13** Integration surface per extractor is ~5 lines once the helper exists.

### TS narrowing approach

- **D-14** Audit before fix: **inspect 3 of the 20 `llmEventExtractor.v1.ts` errors first** before committing to an approach. Per STATE.md, `noUncheckedIndexedAccess` is on for server tsconfig — most `possibly undefined` errors in loops are TS-strictness noise, not Zod optionality.
- **D-15** Preferred fix for `noUncheckedIndexedAccess`-caused errors: **local-bind + early-continue** (`const current = arr[i]; if (!current) continue;`). Preserves runtime check instead of asserting non-null via cast.
- **D-16** Alternative for Zod-schema-caused optionality: **tighten the Zod schema** in `llmSchema.ts` to remove `.optional()` where runtime guarantees presence. Do NOT cast to a non-optional type post-parse if Zod can still produce undefined — that lies to the compiler.
- **D-17** Non-null assertions (`!`) are LAST resort. If used, MUST be paired with an inline comment naming the invariant being asserted.

### Quick wins

- **D-18** `llm-provider.ts:232` TS error: fix per error-specific context — likely a null-check at the call site or argument type narrowing. No speculation without reading the actual line.
- **D-19** `entityLayers.test.ts` color test: **update test expectation to `[220,100,90]`** (the current code value). Canonical is the shipped code as of Phase 27 commit `709fa15`, not the stale test expectation. No code change to the color itself.
- **D-20** `PipelineVersionPill` strip-to-indicator: **remove onClick handler + optimistic local state**, keep all other behavior (version fetch on mount, dot + label render). Do NOT remove `GET`/`POST /api/events/llm-pipeline` endpoints — they stay for scripted/operator use. Update any pill-related tests to expect no-op click.

### Process

- **D-21** Commit cadence: one atomic commit per plan (existing project convention).
- **D-22** Test coverage targets: watchdog helper must have direct unit tests (mock hang, verify timeout + DLQ + telemetry); v1.ts TS cleanup adds no new tests (type-only change). Quick wins all include test updates inline.
- **D-23** No new dependencies. `Promise.race` is native; abort-signal is Web API; DLQ module already exists in Phase 27.4 scope.

<deferred>
## Deferred Ideas

- **Partial-v2 reader semantics.** Serving `events:llm:v2` before `complete: true` is a future UX decision. Needs a threshold (e.g., serve at ≥50% complete) and user-facing "data refreshing" signal. Not in 27.4.1.
- **Preemptive token-budget projection.** P3 from 27.4 HANDOFF — show "on track to hit cap in ~40 min" in DevApiStatus. Not in 27.4.1.
- **Debug session on reproducible Cerebras hang.** If a specific prompt/group reliably triggers a Cerebras hang, that's worth isolating. Not in 27.4.1 — watchdog makes this diagnosable, not remediates the root cause.
- **Replacing Cerebras primary with Groq.** If Cerebras hangs keep happening post-watchdog, consider reordering the provider cascade. Data-driven decision after 27.4.1 lands.

</deferred>
