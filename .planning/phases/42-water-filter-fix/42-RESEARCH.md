## Summary

This is a tightly-scoped, internal-code bug-fix phase. No new external packages, no UI surface, no Overpass query changes. The CONTEXT.md pre-registers the fix (name-aware + deterministic spatial dedup) and gates it on a telemetry-first diagnosis. My job for the planner was to confirm the prime suspect against the actual source and enumerate the exact lockstep surfaces. Both are now verified.

**The bug is confirmed in source** at `server/adapters/overpass-water.ts:1202-1212` (the only spatial-dedup loop). It has TWO defects that together produce the "intermittent drop of legitimate named facilities" symptom:

1. **Name-blind collapse** — the predicate (lines 1205-1209) collapses any two facilities of the same `facilityType` within 50m (`haversine < 0.05`), with NO name comparison. Two distinct named facilities (e.g. a named dam and its named spillway, or two adjacent named reservoirs) within 50m collapse to one. This violates WATER-FILTER-02 literally.
2. **Order-dependent survivor** — the loop iterates `Array.from(unique.values())` and keeps the FIRST-seen element (`deduped.push(f)` only `if (!isDupe)`). `unique` is a `Map` whose insertion order tracks Overpass return order (`all.push(...facilities)` per query, per mirror). So WHICH facility of a colliding pair survives varies run-to-run. This is the "intermittent" symptom — the determinism fix (D-07/D-08) is as load-bearing as the name-awareness.

**Primary recommendation:** Diagnosis-first (D-01/D-02): run `npm run refresh:water` ≥2× and diff admitted ID sets BEFORE any code change; land `42-DIAGNOSIS.md` citing the `duplicate` bucket and naming concrete dropped OSM elements. Then implement the name-aware + deterministic dedup at lines 1202-1212, bump `water:facilities:v3`→`v4` across the 8 source sites + 3 docs + whitelist entry, regenerate `src/data/water-facilities.json`, and add the FIRST-EVER spatial-dedup unit tests (the `duplicate` bucket is currently 0 in every fixture — a real coverage gap).

### Pattern 1: Name-aware collapse predicate (the fix, D-04/D-05)

**What:** Narrow the collapse condition so two facilities collapse ONLY when same-type AND within 50m AND (normalized names match OR one side is unnamed). Keep the 50m radius and same-`facilityType` constraint exactly as-is (D-05).
**When to use:** Replace the predicate at lines 1205-1209.
**Example (illustrative — confirm field choice against diagnosis, D-04 discretion):**

```typescript
// Source: derived from overpass-water.ts:1202-1212 + CONTEXT D-04/D-05/D-07
// normalize: lowercase + collapse whitespace on the post-romanization display name.
// Field choice (label vs nameLatin) is Claude's discretion per D-04 — label is the
// rendered display string and already reflects romanization, so it is the natural pick.
function normName(f: WaterFacility): string {
  return (f.label ?? '').toLowerCase().replace(/\s+/g, ' ').trim();
}

// Deterministic input order kills the "intermittent" symptom (D-07/D-08):
// sort the working set so dedup is order-independent regardless of Overpass return order.
const ordered = Array.from(unique.values()).sort(
  (a, b) =>
    (b.notabilityScore ?? 0) - (a.notabilityScore ?? 0) || // highest score wins survival
    a.osmId - b.osmId, // tie-break: lowest osmId
);

const deduped: WaterFacility[] = [];
for (const f of ordered) {
  const fname = normName(f);
  const isDupe = deduped.some((existing) => {
    if (existing.facilityType !== f.facilityType) return false;
    if (haversine(existing.lat, existing.lng, f.lat, f.lng) >= 0.05) return false;
    const ename = normName(existing);
    // collapse ONLY when names match OR one side is unnamed (D-04)
    return ename === fname || ename === '' || fname === '';
  });
  if (!isDupe) deduped.push(f);
  else stats.rejections.duplicate++;
}
```

**Why deterministic ordering matters:** Pre-sorting by `notabilityScore desc, osmId asc` means the survivor is chosen by D-07's rule, not by which Overpass mirror responded first. Two consecutive runs over the same corpus then produce identical admitted ID sets (D-08 acceptance check).

### Anti-Patterns to Avoid

- **Widening or shrinking the 50m window** — D-05 forbids it. The fix narrows WHAT collapses (add name equality), never the spatial window.
- **Touching `computeAdmissionDecision` / `hasLatinLabel`** — D-06 forbids loosening the Latin gate. The dedup fix is downstream of admission and must not edit the admission function. Any diagnosis finding that implicates `no_resolved_name` must be surfaced to the operator BEFORE action (D-06).
- **Mutating `WaterFilterStats` shape breakingly** — D-13: the 8-bucket shape is frozen; at most ONE additive-OPTIONAL field, mirrored in the schema test the same commit.
- **Bumping the cache key in source without the docs + whitelist** — `redis-registry.test.ts` mechanically greps source literals and cross-checks CLAUDE.md + `redis-keys.md`; a partial bump fails the drift gate.

## Common Pitfalls

### Pitfall 1: `duplicate` is a summed-only bucket — per-type `byTypeRejections.*.duplicate` is never incremented

**What goes wrong:** The diagnosis (D-02) wants to cite the specific `byTypeRejections` bucket(s). But the dedup loop increments `stats.rejections.duplicate` (the SUMMED field, line 1211) and never touches `stats.byTypeRejections[type].duplicate`. So today the per-type `duplicate` is always 0 even when collapses happen.
**Why it happens:** Dedup runs AFTER the per-query loop, on the merged `unique` set — at that point the code no longer knows which query bucket each facility came from.
**How to avoid:** The diagnosis can still cite the SUMMED `rejections.duplicate` and name concrete dropped elements from the two-run ID-set diff (D-02 already requires the ID-set diff as primary evidence). If the planner wants per-type `duplicate` visibility, that is exactly D-13's "at most one additive-OPTIONAL field" — e.g. populate `byTypeRejections[f's originating type].duplicate` during the dedup loop, OR add a capped `dedupCollisions` sample. Either way mirror it in `waterFilterStats.test.ts` the same commit.
**Warning signs:** A diagnosis that claims "the `byTypeRejections.dams.duplicate` bucket ate N facilities" would be citing a field that is structurally always 0 — a tell that the author misread the telemetry.

### Pitfall 2: Determinism fix is invisible without a fixed corpus

**What goes wrong:** D-08 acceptance ("two consecutive `refresh:water` runs produce identical admitted ID sets") can be polluted by Overpass returning a genuinely different element set between runs (network flakiness, mirror differences, OSM edits), masking whether the dedup itself is deterministic.
**Why it happens:** `refresh:water` hits live Overpass; two live runs are not guaranteed to see the same raw corpus.
**How to avoid:** For the determinism unit test, feed a FIXED in-memory corpus directly to the dedup logic (see Pitfall 3 — the loop must be testable). The live two-run diff (D-02) is diagnostic evidence; the deterministic-output guarantee is proven by the unit test against a fixed corpus, not by two live runs alone.
**Warning signs:** Intermittent two-run diffs that vary in count, not just order — that's corpus drift, not dedup non-determinism.

### Pitfall 3: The spatial-dedup loop has ZERO existing unit tests and is not independently callable

**What goes wrong:** The `duplicate` bucket is `0` in every fixture in `overpass-water.test.ts` and `waterFilterStats.test.ts` (verified by grep). The dedup loop is inline inside `fetchWaterFacilities`, which makes live Overpass calls — so it cannot be unit-tested as written.
**Why it happens:** Dedup was never given its own export; it only ran inside the network-bound fetch.
**How to avoid:** To satisfy WATER-FILTER-04's "a fixture for the previously-dropped OSM element fails on regression" (D-14), the dedup logic likely needs extraction into an exported pure function (e.g. `spatialDedup(facilities: WaterFacility[]): { kept: WaterFacility[]; collapsed: number }`) so a fixture corpus can be fed directly. This is the cleanest way to: (a) assert the named pair within 50m BOTH admit post-fix, (b) assert the `duplicate` delta, (c) assert deterministic output order. The `computeAdmissionDecision` extraction (Phase 27.3.1 R-06 D-20) is the precedent pattern for pulling a pure function out of `normalizeWaterElement` for direct testing.
**Warning signs:** A plan that adds dedup tests but keeps the loop inline inside `fetchWaterFacilities` — those tests would have to mock the entire Overpass fetch, which is brittle and slow.

### Pitfall 4: Loosening the collapse for "unnamed" can resurrect dropped-name behavior

**What goes wrong:** D-04 says collapse when "one side is unnamed." If `normName` returns `''` for a facility that actually HAS a romanized label (because the wrong field was read), the predicate treats it as unnamed and collapses a distinct named facility — re-introducing the bug.
**Why it happens:** Field-choice ambiguity — `label` vs `nameLatin` vs `nameOriginal`. Post-romanization, `label` is the rendered display string and is the safest single source; `nameLatin` is set only when `applyRomanizedName` fired.
**How to avoid:** Read `f.label` (always populated by `extractLabel`, line 984) for the comparison, per the Pattern 1 example. Pin a fixture where both sides have distinct non-empty labels and assert NO collapse.
