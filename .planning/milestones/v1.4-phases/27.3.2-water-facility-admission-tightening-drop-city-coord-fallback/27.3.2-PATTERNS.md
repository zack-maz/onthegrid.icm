```typescript
/**
 * Phase 27.3.2 D-01 / D-05: Latin-label admission check. True iff at least
 * one of `name:en` / `name` / `operator` is a non-empty trimmed string AND
 * passes the isLatin script guard. Mirrors the script-check branches already
 * present in extractLabel — consolidated so computeAdmissionDecision can
 * reject non-Latin-only elements with the `no_resolved_name` bucket.
 *
 * Desalination callers bypass this check (see D-03 exemption in
 * computeAdmissionDecision).
 */
export function hasLatinLabel(tags: Record<string, string>): boolean {
  const en = tags['name:en']?.trim();
  if (en && isLatin(en)) return true;
  const name = tags['name']?.trim();
  if (name && isLatin(name)) return true;
  const op = tags['operator']?.trim();
  if (op && isLatin(op)) return true;
  return false;
}
```

#### Pattern 3: `extractLabel` signature extension + desal-only synthesis branches (D-06, D-07)

**Current implementation (lines 411–419):**

```typescript
/** Extract an English label from OSM tags */
function extractLabel(tags: Record<string, string>, facilityType: WaterFacilityType): string {
  const en = tags['name:en'];
  if (en && en.trim() && isLatin(en)) return toTitleCase(en);
  const raw = tags['name'] || '';
  if (raw && isLatin(raw)) return toTitleCase(raw);
  if (tags.operator && isLatin(tags.operator)) return toTitleCase(tags.operator);
  return FACILITY_TYPE_LABELS[facilityType];
}
```

**Pattern for extension (D-06 steps 4–5 + D-07 signature):**

```typescript
/**
 * Extract an English label from OSM tags.
 *
 * Phase 27.3.2 D-06: extended with a desalination-only synthesis branch for
 * the 5 exempt non-Latin desal facilities. Non-desal facilities never hit
 * the synthesis branches because `computeAdmissionDecision` rejects them
 * via `no_resolved_name` at admission time (D-05). Label synthesis lives
 * server-side so the client can be a one-line read (D-08).
 *
 * Resolution order:
 *   1. name:en Latin → title-cased name:en
 *   2. name Latin → title-cased name
 *   3. operator Latin → title-cased operator
 *   4. [NEW — desal only] "Desalination Plant near {city}" (nearestCity within 150km)
 *   5. [NEW — desal only] "Desalination Plant at {lat}°, {lng}°" (no city)
 *   6. Bare FACILITY_TYPE_LABELS[facilityType] — never reached for non-desal
 *      post-admission (defense-in-depth only).
 */
function extractLabel(
  tags: Record<string, string>,
  facilityType: WaterFacilityType,
  lat: number,
  lng: number,
  nearestCity: ReturnType<typeof findNearestCity>,
): string {
  const en = tags['name:en'];
  if (en && en.trim() && isLatin(en)) return toTitleCase(en);
  const raw = tags['name'] || '';
  if (raw && isLatin(raw)) return toTitleCase(raw);
  if (tags.operator && isLatin(tags.operator)) return toTitleCase(tags.operator);

  // D-06 desal-only synthesis branches (non-desal rejected at admission).
  if (facilityType === 'desalination') {
    if (nearestCity) {
      return `Desalination Plant near ${nearestCity.name}`;
    }
    const latStr = `${Math.abs(lat).toFixed(2)}°${lat >= 0 ? 'N' : 'S'}`;
    const lngStr = `${Math.abs(lng).toFixed(2)}°${lng >= 0 ? 'E' : 'W'}`;
    return `Desalination Plant at ${latStr}, ${lngStr}`;
  }

  return FACILITY_TYPE_LABELS[facilityType];
}
```

**Note:** The coord format exactly mirrors the old client fallback from `src/lib/waterLabel.ts` lines 87–89 (`Math.abs().toFixed(2)` + cardinal), so the synthesized string is byte-identical to what the client used to produce for stale desal records (per D-06 step 5 "mirrors old client coord fallback format").

## Shared Patterns

### Rejection Bucket Lock-Step

**Source:** `server/adapters/overpass-water.ts` — 3 seed locations + 1 interface shape

**Apply to:** Any extension of `WaterFilterStats['rejections']`.

**Rule:** Every new bucket requires FOUR synchronized edits:

1. TS interface `rejections` shape (line ~573)
2. TS interface `byTypeRejections` inner shape (line ~600)
3. `fetchFacilityType` per-type bucket seed (line ~866)
4. `fetchWaterFacilities` top-level rejections seed (line ~987)

PLUS: 5. Zod `rejectionsSchema` in `server/schemas/cacheResponse.ts` (line ~138) — auto-propagates to summed + per-type. 6. Redis key bump in `server/routes/water.ts` (line ~113) — because `.strict()` rejects cached entries missing the new key. 7. DevApiStatus `WaterFiltersSection` — summed row + per-type row, both get the new token.

A PR that edits only a subset of these will either fail typecheck (missing field in seed) or fail cached-response parse (strict Zod on stale Redis data).

### Desalination Exemption Pattern

**Source:** `server/adapters/overpass-water.ts` `computeAdmissionDecision` step 4 (lines 740–745)

**Current exemption literal:**

```typescript
if (facilityType !== 'desalination') {
  const signalCount = [isNotable(tags), inPriority, hasCapacityData(tags)].filter(Boolean).length;
```

**Apply to:** The new D-05 branch — use the exact `facilityType !== 'desalination'` guard, mirroring Plan 04 Branch 2c. Keeps the "single sparse-OSM-coverage carve-out" architecture consistent.

### Redis Key Bump on Shape Change

**Source:** `server/routes/water.ts` line 113 + CONTEXT.md `<code_context>` "Redis key bump on shape change"

**Apply to:** Any PR that adds a required key to the Zod envelope. `.strict()` parsing means stale cached entries without the new key fail validation — bump forces cold-fill, avoids migration code.

**Convention:** Bump by integer suffix (`v2` → `v3`), update the JSDoc note with a new paragraph citing the phase and the field that changed.

### First-Match-Wins Admission Ordering

**Source:** `server/adapters/overpass-water.ts` `computeAdmissionDecision` JSDoc (lines 682–697)

**Apply to:** Any insertion into the admission decision function. Each new branch short-circuits on reject; ordering determines which bucket a marginal element lands in when it fails multiple gates. Insertion of `no_resolved_name` BETWEEN `no_name` (step 3) and `not_notable` (step 4) means:

- An element missing both name AND Latin name lands in `no_name` (most-specific failure first).
- An element with name-but-non-Latin-only lands in `no_resolved_name`.
- An element with Latin name but failing 2-of-3 compound lands in `not_notable`.

This ordering preserves the "progressive strictness" reading per D-04.
