> **Phase shape:** Surgical bug-fix phase — one architectural defect in `server/lib/llmExtractionPipeline.ts`, two coupled code changes that must ship together. Both changes are independently insufficient; the value is in their composition. This phase exists because Phase 28.2.5's tier-green CI gate (D-09) keeps returning `allTiersGreen=false` until `critical[llmEvents]` flips from `unknown` → `healthy`, which can't happen until `events:llm:v3` is non-empty, which requires the cron to actually run extraction batches to completion on Vercel Fluid Compute.

<domain>
## Phase Boundary

**The single defect:** The cron at `/api/cron/refresh-events` uses `void (async () => {...})()` to run LLM extraction in the background after returning HTTP 200. On Vercel Fluid Compute, the function instance is killed the moment the response is sent — the background work never executes. Verified 2026-05-07 on prod: forced cron with `?force=true`, polled `/api/events/llm-status` 5 times across instances; every poll showed `stage: idle, callHistory: 0, dlqCount: 0`. Zero batches ran. Terminal cache key `events:llm:v3` stays empty. The dashboard's "Events (LLM)" health row, the `/api/health endpoints.llmEvents` field, and the prod-connectivity-audit.yml tier-green gate all sit downstream of that key — so they all stay `unknown` indefinitely.

**Awaiting the IIFE inline** (instead of fire-and-forget) keeps the function alive but hits a different ceiling: full v3 extraction is ~10 minutes wall time, Vercel Hobby caps `maxDuration` at 300s. Tried in commit `b016a5c`; the function timed out mid-extraction with 6 batches in DLQ and the final terminal-key cacheSet at `llmExtractionPipeline.ts:386` unreachable. Reverted in `b4bf4a3`.

**The fix:** Two coupled changes. Both must land together; neither works alone.

- **Change A — incremental terminal-key write.** `events:llm:v3` (and v2/v1 fallbacks) gets `cacheSet`-ed periodically during extraction, not only at end-of-pipeline. Within a 300s function window we now leave a non-empty cache even if the function aborts before reaching the final write. Resume semantics on the next 4am UTC tick are handled by the existing D-18 `groupLineageHash.ts` pre-filter (no change required there).

- **Change B — Vercel `waitUntil` migration.** Replace `void (async () => {...})()` at `server/lib/llmExtractionPipeline.ts:203` with `waitUntil(...)` from `@vercel/functions`. Without this, Change A is academic — the function still dies the instant the response is returned, so the incremental writes never run. `waitUntil` is Vercel's official mechanism for "let the function instance survive past the response so background work completes within the maxDuration budget."

**Out of scope for 28.2.6:**

- **Vercel Pro plan upgrade.** Considered as Path B in discuss-phase (would lift maxDuration to 800s/3600s). Rejected — operator preference for code-only fix.
- **Splitting extraction into N parallel cron routes.** Bigger refactor; the incremental-write + waitUntil combo gets us to green without sharding.
- **Optimizing extraction wall time below 10 minutes.** Concurrency, prompt size, batch size are all tunable, but they're 28.4+ scope. 28.2.6 only needs to make the existing 10-min extraction survive the function-boundary problem.
- **`@vercel/functions` adoption beyond this one call site.** Other cron routes (`cron-warm`, `cron-health`) currently work fine because their bodies are synchronous-await within the route handler — no fire-and-forget. Don't migrate them as part of this phase.
- **Changing the 4am UTC cron schedule.** Out of scope.
- **Refactoring `groupLineageHash.ts` or `events:llm:v3:partial` semantics.** Both are working as designed; the partial-key writer + lineageHash pre-filter together provide the cross-tick resume semantics that make incremental writes safe.

**Branch discipline:** Own feature branch (`feature/28.2.6-cron-architecture-fix` per `feedback_branch_per_phase.md`). Close = merge to main. After merge, force-trigger `?force=true` once to populate the cache, then trigger prod-connectivity-audit.yml and verify `allTiersGreen=true`. Phase 28.3 unblocks.

<decisions>
## Implementation Decisions

### Phase Shape & Sequencing

- **D-01:** Resolution path = **architecture refactor — incremental terminal-key write + Vercel `waitUntil` migration (Changes A + B coupled).** Both must land together; neither works alone.
  - **Why:** Verified empirically. Just Change A (incremental writes, no waitUntil) → function dies in <1s after response, incremental writes never execute (matches the `callHistory: 0` evidence pre-hot-fix #2). Just Change B (waitUntil, no incremental writes) → function stays alive up to 300s, runs as many batches as fit, then dies before reaching the single end-of-pipeline cache write — same outcome as the awaited-IIFE attempt in `b016a5c`. Both together → function survives past response, runs batches, writes incrementally, next tick resumes via lineageHash pre-filter. Within 1-2 cron ticks the cache is fully populated.
  - **How to apply:** Two atomic plans (or one combined plan with two stages — planner's discretion). Change A and Change B can land in either order in the same PR but must NOT be split across PRs. The "both together" invariant is the load-bearing property.

- **D-02:** Phase 28.3 (load test) remains gated on this phase. The 28.2.5 D-09 tier-green CI gate keeps `allTiersGreen=false` until `critical[llmEvents]` flips from `unknown` → `healthy`.
  - **Why:** A 1–300 VU sweep against a half-broken data path produces meaningless numbers. The gate exists exactly to prevent that.
  - **How to apply:** ROADMAP.md Phase 28.3 `Depends on:` line already includes Phase 28.2.6 (added during /gsd-discuss-phase 28.2.6). After 28.2.6 merges, force-trigger the cron once, wait 4 minutes, then trigger prod-connectivity-audit.yml from the GH Actions UI — when `allTiersGreen=true`, 28.3 unblocks.

### Change A — Incremental Terminal-Key Write

- **D-03:** **Cadence: every N batches (N=10 suggested).** Final write at end-of-pipeline still happens (no behavior change there); only adds intermediate writes.
  - **Why:** Per-batch writes (N=1) overload Redis under concurrency=12. Per-end-only (status quo) doesn't survive the function boundary. N=10 keeps Redis write rate bounded while ensuring incremental progress survives function termination.
  - **How to apply:** Track `batchesSinceLastFlush` counter alongside the existing `completedBatchesCounter` in `server/lib/llmExtractionPipeline.ts`. When `batchesSinceLastFlush >= 10`, call the same `cacheSet(events:llm:v3, terminalArray, TTL)` block currently at `llmExtractionPipeline.ts:386` and reset the counter. Final write at line 386 unchanged. Planner picks the exact insertion site.

- **D-04:** **Shape: terminal key continues to hold `ConflictEventEntity[]` (NOT `LLMCachePayload` envelope).** Two-key discipline preserved.
  - **Why:** Phase 27.4.1 documented this load-bearing invariant: `events:llm:v3` is `ConflictEventEntity[]`, `events:llm:v3:partial` is `LLMCachePayload`. The original Plan 03 wrote envelopes to the terminal key and crashed every consumer (`events.map is not a function`). Key split landed in `a5c8846`. Reader defense-in-depth helpers `toEntityArray` / `coerceCachedEvents` (commit `e26ceca`) stay as the safety net. Plan 28.2.6 must NOT collapse the two-key discipline.
  - **How to apply:** The intermediate writes use the same terminal-key write path the final write uses today (line 386). They produce the same shape (`ConflictEventEntity[]`). The `events:llm:v3:partial` envelope writes via `writePartialCache` are unchanged.

- **D-05:** **Geocoding interaction: geocode-per-batch-window** — partial cache contents must always be self-consistent (extraction + geocoding done) so consumers never see half-enriched events.
  - **Why:** The user's discuss-phase lean. The alternative (extraction-only writes, geocoding fires on the next tick) would let events sit in cache un-geocoded for up to 24h. With geocode-per-batch-window, every flush at N batches yields a fully-enriched slice — read consumers downstream see consistent state at every cache observation.
  - **How to apply:** Run the geocoding loop on the just-completed N-batch window (not the full accumulated array) before each intermediate flush. Final-flush geocoding still runs over any batches not yet geocoded. Confirm exact wiring in plan-phase. Re-confirm if research surfaces a constraint.

- **D-06:** **Lineage hash interaction: no code change needed in `groupLineageHash.ts`.**
  - **Why:** D-18 (Phase 27.4.4) already partitions which groups need extraction by hashing the prior cache. Incremental writes mean the lineage filter sees more "already done" entries on re-runs, which IS the resume property we want. No code change needed in `groupLineageHash.ts`.
  - **How to apply:** Don't touch `server/lib/groupLineageHash.ts`. If the planner identifies a real coupling concern, surface as a checker issue rather than silently editing.

- **D-07:** **Test gate: new vitest case asserting cross-function-boundary state preservation.**
  - **Why:** This is the contract test that locks in the "no-state-loss across function boundaries" invariant. Without it, future refactors could re-introduce the silent-data-loss regression.
  - **How to apply:** Add to `server/__tests__/lib/llmExtractionPipeline.test.ts` (or analogous file). Two consecutive partial runs (e.g. 5 batches then function-kill, then 5 more batches) must produce the same final state as one continuous 10-batch run. Use existing test patterns from Phase 27.4.4 Plan 02 (concurrency limiter test) as the analog.

### Change B — Vercel `waitUntil` Migration

- **D-08:** **Install `@vercel/functions` (currently absent).**
  - **Why:** `node_modules/@vercel/` only has `analytics` and `speed-insights` today. `waitUntil` lives in `@vercel/functions`.
  - **How to apply:** `npm install @vercel/functions` as a runtime dep (not devDep — it's invoked at request time). Pin to a major version per project convention. Verify `package.json` + `package-lock.json` updates land in the same commit as the call-site change.

- **D-09:** **Call-site change: replace `void (async () => {...})()` at `server/lib/llmExtractionPipeline.ts:203` with `waitUntil((async () => {...})())`.**
  - **Why:** This is the literal mechanism that makes Change A's incremental writes execute. The cron route currently does `await runRefreshExtraction(...)` and waits for the dispatch decision; the IIFE inside `runRefreshExtraction` is the part that fires-and-forgets the actual work. Migration: keep `runRefreshExtraction`'s sync-decision return, but inside the helper change `void (async () => {...})()` to `waitUntil((async () => {...})())`.
  - **How to apply:** Single-line semantics change. Returning a `dispatched: true` envelope quickly preserves the existing API shape; the background body now actually runs to completion (or to the maxDuration ceiling). The cron route's response shape stays the same: HTTP 200 in <500ms with `{ ok: true, dispatched: true, ... }`. Operator-side curl invocations don't need to change.

- **D-10:** **Local dev fallback: `@vercel/functions`' `waitUntil` no-ops when not running on Vercel.**
  - **Why:** Existing test mocks for the IIFE pattern continue to work without per-environment branches. We don't want a Vercel-vs-Express divergence in the test surface.
  - **How to apply:** Verify no-op behavior on Express/Vitest before claiming the API is unchanged. If `waitUntil` throws or behaves differently in Node-without-Vercel, planner adds a thin shim (e.g., `typeof waitUntil === 'function' ? waitUntil(p) : void p` with the function reference cached at module load). Treat the shim as a fallback, not the default.

### Anti-Patterns (Hard Blocks)

- **D-11:** **Don't write `LLMCachePayload` envelopes to `events:llm:v3`.** That regression already happened once (Phase 27.4.1, fixed in commit `a5c8846`). The terminal key holds `ConflictEventEntity[]`. Use `events:llm:v3:partial` for envelope shape. (Restated from D-04 as a hard block because reader code at multiple sites depends on this.)

- **D-12:** **Don't `await` the IIFE instead of using `waitUntil`.** `await` blocks the response, makes the cron route's HTTP 200 take 5+ minutes, and the curl/Vercel-cron-trigger client may time out before the response arrives. `waitUntil` returns the response immediately AND keeps the body running. This is the canonical Vercel pattern. (Verified: `b016a5c` did this and broke; reverted in `b4bf4a3`.)

- **D-13:** **Don't try to reach `allTiersGreen=true` in this phase.** That happens automatically after 1-2 cron ticks once the code lands. The success signal for 28.2.6 is "force-trigger of `/api/cron/refresh-events?force=true` followed by 4-min wait shows `events:llm:v3` non-empty AND `/api/health endpoints.llmEvents.status` flipped from `unknown` to `healthy`." The workflow run is downstream evidence, not a phase deliverable.

- **D-14:** **Don't refactor `groupLineageHash.ts` or `events:llm:v3:partial` semantics.** Both are working as designed; the partial-key writer + lineageHash pre-filter together provide the cross-tick resume semantics that make incremental writes safe. (Restated from D-06 for clarity.)
