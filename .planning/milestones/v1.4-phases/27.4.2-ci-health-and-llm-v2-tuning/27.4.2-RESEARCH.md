## Summary

Phase 27.4.2 is a sequenced two-wave phase. **Wave 1 (CI Health)** is mostly cosmetic and dependency hygiene: a single-line fixture fix unblocks 544 cascading test failures, `npm audit fix` (no `--force`) resolves all 8 known advisories cleanly, prettier sweeps 56 canonical files, lint sweeps 412 problems (mostly auto-fixable noise from `react-refresh/only-export-components` warnings). The `.husky/pre-commit` hook already runs `lint-staged` for prettier+eslint on staged files — the D-05 "guard" task is to verify the hook actually invokes both, not to invent new tooling. **Wave 2 (LLM v2 Quality Tuning)** has all observability already in place: `runEval()` returns per-distance counts, DevApiStatus already renders eval/provenance/DLQ blocks, and the 6-path resolver's tuning surfaces (POI keywords, 250km gate, WR-04 single-candidate auto-accept, SYSTEM_PROMPT_V2) are localized to two files (`server/lib/llmResolver.ts` + `server/lib/llmEventExtractor.v2.ts`). The only meaningful infrastructure gap is the v1 baseline capture (no `events:llm-eval-baseline:v1` key exists in code; the +5pp comparison must be a "pre-tuning resolver score → post-tuning resolver score" comparison, not "v1 LLM extractor → v2 LLM extractor"). Two minor planner-callouts: (1) `watchdogTimeoutCount` is set on the live progress singleton but NOT included in `buildSummary()`, so it's only visible mid-run via `/api/events/llm-status`; (2) the provider cascade order `['cerebras', 'groq']` is a function-local constant (line 203 of `server/adapters/llm-provider.ts`) that needs a small refactor to mirror the existing `setPipelineOverride` pattern in `server/config.ts` for D-07's hang-recurrence flip.

**Primary recommendation:** Decompose into ~7 plans across 2 waves. **Wave 1 (CI):** P1 fixture-factory single-line fix for `enabledPrecisions`; P2 `npm audit fix`; P3 prettier sweep (56 canonical files); P4 lint sweep (focus on auto-fixable + targeted high-signal manual fixes; do NOT try to green all 412 problems); P5 husky verification + optional augmentation. **Wave 2 (Tuning):** P6 baseline capture (resolver eval against current shipped state, persist to `events:llm-eval-baseline:v1`-equivalent key, add minimal `npm run eval:replay` script for inner-loop ergonomics, expose provider order override mirroring `setPipelineOverride`); P7 lever 1 (POI keywords + amenity audit) — micro-iteration cadence per D-12. Lever 2 (gates), lever 3 (prompt), lever 4 (blocks) become P8/P9/P10 only if D-13 doesn't close the wave early.

### Pattern 2: Provider Order Override (D-07 mirror of `setPipelineOverride`)

**What:** Mirror the existing in-memory override pattern from `server/config.ts:230-237` (`pipelineOverride` + `setPipelineOverride` + `getPipelineOverride`) to enable the wave operator to flip provider order without redeploy.
**When to use:** When `watchdogTimeoutCount ≥ 3` triggers D-07 ladder.
**Example shape:**

```typescript
// server/adapters/llm-provider.ts (additions, mirroring config.ts:230-242 pattern)

let providerOrderOverride: readonly Provider[] | null = null;

export function setProviderOrderOverride(order: readonly Provider[] | null): void {
  providerOrderOverride = order;
}

export function getProviderOrder(): readonly Provider[] {
  if (providerOrderOverride) return providerOrderOverride;
  // Optional: env var fallback (e.g., LLM_PROVIDER_ORDER='groq,cerebras')
  return ['cerebras', 'groq']; // current default
}

// Then in callLLM (line 203):
// const providers: Provider[] = ['cerebras', 'groq'];           ← BEFORE
// const providers: readonly Provider[] = getProviderOrder();    ← AFTER
```

The wave operator then flips by hitting a small POST endpoint OR a one-liner setter in a tsx script. Following the `setPipelineOverride` precedent, the planner can also add `GET /api/events/llm-provider-order` and `POST /api/events/llm-provider-order` (dev-only) so the flip is observable. **No Redis persistence needed** per D-07 ("wave-scoped, ops-managed") — module-level in-memory is sufficient.

### Anti-Patterns to Avoid

- **Soften production contract** (CONTEXT.md D-03 explicit reject) — making `filters.enabledPrecisions` optional via `?.length` masks future call-site bugs. The fix is the test fixture, not the production type.
- **`npm audit fix --force`** (CONTEXT.md D-04 explicit reject) — major-version bumps for transitive deps risk silent breakage; all 8 current advisories resolve cleanly without `--force`.
- **Big-bang tuning cadence** (CONTEXT.md D-12 explicit reject) — multi-lever batched commits lose attribution; bisection becomes O(n) on the lever count instead of O(1).
- **Pareto improvement requirement across 5km/20km/100km** (CONTEXT.md D-14 explicit reject) — too restrictive; gate on the 20km success metric only.
- **Try to green all 412 lint problems in one commit** — most are `react-refresh/only-export-components` warnings (238 of them) that require structural file splits. The mass sweep should be `lint -- --fix` (auto-fix only) + targeted high-signal manual fixes, not a wholesale 238-warning chase.
- **Schema-shape changes via "tuning" levers** — Cerebras qwen-3-235b will reject any new JSON Schema validation keywords (Pitfall 1 from AI-SPEC); Zod schema changes are out-of-scope per D-16 + 27.4 D-23.
- **Write to `events:llm:v2` from `/api/events/llm-replay/:groupKey`** — Pitfall 6 / dual-gate safety; replay is read-only vs the cache.

## Common Pitfalls

### Pitfall 1: Adding only `enabledPrecisions` and discovering more missing fields after the fact

**What goes wrong:** The test fixture is missing 26 fields total (not just `enabledPrecisions`). If a test ever accesses one of those (e.g., `filters.enabledWaterTypes`, `filters.stressMin`), it'll crash with the same `Cannot read properties of undefined` error pattern.
**Why it happens:** `tsconfig.app.json` excludes `src/__tests__/` from typecheck (verified at `tsconfig.app.json:36`), so the missing fields don't surface as TS errors despite the `: FilterState` return type annotation.
**How to avoid:** After landing the single-line `enabledPrecisions` fix, run `npx vitest run src/__tests__/filters.test.ts` and confirm 0 failures. **Do NOT proactively backfill the other 25 fields** — that turns a 1-line cosmetic fix into a 25-line behavioral diff and risks accidentally enabling code paths the existing tests didn't intend to exercise. Backfill only if a NEW test (Wave 2, P7's POI keyword regression) actually needs another field.
**Warning signs:** Test failures with the same `Cannot read properties of undefined` shape but a different field name (`enabledWaterTypes`, `stressMin`, etc.).

### Pitfall 2: The v1 baseline doesn't exist — runEval is V2-pipeline-gated

**What goes wrong:** The CONTEXT.md success criterion says "tuning iteration beats v1 eval score by ≥5pp at 20km", but `runEval()` is invoked **only** on the v2 branch (`server/routes/events.ts:1018`). There is NO `events:llm-eval-baseline:v1` Redis key written by the codebase (verified by grep — only `events:llm-eval-baseline:v2` exists at `server/lib/llmEvalHarness.ts:45`).
**Why it happens:** Phase 27.4 wired runEval into the v2 fire-and-forget block only; the v1 path was the "rollback" surface, not a comparator.
**How to avoid:** **The +5pp baseline is the resolver-as-shipped score, not the LLM v1 extractor's score.** `runEval()` calls `resolveLocation(ev.hierarchy, ...)` which dispatches through the SAME 6-path resolver regardless of which extractor produced the hierarchy. So the baseline = "current resolver code's score against the 50 ground-truth events" captured BEFORE any P7+ tuning lever changes. P6 (baseline capture) is the right place to (1) run the harness against current `main` HEAD, (2) persist the result to a `:v1`-named key for naming clarity, and (3) lock down the comparator.
**Warning signs:** A planner asks "where's the v1 baseline?" — the answer is "we capture it in P6 against the current resolver state".

### Pitfall 3: `watchdogTimeoutCount` is set live but NOT persisted in `buildSummary()`

**What goes wrong:** D-06 trigger ("`watchdogTimeoutCount ≥ 3` in a single pipeline run") requires the wave operator to read this field after a run completes. It's set on `llmProgress.watchdogTimeoutCount` during the run (verified at `server/lib/llmEventExtractor.v2.ts:472` and `v1.ts:249`), but `buildSummary()` (`server/lib/llmProgress.ts:187-204`) does NOT include it. Once `stage` returns to `idle`, `/api/events/llm-status` returns `lastRun` from `events:llm-summary:v2` (Redis), and the field is gone.
**Why it happens:** Phase 27.4.1 D-06 added the field to the live singleton + `INITIAL_PROGRESS` reset but never extended `buildSummary()` to persist it across the idle transition.
**How to avoid:** Either (a) the wave operator polls `/api/events/llm-status` mid-run while `stage === 'llm-processing'` and captures the field before the run completes, OR (b) P6 includes a tiny patch to extend `buildSummary()` and `LLMRunSummary` interface (`server/lib/llmProgress.ts:102-118` and `src/hooks/useLLMStatusPolling.ts:7-23`) to include `watchdogTimeoutCount`. Option (b) is cleaner and a one-field addition; recommend it as part of P6.
**Warning signs:** D-06 ladder triggers but the operator can't tell after the fact what `watchdogTimeoutCount` reached.

### Pitfall 4: There is no `/api/events?force=true` — the parameter is `?backfill=true`

**What goes wrong:** AI-SPEC and CONTEXT both say "trigger /api/events?force on the tuning branch". The actual query schema (`server/routes/events.ts:58-63`) only supports `?backfill=true`. Hitting `?force=true` is silently ignored (Zod transforms unknown enum to `false`).
**Why it happens:** Naming drift between docs and code; `?backfill=true` was added in Phase 26 for the GDELT history backfill, NOT for forcing an LLM re-run.
**How to avoid:** To force a fresh LLM run, the wave operator must:

1. `redis-cli del events:llm-process-ts` (clear the 15-min cooldown)
2. `redis-cli del events:llm:v2` (clear the cache so the route doesn't serve cached data and skip extraction)
3. `curl http://localhost:3001/api/events`

The 27.4-HANDOFF.md "Option B" already documents this exact pattern via curl + Upstash REST. The runbook the wave operator writes during P6 should include this as the canonical "force fresh run" recipe. **Do NOT spec a new `?force=true` parameter** — it's out-of-scope and the existing pattern works.
**Warning signs:** Wave operator hits `?force=true`, doesn't get a fresh run, blames cooldown logic.

### Pitfall 5: `npm run lint` reports 412 problems — D-02 says "zero warnings" — there are 238 `react-refresh/only-export-components` warnings that require structural file splits

**What goes wrong:** D-02 requires `npm run lint` to report zero warnings as a CI-green precondition. The actual current state is **412 problems (63 errors, 349 warnings)** broken down as:

- 238 `react-refresh/only-export-components` (warning) — files exporting both components AND constants/functions; React Fast Refresh requires they be in separate files
- 102 `react-hooks/exhaustive-deps` (warning) — useEffect/useMemo/useCallback dependency-array warnings
- 48 `@typescript-eslint/no-explicit-any` (error) — `any` usage in non-test files
- 10 `@typescript-eslint/no-unused-vars` (error)
- 5 `prefer-const` (error)

CONTEXT.md said "~20 lint warnings" — actual is **412**. This is a major scope discrepancy.
**Why it happens:** Phase 27.4 wrote a lot of new code without running `npm run lint` continuously; the warnings accumulated.
**How to avoid:** D-05 should be interpreted as "auto-fixable lint errors fixed; manual fixes for high-signal cases; suppress (with comment) or split-file the rest". Trying to green all 238 `react-refresh/only-export-components` warnings would require touching ~20 component files and creating new co-located `*.constants.ts` files — a significant Wave 1 refactor, not a "mass sweep". **Recommend the planner explicitly negotiates the D-02 scope before P4 lands**: either (a) accept that "zero warnings" applies to errors only (treating warnings as advisory), OR (b) carve out `react-refresh/only-export-components` as a known-excluded rule via inline `// eslint-disable-next-line` comments or eslint config rule downgrade, OR (c) split this into a follow-up phase. CONTEXT.md treats this as a single sweep — actual scope demands negotiation.
**Warning signs:** Wave 1 P4 plan estimates 1 day and ships in a week; or Wave 1 P4 lands with `eslint-disable` blanket comments at the top of files.

### Pitfall 6: Prettier drift count is 56 canonical files (not ~25), heavily concentrated in `server/lib/` LLM pipeline files and `.planning/phases/` markdown

**What goes wrong:** CONTEXT.md said "~25 prettier format-drift files" — actual is **56 canonical files** (excluding `.claude/worktrees/` which CI doesn't see). Distribution: 31 `.planning/`, 19 `server/`, 3 `src/`, 2 `docs/`, 1 root. By extension: 34 `.md`, 20 `.ts`, 2 `.tsx`.

The 19 server files are concentrated in `server/lib/llm*.ts` and `server/__tests__/lib/llm*.test.ts` — exactly the files Wave 2 tuning will edit. **A prettier sweep that lands BEFORE Wave 2 will create merge-conflict risk against tuning commits.**
**Why it happens:** Phase 27.4 wrote a lot of code without continuous prettier; the drift accumulated, and is concentrated in the same files Wave 2 needs to edit.
**How to avoid:** Run prettier sweep early in Wave 1 (commit the cosmetic diff in isolation per D-05). Wave 2 commits then start from a prettier-clean base. Optional: include a `.husky/pre-commit` enforcement (already exists) so Wave 2 commits stay clean.
**Warning signs:** Wave 2 P7 plan attempts to edit `server/lib/llmResolver.ts` and gets a merge conflict against a Wave 1 prettier commit on the same file.

### Pitfall 7: No `npm run eval:replay` script exists — runEval only fires on full pipeline runs

**What goes wrong:** D-12 ("micro-iteration cadence: each lever change runs ground-truth replay (~1min)") implies an inner-loop CLI ergonomic that doesn't exist. Searching `package.json` + `scripts/` confirms there's NO eval-replay script. The only way to get an eval score today is to trigger a full `/api/events` LLM run (which costs ~150K-300K tokens, takes 20-45 min, and goes through the LLM extractor — not just the resolver).
**Why it happens:** Phase 27.4 didn't anticipate iteration-loop ergonomics; runEval was wired into the post-geocoding hook only.
**How to avoid:** P6 (baseline capture) should include a tiny `scripts/eval-replay.ts` (mirroring `scripts/refresh-water-facilities.ts` pattern) that imports + invokes `runEval()` directly + prints the result, plus a `package.json` script entry:

```json

```

Then the inner-loop is `npm run eval:replay` (~50 events × 1 req/s Nominatim throttle = ~50 sec on cold cache, instant on warm cache). This is the "1-2 line wrapper" CONTEXT D-17 implicitly assumes; the planner should explicitly include it in P6.
**Warning signs:** P7+ plans estimate "run eval replay" as if it's an existing command; first plan to try it discovers it has to run a full pipeline (which would burn the token budget).

### Pitfall 8: Vitest sees test files in `.claude/worktrees/` — local runs report 577 failures (CI sees ~544)

**What goes wrong:** `npx vitest run` from a workspace with stale agent worktrees in `.claude/worktrees/` picks up duplicate copies of every `.test.ts` file. Local count: **577 failures across 66 test files** (across 8 stale worktrees × 1 main copy). CI on a clean checkout sees **only the canonical ~32-544** baseline.
**Why it happens:** `vite.config.ts` `test.exclude` is `['**/node_modules/**', '**/dist/**', 'scripts/load-test.spec.ts']` — `.claude/` is NOT excluded. The `.claude/` directory is the agent harness scratch space; it's untracked but vitest doesn't know that.
**How to avoid:** When debugging failures locally, either (a) `git worktree list | grep .claude/worktrees` and remove stale ones, OR (b) add `.claude/**` to `vite.config.ts` `test.exclude` (a 1-line cosmetic improvement that doesn't affect CI). The planner doesn't need to worry about this for correctness — CI will run from a clean checkout — but local UAT may be confusing.
**Warning signs:** Plan summary reports "fixed N tests" but CI shows a different number.

## Common Pitfalls (LLM-pipeline specific, retained from CLAUDE.md for Wave 2 planners)

These are quoted directly from CLAUDE.md "LLM Enrichment v2" + "V2 Extractor Watchdog" sections — Wave 2 tuning MUST respect them:

1. **Cerebras qwen rejects `maxLength` on JSON Schema string fields.** Any future tuning lever that adds a string-length constraint on an LLM field MUST add it to Zod, NEVER to the wire JSON Schema. (Commit `8d325ee`.)
2. **`BATCH_SIZE = 2` for v2 (down from v1's `8`).** Don't widen — narrower batches isolate hung calls.
3. **`events:llm:v2` is `ConflictEventEntity[]`; `events:llm:v2:partial` is `LLMCachePayload` envelope.** Non-overlapping writers/readers. Defense-in-depth: `coerceCachedEvents()` at every read site.
4. **Generation-counter / late-resolve guard inside `withBatchWatchdog`.** Don't simplify the watchdog without preserving this guard.
5. **Dev-only `/api/events/llm-replay/:groupKey` needs dual-gate.** Both `NODE_ENV !== 'production'` (mount-time) AND in-handler 404 check.
6. **`runEval()` is resolver-only by design (A6 / Pitfall 8).** `EVAL_HARNESS_EXTRACT=true` env flag is intentionally NOT wired.
7. **Cerebras model: `qwen-3-235b-a22b-instruct-2507` is the only open model on free tier.** Do not "fix" `CEREBRAS_MODEL` constant back to `gpt-oss-120b`.
8. **Nominatim 1 req/s throttle is module-level and load-bearing** (`lastNominatimCallMs` in `llmResolver.ts`). Throttle fires AFTER cache-miss confirmed (WR-01).
9. **Synthetic skip entries in `callHistory`.** Don't remove `skipReason` entries as "useless" — they're the diagnostic for empty-result runs.
10. **`response_format.json_schema.strict: true` plus `additionalProperties: false` at every nested object.** Required for D-05 invariant ("LLM never emits coordinates"). Don't relax either.
