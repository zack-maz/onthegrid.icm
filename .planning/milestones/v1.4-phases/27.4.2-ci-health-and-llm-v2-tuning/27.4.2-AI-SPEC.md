## 1. System Classification

**System Type:** Information Extraction (Hybrid — structured event enrichment + custom 6-path location resolver as the primary downstream consumer of extracted hierarchies)

**Description:**
The v2 LLM enrichment pipeline turns raw GDELT v2 CSV rows into typed `EnrichedEventV2` objects with a 5-type ontology (`airstrike` | `on_ground` | `explosion` | `targeted` | `other`), structured location hierarchies (`country` / `admin1` / `city` / `neighborhood` / `landmark` / `confidence`), and a precision-tagged coordinate produced by a custom 6-path resolver (`own-site-snapshot`, `poi-amenity-nominatim`, `nominatim-direct`, `nominatim-verified-2pass`, `gdelt-actiongeo-fallback`, `bellingcat-coord-passthrough`). The system runs as a fire-and-forget background task triggered on `/api/events` cache miss with a 15-minute cooldown, batches 2 event groups per Cerebras call (qwen-3-235b-a22b-instruct-2507, 1M TPD free tier) with Groq fallback (openai/gpt-oss-120b, 200K TPD free tier), and serves enriched events from `events:llm:v2` Redis cache to a real-time map at `iran-conflict-monitor.vercel.app`. "Good" output is a 5-type-classified event whose resolver-produced lat/lng falls within 20km of the ground-truth coordinate ≥80% of the time (Phase 27.4 D-25 deploy gate), with `gdelt-actiongeo-fallback` provenance below 25% of total resolves, and zero watchdog timeouts on the 184-batch run. The map degrades gracefully to raw GDELT when the LLM is unavailable, so failure mode (1) is silent corruption, not visible downtime.

**Users:** Single operator (the project owner) running real-time conflict-monitoring sessions during the US-Iran conflict (started 2026-02-28). The map is consumed visually — a misplaced event marker creates an immediate, observable signal mismatch ("why is this airstrike in the Persian Gulf?"), so wrong answers produce false analytical conclusions, not silent harm.

**Critical Failure Modes:**

1. **Confident wrong coordinates** — resolver returns a precise lat/lng for a region that is hundreds of kilometers from the actual event (e.g., "Beirut, Oregon" returned for "Beirut, Lebanon" via Branch 4 single-candidate auto-accept). Worse than a missed extraction because it appears authoritative on the map.
2. **Map goes blank** — v2 cache empty AND v1 fallback bridge fails AND raw GDELT degrade path breaks. The Phase 27.4.1 two-key cache discipline + reader defense-in-depth (`coerceCachedEvents`) was the response to this exact failure mode reaching production once already.
3. **184-batch run never completes** — Cerebras hangs at the tail (one or more batches exceeds 90s watchdog) and `watchdogTimeoutCount > 0`, blocking the eval baseline capture that gates the +5pp comparison. Phase 27.4.1 `withBatchWatchdog` is the mitigation; D-06/D-07 ladder is the operational fallback.
4. **Schema regression poisons the cache** — a tuning lever inadvertently changes the response shape (extra field, missing field, wrong enum) and Zod fails on every batch, DLQ-routing the entire run while v1 cache silently keeps serving stale data. The Pitfall 1 v1→v2 bridge masks the failure for hours unless DevApiStatus eval/DLQ blocks are watched.
5. **Hallucinated landmarks / fabricated coordinates** — the prompt explicitly forbids the LLM from emitting coordinates (`.strict()` Zod schema rejects them), but a tuning lever that loosens the system prompt could re-open this failure if the LLM emits a plausible-but-fictional landmark name that Nominatim then "matches" via Branch 3 unconstrained search.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** OSINT (open-source intelligence) on active conflict events, with a cartographic intelligence consumption surface. Specifically the _single-operator personal analytical tool_ slice — NOT the _intelligence-agency / state-targeting_ slice (which would be Critical-stakes), and NOT the _broadcast newsroom_ slice (which would carry editorial-liability stakes). The product sits in the same OSINT tradition as Bellingcat, ACLED, the Institute for the Study of War's interactive maps, and Liveuamap — public-source aggregation with verifiable provenance, geographic placement, and event-type taxonomy. The defining stance is "numbers over narratives" — counts, coordinates, and source links over editorialized commentary.

**User Population:** Single operator (the project owner) running real-time conflict-monitoring sessions during the US-Iran conflict (started 2026-02-28). The analytical audience is the operator themselves — there is no third-party report, no client deliverable, no broadcast. Consumption surface is a 2.5D map at `iran-conflict-monitor.vercel.app` (visual, real-time). Because the surface is visual, interpretive errors are immediately observable — a mismarker on the map produces a "huh?" reaction, not a downstream silent decision. The operator can click through to the GDELT source URL on any event marker and read the underlying article, so there is always an inspectability path for any single output.

**Stakes Level:** **Medium**. Justification:

- This is NOT a high-stakes targeting / kinetic-decision system (Critical) — no military, law-enforcement, or operational decision flows from this output. There is no human-in-the-loop downstream actor whose action depends on system correctness.
- This is NOT a low-stakes content-recommendation / entertainment system (Low) — wrong outputs do degrade the operator's analytical mental model of the conflict, and persistent systematic errors (e.g., "every Beirut airstrike resolves to Beirut, Wisconsin") would erode trust in the entire dashboard, leading to abandonment.
- It is a **Medium-stakes analytical tool**: the operator's pattern-recognition is informed by accurate event placement, but no military or operational decision flows from this output. Wrong outputs degrade analytical confidence; they do not cause physical harm. The "Map goes blank" failure mode (worse than wrong) is the tightest constraint on the system — graceful degradation to raw GDELT is the project's Medium-stakes calibration in code.

**Output Consequence:** An event marker on a real-time map that the operator inspects to build a mental model of the conflict's geography over time. False placements degrade the operator's mental model. Persistent systematic errors would erode trust in the entire dashboard. Single-event errors are recoverable — the operator clicks the GDELT source link, reads the article, mentally corrects, and (in a future phase) the corrected case becomes a candidate for ground-truth corpus expansion. The strongest negative consequence is **dashboard abandonment**, not analytical harm. The strongest constraint on the system, expressed in code, is the v1→v2 graceful-degradation bridge: the map must never go blank, even when the LLM is fully unavailable.

### Known Failure Modes in This Domain

These are domain-specific OSINT failure modes — not generic "LLM hallucinates" patterns. Each has been observed in real OSINT pipelines and is mitigated (or NOT YET mitigated) somewhere in the shipped stack.

1. **Place-name homography across theaters** — the "Beirut, Oregon" / "Damascus, Virginia" failure. Common in OSINT because place names recur globally; a 2024 ACLED methodology note explicitly cites this as the dominant geocoding error class. The shipped mitigation is the 22-country allowlist + ME viewbox in `forwardGeocodeConstrained`; the current Phase 27.4.2 lever 2 (250km gate, WR-04 single-candidate auto-accept) targets the residual rate inside the constrained set.
2. **Conflation of military exercises with combat events** — GDELT CAMEO codes don't reliably distinguish "joint exercise" from "live engagement"; the LLM should read the source article to disambiguate. A pre-2026 example: the routine "Eager Lion" Jordan-US exercise routinely triggered CAMEO 19x codes that look identical to combat. Mitigation: the prompt should instruct the LLM to override CAMEO on exercise-language detection. (Current `SYSTEM_PROMPT_V2` does not explicitly cover this — backlog candidate.)
3. **Source-tier conflation** — treating Iranian state media (Tasnim, Fars, IRNA), Israeli outlets (Times of Israel, Ynet, Haaretz), and Western wire services (Reuters, AP, AFP) as equally authoritative. A Tasnim claim of Israeli casualties and a Reuters wire of the same event are NOT equivalent epistemic units. Mitigation: tier-tagged news context (T1/T2/T3) feeds the prompt; lever 4 NEWS-block tuning may surface tier-weighting changes if the wave reaches it.
4. **Date-drift from natural-language temporal anchors** — source articles say "yesterday" / "this morning" / "earlier today"; without source-date primacy, the LLM can mis-anchor these to its own training-time "today". Mitigation: GDELT row date is server-supplied to the prompt; v2 prompt instructs source-date primacy. (Not currently a known live failure, but a known risk class.)
5. **Missing-modifier failures** — "near Damascus" vs "in Damascus" carries a 10-50km uncertainty; the precision tag must honestly reflect this. Practitioner norm: "near" → `city` precision, NOT `neighborhood`. (Current prompt covers this; lever 3 may sharpen.)
6. **Casualty invention from social-media echo** — popular OSINT failure where a "fatalities" field gets inflated from social-media reposts that compound the same death count across multiple "sources". The first wire reports "5 killed", a second wire reports "5 killed (per @firstwire)", and a naive aggregator counts 10. Mitigation: GDELT NumMentions is observability, not a multiplier; the LLM is instructed to use only the source-article-stated count.
7. **Bellingcat-coord misuse** — Bellingcat OSINT coords (Branch 6 passthrough) are gold-standard for verified events but can be wrong if the article cites Bellingcat in passing without an actual coord (a research piece referencing Bellingcat's methodology, not a Bellingcat-verified event). Mitigation: regex-extract only well-formed coord patterns from titles; passthrough requires actual `lat,lng` payload.
8. **Confident-wrong over silent-error** — across all OSINT pipelines, the worst class of error is one that LOOKS authoritative on the map. A "no answer / cluster of uncertainty" is recoverable; a precise marker on the wrong city for a real event is a trust-killer. The Phase 27.4.2 fallback-rate ceiling (<25%) is partially a defense against this — pushing more events into Branch 5 (which produces a country-centroid, visibly imprecise) is _better_ than pushing more events into a confidently-wrong precise placement.

### Regulatory / Compliance Context

The project sits in a **legally-thin OSINT zone**. There are no mandatory regulatory frameworks that apply:

- **No PII / surveillance regulatory exposure (GDPR, CCPA):** the system operates exclusively on already-public news article metadata via GDELT and curated public news feeds (BBC, Al Jazeera, Tehran Times, Times of Israel, Middle East Eye). No personal data is processed; no individual is profiled or tracked.
- **No export-control / ITAR exposure:** no targeting data, no military computations, no fire-control or kinetic decision support. Output is geographic event placement on a public map — same content shape as any conflict-tracking news outlet (Liveuamap, ISW interactive map, ACLED dashboards) that publishes globally without licensing.
- **No content-moderation regulatory framework (DSA, etc.):** the system is single-operator, not a published service with users. No third-party content is hosted; only links to source articles on their original publishers.
- **No medical / financial / legal regulatory framework:** the system is not in any regulated-vertical adjacent space.

**Best-practice norms (not regulation, but they inform the design):**

- **Source-attribution norm:** every event marker links to its GDELT source URL — the OSINT community norm is verifiable provenance over editorial polish. Bellingcat's "show your sources" methodology is the reference standard.
- **Inspectability norm:** the operator should treat outputs as "machine-aided notetaking", not as reportable analysis. Errors should be expected and inspectable (click-through to source).
- **Fallback-honesty norm:** when geocoding can't determine a precise location, the system shows a country-centroid (Branch 5) rather than guessing — an OSINT analyst would prefer a visibly-imprecise placement to a confidently-wrong one. This is the design philosophy behind keeping `gdelt-actiongeo-fallback` available even in the v2 pipeline.

**Stated explicitly:** No mandatory regulatory framework applies. Best-practice norms (verifiable provenance, error inspectability, fallback honesty) inform the design but are not legal requirements.

## 2. Framework Decision

**Selected Framework:** Direct OpenAI SDK with custom orchestration (Cerebras + Groq via baseURL swap, Zod v3 schema validation, hand-rolled reliability primitives, custom 6-path Nominatim resolver, custom resolver-only eval harness, Upstash Redis for cache + state)

**Version:**

- `openai` ^6.34.0 (TypeScript SDK; both Cerebras and Groq endpoints are OpenAI-chat-compatible)
- `zod` ^3.25.76 (response validation, JSON Schema generation via `zod-to-json-schema`)
- `@upstash/redis` ^1.37.0 (REST-based, Vercel-serverless-friendly)
- `@upstash/ratelimit` ^2.0.8 (token-budget enforcement)
- Cerebras model: `qwen-3-235b-a22b-instruct-2507` (open on Cerebras free tier — `gpt-oss-120b` is paid-tier-gated and was retired here)
- Groq model: `openai/gpt-oss-120b` (200K TPD free tier)
- Nominatim public endpoint with custom `forwardGeocodeConstrained` wrapper (1 req/s spacer)

TypeScript pinned to `~5.9.3` per project convention; Node `>=20` engine.

**Rationale:**

The framework was effectively chosen and locked across Phases 27.4 (the v2 pipeline introduction) and 27.4.1 (the watchdog). Phase 27.4.2 D-16 explicitly forbids new dependencies, so this section documents the locked stack rather than re-selecting. The case for the locked stack:

1. **Provider portability comes for free.** Both Cerebras (`api.cerebras.ai/v1`) and Groq (`api.groq.com/openai/v1`) speak OpenAI-chat-completions with strict JSON-Schema mode. A baseURL swap on the same `OpenAI({ baseURL, apiKey })` constructor gives genuine fallback without dragging in an abstraction layer that would obscure the simple "batch JSON-Schema extraction" shape (single user message → structured response). The Phase 27.4.1 D-07 hang-recurrence flip target is a single env-driven order constant — no framework helps with that.
2. **Location resolution is geo-domain-specific.** The 6-path resolver (`server/lib/llmResolver.ts`) encodes Middle East theater knowledge no off-the-shelf framework carries: a 22-country allowlist (`countrycodes`), a Greater-ME viewbox, POI keyword inference (~22 entries — drone bases, refineries, naval ports), GDELT actiongeo fallback, Bellingcat coord passthrough, and a single-candidate auto-accept that is itself a tuning lever (D-11 lever 2). Phase 27.4.2 explicitly tunes this resolver — wrapping it in a generic chain abstraction would erase the lever surface.
3. **The failure shape is unusual.** Cerebras hangs at the tail of a 184-batch run (the 27.4.1 root cause), free-tier daily caps require token-budget enforcement at the soft 0.8 / hard 0.95 boundary, and the circuit breaker uses a sliding 10-call window with 30% error threshold — none of these match the off-the-shelf retry/breaker shapes ("p95 latency", "5xx-only retries"). Hand-rolled `llmCircuitBreaker.ts` / `llmTokenBudget.ts` / `llmDLQ.ts` / `llmExtractorWatchdog.ts` fit the actual failure topology.
4. **Zod-first matches the project stance.** TypeScript strict mode is a project convention. Zod's `enrichedEventAny` discriminated union encodes the v1+v2 dual-schema contract cleanly, and the same schema generates the wire-format JSON Schema via `zod-to-json-schema` — single source of truth for both runtime validation and the LLM contract.
5. **The eval harness fits the use case.** `runEval()` is resolver-only — it replays 50 curated ground-truth hierarchies through `resolveLocation()` without re-invoking the LLM extractor. This is per-iteration cheap (~1min Nominatim-spaced), deterministic (no LLM nondeterminism), and exactly the right granularity for the inner tuning loop. Off-the-shelf eval libraries (Ragas, DeepEval, Promptfoo) target end-to-end RAG accuracy or prompt-comparison — neither shape matches resolver-only ground-truth coordinate replay.

**Alternatives Considered:**

| Framework                             | Ruled Out Because                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| LangChain (TypeScript)                | Closest swap-in had this been greenfield. Could host the same JSON-Schema extraction with `withStructuredOutput`, but the abstraction would obscure the batch loop, and re-implementing the 6-path resolver + watchdog/breaker/budget/DLQ inside LangChain primitives is a multi-phase rewrite for zero lift on the 20km eval gate. Adds a non-trivial dep (~50 transitive packages).                                                                                                      |
| LlamaIndex (TypeScript)               | RAG-first; retrieval is not the bottleneck. We do not embed/chunk/index — we extract structured data from CSV rows using prompt-supplied news + temporal context. Forcing an "Index → Query Engine" abstraction onto a single-shot extractor is mismatched.                                                                                                                                                                                                                                |
| DSPy                                  | Programmatic prompt optimization is interesting given the lever-3 `SYSTEM_PROMPT_V2` work, but DSPy forces a "signature-first" rewrite that breaks the locked Zod v2 + JSON Schema wire contract (D-23, 27.4). The +5pp eval-gate target is reachable via direct prompt tuning + threshold edits without DSPy's compiler. | Vercel AI SDK                         | Server-side streaming chat focus. ### Entry Point Pattern

Every model invocation in this codebase goes through `callLLM(messages, jsonSchema, opts)` in `server/adapters/llm-provider.ts`. This is the load-bearing pattern: tuning levers that change batch shape, rerank prompts, or system prompts MUST keep the call going through this one function. Never instantiate `new OpenAI({...})` outside that file.

```typescript
// server/adapters/llm-provider.ts (excerpt — the canonical cascade)

export async function callLLM(
  messages: OpenAI.Chat.ChatCompletionMessageParam[],
  jsonSchema: Record<string, unknown>,
  opts: { batchSize?: number } = {},
): Promise<string | null> {
  const batchSize = opts.batchSize ?? 1;
  const providers: Provider[] = ['cerebras', 'groq']; // D-07 flip target

  for (const provider of providers) {
    // Gate 1: circuit breaker — sliding 10-call window, 30% err rate, 5min pause
    if (!isAvailable(provider)) {
      recordSkippedAttempt(provider, batchSize, 'breaker'); // synthetic ⊘ entry
      continue;
    }
    // Gate 2: token budget — soft 0.8, hard 0.95 (per-day, per-provider)
    const used = await getDailyTokens(provider);
    if (budgetState(provider, used) === 'hard') {
      recordSkippedAttempt(provider, batchSize, 'hard_cap'); // synthetic ⊘ entry
      continue;
    }

    for (let attempt = 0; attempt < RETRY_ATTEMPTS; attempt++) {
      // 2 attempts
      try {
        const result = await tryProviderOnce(provider, messages, jsonSchema, batchSize);
        if (result.content) return result.content;
        break; // null → don't retry same provider
      } catch {
        if (attempt < RETRY_ATTEMPTS - 1) {
          await sleepWithJitter(BACKOFF_MS[attempt] ?? 1000); // 1s / 4s + ±250ms jitter
        }
      }
    }
  }
  return null; // Both providers exhausted → caller falls to raw GDELT (D-29)
}
```

### Common Pitfalls

OpenAI-SDK-and-Cerebras/Groq-specific gotchas this team has hit. Each item ends with the file/commit where the fix lives so a future executor can verify the constraint hasn't drifted.

1. **Cerebras qwen rejects `maxLength` on JSON Schema string fields.** Error: `wrong_api_format: Invalid fields for schema with types ['string']: {'maxLength'}`. Cerebras's structured-output engine does not implement the full JSON Schema validation keyword set that OpenAI/Groq do. Removed from `EVENT_EXTRACTION_SCHEMA_V2.properties.reasoning` (commit `8d325ee`); Zod still enforces `.transform((s) => s.length > 200 ? s.slice(0,197) + '…' : s)` on parse. **Why a pitfall:** any future tuning lever that adds a string-length constraint on an LLM field MUST add it to Zod, NEVER to the wire JSON Schema.
2. **`BATCH_SIZE = 2` for v2 (down from v1's `8`).** v2 enrichment blocks (NEWS + BELLINGCAT + TEMPORAL) consume 3-4× more prompt tokens per group than v1's bare CSV row. Wider batches stress provider attention budget and compound timeout risk — a single hung 8-event batch blocks 8 events; a hung 2-event batch blocks 2. **Why a pitfall:** a planner who notices "lots of small batches, let's widen" without measuring the timeout-rate impact will rediscover the 27.4.1 hang root cause.
3. **`events:llm:v2` is a `ConflictEventEntity[]`; `events:llm:v2:partial` is an `LLMCachePayload` envelope.** These are non-overlapping writers and readers. The original Plan 03 wrote the envelope to the terminal key, which crashed every consumer (`events.map is not a function`). Phase 27.4.1 commit `a5c8846` split the writes; commit `e26ceca` added `coerceCachedEvents()` defense-in-depth at every read site (search `events.ts` for `toEntityArray`). **Why a pitfall:** any tuning lever that touches `writePartialCache()` or the route's read path must keep the two keys non-overlapping. The reader's `coerceCachedEvents` will demote a regression to "serve empty + Pitfall 1 bridge takes over" instead of HTTP 500 — but that's a defense-in-depth, not a license to write envelopes to the terminal key.
4. **Generation-counter / late-resolve guard inside `withBatchWatchdog`.** A timed-out Cerebras call that eventually resolves 10+ minutes later cannot clobber `events:llm:v2:partial` or invoke `onTimeout` a second time. The `timedOut` closure flag in `llmExtractorWatchdog.ts` short-circuits the late handler. **Why a pitfall:** a tuning lever that "improves" the watchdog by simplifying it must preserve this guard; without it, a late resolve overwrites the cache with stale data after the run has already moved on.
5. **Dev-only `/api/events/llm-replay/:groupKey` needs dual-gate.** Pitfall 6 — defense-in-depth: registered only when `NODE_ENV !== 'production'` AND in-handler 404 check. The endpoint re-extracts a single group with the current prompt WITHOUT writing to `events:llm:v2`. **Why a pitfall:** a planner who removes one of the two gates trusting the other is "enough" loses the second line of defense. Spot-check prompts in dev only.
6. **`runEval()` is resolver-only by design (A6 / Pitfall 8).** Wrapping it inside the LLM pipeline doubles daily token spend without lift — the resolver is the dominant accuracy lever, and the LLM's contribution is fixed by ground-truth hierarchies. The optional `EVAL_HARNESS_EXTRACT=true` env flag is intentionally NOT wired. **Why a pitfall:** a tuning iteration that "wants more signal" by re-extracting will burn 4M+ tokens/day on Cerebras and trip the hard cap mid-run.
7. **Cerebras model: `qwen-3-235b-a22b-instruct-2507` is the only open model on free tier.** `gpt-oss-120b` was the original Cerebras pick; access was revoked when Cerebras gated it to paid tiers (commit `191708f`). Calls return `model_not_found`. **Why a pitfall:** a planner who reads "gpt-oss-120b" in old docs and "fixes" the constant will break Cerebras entirely. The constant is `CEREBRAS_MODEL` in `server/adapters/llm-provider.ts:17`; only flip back if Cerebras tier upgrade lands (out of scope for 27.4.2 per CONTEXT).
8. **Nominatim 1 req/s throttle is module-level and load-bearing.** `lastNominatimCallMs` in `llmResolver.ts` spaces every call — but only AFTER cache-miss is confirmed (WR-01 fix). A bug that throttled before the cache check would let an uncached call bypass the rate limit when a cache-hit reset the timer. **Why a pitfall:** Nominatim soft-bans IPs that exceed 1 req/s. A tuning lever that adds a new resolver path must respect the same throttle; if it doesn't go through `forwardGeocodeConstrained()`, add `await throttleNominatim()` before the network call.
9. **Synthetic skip entries in `callHistory`.** When a provider is bypassed without network activity (breaker paused, hard cap reached, no API key) the cascade appends a `skipReason: 'breaker' | 'hard_cap' | 'no_client'` entry. Without this, `completedBatches=N, enrichedCount=0` runs leave an empty call history — undiagnosable on DevApiStatus. **Why a pitfall:** a "cleanup" PR that removes "useless" zero-token entries deletes the only diagnostic for empty-result runs.
10. **`response_format.json_schema.strict: true` plus `additionalProperties: false` at every nested object.** Both are required to enforce the D-05 invariant ("LLM never emits coordinates"). Drop strict, or omit `additionalProperties: false` on `location`/`casualties`, and the LLM can leak `lat`/`lng`/`coordinates` keys through the wire gate; Zod's `.strict()` would still catch it on parse but the failure mode shifts from "structured rejection at Cerebras" to "every batch DLQs". **Why a pitfall:** a JSON-Schema cleanup PR ("we don't need this on every sub-object") would silently weaken the invariant.

### Core Pattern

```typescript

for (let i = 0; i < groups.length; i += BATCH_SIZE) {
  const batch = groups.slice(i, i + BATCH_SIZE)
  const batchIndex = Math.floor(i / BATCH_SIZE)

  // 2. Build prompt context per group — reads news:gdelt + events:llm:v2 (TEMPORAL).
  //    Three enrichment blocks: NEWS (T1/T2/T3 tier-tagged), BELLINGCAT (coord hints), TEMPORAL (±72h ±1deg).
  //    Lever 4 tunes window/count/format here.
  const contexts = await Promise.all(batch.map(buildPromptContext))
  const userPrompt = buildBatchUserPromptV2(contexts)

  // 3. Wrap callLLM in watchdog — 90s hard kill, 60s soft warn.
  const content = await withBatchWatchdog(
    () => callLLM(
      [{ role: 'system', content: SYSTEM_PROMPT_V2 },         // lever 3 target

      { batchSize: batch.length },
    ),

      onSoftWarn: (ms) => { /* append synthetic ⊘ entry to callHistory */ } },
  )

  if (content === null) {
    await writePartialCache(results, batchIndex + 1, totalBatches, false)   // observability key only
    continue
  }

  const parsed = JSON.parse(content)
  const validated = batchResponseV2.safeParse(parsed)

    for (const g of batch) await enqueueDLQ({ id: g.key, reason: 'zod_fail', ... })
    await writePartialCache(results, batchIndex + 1, totalBatches, false)
    continue
  }

  // 6. Append validated events. Per-batch flush to PARTIAL key (observability — never served to users).
  results.push(...validated.data.events)
  await writePartialCache(results, batchIndex + 1, totalBatches, false)
}

  // Yield GeocodedEnrichedEventV2 with provenance tag.
}

// 9. ROUTE-LEVEL only (server/routes/events.ts:1016): write to TERMINAL key.
//    The extractor never touches events:llm:v2 directly.
await cacheSetSafe('events:llm:v2', conflictEventEntities, LLM_REDIS_TTL_SEC)
```

**Critical cache-discipline rule:** the post-batch flush to `events:llm:v2:partial` is observability-only. It carries an `LLMCachePayload` envelope (`{events, progress, complete, generatedAt}`); the `/api/events` user-facing reader NEVER touches this key. The terminal key `events:llm:v2` is only written by the route handler after geocoding completes, and only as a flat `ConflictEventEntity[]`. A tuning lever that conflates these surfaces will rediscover the Phase 27.4.1 cache-shape failure mode.

### Tool Use

**N/A.** The pipeline does not use OpenAI tool-calling / function-calling. It uses strict JSON Schema response mode (`response_format.type: 'json_schema'`) for structured extraction. The reranker (`server/lib/llmResolver.ts:407-414`) is a second LLM call but it too uses strict JSON Schema, not tools.

This is a deliberate design choice — tool-calling adds round-trip latency (model → tool → model) that wouldn't help here because all the "tool" the LLM would call is the deterministic resolver, which we run after extraction without LLM mediation. **Document this explicitly so a future planner doesn't propose adding tool-use complexity to `EVENT_EXTRACTION_SCHEMA_V2`.**

### Context Window Strategy

At 235B parameters (qwen) the model context window (~32K tokens for Cerebras qwen) is plenty for a 2-event batch + 3 enrichment blocks. Per-batch prompt cost is roughly:

- System prompt (`SYSTEM_PROMPT_V2`): ~400 tokens (fixed)
- 2 GDELT event headers + actors + URLs: ~200 tokens
- NEWS BLOCK: 5 articles × ~50 tokens = ~250 tokens (when full)
- BELLINGCAT BLOCK: 3 hits × ~30 tokens = ~90 tokens (when present)
- TEMPORAL BLOCK: 3 prior events × ~40 tokens = ~120 tokens (when populated)
- Response (structured JSON): ~600 tokens × 2 events = ~1200 tokens

Per-batch total: roughly **2,000-2,500 tokens** (input + output). A full 184-batch run consumes roughly **400K-500K tokens** out of the daily 1M Cerebras cap — comfortably below the 0.8 soft cap if there are no rerun loops.

**The constraint is the daily token budget, NOT context window per call.** A tuning lever that doubles the BELLINGCAT block depth (5 hits instead of 3) or expands the TEMPORAL window (96h instead of 72h) increases per-batch tokens linearly, which halves the daily run capacity. Quantify before shipping:

- BELLINGCAT 3 → 5: +60 tokens/batch × 184 batches = +11K tokens/run (2.2% of daily) — acceptable
- TEMPORAL count 3 → 5: +80 tokens/batch × 184 = +15K tokens/run (3.0%) — acceptable
- TEMPORAL window 72h → 96h: only matters when more events fit; same +80 tokens upper bound — acceptable
- NEWS 5 → 10 articles: +250 tokens/batch × 184 = +46K tokens/run (9.2%) — significant; couple with eval delta to justify
- BATCH_SIZE 2 → 4: per-batch tokens roughly 1.5× (system prompt amortized) but per-run batch count halves — net token-neutral, but **doubles attention budget per call** which is the 27.4.1 hang risk; do NOT widen in 27.4.2

The soft-cap (0.8 = 800K) and hard-cap (0.95 = 950K) thresholds are the operational guards. Watch DevApiStatus token block during the wave; if a lever pushes a single full-production run above 0.6 of daily, schedule a second tuning iteration for the next UTC day instead of compounding.

### Structured Outputs with Zod

(Renamed from "Pydantic" — this is a TypeScript project. Same idea.)

The shipped pattern in `server/lib/llmSchema.ts`:

1. **Two-encoding source of truth.** A Zod schema (`enrichedEventV2`) for runtime validation, and a hand-written JSON Schema (`EVENT_EXTRACTION_SCHEMA_V2`) for the LLM wire contract. Both must move together, but Zod is the enforcement-of-last-resort because providers vary in JSON Schema keyword support (Cerebras qwen rejects `maxLength`).

2. **Discriminated union for cache-read safety.** `enrichedEventAny = z.discriminatedUnion('schemaVersion', [enrichedEventV1, enrichedEventV2])` lets v1 and v2 payloads coexist during rollout (Pitfall 4 — `schemaVersion` attached server-side, never LLM-emitted; the `batchResponseV2` `z.preprocess` wrapper seeds it on read).

3. **`.strict()` on `locationHierarchyV2` is the D-05 enforcement.** Any extra key (including `lat`/`lng`/`coordinates`/`coords` the LLM might hallucinate despite the system prompt) fails `safeParse` and the whole batch routes to DLQ with `reason: 'zod_fail'`. Combined with `additionalProperties: false` at every level of the wire JSON Schema, this is a two-layer wall against fabricated coordinates.

4. **Server-side derivation of LLM-adjacent fields.** `derivePrecision(hierarchy)` and `deriveSuspect({confidence, precision, distance, tiers})` are pure functions in `llmSchema.ts`. The LLM does NOT compute precision (which would create dual sources of truth), and does NOT compute the suspect flag (which depends on resolver output). Keeping these functions pure and deterministic is what makes ground-truth replay (`runEval`) meaningful.

5. **Truncate, don't reject.** The `reasoning` field uses `z.string().transform((s) => s.length > 200 ? s.slice(0,197) + '…' : s)` instead of `.max(200)`. Verbose models routinely emit 250-400 char reasoning; rejecting the whole batch for one over-long field loses ALL events in the batch. Truncation keeps the batch alive while the system prompt continues to ask for ≤200 chars (commit `a2ad342`).

**Tuning-wave discipline:**

- Levers 1, 2, 4 do not touch the schema.
- Lever 3 (system prompt) does not change the schema, but **a careless edit that introduces a new instruction like "include `coordinates: {lat, lng}`" would break D-05** — verbose models would emit `coordinates`, Zod would reject, every batch DLQs, run produces 0 enriched events, Pitfall 1 bridge silently keeps serving v1 stale data, eval baseline never updates. This is failure mode 4. The eval-replay endpoint (`POST /api/events/llm-replay/:groupKey`, dev-only, dual-gated) is the cheap safety check before committing a prompt edit — verify single-group output passes `batchResponseV2.safeParse` before triggering a full run.
- Retry on Zod failure: NONE at the batch level (already retried 2× per provider × 2 providers in the cascade; another retry on the same content would repeat the same parse failure). The DLQ entry IS the surfaced retry signal — DevApiStatus DLQ block shows the count and the first 500 chars of the error.

```typescript
// Canonical Zod-validated extraction (excerpt — full path in llmEventExtractor.v2.ts:509-533)
const parsed = JSON.parse(content);
const validated = batchResponseV2.safeParse(parsed);
if (!validated.success) {
  log.warn({ issues: validated.error.issues.slice(0, 3), batchIndex }, 'v2 Zod parse failed');
  const errPayload = JSON.stringify(validated.error.issues.slice(0, 3));
  for (const g of batch) {
    await enqueueDLQ({
      id: g.key,
      reason: 'zod_fail',
      lastError: errPayload,
      timestamp: Date.now(),
    });
  }
  continue; // do NOT retry — surface to DLQ + DevApiStatus, move to next batch
}
results.push(...validated.data.events);
```

### Async-First Design

The pipeline is **fire-and-forget**: `processEventGroupsV2()` returns `Promise<V2ExtractionRun>` that the route handler does NOT `await` on the user-facing path. The user gets raw GDELT immediately; the LLM background task lands the v2 cache 30-90s later (depending on cooldown, batch count, provider speed).

```typescript
// server/routes/events.ts (illustrative — actual code is more involved)
const cached = await cacheGetSafe('events:llm:v2', LLM_TTL)
if (cached?.data && !stale) {
  res.json({ data: coerceCachedEvents(cached.data), source: 'llm-v2' })
  return                                              // user sees cache immediately
}

if (shouldRunLLM()) {                                  // 15-min cooldown gate
  void llmCachedRef.then(async () => {                // FIRE-AND-FORGET
    const run = await processEventGroupsV2(groups)
    if (run.events) {
      const geocoded = await geocodeEnrichedEventsV2(...)
      await cacheSetSafe('events:llm:v2', toEntities(geocoded), LLM_TTL)
    }
  })
}

res.json({ data: rawGdelt, source: 'gdelt-fallback' })   // raw GDELT served NOW
```

**Common mistake (the one Cerebras-specific async gotcha):** awaiting the LLM call inside the request lifecycle. Cerebras hangs (the Phase 27.4.1 root cause) would block the HTTP request indefinitely. The `withBatchWatchdog` wrap at the per-batch level is the timeout boundary — **the watchdog is what makes fire-and-forget actually safe**. Without it, a hung Cerebras call holds the Vercel function open until the platform's 60s gateway timeout, which kills the function but leaves the in-flight Promise dangling (the late-resolve guard in `withBatchWatchdog` is the second line of defense — a promise that resolves 10 minutes later cannot clobber the cache because the `timedOut` closure flag is set).

**Stream vs. await:**

- **No streaming used.** Structured-output JSON is parsed atomically; partial JSON is meaningless. Streaming would also break Zod validation (you can only `safeParse` complete objects).
- **Await within batches; fire-and-forget at the run level.** Per-batch `await` keeps batch order deterministic (TEMPORAL block reads accumulated `events:llm:v2` from prior runs, not concurrently with this run). Per-run fire-and-forget keeps user latency bounded.
- **Parallel reads inside a batch.** `Promise.all(batch.map(buildPromptContext))` runs the per-group Redis reads concurrently — there are 2 groups × 2 keys = 4 parallel Redis reads per batch. This is the only intra-batch concurrency.

**AbortController + generation-counter late-resolve guard.** Inside `withBatchWatchdog`, after the hard-timeout fires, the workPromise's `.catch(() => {})` swallows the late rejection so Node doesn't emit an `unhandledRejection`. The `timedOut` closure flag prevents `onTimeout` from being invoked twice. **A tuning lever that "improves" the watchdog by simplifying it must preserve both guards.**

### Prompt Engineering Discipline

`SYSTEM_PROMPT_V2` (lines 84-114 of `llmEventExtractor.v2.ts`) is the lever-3 target. It's 30 lines, structured as: role declaration → field-by-field extraction rules → hierarchy schema → hard rules / negative examples. The shipped structure encodes several discipline patterns the tuning wave must preserve:

1. **System vs. user separation.** The system prompt carries the role + extraction rules + schema description (immutable per-call). The user message carries the per-group GDELT data + 3 enrichment blocks (NEWS / BELLINGCAT / TEMPORAL). **Tuning lever 4 affects ONLY the user-message blocks; lever 3 affects ONLY the system prompt.** A clumsy edit that moves NEWS into the system prompt would cache-bust every cached extraction (system prompt stickiness varies by provider) and explode token costs.

2. **The system prompt forbids LLM coord emission.** Hard rule lines 108-111: `"NEVER emit coordinates (lat/lng). Only output place names." / "NEVER emit a 'precision' field — the server derives it from which hierarchy fields you populated." / "Use null when a field is not supported by the source text — do NOT guess."` These three lines are load-bearing — they're the prompt-level enforcement of the schema's `.strict()` and `additionalProperties: false`. **Lever 3 may tighten by adding negative examples ("do not invent landmarks like 'Tehran Central Drone Base' if no source mentions one"); it may NOT relax these rules.**

3. **Tier-tagged news context (`T1`/`T2`/`T3`) is a read-only signal.** The NEWS BLOCK includes `[T1]`, `[T2]`, `[T3]` source-tier tags via `getSourceTier(article)`. The LLM is free to use this signal but the prompt does NOT make tier authoritative ("prefer T1 over T3" but not "trust T1 unconditionally"). Hypothesis 10 in the analysis suggests reordering or weighting; the canonical version is unweighted. **A lever 4 change that makes tier weights authoritative requires explicit eval before commit — track the 5km bucket carefully (a tier-weighting could lift 100km but drop 5km).**

4. **Few-shot examples are NOT used currently.** The system prompt declares the schema and rules in prose; there are no in-context worked examples. Adding few-shot would consume ~500-1000 tokens × 184 batches = 92K-184K tokens/run, a meaningful fraction of the 1M daily cap. **A lever 3 change that adds few-shot must measure +5pp delta on the 20km gate to justify the token cost.** Cheaper alternative: use `/api/events/llm-replay/:groupKey` to spot-check edge cases before committing.

5. **`max_tokens` is not set.** The structured-output schema bounds the response shape; `max_tokens` would only impose an additional cap and risk truncating a long `reasoning` field mid-string (which would produce invalid JSON and fail `JSON.parse`). The Zod truncation pattern (`reasoning.transform`) handles over-long output downstream. **Do not introduce `max_tokens` in 27.4.2** — it would create a new failure mode (truncated JSON) without addressing the actual constraint (daily TPD).

// SYSTEM_PROMPT_V2 — DO NOT modify outside lever 3 work; preserve the structure.

### Context Window Management

See Section 4 — **the constraint is daily token budget, not context window per call.** A 235B-parameter model with a 32K context handles a 2-event batch + 3 enrichment blocks at 2-3K tokens easily. The operational management surfaces:

- **TEMPORAL BLOCK (`events:llm:v2` read).** The extractor reads its own previous output to seed regional context. If the cache is empty (first run after deploy), the TEMPORAL block is empty for every batch; the prompt structure stays consistent (the block is omitted entirely, not populated with placeholders), and the run still completes — just with less context. **Lever 4 changes to TEMPORAL_CONTEXT_WINDOW_MS / BBOX_DEG / COUNT cycle cleanly — no cache invalidation, just different scope per next-run.**
- **NEWS BLOCK (`news:gdelt` read).** Time-only match (±24h via `NEWS_MATCH_WINDOW_MS`); no haversine. A wider window includes more articles per batch; ≥5 articles per group are dropped (slice(0, 5)). Hypothesis 3 in the analysis suggests narrowing to ±12h or adding haversine. **Tuning impact:** wider window adds tokens/batch but improves chance of relevant context; narrower drops ambiguity.
- **BELLINGCAT BLOCK.** Parsed coord hints from article titles via `extractBellingcatGeo`. ≤3 hits per group. Hypothesis 4 (coord precision in prompt — toFixed(2) ≈ 1km vs toFixed(0) coarser): low-leverage; the LLM doesn't do coord arithmetic, but specifying coords at all leaks structure that may bias landmark extraction.

**Truncation discipline:** every block uses `.slice(0, N)` (5 articles, 3 bellingcat, 3 temporal) — hard caps, not "as much as fits". This is what keeps per-batch token cost predictable and the daily budget calculation reliable.

### Cost and Latency Budget

**Per-call cost: $0** (Cerebras + Groq free tiers). **Bounded by daily TPD caps:** Cerebras 1M, Groq 200K. A full 184-batch run consumes roughly **400-500K Cerebras tokens** under shipped settings (Section 4 Context Window Strategy). A second full run on the same UTC day would push total to 800K-1M, brushing the soft cap. **Tuning-wave budget: 1-2 full production runs per wave (D-12).**

**Latency budget per batch:**

| Phase                         | Cerebras (typical)              | Groq (typical) | Watchdog cap            |
| ----------------------------- | ------------------------------- | -------------- | ----------------------- |
| Token-budget + breaker check  | <10ms                           | <10ms          | —                       |

**Caching strategy:**

- **30d Nominatim cache** (`geocode:fwd:constrained:<hash>`) — the hot path. POI keys, direct keys, verify keys are all cached including misses (negative caching, `{miss: true}`). A tuning lever that increases cardinality — e.g., adds `neighborhood` to the cache-key hash — effectively bypasses cache for novel inputs and re-traffics Nominatim. **Quantify cache-hit-rate impact before shipping.**
- **7d DLQ TTL** — recovery window long enough to triage failures; short enough to discard stale errors after a tuning iteration.
- **90d eval baseline** — stable comparator. Survives 27.4.2 wave; only overwritten when a new `runEval()` completes.
- **15-min `events:llm-process-ts` cooldown** — caps run frequency. A tuning iteration that wants to force a re-run uses `?backfill=true` query param or the `/api/events/llm-pipeline` runtime override; do not lower the cooldown.

**Sub-task model routing:**

NONE currently. All extraction goes to Cerebras qwen-3-235b first; reranker reuses the same cascade (whichever provider is healthy). A future phase could route shorter/simpler batches to Groq (lower latency, smaller daily cap) and longer/complex batches to Cerebras (higher capacity). **Out of scope for 27.4.2** — flag as future lever in the deferred backlog if a tuning iteration surfaces a clear case.

**Reliability primitives best practices** (added because reliability is the unusual shape of this system; do NOT add new primitives during 27.4.2 tuning per D-16):

- **Watchdog** (`server/lib/llmExtractorWatchdog.ts`): 90s hard timeout (env-tunable via `LLM_BATCH_TIMEOUT_MS`), 60s soft-warn (hard-coded), AbortController-style late-resolve guard via `timedOut` closure flag. A timed-out batch routes every group to DLQ with `reason: 'timeout_watchdog'`; the run continues to the next batch (timeout on batch N does NOT abort the run).
- **Circuit breaker** (`server/lib/llmCircuitBreaker.ts`): sliding 10-call window per provider, 30% error-rate threshold, 5-minute pause. Module-level state survives Vercel warm starts; resets on cold (worst case: 10 calls to rebuild the window, inside the retry budget).
- **Token budget** (`server/lib/llmTokenBudget.ts`): 0.8 soft cap (`shouldPauseNewEvents()` returns true → handler serves cached LLM, skips new extraction; `prioritizeBySeverity()` reorders groups so the BATCH_SIZE slice contains highest-severity events). 0.95 hard cap (cascade skips provider entirely with `skipReason: 'hard_cap'`). 48h Redis TTL on per-day counters resets cleanly across midnight UTC.
- **DLQ** (`server/lib/llmDLQ.ts`): bounded SADD set, 200-entry cap, oldest-by-timestamp eviction via raw-string `srem` (Upstash REST may not byte-round-trip JSON, so re-serializing for eviction would silently no-op). 7d TTL refreshes on every enqueue. `lastError` capped at 500 chars (Pitfall 7).
- **Retry** (`server/adapters/llm-provider.ts`): 2 attempts × 1s/4s exp backoff + ±250ms jitter. Synthetic skip entries (`skipReason: 'breaker' | 'hard_cap' | 'no_client'`) appended to `callHistory` when a provider is bypassed without network activity — without this, empty-result runs leave an empty call history and become undiagnosable on DevApiStatus.

**The recommendation:** do NOT add new reliability primitives during 27.4.2 tuning. The existing primitives are sufficient and tested. New tuning levers must plug into the existing wraps (`withBatchWatchdog(callLLM(...))`) and the existing budget/breaker checks — they should NOT introduce parallel reliability surfaces. If a future incident reveals a primitive gap, that's a separate ops phase (CONTEXT D-deferred §6, §7, §9 are already captured as backlog candidates).

### Eval Tooling

**Primary Tool:** Custom in-house `runEval()` harness at `server/lib/llmEvalHarness.ts` — resolver-only ground-truth replay against 50 curated events, per-distance buckets (5km / 20km / 100km / total), baseline persisted to Redis at `events:llm-eval-baseline:v2` (90-day TTL). Already shipped in Phase 27.4 (Plan 08, D-20 / D-25). **No installation required, no new dependencies, no platform account.**

**Why not Arize Phoenix / Langfuse / Promptfoo / Ragas / DeepEval?** Adding any of them violates D-16 (no new dependencies in Phase 27.4.2). Phoenix's OpenTelemetry tracing is the closest match for an "observability platform" but its value lands on multi-team production AI systems with cross-service trace correlation needs — this project is single-operator, single-pipeline, single Vercel function. The de-facto observability surface (DevApiStatus 8-block dashboard) is appropriate to that scale; see Section 7. Ragas and DeepEval target end-to-end RAG accuracy with LLM-as-judge — neither matches the resolver-only ground-truth coordinate replay shape (objective haversine distance against a verified coord, no judge needed). Promptfoo's CLI-first prompt-comparison shape would be a reasonable inner-loop driver if `runEval()` didn't already exist; it does.

### Reference Dataset

## 7. Production Monitoring

**Tracing Tool:** **Custom in-app DevApiStatus dashboard** (`src/components/dev/DevApiStatus.tsx`) — dev-only, gated on `import.meta.env.DEV && schemaVersion === 'v2'`. The 8 blocks comprising the de-facto tracing surface:

1. **Pipeline waterfall** — per-stage timings (group → extract → resolve → cache-write) for the most recent run.
2. **Precision histogram** — distribution of `exact` / `neighborhood` / `city` / `region` precision tags (Section 1b dim 2 observability).
3. **Confidence histogram** — distribution of `high` / `medium` / `low` confidence values (Section 1b dim 7 observability).
4. **Source-tier histogram** — T1 / T2 / T3 enrichment fingerprint (NEWS-block tier-tagging visibility).
5. **Eval-score block** — per-distance ratios (`within5km/total`, `within20km/total`, `within100km/total`) + the D-25 deploy-gate visual at `within20km/total >= 0.8`.
6. **Per-event drill-down** — last 50 enriched events with copy-prompt button for the `/api/events/llm-replay/:groupKey` dev endpoint (D-21 prompt iteration).
7. **LLM call log** — last 20 `callHistory` entries with the amber `⊘` skip-entry glyph for watchdog soft-warns + breaker / hard-cap synthetic entries (so any error / skip path is diagnosable).
8. **DLQ recent list + suspect-count badge + per-provider token-budget bars with pause badge** — the failure-mode rollup (DLQ for schema/timeout regressions, suspect for Section 1b dim 8 observability, budget bars for runway visibility).

**Why no Arize Phoenix / Langfuse / Helicone:** adding any of them violates D-16 (no new dependencies in Phase 27.4.2), and the value those platforms deliver — multi-team trace correlation, role-based access, prompt-version A/B platform-side, dataset experiment tracking — is not load-bearing for a single-operator analytical tool. The DevApiStatus dashboard renders the same telemetry (per-call traces via `callHistory`, per-stage waterfall, eval scores, DLQ) in 8 in-app blocks. If the project ever expands to a multi-operator team or a hosted service, Phoenix is the migration target on the OpenTelemetry-friendliness axis; in 27.4.2 it would be over-engineering for a phase whose success criteria are two numeric gates.

**Key Metrics to Track:**

1. **`evalScore.within20km / evalScore.total`** — primary success criterion delta vs v1 baseline (≥ +5pp). Captured every tuning sub-lever via `runEval()` (D-12 cadence).
2. **`provenanceCounts['gdelt-actiongeo-fallback'] / sum(provenanceCounts)`** — secondary success criterion (target `< 0.25` per D-13). Captured on every full /api/events?force production run.
3. **`watchdogTimeoutCount`** per run — health invariant (target `0` for baseline-capture run per D-08; `< 3` for tuning runs per D-06 noise-floor tolerance).
4. **DLQ count by reason** (`zod_fail` / `timeout_watchdog` / other) — schema + timeout regression watch.
5. **Token-budget consumption per provider per day** — runway visibility for the `~2 full production runs per wave` budget envelope.

**Alert Thresholds:**

In a single-operator analytical tool there is no pager. The "alert" surface is **what the operator notices in DevApiStatus when they refresh during a tuning session**, plus what they see on the live map at `iran-conflict-monitor.vercel.app`. Define visual alert thresholds:

| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

**Smart Sampling Strategy:**

Per-iteration sampling, manual, by the operator:

1. **After each tuning sub-lever change** — run `runEval()` (~1 min), capture before/after per-distance counts, decide commit/revert per D-14.
2. **After each wave-boundary** — trigger `/api/events?force`, wait for `llmProgress.stage === 'done'`, capture provenanceCounts + watchdogTimeoutCount + DLQ count. Compare against criteria; if D-13 stop condition is met (≥ +5pp at 20km AND fallback < 25%) → wave complete, capture untouched levers as backlog, proceed to phase close.
3. **Per session, 5-event drill-down** — operator picks 5 representative events from DevApiStatus per-event drill-down and eyeballs:
   - Event-type classification matches source article (Section 1b dim 1)
   - Hierarchy depth honest vs source specificity (Section 1b dim 4)
   - Confidence calibration plausible (Section 1b dim 7)
   - `suspect: true` flag fires on Tier-3 / satirical sources (Section 1b dim 8)
4. **Source-link audit (signal-driven, not scheduled)** — when an event marker on the live map looks wrong, operator clicks through to the GDELT source URL and reads the article. Persistent disagreements get captured for the future-phase ground-truth corpus expansion.

**Signal-based filter is operator attention**, not automated paging. The tool is built for a single human session, not for 24/7 SRE coverage. The DevApiStatus dashboard is the primary inspection lens; the live map is the secondary signal (a user-facing failure visible at the consumption surface).
