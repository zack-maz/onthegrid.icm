## Implementation Decisions

### Remediation strategy (Area 1)

- **D-01** Primary remediation lever: **model swap**. Lock a faster NVIDIA NIM
  model as v3 primary, replacing qwen/qwen3.5-397b-a17b. Runner-up
  `meta/llama-3.3-70b-instruct` is the leading candidate (Plan 03 bake-off
  p50 7.7s, p95 19.7s). At p50 7.7s, 196-batch sequential ≈ 25-30 min,
  comfortably under the 120min Gate B threshold.
  - **Why:** Qwen's long-tail (p99 929s) is fundamentally too slow regardless
    of watchdog tuning. Even raising LLM_BATCH_TIMEOUT_MS doesn't help if a
    single batch eats 15+ minutes. Adaptive batching alone splits a 929s
    batch into two 465s batches — still blows the watchdog. Model swap is
    the single lever that addresses the root cause.
  - **How to apply:** New `NVIDIA_NIM_DEFAULT_MODEL` value in
    `server/lib/freeClaudeRouter.ts` after bake-off lock. Old qwen value
    preserved as `NVIDIA_NIM_FALLBACK_MODEL` for in-incident reversion.

- **D-02** Bake-off scope: **Tier 1+2 with prompt-tuning**. Full 50-event
  LLM-in-loop bake-off on:
  1. `qwen/qwen3.5-397b-a17b` — incumbent (control / regression baseline)
  2. `meta/llama-3.3-70b-instruct` — runner-up (leading candidate)
  3. `nvidia/nemotron-3-super-120b-a12b` with tuned prompt for envelope shape
     (Plan 03: emitted flat shape → Zod fail; tuneable per BAKEOFF.md)
  4. `z-ai/glm4.7` with alternate `response_format` mode
     (Plan 03: returned empty content under `response_format: json_object`)
  - **Why:** Plan 03's bake-off was 10-event sample; 50-event LLM-in-loop
    raises confidence on the leading candidate before committing to a
    cutover. Prompt-tuning the deferred candidates may unlock new winners
    that were prompt-failures, not capability-failures.
  - **How to apply:** Extend `scripts/bakeoff-v3-direct.ts` with
    `--limit=50` + per-model prompt-override hook. Persist resolver-only
    baseline per candidate to `events:llm-eval-baseline:v3:<sanitized-id>`
    (90d TTL pattern from Plan 03).

- **D-03** Winner selection: **dual hard floors**. Candidate must clear BOTH:
  - within20km / total ≥ 0.890 on 50-event LLM-in-loop sample (mirrors
    27.4.3 D-16 Gate A floor)
  - p95 latency ≤ 30s in bake-off (extrapolates to <50min sequential for
    196 batches; 2.4× margin under 120min Gate B)
    Tiebreaker among passers: lowest p99 (long-tail predictor).
  - **Outcome ladder:** 0 candidates pass both floors → escalate to combo
    path (D-01 winner + D-04 adaptive batching forced ON) or defer phase.
    1 candidate passes → lock it. 2+ candidates pass → lowest p99 wins.
  - **Why:** Falsifiable, audit-clean. Accuracy is the primary requirement
    (Gate A is hard); latency is the differentiator. Composite scores are
    arbitrary weights — dual hard floors avoid that trap.
  - **How to apply:** Encoded in BAKEOFF.md table evaluation logic; printed
    PASS/FAIL per candidate.

- **D-04** Adaptive batching: **opt-in defensive layer**. Implement once
  (split BATCH_SIZE=2 into 1+1 on timeout, retry failed groups once at
  smaller size, otherwise DLQ-enqueue with reason `v3:adaptive-retry-fail`).
  Default OFF, enabled via env flag `V3_ADAPTIVE_BATCH=true`. Activated
  when bake-off telemetry shows winner p95 > 20s OR production smoke
  reveals fresh long-tail.
  - **Why:** Belt-and-suspenders without always-on cost. Code ships
    pre-tested; activates only when data demands. Same pattern as the
    deferred-feature flag philosophy of 27.4.x.
  - **How to apply:** New helper in `server/lib/llmEventExtractor.v3.ts`
    `splitBatchOnTimeout(batch, opts)`. Bounded retry: max 1 retry per
    group. Tested in `server/__tests__/lib/llmEventExtractor.v3.test.ts`.
    Default OFF in env config; `.env.example` documents the flag.

- **D-05** Pre-bake-off characterization: **instrumented v3 trace** (20-batch
  segment) before bake-off begins. Captures per-batch:
  - TTFB (time-to-first-byte) — diagnoses NIM cold-start vs network
  - Token-emission rate — diagnoses generation speed vs total wall clock
  - Reasoning content size (`<think>` block bytes)
  - max_tokens hit count (truncation signal)
  - Per-call wall clock vs network duration
    Output: `27.4.4-PREFLIGHT-CHARACTERIZATION.md` with breakdown of
    qwen's 929s p99 root cause (inference burst vs network vs reasoning
    explosion). Tells us if model swap alone is enough, or if max_tokens
    cap / circuit breaker tweak is also needed.
  - **Why:** "Measure before fix" Palantir-grade discipline. Prevents
    picking a remediation that doesn't address the actual failure mode.
  - **How to apply:** New `--mode=characterize` flag on
    `scripts/bakeoff-v3-direct.ts` runs 20 batches with extra logging.
    Cost: ~5-10min, ~10 LLM calls.

- **D-06** Token cap: **data-driven max_tokens** from D-05 preflight.
  Set `max_tokens` in `freeClaudeRouter.callLLM()` to ≈ p99(tokens-out) + 20%
  buffer per model, with hard ceiling 4096. E.g., if winner emits p99 1200
  tokens, cap at 1500.
  - **Why:** Cheapest defense against runaway reasoning. Reasoning models
    can think for thousands of tokens; capping bounds worst-case latency.
  - **How to apply:** Per-model config in `freeClaudeRouter.ts`
    `MAX_TOKENS_PER_MODEL: Record<string, number>`. Falls back to 4096
    for un-cataloged models. Logged in CONTEXT for audit. If cap is too
    low → truncated JSON → schema_fail visible in error taxonomy →
    recoverable via DLQ retry.

- **D-07** Tier 2 prompt-tuning budget: **30min total wall-clock** across
  nemotron + glm4.7 combined. Run baseline bake-off first (existing v3
  prompt). For each tier 2 failure, attempt one targeted prompt fix
  (envelope-shape demand for nemotron, alternate `response_format` for
  glm4.7). If still failing within budget, defer with notes captured in
  BAKEOFF.md "Loser Deferral" section.
  - **Why:** Anti-rabbit-hole budget. Prevents bake-off from spiraling into
    open-ended prompt iteration. Audit-friendly: "30min spent, here's what
    we tried."
  - **How to apply:** Wall-clock timer in BAKEOFF.md; budget tracked at
    operator level (executor logs start + end timestamps).

### Gate B threshold tuning (Area 2)

- **D-08** Hold strict numeric thresholds: **watchdog=0, DLQ≤5, dur≤120min,
  provenanceCounts populated** (no all-zero bug). Same falsifiable bar as
  Plan 05.
  - **Why:** With llama-3.3-70b expected to finish ~25-30min sequentially,
    all 4 originals are easily achievable. If we can't pass strict, we
    shouldn't cut over. Audit rationale: gates unchanged from Plan 05 —
    same falsifiable bar across phases.

- **D-09** Add **3 observability gates** beyond the 4 originals:
  1. Schema_fail rate ≤ 2% (production validation of Zod parsing at scale —
     Plan 05 saw 2/196 = 1% on qwen, set bar conservatively)
  2. p95 latency ≤ 30s in `llmProgress.latencyHistogram.{provider}.p95`
     (extends D-03 bake-off floor into prod observability)
  3. routingTrace shows ≥ 90% primary routes vs fall-throughs (validates
     NIM dominance under sustained load)
  - **Why:** Production-only failure modes invisible to bake-off. Each
    gate is measurable from existing v3 dashboard fields.
  - **How to apply:** Encoded in CUTOVER.md per-pass threshold table;
    auto-extracted from llm-status JSON snapshot.

- **D-10** Run count: **2 consecutive Gate B passes required**, both must
  clear all 7 gates. ~60min total at llama-3.3-70b speed.
  - **Why:** Catches transient/edge issues. Single Plan 05-style run let
    a model-specific long-tail surprise leak through. Reproducibility is
    the Palantir-grade signal.

- **D-11** Failure semantics: **strict — any pass missing any gate = overall
  fail + defer**. If Pass 1 succeeds but Pass 2 fails any gate, the run
  sequence fails. Document failure mode in CUTOVER.md (which gate, which
  auto-rollback fired). Operator decides: investigate root cause and
  re-attempt 2-pass sequence, or defer phase.
  - **Why:** Two consecutive passes is the bar. "Best 2 of 3" or "allow 1
    retry" introduce slippery-slope tolerance. Audit-clean: gates are
    gates.

### OpenRouter activation + auto-rollback retuning (Area 3)

- **D-12** OpenRouter activation: **dev-only**, exclude from production
  smoke. Set `OPENROUTER_API_KEY` in dev `.env.local` for cascade testing.
  Do NOT propagate to Vercel prod env in this phase.
  - **Why:** Cleaner Gate B telemetry — production cascade stays dormant,
    every NIM call must be the primary path under D-09's 90% primary-route
    gate. Promotion to prod is a future-phase decision after Gate B passes
    twice with NIM as sole live provider.
  - **How to apply:** Document `OPENROUTER_API_KEY` in `.env.example` as
    optional. Synthetic NIM-failure smoke test in dev validates cascade
    routing actually kicks in (manually disable NVIDIA_NIM_API_KEY mid-run,
    confirm OpenRouter call succeeds, audit log records `fall_through:nvidia_nim_no_client`).

- **D-13** Auto-rollback Trigger 1 threshold: **lower to ≥ 2, env-tunable**.
  Add `V3_WATCHDOG_ROLLBACK_THRESHOLD` env var (default 2). Currently
  hardcoded `>= 3`.
  - **Why:** With strict gate watchdog=0 (D-08), the existing ≥ 3 threshold
    is more lenient than the gate — a 2-timeout run still passes Trigger 1
    but fails Gate B. Inconsistent. Lowering to 2 keeps Trigger 1 as a
    consistent defense-in-depth net while letting single timeouts (NIM
    cold-start, network blip) recover without spurious flip.
  - **How to apply:** `server/lib/llmEventExtractor.v3.ts`
    `checkWatchdogRecurrenceTrigger()` — change literal `3` to
    `env.V3_WATCHDOG_ROLLBACK_THRESHOLD`. Update tests in
    `server/__tests__/lib/llmAutoRollback.test.ts`.

- **D-14** Eval drift detection: **daily Vercel cron** at `0 4 * * *` UTC.
  Add `/api/eval-cron` endpoint that runs `runEval()` resolver-only against
  the locked 50-event GT corpus, persists to `events:llm-eval-baseline:v3`,
  and invokes `checkEvalDropTrigger()`.
  - **Why:** Trigger 2 is currently dormant unless operator manually runs
    eval. Daily cron keeps it continuously armed against drift introduced
    by resolver/code/snapshot changes. Resolver-only = zero LLM token
    spend per cron run; ~10s execution.
  - **How to apply:** New `server/routes/eval-cron.ts` mounted at
    `/api/eval-cron`. Vercel cron config in `vercel.json` `crons[]`.
    Authentication: same JWT/header pattern as existing `/api/cron-warmup`
    (verify with existing auth middleware).

### Lineage-hash pre-filter (Area 5)

- **D-18** Skip-already-enriched: **opt-in env flag**, default off. Implement
  in v3 extractor: at start of `processEventGroupsV3`, compute lineage hash
  per group (sha256(groupKey || sourceUrls || gdeltMentionCount)); query
  `events:llm:v3:lineage:<groupHash>` Redis key; if hit AND age < 7d, skip
  the LLM call and reuse cached enriched event. Default OFF via
  `V3_LINEAGE_PREFILTER=true` env flag.
  - **Why:** Cuts 196 batches → ~30-50 on stable runs (massive runtime
    reducer independent of model). Default off keeps Gate B telemetry
    pure (every test run processes all groups). Activates post-cutover
    when ongoing-ops cost optimization matters.
  - **How to apply:** New helper `computeGroupLineageHash(group)` in
    `server/lib/llmLineage.ts`; pre-filter loop in
    `server/lib/llmEventExtractor.v3.ts` before main batch dispatch;
    cache key `events:llm:v3:lineage:<groupHash>` (7d hard TTL).
    Documented in CONTEXT for downstream operator activation decision.

### NIM cold-start pre-warm (Area 8)

- **D-21** Smart pre-warm: **only if last NIM call > 5min ago**. Track
  `lastNimCallTs` in `freeClaudeRouter.ts` module state. At start of each
  `/api/events` refresh that triggers v3 extraction, if
  `Date.now() - lastNimCallTs > 5 * 60_000`, fire a no-op LLM call
  (`{role:'system',content:'.'}` w/ `max_tokens=1`) before the main batch
  loop.
  - **Why:** NIM cold-start adds ~2-5s on first call after idle.
    Removing first-batch lag tightens p99. Smart-only: zero cost when
    warm; cheap (~1 call when cold) when needed. Cost-shadow tracked
    per pre-warm call.
  - **How to apply:** New `prewarmIfCold()` function in freeClaudeRouter,
    called from v3 extractor `processEventGroupsV3()` before main loop.
    Pre-warm call recorded in `routingTrace` with
    `reason: 'prewarm:cold-start'` so it shows up in audit. Cost-shadow
    increments by p_in/p_out from the pre-warm response.

### freeClaudeRouter pre-warm + token cap shape (illustrative)

```typescript
// server/lib/freeClaudeRouter.ts — 27.4.4 D-06 + D-21 additions

const MAX_TOKENS_PER_MODEL: Record<string, number> = {
  'meta/llama-3.3-70b-instruct': 1500, // D-06: data-driven from preflight
  'qwen/qwen3.5-397b-a17b': 1500, // fallback model preserved (D-01)
  // ... per-candidate limits set by D-05 preflight characterization
};
const MAX_TOKENS_DEFAULT = 4096; // D-06 hard ceiling

let lastNimCallTs = 0; // D-21 module state
const PREWARM_THRESHOLD_MS = 5 * 60_000;

export async function prewarmIfCold(): Promise<void> {
  // D-21 — only if last call > 5min ago
  if (Date.now() - lastNimCallTs <= PREWARM_THRESHOLD_MS) return;
  try {
    const client = getNvidiaNimClient();
    if (!client) return;
    await client.chat.completions.create({
      model: NVIDIA_NIM_DEFAULT_MODEL,
      messages: [{ role: 'system', content: '.' }],
      max_tokens: 1,
    });
    lastNimCallTs = Date.now();
    // record routingTrace entry: reason='prewarm:cold-start'
    appendRoutingTrace({
      provider: 'nvidia_nim',
      model: NVIDIA_NIM_DEFAULT_MODEL,
      reason: 'prewarm:cold-start',
      ts: lastNimCallTs,
    });
    log.info({ module: 'pre-warm' }, 'NIM pre-warm fired (cold-start)');
  } catch (err) {
    log.warn({ module: 'pre-warm', err }, 'NIM pre-warm failed (non-fatal)');
  }
}
```
