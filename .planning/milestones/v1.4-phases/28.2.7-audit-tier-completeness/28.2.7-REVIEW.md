# Phase 28.2.7: Code Review Report

**Reviewed:** 2026-05-07
**Depth:** standard

## Summary

Phase 28.2.7 closes three gaps in `/api/health` tier-completeness:

- **R1** — three cron handlers now write `cron:lastTick:<name>` (7-day TTL) on success.
- **R2** — `llm:lastProgress` Redis write-through with `probeLlmStatus` Redis-first read (singleton fallback).
- **R3** — `probeProbeOnly` returns `freshnessMs:0` honest-stub instead of `null`.

The implementation is consistent with CLAUDE.md conventions: keys use the established `<feature>:<sub>:<variant>` shape, `cacheSetSafe`/`cacheGetSafe` wrappers are used everywhere (degrade-open via the `memCache` fallback path established by Phase 28.1 W2), TTLs are seconds-based per CONTEXT D-06, and Bearer auth is gated on a non-empty `env.CRON_SECRET` (consistent with `cron-warm`'s pre-existing un-authed default).

No critical issues. All four warnings are correctness/observability concerns — none block the phase but a few are worth addressing in a follow-up. The six info items are minor maintainability / DRY suggestions.

The test surface (3 new files, 17 cases combined) is appropriately scoped: it exercises the write-through happy path, mid-run skip, terminal-write, both-empty unknown, Redis-down degrade-open, partial cron-warm, and the deriveStatus(0,0,false)→healthy invariant. Two failure-mode gaps surface below as warnings.

## Warnings

### WR-01: Stale `startedAt` in Redis can mask a more-recent in-memory completion

**File:** `server/routes/health.ts:162-163`
**Issue:**

```ts
const memLatest = llmProgress.completedAt ?? llmProgress.startedAt ?? null;
const latest = redisLatest ?? memLatest;
```

`probeLlmStatus` resolves `latest` as `redisLatest ?? memLatest` — Redis wins whenever it has _any_ value, even if memory is newer. Pathological sequence:

1. Run A starts → `resetProgress()` writes `{startedAt: T0, completedAt: null}` to Redis.
2. Process crashes / warm-start drop / OOM → `updateProgress({completedAt})` never fires.
3. New instance handles a fresh request. Run B starts and completes successfully → in-memory singleton has `completedAt: T2 (fresh)`, but the local `cacheSetSafe` call in `updateProgress` is fire-and-forget (`void`) — under back-pressure it could land slightly behind the probe.
4. `redisLatest` resolves to `T0` (yesterday), `memLatest` resolves to `T2` (now). Probe surfaces `T0` → 26h+ later, surfaces stale `unhealthy` even though the local pipeline is healthy.

The 7-day TTL plus the lack of an "in-progress" sentinel means a single crashed run can mask up to 7 days of subsequent successful in-memory completions on cold-started instances that happen to read Redis first.

**Fix:** Take the maximum of the two timestamps, not Redis-first:

```ts
const memLatest = llmProgress.completedAt ?? llmProgress.startedAt ?? null;
// Take the freshest signal — Redis can hold a stale "started but never completed"
// record from a crashed run that masks subsequent in-memory completions until
// the next resetProgress() overwrites the Redis key.
const latest =
  redisLatest === null
    ? memLatest
    : memLatest === null
      ? redisLatest
      : Math.max(redisLatest, memLatest);
```

### WR-02: `updateProgress({ completedAt: <number>, errorMessage: 'NIM throttle' })` writes the same shape as success

**File:** `server/lib/llmProgress.ts:533-549`
**Issue:** The write-through guard fires on `partial.completedAt !== undefined` regardless of whether the run errored. From the pipeline's perspective an errored terminal write (`stage: 'error'`, `errorMessage: '...'`, `completedAt: Date.now()`) is recorded as a successful completion timestamp in `llm:lastProgress`. `probeLlmStatus` then surfaces the _failed_ run's `completedAt` as the freshness signal, hiding the failure from the API Health tab.

This is a conceptual mismatch with `cron:lastTick:*`, where Phase 28.2.7 R1 went out of its way (cron-health.ts:114-118 comment, cron-lasttick.test.ts:212-222 case) to ensure that a failed cron run does NOT advance the tick. The stricter invariant should hold for `llm:lastProgress` too — failure-by-the-pipeline shouldn't masquerade as success-by-the-probe.

**Fix:** Skip the write when the partial carries an error stage:

```ts
if (partial.completedAt !== undefined) {
  // Don't advance the freshness witness for failed runs — mirrors the
  // "tick fires only on success" contract from cron-health.ts:114-118.
  const isErrorTermination =
    partial.stage === 'error' || llmProgress.stage === 'error' || llmProgress.errorMessage !== null;
  if (!isErrorTermination) {
    void cacheSetSafe(
      LLM_LASTPROGRESS_KEY,
      { startedAt: llmProgress.startedAt, completedAt: llmProgress.completedAt },
      LLM_LASTPROGRESS_TTL_SEC,
    );
  }
}
```

If keeping the write is intentional (so the dashboard can see "pipeline is alive even when failing"), the contract should at least be documented above the guard so future maintainers don't assume the cron-tick semantics carry over.

### WR-03: Missing test coverage for cron-warm TTL argument and refresh-events `?force=true` Bearer interaction

**File:** `server/__tests__/routes/cron-lasttick.test.ts:158-168, 195-210`
**Issue:** Two coverage gaps relative to peer tests:

1. `cron-health` and `refresh-events-cron` cases assert `cacheSetSpy.toHaveBeenCalledWith('cron:lastTick:<name>', expect.any(Number), 604_800)` — TTL pinned. The cron-warm "writes ... when both fetches succeed" case (line 158-168) asserts `cacheStore.has(...)` only — TTL drift would slip through.
2. `refresh-events-cron` D-11 documents that `?force=true` is accepted only when Bearer is valid (refresh-events-cron.ts:35-48). The test file exercises the happy path with empty `CRON_SECRET` but does NOT assert that `?force=true` with a wrong Bearer returns 401 _before_ `runRefreshExtraction` is called. A regression that processes `?force=true` ahead of the auth check would bypass the rate gate.

**Fix:**

```ts
// Add to cron-warm "both succeed" case:
expect(cacheSetSpy).toHaveBeenCalledWith('cron:lastTick:warm', expect.any(Number), 604_800);

// Add a new case to refresh-events-cron block:
it('rejects ?force=true with wrong Bearer; runRefreshExtraction NOT called', async () => {
  mockEnv.CRON_SECRET = 's3cret';
  const { refreshEventsCronRouter } = await import('../../routes/refresh-events-cron.js');
  const handler = extractHandler(refreshEventsCronRouter);
  const { req, res, getStatus } = createReqRes(
    { Authorization: 'Bearer wrong' },
    { force: 'true' },
  );
  await handler(req, res);
  expect(getStatus()).toBe(401);
  expect(mockRunRefresh).not.toHaveBeenCalled();
  expect(cacheStore.has('cron:lastTick:refresh-events')).toBe(false);
});
```

### WR-04: Bearer auth uses string `===` instead of constant-time compare (carried-forward, not introduced)

**File:** `server/routes/cron-health.ts:29`, `server/routes/refresh-events-cron.ts:41`
**Issue:**

```ts
if (auth !== expected) {
  res.status(401).json({ error: 'unauthorized' });
  return;
}
```

CLAUDE.md "Vercel Deployment (Phase 14)" calls out `timingSafeEqual` constant-time compare for the rate-limiter Bearer-bypass path. The cron auth gates use a plain string `!==`, which is timing-leaky in principle (early-exit on the first differing byte). The risk is low for cron secrets (high entropy, short-lived if rotated, low-frequency surface), and this pattern predates Phase 28.2.7 (the comment at cron-health.ts:25 explicitly says it "Mirrors eval-cron.ts:33-40"), so the issue is carried-forward, not introduced. Worth flagging because the phase touches both files and could fix it cheaply.

**Fix:**

```ts
import { timingSafeEqual } from 'node:crypto';

const auth = req.header('Authorization') ?? req.header('authorization') ?? '';
const expected = `Bearer ${env.CRON_SECRET}`;
const a = Buffer.from(auth);
const b = Buffer.from(expected);
if (a.length !== b.length || !timingSafeEqual(a, b)) {
  res.status(401).json({ error: 'unauthorized' });
  return;
}
```

Same fix at refresh-events-cron.ts:41. (cron-warm has no auth gate — see IN-04.)

### IN-01: Cron-name strings duplicated between writers and probe registry

**File:** `server/routes/cron-health.ts:118`, `server/routes/cron-warm.ts:85`, `server/routes/refresh-events-cron.ts:64`, `server/routes/health.ts:288-290`
**Issue:** The strings `'health'`, `'warm'`, and `'refresh-events'` appear hardcoded in both the writers (e.g. `cacheSetSafe('cron:lastTick:health', ...)`) and the probe registry (`PROBE_STRATEGIES.cronHealth = { kind: 'cron', cronName: 'health' }`). A typo on either side silently degrades the probe to `unknown`.
**Fix:** Centralize the cron-name → key shape in `healthSources.ts`:

```ts
export const CRON_LASTTICK_KEYS = {
  health: 'cron:lastTick:health',
  warm: 'cron:lastTick:warm',
  refreshEvents: 'cron:lastTick:refresh-events',
} as const;
```

Then writers call `cacheSetSafe(CRON_LASTTICK_KEYS.health, ...)` and the probe builds `\`cron:lastTick:${name}\`` from the same source.

### IN-02: `probeProbeOnly`'s `lastSuccessTs: Date.now()` is misleading semantically

**File:** `server/routes/health.ts:213-214`
**Issue:** Returning `Date.now()` for `lastSuccessTs` on every request says "I succeeded just now," which conflates "probe ran" with "endpoint is exercised." Future operators reading the API Health tab might assume an upstream call landed at this timestamp. Since the comment is explicit that this is a config-introspection probe, returning `null` for `lastSuccessTs` while keeping `freshnessMs:0` would be more honest. (The deriveStatus contract still holds because freshness, not lastSuccessTs, drives the status branch.)

Note: `probeSources` has the same shape (line 183-184). Pre-existing, but worth aligning.

### IN-03: `probeLlmStatus` returns `hadError:false` on Redis exception (degrade-open) — doc this trade-off

**File:** `server/routes/health.ts:159-161`
**Issue:** When `cacheGetSafe(LLM_LASTPROGRESS_KEY)` throws, the catch swallows silently and falls through to the in-memory singleton. This is documented in the comment as "degrade-open" but contrasts with `probeCacheKey` (line 111-119) which sets `hadError:true` on cache read failure. The asymmetry is intentional (R2 D-08 says singleton fallback wins over surfacing the Redis error) but a one-line note in the catch comment mentioning the asymmetry would help future maintainers.
**Fix:** Add `// Note: probeCacheKey sets hadError:true here; probeLlmStatus is degrade-open by design (R2 D-08).`

### IN-04: `cron-warm` has no Bearer auth gate (asymmetric vs. cron-health and refresh-events)

**File:** `server/routes/cron-warm.ts:39`
**Issue:** Pre-existing — but visible in this phase because all three cron handlers were touched. `cron-health` and `refresh-events-cron` honor `env.CRON_SECRET`; `cron-warm` does not. Vercel cron sends Bearer to all three; the asymmetry is silent in prod but anyone hitting `/api/cron/warm` from outside Vercel can force an Overpass refetch (and burn the Overpass rate budget). Not introduced by this phase, but the Plan 03 SUMMARY explicitly added auth to other cron handlers without touching this one. Worth adding to a follow-up ticket.
**Fix:** Mirror the auth block from `cron-health.ts:26-33`.

### IN-05: `STALE_THRESHOLD_MS = 60 * 60 * 1000` redefined in cron-health.ts is unused for the tick-write decision

**File:** `server/routes/cron-health.ts:20`
**Issue:** This local constant is used to flag warnings in the response (`stale ? 'X: stale (Nmin old)' : ...`), but is unrelated to `FRESHNESS_THRESHOLDS_MS` in `healthSources.ts`. It's pre-existing and not in scope, but flagging it because Phase 28.1 W2 centralized the freshness thresholds — this constant is now an outlier.
**Fix:** Move to `healthSources.ts` as `CRON_HEALTH_WARN_THRESHOLD_MS` for visibility, or document the intent here.
