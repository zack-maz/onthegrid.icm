## Open Implementation Decisions for Discuss-Phase

These are the HOW questions discuss-phase should resolve before plan-phase:

### D-01 — `llmProgress` write-through location

R2 mutates `llmProgress` as a singleton. The state changes happen in:

- `server/lib/llmProgress.ts` (the singleton itself — ~5-10 setter functions like `setStartedAt`, `setCompletedAt`, `updateProgress`)
- `server/lib/llmExtractionPipeline.ts` (writes to llmProgress in `runRefreshExtraction`)
- `server/lib/llmEventExtractor.v3.ts` (writes via `updateProgress`)

**Decision needed:** Where does the Redis write-through live?

- **Option A**: Inside `llmProgress.ts` — every setter calls `cacheSetSafe('llm:lastProgress', snapshot, TTL)` after mutating. Centralized, but couples the singleton to Redis.
- **Option B**: At the call sites in extraction pipeline — explicit per write-site. More verbose, but keeps `llmProgress.ts` pure.
- **Option C**: Periodic flush every N progress updates (matching the N=10 batch cadence of 28.2.6) — minimal Redis writes.

**Lean toward A** (simpler, easier to test, single concern per module). But check whether any tests depend on `llmProgress` being pure. If so → B.

### D-02 — `probeLlmStatus()` read order

After R2, `probeLlmStatus()` needs to read Redis with in-memory fallback. Order:

- **Option A**: Try Redis first, if fail/null fall back to in-memory singleton.
- **Option B**: Try in-memory first, only hit Redis on null.

**Lean toward A** — solves the cold-start problem. The whole point of R2. B defeats the purpose.

But: every `/api/health` call now hits Redis. Is that a perf concern? Probably not — `cacheGetSafe` is a single REST call, ~50ms latency, well within /api/health's overall budget. Confirm with current Redis-call counts in the route.

### D-03 — Where do cron tick writers go in each handler?

R1 says "at handler start (after Bearer auth, before the actual cron body)". But each handler has slightly different shape:

- `server/routes/refresh-events-cron.ts` — Bearer auth at line 35-43, then `forceCooldown` parsing at line 46. Tick write goes between line 43 and 46.
- `server/routes/cron-health.ts` — different shape (also calls `runEval`). Tick write at top of try block.
- `server/routes/cron-warm.ts` — different shape (Overpass + water pre-warm). Tick write at top of try block.

**Decision needed:** Should tick write be inside the try block (so it's atomic with cron body) or outside (so it succeeds even if cron body fails)?

**Lean toward INSIDE** — if the cron body crashes before writing the tick, the operator should see "unknown" not "healthy", because the cron didn't actually do its job. INSIDE the try means a thrown handler still records the tick (since `cacheSetSafe` is awaited before the body runs). Wait — that's actually the opposite of what I just said. Let me re-think.

Actually two choices:

- **A (top of try)**: Tick is recorded BEFORE body runs. Handler crash → tick still written → probe shows healthy → operator misled into thinking cron worked. **BAD**.
- **B (after body completes)**: Tick recorded only if body succeeded. Handler crash → no tick → probe shows unknown → operator alerted. **GOOD** — but doesn't catch the case "body succeeded, tick failed". Acceptable since cacheSetSafe is degrade-open.
- **C (after body completes, but skip on body error)**: Same as B but explicit.

**Lean toward B** — write the tick AFTER the cron body's primary work succeeds. Each handler's "primary work succeeded" boundary differs. Discuss-phase should look at each handler.
