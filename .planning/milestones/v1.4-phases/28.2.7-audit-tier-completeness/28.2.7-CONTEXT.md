<decisions>
## Implementation Decisions

### R2 — `llm:lastProgress` write-through (covers SPEC R2)

- **D-01:** Write-through lives in `server/lib/llmProgress.ts` setters. `resetProgress()` and `updateProgress()` each call `cacheSetSafe('llm:lastProgress', {startedAt, completedAt}, LLM_LASTPROGRESS_TTL_SEC)` after mutating the singleton. Centralized in one module — single concern, easy to test, no scattered call-site coupling. Matches cacheSetSafe's degrade-open contract (Redis failure swallowed; in-memory singleton remains authoritative for that instance).
- **D-02:** Write-through fires ONLY on transitions: `startedAt`-set (in `resetProgress`) and `completedAt`-set (when `updateProgress` receives a non-null `completedAt`). Mid-run batch progress (~50–200 `updateProgress` calls per run) is NOT persisted because `probeLlmStatus()` reads `completedAt ?? startedAt` — batch progress fields don't change probe output. Result: ~2 Redis writes per pipeline run.
- **D-08:** `probeLlmStatus()` reads Redis first (`cacheGetSafe('llm:lastProgress', ...)`), falls back to in-memory `llmProgress` singleton if Redis returns `null` or throws. Solves the cold-start problem — fresh function instances that didn't run the cron now see the Redis-backed timestamp.
- **D-09:** When BOTH Redis and in-memory are null (e.g. fresh deploy, no cron has run yet), probe returns `freshnessMs: null` → `deriveStatus` returns `'unknown'`. Preserves existing four-state contract; first cron tick within 26h flips it green. No artificial "fresh deploy → healthy" bias.
- **D-10:** Probe is read-only. No backfill of singleton from Redis. Keeps probe logic minimal (~5 lines) and avoids "probe mutates state" surprise. Singleton becomes eventually consistent via the next pipeline's `resetProgress` call.

### R1 — `cron:lastTick:<name>` writers (covers SPEC R1)

- **D-03:** Each cron handler writes its tick AFTER body work succeeds (status 200 path), not at top-of-try and not in `finally`. Probe shows `'unknown'` if cron body crashed — operator gets honest "cron didn't actually do its job" signal rather than a misleading "healthy" tick from a crashed handler.
- **D-04:** `cron-warm` writes the tick on `partial-or-better` (Promise.allSettled returns `'ok'` OR `'partial'`). Tick semantics are "did the cron tick run at all", not "did every upstream Overpass fetch succeed". Per-source freshness is already covered by the 8 cache-backed probes. Strict allOk gating would surface transient Overpass timeouts as cron-tier red.
- **D-05:** `refresh-events-cron`'s tick write lives in the route handler (`server/routes/refresh-events-cron.ts`), AFTER `runRefreshExtraction()` returns successfully. Not inside `runRefreshExtraction()` itself. Reason: `runRefreshExtraction` is a helper that may grow non-cron callers (manual ops, future dashboard force-trigger UI); cron-tick semantics are a route-level concern, not a helper concern.
- **D-11:** Tick value = `Date.now()`. `cacheSetSafe` wraps in `{data: <epoch>, fetchedAt: <epoch>}` envelope; `probeCronTick` already handles both `entry.data` (numeric) and `entry.lastFresh` shapes (`server/routes/health.ts:200`). Writing the timestamp explicitly is self-documenting at the write site even though `fetchedAt` would carry the same value implicitly.

### R3 — `probeProbeOnly()` honest stub (covers SPEC R3)

- No additional decisions beyond SPEC R3. Two-line change: `freshnessMs: null` → `freshnessMs: 0`. Reuses existing `probeSources()` contract (`server/routes/health.ts:147–154`) — "process running iff probe healthy", same shape, same rationale (pure config introspection, no upstream call to fail).

### TTL constants (override SPEC's `_TTL_MS` naming)

- **D-06:** Both new TTL constants named `*_TTL_SEC` with value `604800` (7 days in seconds). Pass directly to `cacheSetSafe` with no conversion. Matches every other TTL constant in the codebase (`SITES_REDIS_TTL_SEC = 259_200`, `WATER_REDIS_TTL_SEC` etc.). Unit lives in the name; no `/1000` arithmetic at call sites; no drift risk across the 4 write sites.
- **D-07:** `CRON_LASTTICK_TTL_SEC` declared in `server/lib/healthSources.ts` (co-located with `SOURCE_KEYS`, `FRESHNESS_THRESHOLDS_MS`, `TIER_BY_ENDPOINT` — the audit-tier knobs file). `LLM_LASTPROGRESS_TTL_SEC` declared in `server/lib/llmProgress.ts` (co-located with `INITIAL_PROGRESS` and the singleton). Each constant near its usage cluster.

### Tests

- **D-12:** 3 test files, one per SPEC requirement. Mirrors the SPEC's 3-requirement structure so a regression in any one fix surfaces a single failing file:
  - `server/__tests__/routes/cron-lasttick.test.ts` (R1) — exercises all 3 cron handlers via supertest; asserts each writes its tick key after body succeeds AND skips the write if body throws.
  - `server/__tests__/lib/llmProgress.persistence.test.ts` (R2) — write `llm:lastProgress` directly via mock Redis Map; instantiate fresh singleton (no in-memory state); call `probeLlmStatus()`; assert `freshnessMs !== null`. Mirrors the SPEC's R2 acceptance test verbatim.
  - `server/__tests__/routes/health.probeOnly.test.ts` (R3) — assert `probeProbeOnly()` returns `freshnessMs: 0` AND `deriveStatus(0, 0, false) === 'healthy'`. Live shape pinned.
  - All three reuse the in-memory Redis Map mock pattern from `server/__tests__/lib/llmExtractionPipeline.crossBoundary.test.ts`.

### Bundle regen

- **D-13:** Final plan task = `npm run build` + commit `api/vercel-entry.js` + `dist-server/`. Matches Phase 28.2.6's pattern. One atomic commit ensures the bundle reflects the final source state at deploy time. 28.2.6 surfaced exactly the "missing bundle regen" deploy bug; this phase pre-empts it.

### Claude's Discretion

- Exact TypeScript signatures of the new TTL constants (`number` literal vs `as const`) — minor style call.
- Whether `D-01`'s write-through inside `updateProgress` reads the post-merge state or builds a new snapshot — both produce identical JSON; pick whichever reads cleaner.
- Whether `probeLlmStatus()`'s Redis read shares the existing `withTimeout` wrapper or reuses `cacheGetSafe`'s built-in 2s timeout — `cacheGetSafe` already provides timeout + memCache fallback, so either path is safe.
- Whether `cron-lasttick.test.ts` mocks each cron's body collaborators or runs them with a stub Redis — the assertion only cares about the tick write, not the body.

### Reusable Assets

- **`cacheSetSafe(key, data, redisTtlSec)`** (`server/cache/redis.ts:234`) — Phase 27.4.x convention; degrade-open by construction (Redis failure swallowed; memCache populated). All R1 + R2 Redis writes use this single API. No new cache primitive needed.
- **`probeCronTick(name)`** (`server/routes/health.ts:182`) — Already exists, fully written, never receives data. D-04 fixes the upstream "no writers" gap; reader is unchanged.
- **In-memory Redis Map mock** (`server/__tests__/lib/llmExtractionPipeline.crossBoundary.test.ts`) — Established pattern for Redis-backed contract tests. D-12's 3 new files reuse it.
- **`safeWaitUntil`** (Phase 28.2.6) — Already wired into `runRefreshExtraction`. Not needed for D-01's write-through (writes happen pre-`res.end()`, inside the pipeline body) but available if a future caller flips to fire-and-forget.

### Established Patterns

- **Degrade-open probes** — Phase 28.1 W2 contract: probes never throw, return `{hadError: true}` instead. D-08 + D-09 honor this; cacheGetSafe failures fall back to in-memory; both-null returns `'unknown'`, never `'unhealthy'`.
- **TTL constants in seconds** — `SITES_REDIS_TTL_SEC`, `WATER_REDIS_TTL_SEC`, `events:llm-eval-baseline:v3` etc. all use seconds. D-06 aligns the new constants with this convention (overrides SPEC's `_TTL_MS` literal naming).
- **One-mutator-per-event pattern** — `llmProgress` has only 2 mutators (`resetProgress`, `updateProgress`). D-01 hooks both; the surface is small and exhaustive — no risk of "forgot a write site".
- **After-body cron writes** — `cron-health.ts:114-124` already writes its `res.json(...)` after both eval folds complete. D-03's "after body succeeds" matches the existing handler structure.

## Specific Ideas

- **D-06 collides with SPEC literal wording** — SPEC.md §Requirements line 27 says `CRON_LASTTICK_TTL_MS set to 604800000 ms (7 days)`. CONTEXT D-06 is the deliberate override: same value (7 days), seconds-based name (`*_TTL_SEC = 604800`) to match `cacheSetSafe`'s API and existing TTL constants. Planner reads CONTEXT D-06 as authoritative.
- **D-04 worth a second look during planning** — `cron-warm.ts:73` already classifies the result as `allOk: results.every(...)`. D-04's "tick on partial-or-better" means tick fires when `results.some(r => r.status === 'fulfilled')` is true. Effectively: tick fires on `allOk` OR `partial`, NOT on full failure (both Promise.allSettled entries rejected). Planner should confirm this matches the intent during plan writing.
- **HANDOFF self-corrected D-03 mid-document** — the HANDOFF first leaned INSIDE try, then corrected to after-body. CONTEXT D-03 locks the corrected position so the planner doesn't re-derive the same self-correction.
