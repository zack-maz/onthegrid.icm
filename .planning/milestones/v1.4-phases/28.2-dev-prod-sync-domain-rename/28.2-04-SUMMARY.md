## Decisions Made

- **Path B for OSM ID** (recorded in CONTEXT.md addendum, commit `aa3e0d3`): symmetric metadata gating across Event / Site / Water detail panels.
- **Lockdown test designs were tightened beyond the literal Plan 04 spec** to deliver mechanical regression guards: 2 tests per lockdown surface (static-source + render/runtime), instead of the 1-test minimum the plan called out. The test count went from the planned 17 (4+6+5+1+1) to actual 19 (4+6+5+2+2). This is purely additive (no plan-spec test was removed). The static-source guard is the load-bearing protection — it catches the most likely regression vector (search-and-replace drift) directly in the source string.
- **NotificationCard severity-score block is currently absent in source** (the `Notification` type in `notificationStore.ts` has no `score` field as of 2026-05-05). The lockdown test design was pivoted from "render the score, assert it's hidden" to "static-source guard forbidding `shouldRenderDashboard` import" — symmetric to `HealthBanner.test.tsx` Test 8's "forbid `useHealthStatus(`" pattern. This makes the test a future-regression guard rather than a current-bug catch.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Adjusted test design] NotificationCard lockdown test pivoted to static-source guard**

- **Found during:** Task 4 implementation
- **Issue:** The plan called for a render-time test asserting the severity-score numeric (e.g., 8.5) is hidden. But the current `NotificationCard.tsx` source has no severity-score block at all — the `Notification` type in `notificationStore.ts` has no `score` field. A pure render-time assertion would always pass trivially regardless of any future regression.
- **Fix:** Designed the lockdown test as a 2-test suite: (a) static-source guard that forbids any `shouldRenderDashboard` import in `NotificationCard.tsx` — symmetric to `HealthBanner.test.tsx` Test 8's "forbid `useHealthStatus(` to prevent the double-poll regression" pattern; (b) render-time guard with a hypothetical `score` field cast through `unknown` so the test still compiles and asserts no numeric string surfaces. The static guard is the load-bearing protection; the render guard documents the contract.
- **Files modified:** `src/components/notifications/__tests__/NotificationCard.lockdown.test.tsx`
- **Verification:** Both tests pass (commit `8af6587`); the static guard would mechanically fail if a future agent adds `import { shouldRenderDashboard } from '@/lib/dashboardAuth';` to NotificationCard.tsx.
- **Committed in:** `8af6587` (Task 4 commit)

**2. [Rule 1 - Adjusted test design] MapDevExposer lockdown test relies on static-source check rather than mounting BaseMap**

- **Found during:** Task 5 implementation
- **Issue:** The plan suggested mounting `BaseMap` (or `MapDevExposer` directly) to assert `window.__map === undefined`. `MapDevExposer` is an internal-only function (not exported) defined inside `BaseMap.tsx`; mounting `BaseMap` requires the full WebGL/MapLibre stack which is heavily mocked in jsdom (`vite.config.ts` `test.alias` covers maplibre-gl, deck.gl/layers, etc., but mounting the parent for one regression assertion adds significant fragility).
- **Fix:** Designed the lockdown test as a 2-test suite: (a) static-source guard that asserts `BaseMap.tsx` contains the literal `import.meta.env.DEV && <MapDevExposer />` predicate AND does NOT contain `shouldRenderDashboard() && <MapDevExposer />` (in either order); (b) runtime cleanliness assertion that `window.__map` starts undefined and stays undefined when no DEV-code-path render occurs. The static guard mechanically catches the same search-and-replace drift the plan envisioned, without the WebGL setup cost.
- **Files modified:** `src/components/map/__tests__/MapDevExposer.lockdown.test.tsx`
- **Verification:** Both tests pass (commit `c1c66f9`); the static guard would fail if a future agent swaps the predicate.
- **Committed in:** `c1c66f9` (Task 5 commit)

**3. [Rule 3 - Defensive test enhancement] Extended notabilityScore lockdown to a cross-file bleed assertion**

- **Found during:** Task 3 implementation
- **Issue:** The plan called for 5 tests in `WaterFacilityDetail.gateSwap.test.tsx` — 3 OSM ID render-parity + 2 lockdown. The lockdown tests as drafted in the plan would only catch the wrong-direction regression (notabilityScore graduating). They would not catch a future agent who search-and-replaces `import.meta.env.DEV` → `shouldRenderDashboard()` across the entire file (an obvious drift vector).
- **Fix:** Test 4 was tightened to a "cross-file bleed" assertion: in a single Bearer-prod render, OSM ID renders (graduated, line 118) AND notabilityScore stays hidden (locked, line 239). This catches drift in either direction within the same file. No additional tests added; just sharpened the assertions in Test 4.
- **Files modified:** `src/components/detail/__tests__/WaterFacilityDetail.gateSwap.test.tsx`
- **Verification:** All 5 tests pass (commit `1953616` GREEN). The bleed test would fail if a future agent graduated notabilityScore alongside the OSM ID.
- **Committed in:** `fe9e07e` (RED) → `1953616` (GREEN — same Task 3)
