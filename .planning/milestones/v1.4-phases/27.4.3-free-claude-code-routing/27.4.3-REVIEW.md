# Phase 27.4.3: Code Review Report

**Reviewed:** 2026-04-25T00:00:00Z

## Summary

The phase introduces a v3 LLM enrichment pipeline routed through a vendored "free-claude-code" provider cascade (NVIDIA NIM primary → OpenRouter fallback) plus an auto-rollback ladder (watchdog recurrence + eval drop) that flips back to v2 when v3 misbehaves. Core invariants are well-defended:

- **Rollback safety (D-21)** — v1, v2, and `server/adapters/llm-provider.ts` are not touched in this phase's diff; the v3 cascade lives entirely in `server/lib/freeClaudeRouter.ts` + `server/lib/llmEventExtractor.v3.ts`. The barrel `llmEventExtractor.ts` discriminates by `schemaVersion` so flipping the runtime override back to v2 keeps the existing adapters intact.
- **API key handling** — keys are read from `env.NVIDIA_NIM_API_KEY` / `env.OPENROUTER_API_KEY` and passed to the OpenAI SDK via `apiKey` constructor option. No shell interpolation, no logging of key material, no key fields placed on the wire response. Lazy `getNvidiaNimClient()` / `getOpenRouterClient()` return `null` when unconfigured rather than throwing.
- **3-way pipeline dispatch** — `events.ts` correctly threads `getPipelineVersion()` through both the cache-key selection and the extractor branch, with a v3 → v2 → v1 cache fallback chain so the map never goes blank during cutover (Pitfall 1 bridge extended).
- **Cache-key discipline** — the terminal/partial split (`events:llm:v3` vs `events:llm:v3:partial`) preserves the post-27.4.1 invariant that user-facing readers never touch envelope-shaped payloads. `coerceCachedEvents` belt-and-suspenders defends every read site.
- **Auto-rollback** — both triggers are guarded by `isPipelineV3()` so a v1/v2 run cannot accidentally flip the override; the eval-drop trigger handles enveloped/raw/legacy/null/malformed baseline shapes without throwing.
- **Test coverage** — `llmAutoRollback.test.ts` exercises both triggers' positive and negative paths plus envelope-shape variants; `freeClaudeRouter.test.ts` covers rate-limiter, fall-through, error taxonomy, and reasoning-block stripping; `llmCircuitBreaker.test.ts` was widened to assert all four providers; `llmSchema.test.ts` admits the v3 discriminator branch.

The 5 warnings below are mostly about latent observability gaps and one race-prone instrumentation block. Nothing rises to Critical (no security holes, no data corruption, no auth bypass). The Info items are code-quality nits worth fixing during 27.4.3 cleanup.

## Warnings

### WR-01: `recordHeadroom` for openrouter races a fire-and-forget update against a synchronous one

**File:** `server/lib/freeClaudeRouter.ts:438-467`
**Issue:** Inside `recordHeadroom('openrouter')`, the function (a) reads the current `rateLimit` snapshot, (b) dispatches a `getOpenRouterDaily().then(used => updateProgress({...}))` fire-and-forget that completes asynchronously, then (c) immediately calls `updateProgress({ rateLimit: current })` with the snapshot taken before the async `used` value was applied. The synchronous write at line 466 will overwrite any `openrouter.used` value the in-flight `.then()` block writes if the promise resolves between the snapshot and the synchronous assignment. The net effect is that `rateLimit.openrouter.used` will frequently lag the actual counter by one batch and may never reflect the true value when batches arrive faster than the round-trip.
**Fix:** Either await the daily counter inline (the function is already in an `async` context at the call site) or drop the synchronous `updateProgress({ rateLimit: current })` at line 466 and let the `.then()` block be the single writer. Recommended:

```ts
async function recordHeadroom(provider: FreeProvider): Promise<void> {
  const current = llmProgress.rateLimit ?? {
    nvidia_nim: { used: 0, cap: 40, window: 'minute' as const, perModel: {} },
    openrouter: { used: 0, cap: OPENROUTER_DAILY_CAP, window: 'day' as const, perModel: {} },
  };
  if (provider === 'nvidia_nim') {
    const h = nvidiaNimWindow.headroom();
    current.nvidia_nim = { ...current.nvidia_nim, used: h.used, cap: h.cap };
  } else {
    const used = await getOpenRouterDaily();
    current.openrouter = { ...current.openrouter, used };
  }
  updateProgress({ rateLimit: current });
}
```

And update the single caller at line 344 to `await recordHeadroom(p.name)`.

### WR-02: `enrichedV3ToEntities` never writes `data.location`, breaking the v3 extractor's own TEMPORAL CONTEXT BLOCK

**File:** `server/routes/events.ts:459-473` (writer); `server/lib/llmEventExtractor.v3.ts:353-383` (reader)
**Issue:** `loadTemporalContext` reads `events:llm:v3` (the terminal cache) and filters with `if (!e.data?.location || !e.data?.summary || !e.timestamp) continue;` — but `enrichedV3ToEntities` at events.ts:459-473 never writes `data.location` (the structured hierarchy object), only `data.locationName` (a flat string label). Every cached entity therefore fails the `!e.data?.location` guard and is skipped. The TEMPORAL CONTEXT BLOCK that the v3 prompt advertises (system prompt line 148: "TEMPORAL BLOCK lists prior events in the same region") will be empty for every batch in production. This is inherited from the same gap in v2 (`enrichedV2ToEntities` at events.ts:393-411 has the identical omission), but v3 amplifies the regression because the bake-off (BAKEOFF.md) and Gate B latency tuning likely assumed temporal context was contributing.
**Fix:** Persist the structured hierarchy onto the entity in both v2 and v3 adapters:

```ts
data: {
  ...template.data,
  locationName: placeLabel,
  location: enriched.location,   // <-- ADD: structured hierarchy for temporal-context lookback
  summary: enriched.summary,
  precision: enriched.precision,
  // ...
}
```

Verify ConflictEventEntity's `data` typings admit a `location: LocationHierarchyV2` field, then add a unit test that round-trips a v3 entity through `loadTemporalContext` and asserts the entity is admitted into the prior-events list.

### WR-03: `breakerState` not refreshed on the v3 path — DevApiStatus shows stale breaker pause indicators across pipeline switches

**File:** `server/lib/freeClaudeRouter.ts:360, 379`
**Issue:** The v3 cascade calls `record(p.name as Provider, 'ok')` and `record(p.name as Provider, 'err')` to update the circuit breaker's internal sliding window, but never calls `updateProgress({ breakerState: getBreakerState() })` after the call. The v1/v2 cascade in `server/adapters/llm-provider.ts:147,259` does push the refreshed state. Result: when v3 trips a breaker for `nvidia_nim` or `openrouter`, the `/llm-status` response and any v2-surface DevApiStatus block that reads `breakerState.cerebras/groq` will show whatever the previous v1/v2 run last wrote — which may be `'ok'` even though the v3 provider is actually paused. The v3 EventsFiltersSectionV3 surface doesn't render `breakerState` directly, so this is a silent-degradation bug rather than a visible one, but BudgetBarsBlock (used by v2 surface) will misreport breaker state if a v2 → v3 → v2 sequence happens.
**Fix:** Inside `freeClaudeRouter.ts`, after each `record(...)` call (lines 360 and 379), add `updateProgress({ breakerState: getBreakerState() })`. Import `getBreakerState` from `./llmCircuitBreaker.js`.

### WR-04: `shouldPauseNewEvents()` only checks cerebras/groq budget — v3 has no soft-cap pause path

**File:** `server/lib/llmTokenBudget.ts:150-158` (called from `server/routes/events.ts:1090`)
**Issue:** When v3 is the active pipeline, the soft-cap gate at events.ts:1090 calls `shouldPauseNewEvents()` which only reads `getDailyTokens('cerebras')` and `getDailyTokens('groq')` — neither relevant to v3, which uses NVIDIA NIM (40 req/min) and OpenRouter (≤200 req/day). The v3 cascade therefore has NO soft-cap pause behavior; the only protections are (a) the rolling-window 40 req/min limiter that bypasses the provider with `rate_limit_window` skip, and (b) the OPENROUTER_DAILY_CAP=200 hard cap that bypasses with `daily_cap` skip. Both kick in at 100% utilization, not at 80%. If NVIDIA NIM ever introduces a daily token cap (or OpenRouter shifts from request-based to token-based caps), v3 will sail past the 80% pause threshold without warning.
**Fix:** Either (a) extend `shouldPauseNewEvents()` to honor v3 providers when `getPipelineVersion() === 'v3'` (e.g., return true when `nvidiaNimWindow.headroom().used / cap >= 0.8` or OpenRouter daily counter >= 0.8 \* cap), or (b) document the design choice explicitly in `llmTokenBudget.ts` and on the v3 extractor's soft-cap gate path so future operators know the v3 path has only hard-cap protection. Recommended (a) for parity with v1/v2 ops experience.

### WR-05: Bake-off scripts call `runEval({model})` which now triggers `checkEvalDropTrigger()` — risk of accidentally rolling back v3 from a bake-off run

**File:** `scripts/bakeoff-v3.ts:279`, `scripts/bakeoff-v3-direct.ts:296` (both call `runEval({model})`)
**Issue:** The auto-rollback wiring in `llmEvalHarness.ts:289-294` calls `checkEvalDropTrigger()` only when `!opts.model` — that's the correct guard, so a per-model bake-off does NOT trip the rollback. Good. However, the bake-off scripts also do NOT reset the in-memory pipeline override before/after the run, and `__resetThrottleForTests()` is the only state clear. If an operator runs `npm run eval:replay` (no model arg) from a workstation while the production override happens to be `v3`, the harness will compare against `events:llm-eval-baseline:v3` and CAN trip an auto-rollback against the live deployment's Redis if the workstation shares Redis credentials. This is a footgun, not a bug — but it deserves an explicit guard.
**Fix:** Add a defensive check at the top of `runEval()` (or in a wrapper used by bake-off scripts) that no-ops `checkEvalDropTrigger()` when `process.env.NODE_ENV !== 'production'` AND the harness is invoked outside the route handler context. Simpler: in `eval-replay.ts`, set an env var like `EVAL_HARNESS_NO_ROLLBACK=1` and have the harness skip the trigger when set. Document the rollback side-effect in the script's JSDoc.

### IN-01: Variable shadowing of imported `env` inside `checkEvalDropTrigger`

**File:** `server/lib/llmEventExtractor.v3.ts:812`
**Issue:** `const env = raw as { data?: unknown; within20km?: unknown; total?: unknown };` declares a local `env` that shadows the module-level `env` imported from `../config.js` at line 49. Functionally fine inside this block, but confusing for readers and linters; an unrelated future edit could accidentally reach for the module env via the shadowed name and silently get the unwrapped envelope object instead.
**Fix:** Rename the local to `envelope` (matches the comment "Unwrap CacheEntry<T> envelope"):

```ts
const envelope = raw as { data?: unknown; within20km?: unknown; total?: unknown };
const inner = (envelope.data ?? envelope) as { within20km?: unknown; total?: unknown };
baselineScore = inner;
```

### IN-02: `OPENROUTER_DAILY_CAP` documented as "rough envelope" but enforced as a hard gate

**File:** `server/lib/freeClaudeRouter.ts:86-88, 309`
**Issue:** The constant is annotated "rough envelope; per-model caps vary 100-200/day on the free pool", but it is then enforced as a hard `>= OPENROUTER_DAILY_CAP` gate that skips the provider entirely. If OpenRouter's actual cap on the chosen free model is 100, the cascade will hit the real 429 at request 101 and back off, but `decisions` will still record `daily_cap` as the gate reason at request 200 — confusing post-hoc telemetry. If the cap is 250, the script will conservatively skip when there's still budget.
**Fix:** Either (a) make the cap per-model via a `OPENROUTER_MODEL_CAPS: Record<string, number>` lookup with a 100 default, or (b) downgrade the gate to a soft warning ("approaching daily cap") and let the actual 429 from OpenRouter drive the back-off. The breaker + reactive 429 retry already handle the real cap correctly; the synthetic gate is observability-only.

### IN-03: `_schemaText` parameter in `callLLM` is intentionally unused but the disable comment hides the design intent

**File:** `server/lib/freeClaudeRouter.ts:243-247`
**Issue:** The signature accepts `_schemaText: string` (unused) with `// eslint-disable-next-line @typescript-eslint/no-unused-vars` to silence the lint. The reason — "schema is delivered to the model as instruction text by the caller" — is documented in the JSDoc above, but a future refactor could accidentally drop the parameter on the assumption that it's dead. The schema text is in fact passed by every caller (`server/lib/llmEventExtractor.v3.ts:485`, both bake-off scripts), suggesting the intent is to keep the API surface compatible with a future strict-mode wire contract.
**Fix:** Either (a) consume the parameter in a no-op telemetry call (e.g., `log.debug({ schemaLen: _schemaText.length })`) so it has a real reason to exist, or (b) remove the parameter entirely and adjust callers — the v3 wire contract relies on prompt-embedded schema and doesn't need a separate channel.

### IN-04: Bake-off script duplication — three near-identical SYSTEM_PROMPT constants

**File:** `scripts/bakeoff-v3.ts:83-116`, `scripts/bakeoff-v3-direct.ts:72-100`, `server/lib/llmEventExtractor.v3.ts:119-154`
**Issue:** The system prompt is duplicated three times with subtle variations (the bake-off variants drop the TEMPORAL/BELLINGCAT block instructions but keep the schema instructions; the direct variant additionally trims the "extracted_at" guidance). When the production prompt evolves, the bake-off scripts will silently diverge unless someone remembers to update all three.
**Fix:** Export `SYSTEM_PROMPT_V3` from `server/lib/llmEventExtractor.v3.ts` and import it from both bake-off scripts. If the bake-off needs a stripped-down variant, define it as `SYSTEM_PROMPT_V3.replace(...)` so the source of truth stays single.

### IN-05: `appendLineage` writes a placeholder coord `{lat: 0, lng: 0}` plus `provenance: 'gdelt-actiongeo-fallback'` for every v3 event

**File:** `server/lib/llmEventExtractor.v3.ts:642-651`
**Issue:** Lineage is captured at extract-time before the resolver runs, so coord and provenance are placeholder values. The lineage record at `events:llm:v3:lineage:{eventId}` will therefore always claim `'gdelt-actiongeo-fallback'` regardless of which resolver branch actually fired. The drill-down UI in DevApiStatus reads this provenance and color-codes it (PROVENANCE_COLORS map at DevApiStatus.tsx:1214); operators inspecting the lineage drill-down will see misleading provenance for every event.
**Fix:** Either (a) defer the lineage write to after `resolveLocation` runs in `geocodeEnrichedEventsV3` so the real coord and provenance are recorded, or (b) split the lineage record into "extract-time" (no coord, no provenance) and "resolve-time" (coord + provenance) phases with a status field. Option (a) is cleaner — pass the prompt + raw response through the V3ExtractionRun return value into the geocoder and write lineage there.

### IN-06: `recentEvents` ring buffer has an off-by-one cap

**File:** `server/lib/llmEventExtractor.v3.ts:675-676`
**Issue:** `const recents = (llmProgress.recentEvents ?? []).slice(0, 49);` then `updateProgress({ recentEvents: [recentEvent, ...recents] });` produces an array of length 50 maximum. The intent appears to be "keep last 50 events." That works mathematically but the slice bound `49` reads as a magic number without comment. The comment in `llmProgress.ts` says `Last N enriched events` without specifying N. `loadRecentEnrichedEvents` in events.ts:143 also defaults to `limit=50`. The values agree, but the magic number is fragile.
**Fix:** Extract a constant:

```ts
const RECENT_EVENTS_CAP = 50;
// ...
const recents = (llmProgress.recentEvents ?? []).slice(0, RECENT_EVENTS_CAP - 1);
updateProgress({ recentEvents: [recentEvent, ...recents] });
```

Apply the same constant in `loadRecentEnrichedEvents`'s default limit and document it in the type's JSDoc.
