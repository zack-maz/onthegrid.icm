## Landmines

### 1. `/api/cron/refresh-events?force=true` exists and is Bearer-gated as D-06 assumes

**Verified.** `server/routes/refresh-events-cron.ts:33-68`:

- Line 36-43 — auth gate: `env.CRON_SECRET` non-empty → requires `Authorization: Bearer ${CRON_SECRET}`. Empty CRON_SECRET preserves un-authed dev behavior.
- Line 45-46 — `forceCooldown = req.query.force === 'true'`.
- Line 50-53 — calls `runRefreshExtraction({triggeredBy: 'cron', forceCooldown})`.

**Implication for D-06:** Workflow-side force-trigger needs `Authorization: Bearer ${CRON_SECRET}` (NOT `${DASHBOARD_PASSWORD}` — different secret). The existing 28.2 W6 workflow only has `PROD_DASHBOARD_PASSWORD` as a secret. Planner must add `PROD_CRON_SECRET` to the workflow secrets list, OR the workflow's force-trigger step must run server-side via a different path.

**Cold-cache self-heal at `llmExtractionPipeline.ts:123-135`** ALREADY bypasses cooldown when cache is empty (line 135 `effectiveForceCooldown = opts.forceCooldown === true || isColdCache`). So if the gate-check finds `events:llm:v3` empty, the next regular cron tick (or any manual force-trigger) will populate it without operator intervention. The workflow can either: (a) just curl the endpoint un-authed in dev / Bearer'd in prod and trust cold-cache self-heal, or (b) wait for the next cron tick.

### 2. `useWaterPrecipPolling` hydration is unconditional — D-05 widening will have data to find

**Verified.** `src/components/layout/AppShell.tsx:45` — `useWaterPrecipPolling()` is called as a sibling to `useFlightPolling()` etc., with no water-layer-toggle gate. ## Open Questions for Planner Discretion

1. **Tier slug for `events:llm:v3`** — D-06 says `'critical'`. If `'critical-llm'` is introduced, it requires a Zod schema bump in `server/lib/healthSchema.ts:36` `healthTierEnum` AND a new bucket in `buildSummary()` at `health.ts:261-296` AND a new tier rollup in `healthResponseSchema.summary` at `healthSchema.ts:91-103`. This is non-trivial — recommend staying at `'critical'` unless the LLM-down-but-fallback-up dashboard treatment is operator-mandated. Defer the sub-tier per CONTEXT Deferred Ideas.

2. **Exact widened distance threshold inside `findNearestPrecip`** — precip grid is `0.5°` (~50km) deduplication step on a sparse facility-location source (~305 facilities post-27.3.2). Manhattan distance `2.0°` ≈ ~200km Manhattan ≈ ~140km Euclidean for a typical mid-latitude. CONTEXT suggests `4.0°` (~400km Manhattan, ~280km Euclidean). Planner should: (a) hit `/api/water/precip` once locally, count samples in the Iran bbox, plot worst-case-no-coverage points, and pick the threshold that covers all bbox positions with margin. Reasonable bounds: 3.5°–5°. Sub-task: emit a one-time diagnostic from a server route or a vitest fixture so the choice is data-driven, not seat-of-pants.

3. **"Nearest sample, X km away" copy** — CONTEXT example: `"30-day: 12 mm — nearest sample 320 km away"`. Alternative formats: append in dim text below `"30-day: 12 mm"` or render the distance as a tooltip-of-tooltip. Planner picks; the data shape from D-05's `findNearestPrecip` change to return `{value, distanceKm}` is what enables either. **Distance threshold for showing the hint:** CONTEXT says "when distance > existing-tight-cutoff" — concretely, show hint when `distanceKm > ~100km` (existing 2° ≈ 200km Manhattan ≈ ~100km Euclidean for inset-from-center positions).

4. **Same DevApiStatus group vs new LLM group for `Events (LLM)` row** — D-07 says sibling. If a new "LLM" group is introduced, it would also house the existing `LLM Pipeline` section data already in DevApiStatus (reference at line 82 onward). That's a much larger refactor and probably out of scope. Recommend sibling rows under the existing flat list.

5. **Audit JSON shape extension** — three viable shapes:
   - **(A)** `{...existing, allTiersGreen: boolean}` — minimal addition, but loses tier-by-tier visibility in the banner.
   - **(B)** `{...existing, tierStatus: { critical, nonCritical, static, probeOnly, cron }}` — gives the banner a richer display surface but makes "all green" a derived computation.
   - **(C)** `{...existing, allTiersGreen: boolean, tierStatus: {...}}` — both, redundant but operator-friendly. Single boolean for fast-glance, full breakdown for drill-down.

   Recommend (C) — minor cost (~5 lines extra in workflow + 1 line in route + 1 assertion in W-3 test) with strictly better UX. The banner's existing render path can default-fold to `allTiersGreen` and expand into `tierStatus` rows on click.

6. **Workflow secret `PROD_CRON_SECRET` not currently configured** — D-06 force-trigger needs it. Two paths:
   - **(A)** Add `PROD_CRON_SECRET` to GH Actions secrets, attach to the new force-trigger step. Requires operator action in GitHub UI.
   - **(B)** Skip force-trigger from the workflow entirely; rely on cold-cache self-heal (the next 4am cron tick populates v3 if empty). Slower feedback loop but zero secret-management cost.

   Planner's call. (A) is more aggressive — gate fails → workflow auto-recovers within seconds. (B) is more conservative — gate fails → operator notices, runs manual `gh workflow run` next cron cycle. CONTEXT D-06 implies (A) ("if empty at gate-check, run `GET /api/cron/refresh-events?force=true`") so default to (A) unless secret-management cost is prohibitive.
