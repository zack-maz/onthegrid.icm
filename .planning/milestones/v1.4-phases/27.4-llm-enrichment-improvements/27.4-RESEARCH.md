### Locked Decisions

Forty decisions D-01 through D-40 are locked. They are grouped into eight clusters, summarized below verbatim in behavior (not wording) so downstream planners can scan them without re-reading CONTEXT.md, but CONTEXT.md remains the source of truth.

**Geolocation Accuracy (layered resolver):**

- **D-01** — LLM output replaces single `location.name` with a structured place hierarchy: `{ country, admin1, city, neighborhood, landmark, confidence }`. Confidence is 0–1 numeric. Each hierarchy field nullable. Precision indicator (`exact | neighborhood | city | region`) is derived from the deepest non-null field.
- **D-02** — Every Nominatim call is constrained by `countrycodes=IR,IQ,SY,LB,IL,PS,JO,EG,SA,AE,BH,KW,OM,QA,YE,TR,AF,PK,TM,AZ,AM,GE` plus a Middle East viewbox.
- **D-03** — POI-type specialist path: facility-flavor landmarks (nuclear / military / port / airbase / dam / reservoir) first match against `sites:overpass` and `water:facilities:v3` snapshots within-country; on miss, query Nominatim with amenity/landuse filter.
- **D-04** — Sanity gate: if resolved coord falls outside GDELT ActionGeo bbox + 250 km tolerance OR precision ≤ `city`, trigger two-pass verify (top-5 Nominatim candidates → LLM picks consistent one).
- **D-05** — Reject geocode-in-prompt. LLM stays on names; geocoding stays deterministic.

**Prompt Input Enrichment:**

- **D-06** — News cache cross-match against `news:gdelt` by time (±24h) + location proximity. Article titles + snippets tagged by source tier (gold/silver/bronze via `sourceTiers.ts`).
- **D-07** — Bellingcat OSINT block as separately-tagged high-trust section when `extractBellingcatGeo`-matched articles exist.
- **D-08** — Temporal context: last 3–5 enriched events in same region (bbox + 72h) included as lightweight context, pulled from `events:llm:v2`.
- **D-09** — Defer scraped article bodies.
- **D-10** — `BATCH_SIZE` drops `8 → 2`. (27.2 D-02 proposed 8→4 but did not ship; 27.4 goes further.)

**Extraction Output Schema:**

- **D-11** — `location` object replaced with structured hierarchy per D-01.
- **D-12** — Add `confidence: number` (0–1) and `reasoning: string` (≤200 chars) per event.
- **D-13** — Add `weaponType: 'airstrike' | 'drone' | 'missile' | 'artillery' | 'small_arms' | 'IED' | null` and `targetType: 'military' | 'infrastructure' | 'civilian' | 'leadership' | null`.
- **D-14** — Add `timeOfDay: 'HH:MM' | null` (UTC) and `durationMinutes: number | null`.

**DevApiStatus Events Section:**

- **D-15** — New dedicated section below existing per-source rows. Collapsible. Dev-only.
- **D-16** — Pipeline waterfall + throughput (per-stage durations, batches/min, geocodes/min, concurrency).
- **D-17** — Precision + confidence + source-tier + casualty-bearing histograms.
- **D-18** — Per-event drill-down (last N=50). Each row: hierarchy, precision, confidence, reasoning, weapon/target, tokens in/out, geocoding provenance path, sources. Click to copy prompt+response JSON.
- **D-19** — LLM call log + token/cost: last N=20 calls with provider/model/tokens/duration/success/batch-size. Cumulative daily totals. Driven by `llmProgress.ts` + call-history array.

**Palantir-Grade Extras:**

- **D-20** — Accuracy eval harness — 20–30 curated ground-truth events committed to repo. Quietly re-extracted on every LLM run. Reports accuracy at 5km / 20km / 100km thresholds.
- **D-21** — Prompt replay / shadow mode: DevApiStatus button "re-extract with current prompt" on any cached event. Side-by-side old vs new.
- **D-22** — Geocoding provenance per event: `own-site-snapshot | poi-amenity-nominatim | nominatim-direct | nominatim-verified-2pass | gdelt-actiongeo-fallback | bellingcat-coord-passthrough`.
- **D-23** — Deviation / outlier detection — events flagged "suspect" on: confidence < 0.5, precision = `region`, coord > 100km from GDELT ActionGeo, or all sources Tier 3.

**Rollout Strategy:**

- **D-24** — Env var `LLM_PIPELINE_V2` toggles old vs new pipeline. Default off in prod, on in dev.
- **D-25** — Prod flip gated on eval harness hitting **≥ 80% of ground-truth events within 20 km**. Gate enforced by `/api/events/llm-status` returning eval score.
- **D-26** — Old v1 extractor preserved under `server/lib/llmEventExtractor.v1.ts` for one phase. Deleted in 27.5.
- **D-27** — Reject shadow mode (doubles daily token load; eval harness provides signal without cost). Reject hard cutover (no rollback path).

**Error Handling + Retry Budget:**

- **D-28** — Per-event retry budget = 2 attempts (same provider, exponential backoff 1s / 4s).
- **D-29** — Provider fallback chain Cerebras → Groq → raw GDELT.
- **D-30** — Exhausted retries go to Redis dead-letter set `events:llm-dlq` with `{id, reason, lastError, timestamp}`. Count + recent entries in DevApiStatus.
- **D-31** — Circuit breaker: if provider error rate > 30% in last 10 calls, pause provider for 5 minutes; fall through.

**Token Budget + Rate Limits:**

- **D-32** — Track daily tokens per provider in Redis `llm:tokens:{provider}:YYYY-MM-DD` (TTL 48h).
- **D-33** — Soft cap 80% of daily limit (Cerebras 800K / Groq 160K) → pause new-event processing.
- **D-34** — Hard cap 95% (Cerebras 950K / Groq 190K) → switch provider; if both hard-capped, disable for the day, serve raw GDELT.
- **D-35** — Near soft cap, prioritize new + high-severity events.
- **D-36** — DevApiStatus renders per-provider budget bar.

**Cache Versioning + Schema Evolution:**

- **D-37** — Bump `events:llm` → `events:llm:v2`. Same for `events:llm-summary` → `events:llm-summary:v2`.
- **D-38** — Dev file cache: `dev-llm-cache.json` → `dev-llm-cache-v2.json`.
- **D-39** — LLM summary payload gains `schemaVersion: 'v2'`.
- **D-40** — Rollback: `LLM_PIPELINE_V2=false` flips to v1; v1 cache regenerates on next miss.

## Summary

Phase 27.4 is **not** a new pipeline — it's a disciplined, flag-gated extension of the Phase 27 LLM extractor. Three coupled deliverables:

1. **Geolocation accuracy:** A layered resolver replaces today's single-shot `forwardGeocode(placeName)` call. The LLM emits a structured place hierarchy (`country → admin1 → city → neighborhood → landmark`). The resolver tries paths in order: (a) own sites/water snapshot match, (b) Nominatim amenity-filtered query for POIs, (c) Nominatim direct constrained by viewbox + countrycodes, (d) two-pass LLM verify for ambiguous results, (e) GDELT ActionGeo fallback. Every path tags the event with its provenance for auditing.
2. **Richer prompts + schema:** Prompts gain three new blocks (cross-matched news titles by source tier, Bellingcat OSINT, last 3–5 enriched regional events). Batch size drops 8→2 so each group gets the LLM's full attention. Output schema extends with confidence, reasoning, weapon/target, time-of-day, duration — all `safeParse`-validated.
3. **Observability:** DevApiStatus gains an Events section with waterfall timings, precision/confidence histograms, per-event drill-down with prompt replay, LLM call log, token-budget bars, accuracy eval-harness score, DLQ list, and suspect-event filter.

The entire rollout is gated by `LLM_PIPELINE_V2`. Old code preserved as `llmEventExtractor.v1.ts`. Cache keys bump to `events:llm:v2`. Prod flip blocked until eval harness hits ≥80% within 20km.

**Primary recommendation:** Build in this order to land a flag-flippable pipeline as soon as possible — (1) bump cache keys + flag wiring + v1 preservation, (2) schema evolution (v2 Zod), (3) resolver plumbing (structured hierarchy only, no new Nominatim features yet), (4) Nominatim viewbox + countrycodes + amenity + top-5, (5) POI specialist + two-pass verify, (6) prompt enrichment blocks, (7) retry + DLQ + circuit breaker + token budget, (8) eval harness, (9) DevApiStatus Events section. Accuracy-impacting changes (3–6) flip the eval-harness needle. Observability (9) lets the user see whether it did.

### Pattern 1: Cerebras/Groq `response_format: json_schema` — strict mode

**What:** Both providers support OpenAI's `json_schema` response_format with `strict: true`. The schema is enforced server-side by the provider — malformed output is rejected before returning. Already used in this codebase.

**When to use:** Every LLM call for v2 extraction. Strict mode guarantees the response parses as JSON matching the schema; Zod is a defense-in-depth validator for field value constraints (enums, string lengths).

**Example (from Cerebras docs):**

```javascript
// Source: https://inference-docs.cerebras.ai/capabilities/structured-outputs [VERIFIED via Context7 2026-04-20]
const schemaCompletion = await client.chat.completions.create({
  model: 'gpt-oss-120b',
  messages: [
    { role: 'system', content: '...' },
    { role: 'user', content: '...' },
  ],
  response_format: {
    type: 'json_schema',
    json_schema: {
      name: 'event_extraction_v2',
      strict: true,
      schema: EVENT_EXTRACTION_SCHEMA_V2,
    },
  },
});

const data = JSON.parse(schemaCompletion.choices[0].message.content);
```

**Critical notes:**

- `strict: true` requires `additionalProperties: false` on every object in the schema (already the pattern in `llmEventExtractor.ts`). Missing this → provider rejects schema at compile time.
- Nested nullable fields must declare type as a union including `"null"` (e.g., `"type": ["integer", "null"]` — current code already does this for casualties).
- Enum fields (`type`, `severity`, `precision`, `weaponType`, `targetType`) work natively.

### Pattern 3: Nominatim viewbox + countrycodes constraint (D-02)

**What:** Two independent constraints applied to every forward geocode call. `countrycodes` is a comma-separated list of ISO-3166-1-alpha-2 codes (lowercase by convention, uppercase also accepted). `viewbox` is four comma-separated numbers `<lng1>,<lat1>,<lng2>,<lat2>` — two corners. `bounded=1` converts the viewbox from a preference hint into a hard filter.

**Example URL:**

```
https://nominatim.openstreetmap.org/search
  ?q=Deir+ez-Zor
  &format=jsonv2
  &countrycodes=ir,iq,sy,lb,il,ps,jo,eg,sa,ae,bh,kw,om,qa,ye,tr,af,pk,tm,az,am,ge
  &viewbox=30,15,70,42
  &bounded=1
  &addressdetails=1
  &limit=5
  &accept-language=en
```

**Critical notes:**

- **Viewbox param order** — x/lng first, y/lat second. Middle East bbox in CLAUDE.md (south:15, north:42, west:30, east:70) maps to `viewbox=30,15,70,42` where the corners are (west,south)=(30,15) and (east,north)=(70,42). [VERIFIED: Nominatim docs via WebFetch 2026-04-20]
- **`bounded=1` requires viewbox** — silently ignored otherwise.
- **`countrycodes` + `viewbox` AND-combine** — both must match. No conflict; results must satisfy both.
- **`limit=5` for verify-pass** (D-04), `limit=1` for direct calls — same endpoint.
- **`addressdetails=1`** adds an `address: { country_code, state, city, ... }` object to each result. Useful for D-04 candidate display.
- **Rate limit is 1 req/s hard** — an unconditional policy from OSMF, not a soft limit. [VERIFIED: operations.osmfoundation.org/policies/nominatim via WebFetch 2026-04-20]
- **User-Agent is required** — generic library defaults are "insufficient" per policy. Current code uses `'IranConflictMonitor/1.0 (personal project)'` — keep.
- **Bulk geocoding prohibited** — cache aggressively (already 30d TTL via `geocode:fwd:...`).
- **Violation penalty is a ban** — not throttling. Redis-cache every lookup, never hit the endpoint uncached in a test loop.

### Pattern 4: Nominatim amenity structured query (D-03)

**What:** For POI-flavor landmarks, Nominatim supports a structured query: `amenity=<poi>` + `city=`/`country=`. Cannot combine with `q=` free-form — it's the other of two query modes.

**Example URL:**

```
https://nominatim.openstreetmap.org/search
  ?amenity=nuclear+power+plant
  &country=iran
  &format=jsonv2
  &limit=3
```

**Critical notes:**

- **`amenity` + `q` are mutually exclusive** — sending both returns empty results or an error. Branch the adapter call based on whether the resolver has a POI-type hint.
- **`amenity=<string>` is a free-text name/type filter** — not the OSM tag `amenity=*`. Confusing but documented. [VERIFIED: nominatim.org/release-docs/develop/api/Search/ via WebFetch 2026-04-20]
- **For military/nuclear/port/airbase** — the better match is often a structured `q` with viewbox+country, since OSM tagging of these is inconsistent. Fall through from amenity to viewbox-constrained direct query.

### Pattern 5: Two-pass LLM verify for ambiguous coords (D-04)

**What:** When the resolver hits a precision-ambiguous result (≤ city) or a coord far from GDELT ActionGeo (>250km), send the top-5 Nominatim candidates back to the LLM as a small enum-choice prompt. This is classic "retrieve-then-rerank."

**Example prompt (to be drafted in plan):**

```
You extracted the location "Deir ez-Zor". Nominatim returned 5 candidates.
Pick the one most consistent with this event's context.

Event context: {summary, actors, cameo, news_title}

Candidates:
  1. Deir ez-Zor Governorate, Syria [35.33, 40.15] (region)
  2. Deir ez-Zor, Syria [35.33, 40.15] (city)
  3. Deir ez-Zor District, Syria [35.40, 40.10] (admin)
  4. Deir ez-Zor Military Airport, Syria [35.29, 40.18] (airport)
  5. Deir ez-Zor Bridge, Syria [35.32, 40.16] (bridge)
```

**Critical notes:**

- **Cost is bounded** — only triggered on the ambiguous subset (precision ≤ city OR coord >250km from ActionGeo). Target ≤20% of events per D-04 wording.
- **Uses the SAME provider chain** (Cerebras → Groq), same retry budget, same circuit breaker — no new plumbing.
- **Schema is trivially strict** — `{ pick: integer 1-5, reasoning: string max 100 }`.

### Pattern 7: Redis atomic token-budget counter (D-32..D-36)

**What:** Single-key increment-with-expire pattern — atomic, survives cold starts, self-cleans via TTL.

**Example:**

```typescript
// server/lib/llmTokenBudget.ts (new)

import { redis } from '../cache/redis.js';

const DAILY_LIMITS: Record<'cerebras' | 'groq', number> = {
  cerebras: 1_000_000,
  groq: 200_000,
};

function todayKey(provider: 'cerebras' | 'groq'): string {
  const today = new Date().toISOString().slice(0, 10); // YYYY-MM-DD
  return `llm:tokens:${provider}:${today}`;
}

/** Atomically add n tokens, set TTL first time. */
export async function incrDailyTokens(provider: 'cerebras' | 'groq', n: number): Promise<number> {
  const key = todayKey(provider);
  // @upstash/redis supports pipeline + eval
  const [newVal] = await redis.multi().incrby(key, n).expire(key, 172_800).exec();
  return newVal as number;
}

export async function getDailyTokens(provider: 'cerebras' | 'groq'): Promise<number> {
  return (await redis.get<number>(todayKey(provider))) ?? 0;
}

export function budgetState(provider: 'cerebras' | 'groq', used: number): 'ok' | 'soft' | 'hard' {
  const limit = DAILY_LIMITS[provider];
  if (used >= limit * 0.95) return 'hard';
  if (used >= limit * 0.8) return 'soft';
  return 'ok';
}
```

**Critical notes:**

- **TTL set on every call** — `expire` is idempotent; cheap to call. Prevents infinite-life counters.
- **48h TTL** (D-32) — gives a 24h lookback buffer for DevApiStatus to show "yesterday's" usage after UTC rollover.
- **Upstash `multi()` is pipelined, not atomic** — for strict atomicity use Lua `EVAL`. For this use case (near-real-time counters, not billing), pipeline is fine. [ASSUMED]
- **Don't increment on failed calls** — wraps only successful `res.usage.total_tokens` reads.

### Pattern 8: Sliding-window circuit breaker (D-31)

**What:** Module-level state tracks last 10 call outcomes per provider. If error rate > 30% → `paused` until 5-minute cooldown expires. Same "lazy on demand" style as existing cooldown in `events.ts` (`shouldRunLLM`).

**Example:**

```typescript
// server/lib/llmCircuitBreaker.ts (new)

type Provider = 'cerebras' | 'groq';
interface BreakerState {
  outcomes: Array<'ok' | 'err'>; // bounded to 10
  pausedUntil: number | null;
}

const state: Record<Provider, BreakerState> = {
  cerebras: { outcomes: [], pausedUntil: null },
  groq: { outcomes: [], pausedUntil: null },
};

export function record(provider: Provider, outcome: 'ok' | 'err'): void {
  const s = state[provider];
  s.outcomes.push(outcome);
  if (s.outcomes.length > 10) s.outcomes.shift();
  const errs = s.outcomes.filter((o) => o === 'err').length;
  if (s.outcomes.length === 10 && errs / 10 > 0.3) {
    s.pausedUntil = Date.now() + 5 * 60_000;
    s.outcomes = []; // reset so we don't immediately re-trip
  }
}

export function isAvailable(provider: Provider): boolean {
  const s = state[provider];
  if (s.pausedUntil && Date.now() < s.pausedUntil) return false;
  if (s.pausedUntil && Date.now() >= s.pausedUntil) s.pausedUntil = null;
  return true;
}
```

**Critical notes:**

- **Module-level state survives warm starts on Vercel** — same invariant as `llmProgress`. Cold starts reset; not a problem because a healthy provider will clear in 10 good calls.
- **Reset `outcomes` on trip** — otherwise 3 bad calls + 1 good = still tripped forever because we're at 30% exactly.
- **No Redis persistence of breaker state** — breaker is advisory; worst case after a cold start is two providers get 1–2 bad calls to rebuild the window. That's inside the retry budget (D-28).

### Pattern 9: Redis DLQ via SADD + EXPIRE (D-30)

**What:** Failed events go into a bounded Redis SET with a weekly TTL. UI reads last N via `SMEMBERS` + sort-by-timestamp-in-payload.

**Example:**

```typescript
// server/lib/llmDLQ.ts (new)

const DLQ_KEY = 'events:llm-dlq';
const DLQ_TTL_SEC = 7 * 24 * 3600; // 7 days
const DLQ_MAX = 200; // bounded; newer entries evict oldest

interface DLQEntry {
  id: string;
  reason: 'zod_fail' | 'llm_null' | 'retry_exhausted';
  lastError: string;
  timestamp: number;
}

export async function enqueueDLQ(entry: DLQEntry): Promise<void> {
  const payload = JSON.stringify(entry);
  await redis.sadd(DLQ_KEY, payload);
  await redis.expire(DLQ_KEY, DLQ_TTL_SEC);
  // Cap growth — if card() > DLQ_MAX, pop oldest by timestamp
  const size = await redis.scard(DLQ_KEY);
  if (size > DLQ_MAX) {
    const all = await redis.smembers(DLQ_KEY);
    const parsed = all
      .map((s) => JSON.parse(s) as DLQEntry)
      .sort((a, b) => a.timestamp - b.timestamp);
    const toRemove = parsed.slice(0, size - DLQ_MAX).map((e) => JSON.stringify(e));
    if (toRemove.length > 0) await redis.srem(DLQ_KEY, ...toRemove);
  }
}

export async function listDLQ(limit: number = 50): Promise<DLQEntry[]> {
  const all = await redis.smembers(DLQ_KEY);
  return all
    .map((s) => JSON.parse(s) as DLQEntry)
    .sort((a, b) => b.timestamp - a.timestamp)
    .slice(0, limit);
}
```

**Critical notes:**

- **Bounded at 200** — avoids unbounded Redis memory growth. `DLQ_MAX` is Claude's discretion per CONTEXT.md.
- **`sadd` dedupes on payload string** — if the same event fails twice with different `timestamp`, both land. If payload is identical, one entry. Acceptable.
- **TTL is re-set on every enqueue** — self-cleans 7 days after the last failure.

### Pattern 10: Event-level retry with exponential backoff (D-28)

**What:** Per-event retry budget = 2 attempts. Backoff 1s / 4s. Within the same provider first; then fallback chain (Cerebras → Groq → raw GDELT).

**Example (pseudo-code for the extractor):**

```typescript
async function extractOneWithRetry(group: EventGroup): Promise<EnrichedEventV2 | null> {
  for (const provider of ['cerebras', 'groq'] as const) {
    if (!isAvailable(provider)) continue; // circuit breaker
    if (budgetState(provider, await getDailyTokens(provider)) === 'hard') continue;
    for (let attempt = 0; attempt < 2; attempt++) {
      try {
        const raw = await callProvider(provider, group);
        const validated = enrichedEventV2.safeParse(raw);
        if (validated.success) {
          record(provider, 'ok');
          return validated.data;
        }
        // schema fail — don't retry same provider, bubble to next
        await enqueueDLQ({
          id: group.key,
          reason: 'zod_fail',
          lastError: JSON.stringify(validated.error.issues),
          timestamp: Date.now(),
        });
        record(provider, 'err');
        break;
      } catch (err) {
        record(provider, 'err');
        if (attempt === 0)
          await new Promise((r) => setTimeout(r, 1000)); // 1s backoff
        else await new Promise((r) => setTimeout(r, 4000)); // 4s backoff
      }
    }
  }
  await enqueueDLQ({
    id: group.key,
    reason: 'retry_exhausted',
    lastError: 'all providers failed',
    timestamp: Date.now(),
  });
  return null;
}
```

**Critical notes:**

- **Schema fails do not retry** — the LLM produced invalid output; retrying the same prompt will likely fail again. Go straight to next provider / DLQ.
- **Transient errors (timeout / 429 / network) retry once then backoff** — matches `LLM_TIMEOUT_MS = 30_000` existing timeout.
- **Jitter** — Claude's discretion per CONTEXT.md. **Recommendation:** add ±250ms jitter to the 1s/4s backoff to avoid thundering-herd on first retry wave after a provider blip. [ASSUMED — no prior art in repo, but textbook pattern]

### Anti-Patterns to Avoid

- **Geocoding in the LLM prompt (D-05 violation).** The schema must not include `lat` / `lng` / `coordinates`. The system prompt must explicitly forbid coordinate emission. Any temptation to "let the LLM fill in" when Nominatim fails should go to `bellingcat-coord-passthrough` or `gdelt-actiongeo-fallback` — never LLM-invented coords.
- **Removing v1 before prod flip (D-26 violation).** `llmEventExtractor.v1.ts` stays for one phase. Remove in 27.5, not 27.4.
- **Incrementing token counters on error.** `res.usage.total_tokens` is only reliable on success. Don't count failed retries against the daily budget.
- **Redis `KEYS` scans.** Use `SMEMBERS` / `SCARD` on the DLQ set, not key-pattern scans. [ASSUMED — Upstash strongly discourages KEYS]
- **Synchronous eval harness in `/api/events` path.** The eval harness must run inline with the fire-and-forget background block; it must not block the user request. Summary write to Redis on completion (same pattern as `buildSummary()`).
- **Prompt replay writing to cache (D-21).** Replay endpoint must be read-only re: cache — return `{old, new}` diff for UI. Writing would pollute `events:llm:v2` with unreviewed prompts.
- **Flag check at build time.** `LLM_PIPELINE_V2` must be read at request-handler time (not module-init) so `vercel env pull && vercel dev` or a prod env-var flip takes effect without a rebuild.

## Common Pitfalls

### Pitfall 1: Breaking v1 readers during rollout

**What goes wrong:** You ship v2 schema + v2 cache key, but the serving path still tries to `safeParse` v2 against v1 Zod. Client gets `502 UPSTREAM_FAIL` until a fresh LLM run happens.
**Why it happens:** Cache-key bump (D-37) must land _before_ schema bump (D-11..D-14). If they land together and you skip the v1 fallback branch in `events.ts`, any existing `events:llm` cached payload fails validation.
**How to avoid:** Land D-37 + `llmEventExtractor.v1.ts` preservation (D-26) first, in isolation. Verify both endpoints serve. Only then ship schema-v2 work. `enrichedEventAny` discriminated union tolerates both shapes during rollout.
**Warning signs:** `sendValidated` throws `RESPONSE_SCHEMA_MISMATCH` in dev after deploy; DevApiStatus shows "loading…" that never resolves; raw-GDELT fallback path gets hit suspiciously often.

### Pitfall 2: Nominatim bans (policy violation)

**What goes wrong:** Eval harness re-extracts 30 events on every 15-min pipeline run → 30 forward-geocodes → Nominatim rate-limits or bans the project IP.
**Why it happens:** The 1 req/s limit is a hard ceiling; the eval harness runs _in addition_ to the regular flow. If the existing `GEOCODE_DELAY_MS = 1000` isn't re-enforced for eval calls, the second call per second will 429.
**How to avoid:** Eval harness caches aggressively — ground-truth event lookups go through the same `geocode:fwd:...` Redis cache as regular calls. Lookups hit cache 29/30 times after the first run. Also: space eval harness calls 1s apart (reuse `GEOCODE_DELAY_MS`). Never make a fresh Nominatim call when a cached value exists.
**Warning signs:** 429 responses in logs, user-agent-style complaints from OSMF, missing geocoded results spiking.

### Pitfall 3: Token-budget counter drift under concurrent runs

**What goes wrong:** Two Vercel instances hit the LLM simultaneously (warm start + scheduled cron overlap). Each reads budget, passes the soft cap check independently, both increment. Budget overshoots. Eventually: 429 from provider.
**Why it happens:** Check-then-increment is not atomic without `WATCH` / Lua. Upstash `multi()` is pipelined (sequential) but not transactional.
**How to avoid:** Concurrent-run guard at the handler level (already present — `llmProgress.stage !== 'idle'` check). Also: gate new calls on `budgetState(provider, used) !== 'hard'` _after_ every successful call, not just at pipeline start. If two pipelines race past the start gate, the second one will notice `hard` mid-run and abort cleanly.
**Warning signs:** `429 Too Many Requests` in `llm-provider.ts` warn logs; Redis token counter exceeding the daily limit.

### Pitfall 4: Zod discriminated-union fails on `schemaVersion` typo

**What goes wrong:** V2 writes `schemaVersion: "v2"` but a code path writes `"V2"` or omits it. `enrichedEventAny.safeParse` fails with an opaque `Invalid discriminator value, expected 'v1' | 'v2'`. Cache serves stale v1 forever because v2 never validates.
**Why it happens:** Zod discriminated unions are brittle to typos; case-sensitive.
**How to avoid:** Set the `schemaVersion` field _on schema output, not on LLM output._ The LLM doesn't emit it — the extractor attaches it before cache write. Zod preprocessing: `z.preprocess((v) => ({ ...v, schemaVersion: 'v2' }), enrichedEventV2)` for cache-read safety.
**Warning signs:** `llm-extractor` logger `warn` rate spikes after deploy; `events:llm:v2` cache never populates; DevApiStatus `schemaVersion` renders `undefined`.

### Pitfall 5: Precision derivation disagrees with LLM's stated precision

**What goes wrong:** LLM emits `location: { city: 'Baghdad', neighborhood: null, landmark: null }` and self-classifies `precision: 'neighborhood'`. Derived precision from D-01 says `'city'` (deepest non-null = city). Downstream consumers (map ring size) are confused.
**Why it happens:** D-01 says precision is _derived from deepest non-null field_, but the LLM might still emit its own precision guess (v1 behavior). Dual sources of truth.
**How to avoid:** Drop `precision` from the LLM schema; always derive server-side. Authoritative derivation function: `derivePrecision(hierarchy) => 'exact' if landmark != null else 'neighborhood' if neighborhood != null else 'city' if city != null else 'region'`. Log when LLM-claimed precision would differ — audit signal, not error.
**Warning signs:** Precision rings render the wrong size in a handful of events; DevApiStatus precision histogram doesn't match per-event drill-down claims.

### Pitfall 6: Replay endpoint leaks into production

**What goes wrong:** `/api/events/llm-replay` is wired but the dev-gate check is on the request path, not the route registration. Someone hits it with a valid groupKey in prod → unauthenticated LLM call → burns token budget on attacker's query.
**Why it happens:** Pattern in Phase 27.1 puts the gate _inside_ the handler (`if (NODE_ENV === 'production') return 404`). Fine for dev visibility of the endpoint, but means the route still exists at build time.
**How to avoid:** Keep the existing in-handler gate (returns 404 in prod). Additionally: register the route conditionally — `if (process.env.NODE_ENV !== 'production') eventsRouter.post('/llm-replay/:groupKey', ...)`. Defense in depth.
**Warning signs:** `/api/events/llm-replay/...` showing up in prod access logs.

### Pitfall 7: DLQ payload string length explosion

**What goes wrong:** A schema validation failure dumps the full Zod `error.issues` array into `lastError`. A 10KB error message × 200 DLQ entries = 2MB Redis SET. Upstash command budget spikes.
**Why it happens:** Zod issue objects are verbose. `JSON.stringify(validated.error.issues)` can be huge.
**How to avoid:** Cap `lastError` at 500 chars in `enqueueDLQ`. Include the first issue's `path` + `message`, not the full array.
**Warning signs:** Redis memory usage creeps up over days; DLQ `scard` stays at 200 but bytes balloon.

### Pitfall 8: Eval harness double-counts tokens

**What goes wrong:** Eval harness re-extracts 30 events each run. If those ground-truth events also happen to be in live GDELT (same time window), the extractor runs them twice — once for the real pipeline, once for eval. Daily budget doubles on the overlap.
**Why it happens:** Eval harness runs on _every_ pipeline invocation (D-20). Real pipeline runs every 15 min. If the ground-truth set overlaps with current 24h window, the LLM call path is hit twice.
**How to avoid:** Eval harness runs through the **resolver**, not the full extractor. It consumes a pre-extracted `EnrichedEventV2` from the ground-truth file, runs resolver paths, compares resolver output coords to ground-truth coords. No LLM call needed for the ground-truth set. [This is a design assertion — the eval harness tests the resolver, which is the highest-value path. Extraction correctness is tested by Zod; resolver accuracy is the unknown.]
**Warning signs:** Token budget consumed 2x expected rate; two identical prompt/response pairs in the call log.

```typescript
// server/lib/llmTokenBudget.ts
import { redis } from '../cache/redis.js';

export async function incrDailyTokens(provider: 'cerebras' | 'groq', n: number): Promise<number> {
  const today = new Date().toISOString().slice(0, 10);
  const key = `llm:tokens:${provider}:${today}`;
  // Upstash pipeline: 2 roundtrips collapsed to 1 HTTP call
  const pipeline = redis.multi();
  pipeline.incrby(key, n);
  pipeline.expire(key, 172_800); // 48h, idempotent
  const [newVal] = await pipeline.exec<[number, boolean]>();
  return newVal;
}
```

## Open Questions

1. **Should `precision` be removed from the LLM schema entirely (A7)?**
   - What we know: D-01 says precision is "derived from the deepest non-null field." Current v1 schema has LLM emit `precision` directly.
   - What's unclear: If both sources exist, which wins? CONTEXT.md implies derivation.
   - Recommendation: Remove from v2 schema; derive server-side. Log when LLM-claimed precision would differ as an audit signal (optional schema field `llmClaimedPrecision`).

2. **Does eval harness run ground-truth events through the LLM, or only through the resolver (A6)?**
   - What we know: D-20 says "quietly re-extracts the ground-truth set." Ambiguous whether "re-extract" means LLM pass or full pipeline.
   - What's unclear: Token-cost implications. Full LLM re-extraction on every 15-min pipeline = ~20 events × 2000 tokens × 96 runs/day = ~4M tokens/day on ground truth alone, exceeding Cerebras 1M daily.
   - Recommendation: Resolver-only by default; add an env flag `EVAL_HARNESS_EXTRACT=true` for a weekly full-extraction run.

3. **POI-specialist landmark detection heuristic (D-03)?**
   - What we know: CONTEXT.md lists facility flavors: "nuclear / military / port / airbase / dam / reservoir." LLM emits `landmark` as free text.
   - What's unclear: How does the resolver decide a landmark is "POI-flavor"? Regex? Hand-tuned keyword list? Send the landmark through another LLM pass?
   - Recommendation: Hand-tuned keyword list (~40 terms: "nuclear plant," "airbase," "naval base," "reservoir," "dam," etc.) — same approach as `server/lib/sourceTiers.ts` domain sets. If keyword hits AND landmark matches a snapshot name within country, hit path 1.

4. **What does "news cache cross-match by location proximity" mean numerically (D-06)?**
   - What we know: News clusters have `articles` with `NewsArticle.sourceCountry`, but `news:gdelt` cache has no per-article lat/lng (only by-title-tokenization).
   - What's unclear: How to compute haversine proximity if articles don't have coords.
   - Recommendation: Match by source-country + time window first. Use event group centroid as "near" anchor. If the article's `sourceCountry` matches one of the event's actor countries AND publishedAt within ±24h, include the title. This degrades gracefully if no article coords exist.

5. **How many temporal-context events to include (D-08 says 3–5)?**
   - Recommendation: Start with 3 (smaller prompt). Bump to 5 only if eval harness shows name-consistency gains.
