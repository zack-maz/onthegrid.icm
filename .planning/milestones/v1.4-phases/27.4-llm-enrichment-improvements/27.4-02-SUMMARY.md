# Phase 27.4 Plan 02: Zod schema + derivation helpers + progress extensions Summary

Authoritative Zod schema contract (`server/lib/llmSchema.ts`) — v1 + v2 coexisting behind a `schemaVersion`-keyed discriminated union, with `.strict()` enforcing D-05 (no LLM-emitted coordinates), plus server-derived `derivePrecision` / `deriveSuspect` helpers, the `GeocodeProvenance` six-path enum (D-22), a strict-mode JSON Schema (`EVENT_EXTRACTION_SCHEMA_V2`), and a one-shot extension of `llmProgress.ts` with every Plan 03-09 observability field so downstream plans can populate them without re-growing the interface.

## What Shipped

### Task 1 — `server/lib/llmSchema.ts` + tests (commits `c8fdee4` RED, `f41435c` GREEN)

Followed TDD cycle: wrote 21 failing tests first (21 not 19 because Test 8 was split into three discriminator subtests), confirmed RED via `Cannot find module '../../lib/llmSchema.js'`, then implemented the module. All 21 tests pass.

**Named exports (schemas):**

- `enrichedEventV1` — frozen mirror of pre-27.4 `enrichedEventSchema` in `server/lib/llmEventExtractor.ts`, with `schemaVersion: z.literal('v1')` added as discriminator
- `enrichedEventV2` — D-01/D-11..D-14 shape: structured location hierarchy + per-event `confidence` + `reasoning` (<=200 chars) + `weaponType` + `targetType` + `timeOfDay` (HH:MM, strict regex) + `durationMinutes`
- `locationHierarchyV2` — the nested hierarchy object with `.strict()` (D-05 enforcement lives here)
- `enrichedEventAny` — `z.discriminatedUnion('schemaVersion', [enrichedEventV1, enrichedEventV2])` for cache-read rollout safety (Pitfall 1)
- `batchResponseV2` — batch envelope with `z.preprocess` seeding server-side `schemaVersion: 'v2'` on items missing it (Pitfall 4)

**Named exports (derivation helpers):**

- `derivePrecision(hierarchy)` — deepest-non-null rule: landmark → `exact`, neighborhood → `neighborhood`, city → `city`, else → `region`. Pure function, no side effects. Plans 03 + 06 + 09 will consume it.
- `deriveSuspect(input)` — D-23 outlier flag. Returns true if any of: confidence < 0.5, precision === 'region', actionGeoDistanceKm > 100, all tiers === 'bronze'.

**Named exports (constants/types):**

- `GEOCODE_PROVENANCE_VALUES` — six-element const array (D-22)
- `geocodeProvenanceSchema` — Zod enum wrapper
- `EVENT_EXTRACTION_SCHEMA_V2` — JSON Schema for Cerebras/Groq `response_format: json_schema` strict mode; `additionalProperties: false` at every object level; omits `schemaVersion` because the LLM never emits it server-side

**Exported types:** `GeocodeProvenance`, `Precision`, `EnrichedEventV1`, `EnrichedEventV2`, `EnrichedEventAny`, `LocationHierarchyV2`, `SuspectInput`, `BatchResponseV2`.

**Test coverage (21 tests):**

- 2 acceptance: minimal valid v2, nullable weapon/target
- 5 rejection: surplus `location.lat`, confidence=1.5, reasoning=201ch, weaponType="nuke", timeOfDay="25:00"
- 3 discriminator: v1 parses v1, v2 parses v2, "v3" rejects

### Task 2 — `server/lib/llmProgress.ts` extension + tests (commit `01a9c40`)

Extended `LLMPipelineProgress` and `LLMRunSummary` interfaces with 8 optional fields per D-19, D-20, D-22, D-23, D-30, D-31, D-32, D-39:

| Field              | Type                                                                                  | D-ref | Consumer                   |
| ------------------ | ------------------------------------------------------------------------------------- | ----- | -------------------------- |
| `schemaVersion`    | `'v1' \| 'v2'`                                                                        | D-39  | DevApiStatus schema banner |
| `callHistory`      | `Array<{provider, model, tokensIn, tokensOut, durationMs, ok, batchSize, timestamp}>` | D-19  | call-log panel             |
| `tokenCounters`    | `{cerebras: number, groq: number}`                                                    | D-32  | budget bars                |
| `dlqCount`         | `number`                                                                              | D-30  | DLQ badge                  |
| `breakerState`     | `{cerebras: 'ok'\|'paused', groq: 'ok'\|'paused'}`                                    | D-31  | circuit breaker indicator  |
| `evalScore`        | `{within5km, within20km, within100km, total}`                                         | D-20  | accuracy histograms        |
| `provenanceCounts` | `Partial<Record<GeocodeProvenance, number>>`                                          | D-22  | provenance pie chart       |
| `suspectCount`     | `number`                                                                              | D-23  | suspect-events badge       |

**`LLMRunSummary`** gains the subset of these fields worth persisting to Redis for cold-start dashboard reads (tokenCounters, dlqCount, evalScore, provenanceCounts, suspectCount + schemaVersion). Cold Vercel starts drop the in-memory progress singleton; the Redis summary is the only read path, so surfacing these observability fields survives cold starts.

**`INITIAL_PROGRESS`** explicitly seeds every new field to `undefined` so `resetProgress()` (which `Object.assign`s `INITIAL_PROGRESS` over the mutable singleton) clears lingering state between runs. Without this, yesterday's `evalScore` would mislead DevApiStatus when today's run hasn't populated the field yet.

**`buildSummary()`** threads every new optional field from `llmProgress` into the returned summary.

Added import at top of `llmProgress.ts`:

```typescript
import type { GeocodeProvenance } from './llmSchema.js';
```

2. `updateProgress` merges v2 fields without touching v1 fields (v1 stage/totalGroups preserved)

## Deviations from Plan

### Minor deviations (not blocking; documented in decisions frontmatter)

1. **[Non-deviation] Test count 21 vs 19 — plan split.** The plan spec listed 19 behavior tests. Test 8 (discriminator) was inherently a three-case test (v1 accept / v2 accept / v3 reject); I kept it as three individual `it()` blocks for clearer failure messages. Net: 21 tests. All 19 planned behaviors are covered 1:1.

2. **[Strengthening within plan sanction] timeOfDay regex.** The plan said "minimum is format-only (`/^\d{2}:\d{2}$/`), executor may strengthen regex to validate range if desired." I chose the stronger regex `/^([01]\d|2[0-3]):[0-5]\d$/` because:
   - Test 7 requires rejecting `'25:00'`, which the loose regex would accept. So the stronger regex is actually _required_ for Test 7 to pass.
   - Calendar math (e.g., 2:60 equivalence) stays out of the schema — it's still format-only.

3. **[Scope clarification] Plan 01 dependency.** The plan's `<read_first>` references `server/lib/llmEventExtractor.v1.ts` (which Plan 01 creates via `git mv`). In my Wave 1 worktree that file does NOT yet exist. I mirrored the v1 schema shape from the existing `server/lib/llmEventExtractor.ts` instead — the plan objective is "freeze-wrap the v1 schema," and structurally `llmEventExtractor.ts` is the same thing the Plan 01 `git mv` will preserve. This lets Plan 01 and Plan 02 run truly in parallel without coordination.

## Threat Flags

None. The `<threat_model>` in the plan (T-27.4-02-01 through T-27.4-02-04) is fully mitigated by the delivered code:

- **T-27.4-02-01 (Tampering / surplus-key injection):** `locationHierarchyV2.strict()` rejects surplus keys in safeParse — verified by Test 2.
- **T-27.4-02-02 (Prompt injection defense-in-depth):** The `additionalProperties: false` JSON Schema + Zod safeParse on response body form a two-layer defense; hostile LLM output fails parse → downstream DLQ flow consumes it.
