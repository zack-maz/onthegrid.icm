## Decisions Made

- **Barrel over re-implementation of llmEventExtractor.ts:** the current file is now a one-line `export * from './llmEventExtractor.v1.js'` re-export, not a re-implementation of the v1 logic. Plan 02 swaps the barrel body to route by flag without touching any importer. This is the minimum-churn rollout shape.
- **Module-level v1 cache key constants (`LLM_EVENTS_KEY = 'events:llm'`, etc.) left intact:** they still serve the v1 branch of the `pipelineV2 ? 'events:llm:v2' : LLM_EVENTS_KEY` ternary, and preserving them is the D-40 rollback path — setting `LLM_PIPELINE_V2=false` restores pre-27.4 behavior bit-for-bit.
- **`isPipelineV2()` helper as the canonical flag reader (W4 fix):** grep `grep -rn "process\.env\.LLM_PIPELINE_V2" server/routes/events.ts` returns zero matches post-Task-3 — every consumer flows through the helper. Eases 27.5 flag deletion.
- **Graceful v2→v1 fallback during rollout (Pitfall 1):** when `pipelineV2` is true but v2 cache is empty (cold post-flip), serve v1 fresh data and promote stale v1 to the local `llmCached` var so the stale-serve path at the bottom of the handler still works. Prevents the map from going blank during the rollout window.
- **`schemaVersion` as optional on both LLMPipelineProgress and LLMRunSummary:** existing v1 summaries written before this plan continue to parse without migration. The field is populated by the fire-and-forget block immediately after `resetProgress()`.
- **Dev file cache fork without deleting v1 file:** `.dev-cache/llm-events.json` is not deleted on upgrade — it ages out via MAX_AGE_MS=48h so `LLM_PIPELINE_V2=false` rollback still has a dev warm-start path.
