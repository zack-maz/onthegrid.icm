# Phase 27.4 Plan 03: Layered Geocoding Resolver Skeleton Summary

Six-path resolver dispatcher (`server/lib/llmResolver.ts`) implementing D-22's provenance contract — three paths fully functional (own-site-snapshot, nominatim-direct, bellingcat-coord-passthrough) plus the unconditional last-resort gdelt-actiongeo-fallback, and two stub paths (poi-amenity-nominatim, nominatim-verified-2pass) returning null so dispatch falls through to the next branch. Plans 04/05 swap the stubs in place; Plan 06's v2 extractor is the sole consumer.

## Deviations from Plan

### [Rule 1 - Bug fix within spec sanction] POI keyword regex boundary

The plan's reference implementation used `lower.includes(kw)` on a keyword list including literal `'port '` (trailing space — to avoid matching "airport"). But Test 11 asserts `isPoiLandmark('Bandar Abbas port') === true`, and `'port '` does not match "Bandar Abbas port" (no trailing space because it's end-of-string). Fix:

- Added `'port'` as a standalone keyword (overlaps with existing `'airport'` keyword — benign, both already match).
- Upgraded `isPoiLandmark` probe to whole-word regex: `new RegExp('(?:^|\\b)' + escaped + '(?:\\b|$)', 'i')`.
- Regex metachars escaped defensively (future-proof for new keywords).

Net effect: Test 11 passes as written; no false-positives on "passport"/"transport". Future keyword additions remain safe because escaping is in place.

### [Non-deviation] Test count 16 vs 13 — plan split

The plan spec listed 13 behavior tests. Test 10 (country filter) was inherently a two-case test (cross-country rejection + same-country acceptance) — kept as two `it()` blocks for clearer failure messages. Test 13 (TypeScript compile-time check) was documentary-only in the plan; I added a 16th test asserting `haversineKm(30,50,30,50) === 0` as a quick export-sanity check since Plan 05's D-04 sanity gate depends on this helper being exported and behaving.

Net: 16 tests. All 13 planned behaviors are covered 1:1.

### [Non-deviation] SiteEntity / WaterFacility country-field cast

The plan's reference code uses `(site as { country?: string }).country ?? null` to read country off snapshot entries. I verified that `server/types.ts` does NOT currently carry a `country` field on either `SiteEntity` (line 91) or `WaterFacility` (line 188). The cast is intentional:

1. Tests mock snapshot entries with an explicit `country` field (Tests 1, 6, 10) — exercises the matching logic.
2. Real committed snapshots (`src/data/sites.json`, `src/data/water-facilities.json`) do not persist country — so branch 1 will often skip with real data when hierarchy.country is non-null.
3. Plan 04 or a future extension can (a) add `country` to `SiteEntity`/`WaterFacility`, or (b) derive country at snapshot load time from ISO reverse lookup on (lat,lng).

Documenting this as a known gap rather than a deviation — the skeleton behavior matches the plan exactly, and the matching infrastructure is ready the moment country data lands.

## Threat Flags

None. The `<threat_model>` in the plan (T-27.4-03-01 through T-27.4-03-05) is fully mitigated by the delivered skeleton:

- **T-27.4-03-01 (Spoofing via LLM landmark):** POI stub returns null today, so the attack surface for the specialist path literally does not exist yet. Plan 05 will wire with `countrycodes` + `viewbox` constraints already built into `forwardGeocodeConstrained` (Plan 02's nominatim adapter extension).
- **T-27.4-03-02 (OSM tampering of snapshot labels):** Accepted. Snapshots are committed to the repo; future refresh is developer-gated via `npm run refresh:sites/water`.
- **T-27.4-03-03 (Info disclosure in logs):** Pino child logger with project-standard redaction paths; only error objects and query strings logged. No secrets.
- **T-27.4-03-04 (DoS via 6-branch misses):** Accepted. Branch 6 always succeeds in O(1). Real worst-case is branch 3 Nominatim call, rate-limited upstream in Plan 06.
- **T-27.4-03-05 (Resolver invents coordinates):** Mitigated architecturally. `resolveViaActionGeoFallback` uses `ctx.centroidLat/Lng` (GDELT-sourced); `resolveViaBellingcat` uses `ctx.bellingcatCoord` (third-party parsed); nothing synthesises coords.
