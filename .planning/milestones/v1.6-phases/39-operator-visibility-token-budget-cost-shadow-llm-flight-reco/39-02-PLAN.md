<objective>
Thread a per-run `runId` through the extraction pipeline so every LLM call back-correlates to its parent run, open/close a durable run record at the run boundary (surviving crashes via GA-2's start-write), and dual-write each call entry to `llm:calls:history`.

Purpose: This is the only genuinely-new logic in the phase (RESEARCH: "~95% wiring; the only new logic is runId generation/threading + run-record open/close"). It makes the flight recorder actually record — without it the Plan-04 endpoint returns empty lists and the UI shows nothing.

Output: edits to `llmExtractionPipeline.ts` (runId + run record lifecycle), `freeClaudeRouter.ts` (stamp + dual-write on both call paths), `llmEventExtractor.v3.ts` (batchIndex threading), plus an integration assertion extending the Plan-01 call-history test.
</objective>

<critical_finding>
**Source-verified correction to RESEARCH/PATTERNS code examples (executor MUST honor):**

1. `callLLM` (server/lib/freeClaudeRouter.ts:340) does NOT currently have a success-path callHistory writer. The success branch at ~:481-485 simply `record(p.name,'ok')` then `return { content, routing, finishReason }`. Only the FAILURE path (:519-535) appends to `callHistory`. Therefore this plan must ADD a success-path callHistory append (with `ok:true`, real `tokensIn`/`tokensOut`) right before the success `return`, in addition to dual-writing. Both paths then carry runId + batchIndex and both dual-write to `llm:calls:history`.

2. `batchIndex` is NOT in `callLLM`'s opts today. The opts type is `{ batchSize?, modelOverride?, skipOpenRouter? }`. `batchIndex` IS in scope at the `processEventGroupsV3` call site (server/lib/llmEventExtractor.v3.ts:584 `const batchIndex = Math.floor(i / BATCH_SIZE)`) and is passed to `withBatchWatchdog` opts (:647) — but NOT into the inner `freeClaudeCallLLM(...)` call (:618-634). This plan adds `batchIndex?: number` to `callLLM`'s opts and passes `batchIndex` at the call site. Fall back to `-1` if structurally unavailable (Open Q2 / A3) — but it IS available, so thread it.

3. `record(p.name, 'err')` exists exactly once per call at :562 (the post-attempt-loop recording). Do NOT add a second `record(...,'err')` near the failure-path callHistory append (Pitfall 4 — double-counting the breaker window).

4. `withBatchWatchdog` (server/lib/llmExtractorWatchdog.ts) MUST NOT be edited (Pitfall 1 — it is deliberately dependency-free).
   </critical_finding>
